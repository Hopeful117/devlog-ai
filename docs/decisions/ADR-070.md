# ADR-070 - Principal and Project Authorization Boundary

## Status

ACCEPTED - approved by the human project owner on 2026-10-01.

## Context

Story 0154 introduced read-only Story Context Agent snapshots persisted on
`AiTask`. The snapshot contains project-scoped engineering context and a
non-trusted AI result. The current endpoint can identify a snapshot, but the
repository does not yet expose an application-level principal/project
authorization model.

ADR-067 assigns authorization to Java/Core. ADR-063 requires authorization to
be applied before shared retrieval and states that transport must not determine
authorization scope. ADR-069 requires all projections to remain inside the
Core-authorized canonical context.

## Problem

An `aiTaskId` or `snapshotId` is an object identity, not proof that a caller may
read the object. Project slug equality, MCP transport, internal network access
or a valid HMAC callback must not grant human or agent read permission.

## Decision

The project selects and documents:

1. the principal representation used by application capabilities;
2. the source of authenticated identity at the HTTP and MCP boundaries;
3. the project membership/role relation used for authorization;
4. the Core service boundary where authorization is evaluated;
5. the policy for service-to-service callers and local development;
6. the audit data that may be recorded without logging secrets or snapshot
   content.

The implementation must not choose an identity provider, token format or role
model implicitly beyond the boundaries defined below. A concrete identity
provider remains an implementation or separate architecture decision.

### Principal representation

Application capabilities receive an immutable authenticated principal with one
normative classification:

```text
AuthenticatedPrincipal
  principalId
  kind: HUMAN | AI_AGENT | SYSTEM
  authenticationSource
```

`kind` is the only principal classification. A separate `type` field is not
introduced because it would duplicate the same semantic distinction.

`SERVICE` is not a principal kind. An AI agent or system may authenticate
through a service mechanism, but the authentication mechanism must not be
confused with the actor classification.

### Project authorization

Project membership and actor classification remain separate:

```text
ProjectMembership
  principalId
  projectId
  role: PROJECT_READER | PROJECT_OWNER
```

The initial snapshot read capability requires `PROJECT_READER` or
`PROJECT_OWNER`. No principal receives project access by default.

### Transport identity boundary

REST obtains the authenticated principal from its authenticated HTTP boundary.
MCP obtains or forwards the authenticated principal from its authenticated MCP
boundary. Both adapters pass the same Core principal representation to the
authorized application capability. Transport-specific identity data must not
be used to infer project scope.

### Local and test policy

There is no implicit unauthenticated bypass. A development or test principal
may be configured explicitly by the relevant environment profile, and is
disabled by default outside those profiles.

### Disclosure and audit policy

Unauthenticated requests fail with `401`. Authenticated callers that are not
authorized, and unknown or inaccessible snapshots, use the same public
outcome, initially `404`, unless a later approved contract changes this
policy. Expired snapshots also return `404` without mutation or resurrection.

Authorization diagnostics may contain a pseudonymized principal identifier,
project identifier, correlation identifier, decision and categorized reason.
They must not contain prompts, snapshots, tokens, secrets or repository
content.

## Normative Constraints

- Java/Core remains the sole authority for project and snapshot authorization.
- Authorization is evaluated before snapshot materialization or detailed
  context retrieval.
- REST and MCP adapters call the same authorized application capability.
- Transport identity, object identity and authorization scope remain separate.
- A valid callback HMAC authenticates the Core-to-Core callback only; it does
  not authorize a caller to read arbitrary snapshots.
- Authorization failures fail closed and do not reveal whether an inaccessible
  snapshot exists unless the approved contract explicitly permits it.
- Authorization scope is carried into the canonical context boundary and is
  available for deterministic tests and audit diagnostics.

## Out Of Scope

- AI trust promotion or proposal governance.
- New retrieval, RAG, vector search or context composition.
- UI redesign.
- Generic multi-tenant billing or organization management.
- Authorization of mutation capabilities not required by snapshot reading.

## Consequences

The next implementation Story depends on this ADR. Existing unauthenticated
development paths require an explicit development policy rather than an
implicit bypass. Existing REST/MCP contracts may need versioned error mapping,
but the domain authorization decision must remain transport-neutral.

## Follow-up Implementation Questions

- Which concrete identity provider and token format will supply the authenticated
  principal in each deployment?
- Which MCP authentication boundary is available in the current deployment?
- What concrete persistence representation will store project memberships?
