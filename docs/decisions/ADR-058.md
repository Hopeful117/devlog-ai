# ADR-058 — Engineering Knowledge Data Lineage

## Status

Proposed

## Date

2026-08-17

## Context

DevLog is progressively becoming an Engineering Context Engine responsible for
transforming project activity, validated engineering knowledge, architectural
decisions, Engineering Stories and repository history into reliable,
task-specific engineering context.

ADR-006 established the governance principle that AI-generated outputs are
represented as `ValidatableProposal` objects and cannot directly become trusted
project knowledge.

A proposal must pass through an explicit validation workflow before accepted
information can be promoted into an authoritative domain concept.

Recent work extended this lifecycle to structured engineering decisions:

```text
AI analysis
    ↓
ValidatableProposal
    type = ENGINEERING_DECISION
    ↓
Human / business validation
    ↓
ACCEPTED
    ↓
Decision
    ↓
Project Context
    ↓
Repository Evidence
    ↓
Engineering Context
    ↓
MCP
```

Each individual part of this pipeline can be implemented and tested correctly
while the complete lifecycle remains difficult to understand or diagnose.

This problem became visible while validating the `ENGINEERING_DECISION`
lifecycle.

The system contained:

* a `Decision` domain entity;
* a Decision repository;
* Decision application services;
* Decision REST capabilities;
* Decision projection into `AnalysisContext`;
* Decision projection into `RepositoryEvidence`;
* deterministic ranking and selection support;
* MCP engineering-context exposure.

However, the real `devlog-ai` project contained zero persisted Decision
instances.

The initial investigation therefore had to manually reconstruct the complete
lifecycle across multiple application layers.

A second investigation established that the Decision model was active but
underused.

A governed promotion path was then introduced:

```text
ENGINEERING_DECISION proposal
    ↓
ACCEPTED validation
    ↓
Decision
```

An end-to-end validation subsequently revealed another missing link: the
application did not yet expose an Intent capable of generating an
`ENGINEERING_DECISION` proposal through the normal AI task workflow.

After this missing application entry point was addressed, runtime validation
revealed another gap: the AI Engine path for
`DECISION_PROPOSAL_GENERATION` was still a hardcoded stub rather than a
provider-backed generation workflow.

The individual components were valid.

The lifecycle as a whole was incomplete.

This demonstrates an important architectural limitation:

> DevLog currently knows how to store and process engineering knowledge, but it
> cannot systematically explain how a specific piece of knowledge travelled
> through its lifecycle or where that lifecycle is broken.

As DevLog grows, similar chains will exist for:

* Insights;
* Engineering Events;
* Decisions;
* Engineering Stories;
* project observations;
* validated Knowledge;
* context projections;
* maintenance operations;
* future Retrieval Layer results.

Without explicit lineage, diagnosing a missing downstream result requires
manually inspecting services, repositories, database state, projections,
configuration and runtime behavior.

This approach does not scale.

The next architectural question is therefore:

> How should DevLog represent and diagnose the lineage of engineering knowledge
> without introducing a heavyweight knowledge graph or coupling domain models to
> infrastructure tracing concerns?

## Decision

DevLog will introduce an **Engineering Knowledge Data Lineage capability** that
makes the lifecycle of trusted engineering knowledge explicitly traceable.

The lineage model will initially focus on the governed knowledge lifecycle:

```text
Analysis
    ↓
AI Task
    ↓
ValidatableProposal
    ↓
Validation
    ↓
Promoted Knowledge
```

where Promoted Knowledge initially includes:

```text
Decision
Insight
EngineeringEvent
```

The lineage capability will distinguish three complementary responsibilities:

1. **Provenance** — identify where a piece of engineering knowledge came from;
2. **Lifecycle Trace** — identify which lifecycle transitions actually occurred;
3. **Invariant Checking** — identify expected lifecycle transitions that are
   missing or inconsistent.

The initial implementation must remain deterministic, auditable and independent
from future Retrieval/RAG infrastructure.

### 1. Lineage Represents Engineering Relationships, Not Database Topology

The lineage model must describe meaningful engineering lifecycle relationships.

Examples include:

```text
Analysis
    produced
AI Task

AI Task
    produced
ValidatableProposal

ValidatableProposal
    received
Validation

Accepted ValidatableProposal
    promoted_to
Decision
```

Consumers of lineage must not need to understand:

* JPA relationships;
* foreign-key topology;
* repository implementations;
* internal projection tables;
* transaction implementation details;
* database joins.

The conceptual boundary is:

```text
Domain Activity
      ↓
Lineage Relationship
      ↓
Engineering Lifecycle
```

rather than:

```text
Database Row
      ↓
Foreign Key
      ↓
Database Row
```

Database relationships may support lineage implementation.

They do not define its public semantics.

### 2. Provenance Answers "Where Did This Come From?"

Every trusted engineering artifact participating in the governed lifecycle
should progressively be traceable to its meaningful origin.

For example:

```text
Decision
    ← promoted from
ValidatableProposal
    ← generated from
AI Task
    ← requested from
Analysis
```

A lineage query should eventually allow DevLog to answer questions such as:

```text
Where did this Decision come from?

Which proposal produced this Insight?

Which validation promoted this Engineering Event?

Which analysis caused this proposal to be generated?
```

The initial objective is not to duplicate every domain field.

The objective is to preserve enough stable identity and relationship
information to reconstruct the lifecycle.

### 3. Lifecycle Trace Answers "What Actually Happened?"

Provenance alone describes relationships between existing artifacts.

It does not explain missing artifacts.

DevLog must therefore also support lifecycle-oriented inspection.

Conceptually:

```text
ENGINEERING_DECISION lifecycle

Intent Definition              FOUND
AI Task                        FOUND
ValidatableProposal            FOUND
Proposal Contract              VALID
Validation                     ACCEPTED
Decision                       FOUND
```

or:

```text
ENGINEERING_DECISION lifecycle

Intent Definition              FOUND
AI Task                        FOUND
AI Generation                  INVALID / STUBBED
ValidatableProposal            NOT CREATED
Validation                     NOT APPLICABLE
Decision                       NOT CREATED
```

The second result is more useful than simply returning an empty Decision list.

The lineage capability should make lifecycle state explicit enough for
diagnostic services to distinguish:

* a lifecycle stage that occurred;
* a lifecycle stage that has not occurred yet;
* a lifecycle stage that cannot occur because a prerequisite is missing;
* an inconsistent lifecycle state.

### 4. Lineage Invariants Detect Broken Knowledge Lifecycles

DevLog will progressively define deterministic invariants for governed
knowledge lifecycles.

The first reference invariant will be:

```text
An ACCEPTED ENGINEERING_DECISION proposal
MUST produce exactly one trusted Decision.
```

Other candidate invariants include:

```text
An ACCEPTED INSIGHT proposal
MUST produce exactly one trusted Insight.
```

```text
An ACCEPTED ENGINEERING_EVENT proposal
MUST produce exactly one trusted EngineeringEvent.
```

Lifecycle prerequisites may also become explicit invariants.

For example:

```text
An ENGINEERING_DECISION generation intent
MUST resolve to an AI task capable of producing
ENGINEERING_DECISION proposals.
```

and:

```text
A DECISION_PROPOSAL_GENERATION AI task
MUST use a real provider-backed structured generation path.
```

Invariant violations must be diagnostic findings.

They must not silently repair domain state.

### 5. Lineage Does Not Replace Domain Validation

Lineage observes and explains domain lifecycles.

It does not become the authority responsible for those lifecycles.

For example:

```text
ValidationService
```

remains responsible for proposal validation.

```text
ProposalPromotionService
```

remains responsible for trusted-domain promotion.

```text
DecisionRepository
```

remains responsible for Decision persistence.

The lineage capability may observe:

```text
Proposal
    ↓
Validation
    ↓
Decision
```

but it must not move these responsibilities into a centralized lineage
orchestrator.

The boundary remains:

```text
Domain/Application Services
          ↓
   perform lifecycle
          ↓
    Lineage records /
    reconstructs state
          ↓
 Diagnostic Capability
```

### 6. Lineage Must Preserve ADR-006 Governance

Engineering Knowledge Data Lineage must preserve the proposal and human
validation model established by ADR-006.

The lineage capability must never provide a shortcut such as:

```text
AI Result
    ↓
Lineage Service
    ↓
Trusted Knowledge
```

The governed lifecycle remains:

```text
AI Result
    ↓
ValidatableProposal
    ↓
Validation
    ↓
Promotion
    ↓
Trusted Knowledge
```

Lineage observes this lifecycle.

It does not bypass it.

### 7. The Initial Lineage Scope Is Intentionally Small

The first version will focus on:

```text
Analysis
    ↓
AI Task
    ↓
ValidatableProposal
    ↓
Validation
    ↓
Promoted Knowledge
```

with Promoted Knowledge limited initially to:

```text
Decision
Insight
EngineeringEvent
```

This scope is sufficient to validate the architecture against real governed
knowledge flows.

The first version does not need to represent every relationship already known
by DevLog.

### 8. Context Projection Lineage Is Deferred to a Second Phase

DevLog also contains an important downstream lifecycle:

```text
Trusted Knowledge
    ↓
ProjectContext
    ↓
RepositoryEvidence
    ↓
EngineeringContext
    ↓
MCP
```

This lifecycle is highly relevant to future lineage.

It is not required for the first implementation.

Once governed knowledge lineage is stable, the lineage model may expand to
answer questions such as:

```text
Why did this Decision not appear in EngineeringContext?

Which RepositoryEvidence represents this Insight?

Was this Engineering Story generated as context evidence?

Why was this evidence rejected by ranking or selection?

Which MCP result exposed this knowledge?
```

This second phase should reuse the same lineage concepts rather than introduce a
separate MCP-specific tracing model.

### 9. Lineage Must Distinguish Production From Selection

Future context lineage must distinguish between:

```text
candidate produced
```

and:

```text
candidate selected
```

This distinction is important because an absent MCP result does not necessarily
mean that source knowledge is missing.

For example:

```text
Decision exists
    ↓
DecisionSnapshot exists
    ↓
RepositoryEvidence candidate generated
    ↓
candidate ranked
    ↓
candidate NOT selected
```

is fundamentally different from:

```text
Decision does not exist
```

The lineage architecture must remain capable of expressing this distinction
when context-projection tracing is introduced.

### 10. Lineage Identity Must Be Stable and Domain-Oriented

Lineage relationships require stable references to participating artifacts.

Where domain identifiers already exist, those identifiers should be reused.

Examples include:

```text
analysis:{analysisId}

ai-task:{taskId}

proposal:{proposalId}

validation:{validationId}

decision:{decisionId}

insight:{insightId}

engineering-event:{eventId}
```

The exact serialized representation may evolve.

The important rule is that lineage identity must refer to meaningful
application concepts rather than transient implementation details.

### 11. Lineage Must Be Auditable

Lineage information may be used to explain why trusted engineering knowledge
exists.

It must therefore be auditable.

At minimum, lineage relationships should preserve enough information to
identify:

* source artifact;
* target artifact;
* relationship type;
* project;
* relevant lifecycle time;
* lifecycle outcome where applicable.

Future implementations may include additional metadata.

The initial model should avoid arbitrary unstructured metadata unless a
concrete diagnostic use case requires it.

### 12. Lineage Must Be Deterministic

The initial lineage capability must not require an LLM.

Questions such as:

```text
Did this accepted proposal produce a Decision?
```

or:

```text
Which proposal produced this EngineeringEvent?
```

must be answered deterministically.

AI may eventually help interpret complex lineage graphs or summarize diagnostic
results.

AI must not determine whether a required lifecycle transition occurred.

### 13. Lineage Must Support Diagnostic Queries

The initial architecture should support application-level diagnostic
capabilities.

Conceptually:

```text
get_knowledge_lineage(
    knowledgeReference
)
```

and:

```text
diagnose_knowledge_lifecycle(
    lifecycleType,
    reference
)
```

The exact public API is deferred.

The important capability is that DevLog can reconstruct or retrieve the
lifecycle without requiring an external agent to manually query multiple
repositories.

A diagnostic result may conceptually resemble:

```text
Lifecycle: ENGINEERING_DECISION

Intent
  status: FOUND

AI Task
  status: FOUND

AI Generation
  status: PROVIDER_BACKED

Proposal
  status: FOUND
  proposalStatus: ACCEPTED

Validation
  status: FOUND
  decision: ACCEPTED

Decision
  status: MISSING

Invariant violations:
  - ACCEPTED ENGINEERING_DECISION proposal has no promoted Decision
```

This representation is conceptual and does not define the final contract.

### 14. Diagnostic Results Must Distinguish Missing From Invalid

A missing lifecycle stage is not always an error.

For example:

```text
PROPOSED proposal
    ↓
no Validation
```

may be completely valid.

By contrast:

```text
ACCEPTED proposal
    ↓
no promoted knowledge
```

may violate a lifecycle invariant.

Diagnostics must therefore distinguish states such as:

```text
PRESENT
PENDING
NOT_APPLICABLE
MISSING
INCONSISTENT
```

The exact enum or implementation is deferred.

The semantic distinction is required.

### 15. Lineage Should Prefer Existing Domain Relationships Before Duplicating Data

The initial implementation should first inventory relationships already
available in the current domain model.

If a reliable relationship can be reconstructed deterministically from existing
domain state, DevLog should not automatically introduce duplicated lineage
storage.

Explicit lineage persistence should be introduced when reconstruction is:

* impossible;
* ambiguous;
* excessively expensive;
* historically unstable;
* insufficient for auditability.

This ADR therefore does not mandate that every lineage edge be persisted in a
new table.

The implementation must first determine which relationships require explicit
storage.

### 16. Lineage Must Preserve Transactional Semantics

When explicit lineage persistence is required for an authoritative lifecycle
transition, the lineage relationship and the transition it represents should
share the appropriate transactional boundary.

For example, if an accepted proposal is promoted into a Decision and an
explicit promotion lineage relationship is required, the architecture should
avoid:

```text
Transaction A
    Decision persisted
    COMMIT

Transaction B
    lineage persisted
    FAIL
```

leaving authoritative state with incomplete provenance.

The preferred conceptual behavior is:

```text
Transaction
    ↓
Validation accepted
    +
Trusted Knowledge promoted
    +
Required authoritative lineage recorded
    ↓
COMMIT
```

The exact implementation depends on which lineage relationships require
persistence.

### 17. Lineage Is Project-Scoped

Engineering knowledge lineage must preserve project boundaries.

A lineage query must not accidentally connect artifacts belonging to unrelated
projects.

Every authoritative lineage relationship should either directly carry project
identity or be deterministically resolvable to one project through its
participants.

Cross-project lineage may eventually be useful for transversal knowledge.

It is outside the initial scope.

### 18. Lineage Is Not a Knowledge Graph Requirement

The lineage model naturally forms a graph.

This does not imply that DevLog requires a graph database.

The initial implementation should use the simplest persistence and query model
that satisfies real lifecycle diagnostics.

Possible implementations may include:

* existing relational relationships;
* dedicated relational lineage records;
* deterministic reconstruction;
* a hybrid of reconstruction and persisted edges.

A graph database should only be considered if demonstrated query requirements
cannot be handled cleanly by the existing persistence architecture.

### 19. Lineage Is Independent From Retrieval and RAG

Engineering Knowledge Data Lineage and Retrieval solve different problems.

Retrieval answers:

```text
What context is relevant to this engineering intent?
```

Lineage answers:

```text
Where did this knowledge come from?

What produced it?

Which lifecycle stages occurred?

Where is the lifecycle broken?
```

Future Retrieval may use lineage relationships to improve:

* relationship expansion;
* temporal reasoning;
* provenance;
* ContextPack construction;
* confidence assessment.

However, the initial lineage architecture must not depend on:

* embeddings;
* vector databases;
* semantic retrieval;
* RAG;
* LLM reasoning.

Lineage should be usable before the Retrieval Layer exists.

### 20. MCP May Expose Lineage but Does Not Own It

ADR-056 and ADR-057 established MCP as an adapter over DevLog application
capabilities.

The same boundary applies to lineage.

Future MCP capabilities may expose operations conceptually similar to:

```text
get_knowledge_lineage

diagnose_knowledge_lifecycle
```

but the architecture must remain:

```text
External Agent
      ↓
     MCP
      ↓
Application Lineage Capability
      ↓
DevLog Domain / Projection State
```

not:

```text
External Agent
      ↓
     MCP
      ↓
Direct lineage tables
```

OpenCode, Kiko or another external agent must not become responsible for
reconstructing DevLog's internal knowledge lifecycle from low-level data.

DevLog owns lineage quality.

The external agent consumes it.

### 21. Lineage Does Not Automatically Repair Broken Lifecycles

A diagnostic capability may detect:

```text
ACCEPTED ENGINEERING_DECISION proposal
    ↓
Decision missing
```

The initial lineage system must report this inconsistency.

It must not automatically create the missing Decision.

Repair actions may eventually be introduced through explicit application
workflows.

Such workflows must preserve:

* domain validation;
* authorization;
* human governance where required;
* auditability;
* idempotency.

Detection and repair remain separate responsibilities.

## Consequences

### Positive

* DevLog can explain how trusted engineering knowledge was produced;
* missing lifecycle stages become diagnosable without broad repository
  investigation;
* application-level E2E failures become easier to localize;
* proposal, validation and promotion workflows gain explicit traceability;
* governance established by ADR-006 becomes observable;
* external engineering agents require less manual exploration to understand
  missing knowledge;
* lineage provides a deterministic foundation for future diagnostic tooling;
* the architecture can distinguish missing source data from projection,
  ranking or selection failures;
* future MCP capabilities can expose lifecycle diagnostics without exposing
  internal persistence;
* future Retrieval/RAG can consume lineage relationships without owning them;
* lineage can improve auditability of AI-assisted knowledge production;
* real lifecycle failures can be expressed as deterministic invariants;
* the approach does not require a graph database;
* the first implementation remains small enough to validate against current
  production workflows.

### Trade-offs

* lifecycle relationships become an additional architectural concern that must
  be maintained as domain workflows evolve;
* some relationships may require explicit persistence;
* explicit lineage persistence may add transactional complexity;
* deterministic reconstruction may require queries across multiple domain
  repositories;
* defining lifecycle invariants requires precise domain semantics;
* the boundary between lineage reconstruction and persisted lineage will need
  careful design;
* additional tests will be required to verify lifecycle integrity;
* lineage contracts may need to evolve when context-projection tracing is added;
* diagnostic capabilities add application surface area that must remain
  independent from internal persistence topology.

### Risks

* attempting to model every relationship immediately could create an
  unnecessarily large knowledge graph project;
* lineage infrastructure could become a second domain model duplicating
  existing entities;
* generic relationship models could lose meaningful domain semantics;
* persisting too many edges could create unnecessary write amplification;
* reconstructing every relationship dynamically could create expensive queries;
* poorly defined invariants could report valid intermediate states as failures;
* lifecycle diagnostics could accidentally become automatic repair mechanisms;
* MCP exposure could leak internal lineage implementation details;
* lineage could become coupled to future Retrieval/RAG infrastructure;
* graph-database adoption could be driven by architectural fashion rather than
  demonstrated need;
* lineage recording outside authoritative transactions could create misleading
  provenance;
* introducing lineage across all existing DevLog concepts at once could delay
  stabilization rather than improve it.

## Alternatives Considered

### Continue Diagnosing Lifecycles Through Repository Exploration

Rejected as the long-term approach.

Repository inspection remains necessary for implementation verification.

However, the recent `ENGINEERING_DECISION` investigation demonstrated that
reconstructing application lifecycles manually requires navigating multiple
services, repositories, projections and runtime states.

This is inefficient and does not scale as DevLog grows.

### Rely Only on Logging and Distributed Tracing

Rejected as the complete solution.

Runtime logs and technical traces are useful for operational debugging.

They primarily answer questions such as:

```text
Which method executed?

Which request failed?

How long did this operation take?
```

Engineering knowledge lineage answers different questions:

```text
Which proposal produced this Decision?

Why is trusted knowledge missing?

Which validation authorized this promotion?
```

Operational tracing and engineering lineage are complementary.

### Add More Foreign Keys Between Domain Entities

Rejected as the complete architecture.

Some explicit domain relationships may be appropriate.

However, database relationships alone do not represent lifecycle semantics,
expected transitions or invariant violations.

Lineage must remain an application-level engineering concept.

### Introduce a Generic Lineage Table for Every Relationship Immediately

Rejected for the first version.

A universal structure such as:

```text
source_type
source_id
relationship_type
target_type
target_id
```

may eventually be useful.

Introducing it before identifying which relationships actually require
persistence risks creating a generic graph abstraction without clear domain
semantics.

The implementation should first inventory existing reconstructible
relationships.

### Introduce a Graph Database

Rejected for the initial architecture.

The initial lifecycle is small, structured and strongly domain-oriented.

Relational persistence and deterministic reconstruction are sufficient to
validate the concept.

A graph database may be reconsidered only if future lineage queries demonstrate
a concrete need.

### Implement Context and MCP Lineage Immediately

Rejected for V1.

Tracing:

```text
Trusted Knowledge
    ↓
RepositoryEvidence
    ↓
EngineeringContext
    ↓
MCP
```

is valuable.

However, the immediate stabilization problem exists earlier in the governed
knowledge lifecycle.

The first implementation should validate:

```text
Proposal
    ↓
Validation
    ↓
Promoted Knowledge
```

before expanding downstream.

### Wait for the Retrieval Layer / RAG

Rejected.

Lineage solves an existing deterministic lifecycle problem.

It does not require semantic retrieval.

Delaying lineage until RAG would leave current application workflows difficult
to diagnose and would make future retrieval depend on provenance that has not
yet been formalized.

### Allow External Agents to Reconstruct Lineage

Rejected.

An external agent could inspect REST endpoints, MCP context, repository code and
database state to infer lifecycle relationships.

This reproduces the exact problem this ADR is intended to solve.

DevLog should understand and expose its own engineering knowledge lifecycle.

### Automatically Repair Invariant Violations

Rejected for the initial version.

Automatic repair introduces additional governance and safety concerns.

The first objective is reliable diagnosis.

Repair workflows can be designed separately once failure modes are understood.

## Explicit Non-Goals

This ADR does not define:

* a graph database;
* a generic knowledge graph;
* a complete lineage schema;
* final lineage table structures;
* final JPA entities;
* exact relationship enums;
* final REST endpoints;
* final MCP Tool names;
* final diagnostic response contracts;
* frontend lineage visualization;
* graph visualization;
* automatic lifecycle repair;
* automatic Decision creation;
* automatic Insight creation;
* automatic EngineeringEvent creation;
* bypass of `ValidatableProposal`;
* bypass of human or business validation;
* modification of ADR-006 governance;
* Git commit lineage;
* Engineering Story lineage;
* ADR document lineage;
* source-code symbol lineage;
* file-level lineage;
* complete context-projection lineage;
* ranking lineage;
* selection lineage;
* MCP result lineage;
* cross-project lineage;
* external knowledge lineage;
* vector search;
* embeddings;
* RAG infrastructure;
* Retrieval Layer implementation;
* AI-based invariant evaluation;
* LLM-based lifecycle reconstruction;
* distributed tracing replacement;
* observability platform replacement.

## Implementation Direction

The first implementation should validate Engineering Knowledge Data Lineage
against the smallest real governed lifecycle.

The reference scenario will be the recently introduced
`ENGINEERING_DECISION` lifecycle.

A suitable progression is:

1. inventory the current lifecycle relationships between `Analysis`, AI tasks,
   `ValidatableProposal`, `Validation`, `Decision`, `Insight` and
   `EngineeringEvent`;
2. identify which relationships can already be reconstructed deterministically
   from existing domain state;
3. identify relationships that are currently lost after a lifecycle transition;
4. define the minimal lineage vocabulary required for governed knowledge
   promotion;
5. define stable domain-oriented lineage references;
6. define the first deterministic lifecycle invariant:

```text
An ACCEPTED ENGINEERING_DECISION proposal
MUST produce exactly one trusted Decision.
```

7. determine whether Proposal → Decision provenance requires an explicit
   persisted relationship or can be reconstructed reliably;
8. implement the smallest application-level lineage query capable of tracing an
   `ENGINEERING_DECISION` lifecycle;
9. implement deterministic invariant evaluation for that lifecycle;
10. create focused tests covering:

```text
PROPOSED
    → no Decision expected

REJECTED
    → no Decision expected

ACCEPTED
    → exactly one Decision expected

ACCEPTED + no Decision
    → invariant violation

ACCEPTED + multiple Decisions
    → invariant violation
```

11. validate the capability against the real `devlog-ai` project;
12. verify that the diagnostic result would have identified the lifecycle gaps
    discovered during the recent E2E investigation;
13. extend the same model to `INSIGHT`;
14. extend the same model to `ENGINEERING_EVENT`;
15. evaluate whether a shared governed-knowledge lifecycle abstraction emerges
    naturally from these three implementations;
16. only after the governed lifecycle is stable, design Phase 2 lineage for:

```text
Trusted Knowledge
    ↓
ProjectContext
    ↓
RepositoryEvidence
    ↓
EngineeringContext
    ↓
MCP
```

17. use Phase 2 to distinguish:

```text
source data missing
candidate generation missing
candidate ranked too low
candidate rejected by selection
context exposure missing
```

18. expose lineage through MCP only after the application-level capability is
    stable and demonstrates value to real engineering-agent workflows;
19. design Retrieval Layer integration later so lineage can enrich retrieval
    without becoming dependent on vector infrastructure.

The first implementation should answer a practical question:

> Given an ENGINEERING_DECISION proposal, can DevLog deterministically explain
> whether it was validated, whether it was promoted into a trusted Decision,
> and exactly where the lifecycle is broken if the expected Decision does not
> exist?

A second validation question should be:

> Could DevLog have diagnosed the missing ENGINEERING_DECISION application entry
> point and the hardcoded AI generation path without requiring an engineering
> agent to manually reconstruct the entire proposal-generation and promotion
> pipeline?

If these questions can be answered reliably, the lineage architecture will have
demonstrated immediate value before expanding into broader project and context
lineage.
