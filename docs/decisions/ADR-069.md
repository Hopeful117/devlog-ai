# ADR-069 — Canonical Engineering Context Boundary

## 1. Title

Canonical construction, identity and projection boundary for DevLog engineering context.

## 2. Status

**Accepted**

Accepted by the human project owner on 2026-09-25. The decision is now the
architectural authority for Story 0145; implementation remains bounded by the
scope and migration constraints defined in this ADR.

## 3. Date

2026-09-24

## 4. Context

DevLog currently exposes several representations of related engineering knowledge:

```text
ProjectContextSnapshot / AnalysisContext
        -> RepositoryContextAdapter
        -> RepositoryContext
        -> EngineeringContextContractMapper
        -> public EngineeringContext (REST/MCP)

AnalysisContext
        -> KnowledgeSelectionService
        -> SelectedKnowledge
        -> SelectedKnowledgePromptProjectionService
        -> PromptRequest
        -> Python Story Context Analysis
```

The first path is the public EngineeringContext path. `EngineeringContextFacadeImpl` obtains a project snapshot, asks `RepositoryContextAdapter` to build a bounded repository context, and maps that result to the `EngineeringContext` contract. `RepositoryContextEngine` owns deterministic candidate collection, ranking, enrichment, selection, budgets, diagnostics and the existing repository-context digest.

The Story Context Agent path currently calls `EngineeringContextFacade`, but then builds or adapts an `AnalysisContext`, calls `KnowledgeSelectionService`, produces `SelectedKnowledge`, derives a prompt projection, and builds a separate grounding contract. The callback is validated against the grounding associated with `SelectedKnowledge.repositoryContext()`.

The representations are not interchangeable:

* `EngineeringContext` is a public contract containing project data, evidence, sections, request echo and summary metadata.
* `RepositoryContext` contains selected repository evidence, selection decisions, budget accounting, diagnostics, warnings and a digest.
* `AnalysisContext` contains project, analysis, Facts, Observations, knowledge events, decisions, proposals, relationships and other analysis-oriented snapshots.
* `SelectedKnowledge` is a selection result that retains an `AnalysisContext`-derived subset and the `RepositoryContext` used for grounding.
* `PromptRequest` carries a serialized `selectedKnowledge` map and a separate grounding contract to the Python engine.
* `AiTask` persists context, selection and execution snapshots, but currently names and populates these identities inconsistently.

The repository therefore has a real architectural boundary problem, not merely a DTO naming problem. A public projection must not become an accidental replacement for the richer authority needed by grounding, relations, diagnostics, trust and callback validation. Conversely, the Story Context Agent must not perform a second retrieval or silently enlarge the set authorized by Core.

The relevant current implementation includes:

* `backend/src/main/java/com/hopeful117/devlogai/engineeringcontext/EngineeringContextFacadeImpl.java`
* `backend/src/main/java/com/hopeful117/devlogai/engineeringcontext/mapper/EngineeringContextContractMapper.java`
* `backend/src/main/java/com/hopeful117/devlogai/projectcontext/RepositoryContextAdapter.java`
* `backend/src/main/java/com/hopeful117/devlogai/repositorycontext/RepositoryContext.java`
* `backend/src/main/java/com/hopeful117/devlogai/repositorycontext/RepositoryContextEngine.java`
* `backend/src/main/java/com/hopeful117/devlogai/analysis/context/AnalysisContext.java`
* `backend/src/main/java/com/hopeful117/devlogai/knowledge/selection/KnowledgeSelectionService.java`
* `backend/src/main/java/com/hopeful117/devlogai/knowledge/selection/SelectedKnowledge.java`
* `backend/src/main/java/com/hopeful117/devlogai/knowledge/selection/SelectedKnowledgePromptProjectionService.java`
* `backend/src/main/java/com/hopeful117/devlogai/projectcontext/projection/AgentContextProjectionService.java`
* `backend/src/main/java/com/hopeful117/devlogai/storycontextanalysis/usecase/AnalyzeStoryContextUseCase.java`
* `backend/src/main/java/com/hopeful117/devlogai/ai/task/entity/AiTask.java`
* `backend/src/main/java/com/hopeful117/devlogai/ai/engine/dto/PromptRequest.java`
* `ai-engine/app/schemas/story_context_analysis.py`

The current Python base contract uses Pydantic `extra="forbid"`. Any new envelope or identity fields must therefore be versioned and added deliberately; they cannot be silently added to an existing request.

## 5. Problem

DevLog needs one Core-owned authority for the context built for a conceptual request. REST, MCP and AI consumers need different shapes and budgets, but a projection must only reduce or reorganize the authorized context. It must not perform another retrieval, create a second semantic selection, or add evidence that was not in the canonical context.

The decision must also make the following identities unambiguous:

* `contextDigest`: identity of the Core-authorized canonical context;
* `selectionDigest`: identity of the existing selection result, retained only where compatibility requires it;
* `projectionDigest`: identity of the concrete serialized projection sent to one consumer.

The boundary must preserve typed references, provenance, trust classifications, grounding allow-lists, freshness information and enough execution metadata for future explanation or replay, without introducing a generic replay system or a new retrieval technology.

## 6. Decision Drivers

1. Java/Core must remain authoritative for scope, retrieval, trust, provenance, grounding and deterministic rules.
2. A public REST/MCP DTO must not be used as the internal domain model solely because it already exists.
3. A projection may reduce, order, compress or budget an authorized context, but may not broaden it.
4. Grounding validation must be able to resolve every permitted reference against the exact execution context.
5. Existing REST, MCP, AI task and legacy consumers need a migration path.
6. The decision must remain compatible with typed AI-facing references from ADR-068 and non-trusted AI output from ADR-006/065/067.
7. Context identity must support future replay explanations without requiring replay infrastructure in this ADR.
8. The design must avoid a second retrieval engine, a new database, or a generic agent framework.

## 7. Options Considered

### Option A — Make `EngineeringContext` the canonical model

The Core would enrich the existing public contract until every consumer could derive its needs directly from it.

**Advantages**

* One familiar top-level contract.
* Straightforward REST/MCP documentation.
* Fewer apparent model names.

**Disadvantages and risks**

* The current contract omits or flattens information needed by internal grounding, including the full `RepositoryContext` selection/diagnostic state and analysis-oriented Facts, Observations and relationships.
* Public compatibility would constrain internal evolution and could expose implementation details or overly large payloads.
* Adding every internal concern to the public DTO would couple REST/MCP consumers to AI and retrieval policy.
* A consumer could still reconstruct a second selection unless the service boundary changed; merely enriching the DTO does not enforce single construction.

**Assessment:** rejected. The existing `EngineeringContext` remains valuable, but it is not sufficient as the sole internal authority.

### Option B — Rich Core-owned canonical model, with `EngineeringContext` as a projection

The Core builds one internal canonical context for a request. It contains the authorized scope, source snapshot/freshness, trusted and technical knowledge, typed provenance, relations/diagnostics required by the use case, the bounded repository evidence and the canonical context identity. Public `EngineeringContext`, MCP responses and the Story Context Agent projection are deterministic views of that result.

The internal model may be represented by existing `RepositoryContext` and associated immutable scope/grounding metadata during migration. If a small aggregate/envelope is needed, it is an internal composition result, not a second retrieval model or persistence system.

**Advantages**

* Preserves the richer grounding source without making it public.
* Gives every consumer one Core-owned scope and context identity.
* Allows public contracts to stay bounded and compatible.
* Makes a non-broadening projection rule testable.
* Fits ADR-063's Core-owned composition and ADR-067's Java authority boundary.
* Leaves room for future replay metadata without requiring a replay engine now.

**Costs and risks**

* The current SCA path must be migrated away from an independent second selection.
* The internal canonical envelope and its digest inputs need explicit contracts and tests.
* Some legacy persistence fields remain during compatibility migration.

**Assessment:** selected.

### Option C — Introduce a new dedicated canonical context structure

DevLog would add a new first-class Core structure distinct from `RepositoryContext`, `AnalysisContext` and `EngineeringContext`, and migrate all consumers to it.

**Advantages**

* Explicitly names the desired boundary.
* Could model scope, knowledge, provenance, grounding and identity cleanly.

**Disadvantages and risks**

* High risk of duplicating `RepositoryContextEngine`, `AnalysisContext` composition or selection rules.
* Creates another representation before the current duplication is removed.
* Increases migration cost and compatibility surface.
* The repository has not demonstrated that a wholly new domain model is necessary; the immediate defect is ownership and composition, not the absence of a container.

**Assessment:** rejected for this decision. A small internal envelope may be introduced as an implementation detail of Option B only when it preserves existing Core composition and does not create another retrieval authority.

## 8. Decision

DevLog adopts **Option B: a rich Core-owned canonical context model, with `EngineeringContext` and consumer-specific agent/transport contracts as projections**.

The Core constructs and bounds one canonical context for each conceptual request. The canonical result is immutable for the duration of the request and contains, directly or through owned immutable components:

* request scope and request parameters;
* the source/project snapshot and freshness observation;
* authorized knowledge and repository evidence;
* typed provenance and trust classification;
* relations and diagnostics required by the consumer;
* the effective policy, collector and projection versions;
* budget and truncation accounting;
* `contextDigest`.

The current `RepositoryContext` is the authoritative bounded repository-evidence component during migration. It is not itself declared to be the complete canonical domain object because it does not contain every analysis-oriented item or request-level identity needed by all consumers. The canonical composition boundary may therefore carry `RepositoryContext` together with the already authorized project/analysis knowledge and an explicit scope/grounding envelope.

This envelope is deliberately constrained. It MUST not own repositories,
collectors, ranking algorithms, selection algorithms, persistence or a second
source of truth. It only composes immutable results already produced by the
existing Core services and assigns the request-level identity that binds them.
It is therefore an internal composition value, not a new context engine or
domain persistence model.

This is a composition and ownership decision. It does not authorize a new retrieval algorithm, a second database, a vector store, RAG, memory or a generic orchestration layer.

### Core invariant

For a conceptual request `R`, Core constructs exactly one authorized context `C(R)`.

Every projection `P_i` must satisfy:

```text
authorizedReferences(P_i) ⊆ authorizedReferences(C(R))
```

and must preserve the source identity of every retained item. A projection may order, reduce, serialize, summarize within an explicit deterministic policy, or omit items. It may not retrieve, infer authorization, reintroduce discarded items, or create a second semantic universe for the same request.

## 9. Canonical Context Model

The canonical model is an internal Core composition result, not a public DTO. Its conceptual shape is:

```text
CanonicalEngineeringContext
  contextVersion
  scope
    projectId / projectSlug
    storyId (nullable and explicit)
    intent
    files (canonical order)
    request parameters
  sourceSnapshot
    project/analysis snapshot identity
    source revisions
    freshness state and policy version
  authorizedKnowledge
    trusted knowledge and analysis snapshots selected by Core
    typed relationships
  repositoryContext
    bounded RepositoryEvidence
    provenance and trust
    selection decisions
    diagnostics
    budget/accounting/warnings
  grounding
    allowed typed references
    reference-to-source mapping
  policy
    collector/retrieval/composition versions
    scope policy version
  contextDigest
```

The exact Java record/class names are implementation detail for the follow-up Story. The following semantics are decided:

* scope is Core-owned and immutable after construction;
* trust is assigned by Core and is not inferred from a projection;
* provenance is retained for every citable item;
* typed AI-facing references follow ADR-068;
* relations are carried as explicit data with their relation semantics, not inferred from co-occurrence;
* diagnostics and budgets describe what was available, selected, omitted and truncated;
* freshness is part of the context snapshot and cannot be silently refreshed by Python;
* the canonical model may contain more information than any one projection;
* a public projection must not expose internal fields merely to compensate for an undefined boundary.

`AnalysisContext` remains an analysis composition model and may remain a source component during migration. It is not, by naming alone, allowed to become a second retrieval authority. `SelectedKnowledge` remains a compatibility representation until its consumers are migrated; it is not the canonical authority after this ADR is accepted.

For the Story Context Agent specifically, `EngineeringContextFacade` and
`KnowledgeSelectionService` MUST NOT remain concurrent authorities for one
conceptual request. One Core application method constructs the canonical
result; the SCA projection consumes that result. `KnowledgeSelectionService`
continues only for legacy consumers or for an explicitly different request
with its own scope, request identity and digest.

## 10. Projection Model

Each consumer receives a named, versioned projection produced by a Core-owned projection service from the same canonical context instance.

Projection metadata must include:

* `projectionVersion`;
* `contextDigest`;
* `projectionDigest`;
* scope/request echo;
* source freshness summary;
* deterministic ordering policy;
* effective budget and accounting;
* truncation and warnings;
* authorized typed grounding references and their provenance;
* trust classification for retained items.

The projection service owns reduction and serialization. It must not call retrieval, `KnowledgeSelectionService` or an equivalent semantic selector for the same conceptual request. If a separate selection is required for a genuinely different capability, it must have a different explicit request identity and digest rather than being hidden as a projection.

## 11. Story Context Agent Contract

The Story Context Agent receives a versioned **Story Context Agent Projection** derived from the canonical context. The conceptual payload is:

```text
StoryContextAgentProjection v1
  projectionVersion
  contextDigest
  projectionDigest
  scope/requestEcho
  freshness
  context
    project
    trusted knowledge and analysis sections
    repository evidence
    relations
  groundingCandidates
    typed authorized references
    source/provenance/trust metadata
  accounting
    candidateCount
    selectedCount
    usedTokens
    budget
    truncated
    discardedCount
    warnings
  compatibility
    selectedKnowledge (temporary envelope, if required)
```

The owner of this projection is the Java/Core application layer, not Python and not the transport controller. Its version is independent from the provider model version and from the legacy `selectionVersion`.

Required information:

* context and projection identity;
* project/story scope and request echo;
* authorized evidence and typed grounding references;
* provenance, trust tier and source references;
* freshness and source revision information;
* deterministic accounting and warnings;
* contract and policy versions.

Optional information may include reduced summaries, non-citable explanatory sections and additional diagnostics, provided their omission cannot authorize a reference or change scope.

Budgets apply only to projection after canonical context construction. A projection may omit lower-priority material, but it must expose the reduction and may not replace it with a fresh retrieval. The initial migration may retain the Python field `selectedKnowledge` as a compatibility envelope because the Pydantic request uses `extra="forbid"`. The envelope must carry the new version and identity fields, and the Python contract must be versioned deliberately. It is not permitted to keep the old name while silently changing its semantics.

The Python engine may interpret this projection and generate structured, non-trusted output. It may not query DevLog, read the project repository, call a second retrieval path or add grounding candidates.

## 12. Digest Semantics

All digests are lowercase SHA-256 representations of a canonical, versioned serialization. They are distinct identities and must never be assigned interchangeably.

### `contextDigest`

`contextDigest` identifies the authorized canonical context, before consumer-specific projection.

It includes:

* canonical context model/version;
* project and explicit request scope, including `storyId`, intent, files and relevant request parameters;
* source snapshot identity and source revisions;
* freshness state/policy values that affect eligibility;
* authorized knowledge and repository evidence in canonical order;
* typed identities, provenance, trust and relationship semantics;
* effective composition/retrieval/collector policy versions;
* canonical budget and selection decisions where they affect the retained context;
* canonical diagnostics and omission/truncation state that describes the context.

It excludes:

* AI output;
* provider/model identity;
* projection-specific ordering or serialization shape;
* execution UUIDs and correlation IDs;
* log formatting;
* wall-clock timestamps that do not affect the source/freshness decision.

Freshness timestamps remain in the retained snapshot metadata for audit/replay. They participate in the digest only when their value changes the effective freshness decision or source snapshot identity.

### `selectionDigest`

`selectionDigest` identifies the legacy or capability-specific `SelectedKnowledge` selection result and its `SelectionMetadata`/selection policy. It is not a synonym for `contextDigest`.

It remains temporarily for existing analysis and AI-task consumers that still use `KnowledgeSelectionService`. For the migrated Story Context Agent it is optional compatibility metadata and must not authorize grounding or be used to validate the canonical context. Once no consumer requires it, it may be deprecated and removed through a separate migration decision.

### `projectionDigest`

`projectionDigest` identifies the exact projection sent to a consumer. It includes:

* projection contract/version;
* `contextDigest`;
* retained item identities and serialized values;
* ordering rules and order;
* reduction and budget policy/version;
* accounting, warnings and truncation;
* grounding candidate set and reference mapping;
* scope echo and freshness fields included in the payload;
* the canonical serialized shape relevant to the consumer contract.

It excludes transport headers, retries and provider-generated output. Two projections derived from one context may therefore share `contextDigest` and have different `projectionDigest` values.

### Canonical serialization rules

Every digest uses explicitly versioned canonical JSON: UTF-8 encoding, keys
sorted lexicographically, lists emitted in contract-defined order, consistent
null/omission semantics, locale-independent number and string serialization,
the schema/version identifier included as an input field, and SHA-256 rendered
as lowercase hexadecimal. The implementation Story must provide test vectors
for empty collections, maps, null/omitted optional fields, Unicode, ordering
and budget changes.

Composition budget and selection decisions that determine which material is in
the canonical context participate in `contextDigest`. A consumer-only budget
that reduces or serializes an already-built context participates only in
`projectionDigest`. Projection-only ordering, shape and accounting never
change `contextDigest`.

## 13. Identity Propagation

The following propagation is required by the implementation Story:

| Boundary | Required identity |
|---|---|
| Canonical Core result | `contextDigest`, scope, source/policy versions, grounding mapping |
| Public `EngineeringContext` metadata | `contextDigest`; projection metadata when the contract is versioned to expose it |
| Story Context Agent projection | `contextDigest`, `projectionDigest`, optional legacy `selectionDigest` |
| `AiTask` | separate persisted fields for `contextDigest`, `projectionDigest` and compatibility `selectionDigest`; no overloaded field |
| `contextSnapshot` | immutable scope, freshness, policy, accounting, grounding and all three applicable identities |
| `PromptRequest` | versioned metadata/envelope carrying `contextDigest` and `projectionDigest`; `selectionDigest` only as explicitly marked compatibility data |
| Python callback/result provenance | Core-issued `contextDigest` and projection identity; callback cannot invent or replace them |
| Persisted analysis/result snapshot | input identities, projection version, execution identity, validation outcome and source mapping |
| Logs/observability | correlation/task IDs plus the three identities when present; no secret or full payload requirement |

Before submission, Core must verify that the projection digest was computed from the supplied context digest and that the scope/grounding mapping is internally consistent. At callback time, Core must verify:

1. the task identity and execution are valid;
2. returned `contextDigest` equals the task's Core-issued `contextDigest`;
3. returned projection identity/version is compatible with the submitted projection;
4. every returned reference is typed, allowed for its output field, in the task mapping and in the canonical grounding set;
5. the result does not mutate or expand the stored context snapshot.

Missing, invented, mismatched or retroactively completed identity is a validation failure. The callback cannot establish identity merely by returning a digest.

The execution snapshot is assembled completely before submission and persisted
as one immutable snapshot. It contains the three applicable digests, scope,
source revisions/freshness, policy and budget versions, truncation/accounting,
typed-reference mapping, grounding allow-list version, and the exact
projection (or an immutable content-addressed representation of it). It is not
mutated after the task enters `SUBMITTED`; later callback data can only append
validation outcome and non-trusted result data.

## 14. Grounding and Non-Broadening Rules

Java/Core owns the grounding allow-list and the mapping from each typed reference to its source item. The projection may expose a subset and may separate semantic context from citable grounding candidates, consistent with ADR-068.

The following rules are mandatory:

* visible context is not automatically citable context;
* a reference is valid only in its declared namespace, scope and output field;
* a projection cannot turn an Insight, relationship endpoint or summary into a Fact/Evidence reference without Core authorization;
* Python validation may reject malformed or out-of-subset output, but Java/Core remains authoritative;
* no callback result can add a source, relationship, trust tier or grounding reference;
* AI recommendations and interpretations remain non-trusted output;
* promotion to trusted knowledge follows the existing explicit validation lifecycle and is outside this ADR.

For the SCA migration, repository grounding references MUST use the ADR-068
typed reference abstraction, for example
`{type: "REPOSITORY_EVIDENCE", ref: "...", scope: "PROJECT_REVISION"}`.
The projection must separate semantic context from
`groundingCandidates.repositoryEvidence[]`. Raw reference strings may exist
only inside a versioned compatibility envelope. Core validation must check
reference type, scope, project/revision ownership, task mapping and membership
in the canonical allow-list.

## 15. Java/Python Authority Boundary

Java/Core owns:

* project, story and request scope;
* context construction and freshness snapshot;
* retrieval/composition and budgets;
* trust and provenance;
* typed reference creation and resolution;
* grounding allow-lists;
* context and projection identities;
* deterministic contract and callback validation;
* persistence of immutable execution metadata.

Python may:

* interpret the received projection;
* produce structured findings, uncertainty and recommendations;
* perform defensive schema and subset checks using the supplied contract.

Python must not access project storage/repositories, perform retrieval, broaden grounding, alter canonical context, create trusted knowledge or issue a replacement digest.

## 16. REST/MCP Boundary

REST controllers and MCP tools remain transport adapters. They invoke the same Core application capability and receive a projection from the canonical context result. MCP must not contain context composition, retrieval, trust or projection policy that differs from REST.

The current EngineeringContext REST contract remains supported as a public projection. Its mapper may evolve to expose explicit identity/version metadata compatibly, but it must not become the internal authority. MCP contracts remain bounded adapters over the same service.

The Story Context Agent REST endpoint and MCP tool must use the same Story Context Agent projection service. Any transport-specific envelope is a serialization concern and must preserve `contextDigest`, `projectionDigest`, scope, grounding and provenance.

The current boundary is recorded explicitly for migration:

| Surface | Current path | Target under this ADR |
|---|---|---|
| REST engineering context | `EngineeringContextController` → `EngineeringContextFacade` | shared canonical context → public `EngineeringContext` projection |
| MCP engineering context | `EngineeringContextTool` / project-context client | same Core capability and public projection; no MCP composition |
| REST SCA | `AnalyzeStoryContextUseCase` → facade, then `AnalysisContextService`/`KnowledgeSelectionService` | one canonical Core result → versioned SCA projection |
| AI callback | `AiTaskResultService` / Python provenance | validate Core-issued context and projection identities; never assign them from callback |
| Legacy story context | `EngineeringStoryContextServiceImpl` → adapter/projection | compatibility facade over canonical result, with explicit legacy scope mapping |

`storyId`, when supported, must be explicit in the request echo and canonical
scope. A legacy description-only request is either mapped deterministically to
an explicit scope or treated as a distinct legacy request; it must not silently
claim the identity of a story-scoped request.

## 17. Legacy Compatibility

`EngineeringStoryContext` remains a legacy contract until its external consumers are inventoried and migrated. It may be maintained through a compatibility facade that derives its response from the canonical Core context, but it must not retain an independent retrieval universe for the same request.

The migration must:

1. inventory local and documented external consumers;
2. preserve current endpoint shapes during a dated compatibility window;
3. add identity/version metadata without breaking required fields;
4. compare legacy and canonical outputs where feasible;
5. publish deprecation and rollback criteria;
6. remove or retire the legacy path only in a separate approved change.

No legacy endpoint is deleted by this ADR.

## 18. Determinism and Future Replay

This ADR does not build a replay service. It requires the execution boundary to retain enough facts to answer later:

> Which authorized context and exact projection were supplied for this execution?

At minimum, the persisted snapshot must preserve:

* `contextDigest`, `projectionDigest` and any compatibility `selectionDigest`;
* scope and request parameters;
* source revisions and freshness decision;
* context, collector/composition and projection policy versions;
* budget/accounting/truncation/warnings;
* typed reference mapping and grounding allow-list version;
* the exact projection or a content-addressed immutable representation of it;
* task/execution identity and validation outcome.

Execution timestamps and provider/model details remain useful audit metadata but must not be confused with context identity. A future replay implementation may use these records to reconstruct or explain a run; the current migration need only preserve the required inputs and identities.

Two replay artifacts remain distinct:

* **projection snapshot** — the exact Core-to-Python Story Context Agent input;
* **prompt snapshot** — the complete `PromptRequest`/provider envelope after intent, guidance, output contract and grounding contract are assembled.

The projection snapshot is required to explain context identity and grounding.
The prompt snapshot is additional execution/audit evidence and does not redefine
`contextDigest` or `projectionDigest`.

## 19. Consequences

### Positive

* One Core-owned composition result becomes the authority for all consumers.
* REST, MCP and AI projections can evolve independently without changing grounding authority.
* Grounding and callback validation can refer to the exact source context.
* Public contracts remain bounded and compatibility-friendly.
* Future Developer OS integration can consume a versioned projection without owning retrieval.
* Digest mismatches become diagnosable instead of hidden in `selectionDigest`.

### Negative

* The SCA path requires a non-trivial migration from second selection to canonical projection.
* `AiTask` and Python contracts need explicit versioned identity fields.
* Legacy fields and representations will coexist during the compatibility window.
* Canonical serialization and projection tests add maintenance cost.

## 20. Migration Strategy

The implementation Story must proceed in bounded steps:

1. Define the internal canonical context boundary and immutable identity envelope around the existing Core composition; do not add a second retrieval path.
2. Define canonical serialization and `contextDigest` inputs.
3. Add a Core-owned Story Context Agent projection preserving `RepositoryContext` grounding, typed references, provenance, freshness and accounting.
4. Add `projectionDigest` and separate identity propagation through `AiTask`, snapshots, `PromptRequest`, Python contract and callback validation. Keep `selectionDigest` explicitly compatibility-only.
5. Route the Story Context Agent through the canonical result and remove its second semantic selection for the same request.
6. Adapt REST and MCP to the shared Core projection service.
7. Keep `selectedKnowledge` as a versioned temporary Python envelope until all required consumers migrate; `extra="forbid"` contract changes must be coordinated.
8. Adapt the legacy `EngineeringStoryContext` path through a compatibility facade and measure consumers before deprecation.
9. Add contract, digest, grounding-subset, single-construction, callback-mismatch and compatibility tests.

No database, retrieval algorithm, RAG/vector infrastructure, memory system or generic orchestrator is part of these steps.

## 21. Rejected Alternatives

* **Use `EngineeringContext` as an all-purpose domain model:** rejected because the public contract is not rich enough for internal grounding and would couple public compatibility to internal retrieval policy.
* **Keep `KnowledgeSelectionService` as the SCA authority:** rejected because it creates a second semantic selection for the same conceptual request and makes `selectionDigest` masquerade as context identity.
* **Let Python retrieve missing context:** rejected because it violates Java/Core authority, trust and grounding boundaries.
* **Create a new independent ContextPack/retrieval engine:** rejected because it duplicates the current Core composition and expands scope.
* **Delete `EngineeringStoryContext` immediately:** rejected because external consumers are not proven absent.
* **Treat `selectionDigest` as `contextDigest`:** rejected because selection and canonical context have different semantics and lifecycle.

## 22. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The internal envelope becomes a new hidden domain model | Keep it immutable, Core-owned, backed by existing composition, and prohibit independent retrieval/selection. |
| Public `EngineeringContext` omits grounding data | Generate agent projection from the canonical internal result retaining `RepositoryContext` and reference mapping. |
| Digest fields remain overloaded | Add separate fields and contract tests; reject mismatches before/after callback. |
| Python contract breaks due to `extra="forbid"` | Version the envelope and update Java/Python wire tests together. |
| Projection accidentally broadens grounding | Core-issued typed allow-list, subset validation and single-construction tests. |
| Freshness changes without identity change | Include effective freshness/source revision in canonical identity and retain observation metadata. |
| Legacy consumers are missed | Compatibility window, inventory, telemetry and separate deprecation decision. |
| Canonicalization is confused with full scoping/replay | Keep story scope narrow; record dependencies and follow-ups explicitly. |

## 23. Relationship with Existing ADRs

This proposal complements the existing architecture as follows:

* **ADR-006 — AI Proposal and Knowledge Promotion Workflow:** preserves the rule that AI output is not trusted knowledge and cannot be promoted automatically.
* **ADR-013 — Deterministic Construction of Analysis Context:** retains deterministic Core construction; this ADR clarifies that `AnalysisContext` is not permission for a second retrieval authority.
* **ADR-014 — Hybrid Context Retrieval Owned by the Core:** reinforces Core ownership of retrieval and makes the ownership boundary explicit across projections.
* **ADR-033 — Knowledge Selection Engine:** preserves `KnowledgeSelectionService` for consumers that still require it, but prevents its compatibility digest from becoming the canonical SCA context identity.
* **ADR-055 — Engineering Context Enrichment and Projection:** specializes the projection boundary and adds explicit context/projection identity semantics.
* **ADR-056 — DevLog MCP Integration Boundary and Module Placement:** preserves MCP as an adapter and DevLog ownership of composition/projection.
* **ADR-063 — Engineering Context Retrieval and Composition Architecture:** applies its shared composition and canonical reference requirements to the SCA path; no independent retrieval is introduced.
* **ADR-064 — Hybrid Analysis Context Composition Architecture:** retains analysis composition where needed, but assigns one request-level canonical result to the consumer.
* **ADR-065 — Analysis Synthesis and Knowledge Proposal Separation:** preserves execution-scoped, non-trusted AI output.
* **ADR-067 — DevLog Engineering Story Context Agent:** operationalizes its Java authority, shared REST/MCP capability and fresh-context principles. This proposal refines the term “EngineeringContext” in D3: the Core capability/result is authoritative, while the existing public DTO is a projection of that result. Acceptance of this ADR therefore requires treating that clarification as an amendment to D3, not as a silent contradiction.
* **ADR-068 — Typed AI-Facing References and Grounding Namespace Isolation:** supplies the reference namespace and scope rules used by the canonical grounding envelope.

* **ADR-046 — Separate Rich Repository Context from Agent Transport Projection:** already distinguishes authoritative `RepositoryContext` and a separate `projectionDigest`; this ADR extends that separation to the SCA and request-level canonical identity.
* **ADR-058 — Engineering Knowledge Data Lineage:** its deferred context-projection lineage remains a follow-up; this ADR requires only the execution mapping and snapshot needed to prevent identity loss.

No existing ADR is silently overridden. If implementation reveals that an existing contract explicitly mandates a second independent selection for a different capability, that capability must receive a distinct request identity rather than being folded into this one.

## 25. Reviewer Findings

Independent review completed against the repository and this proposal. The
reviewer confirms that **Option B is justified and preferable to Option A**:
the current public `EngineeringContext` contract is too narrow to be the
complete authority for grounding, relations, diagnostics and internal
selection, while ADR-063/067/068 require Core-owned composition and typed
allow-lists.

The review identified four blocking gaps, resolved in this revision:

| Finding | Resolution |
|---|---|
| Current code aliases `selectionDigest` as `contextDigest` and has no separate `projectionDigest` propagation | Sections 12–13 define the three identities normatively and require distinct `AiTask`, versioned `PromptRequest`, callback/result and snapshot fields with mismatch rejection. |
| SCA still performs `EngineeringContextFacade → AnalysisContextService → KnowledgeSelectionService → SelectedKnowledge` | Sections 9, 10 and 20 require one canonical Core construction, a single-construction test, and legacy-only/different-request use of `KnowledgeSelectionService`. |
| SCA grounding still uses raw repository-reference strings rather than ADR-068 typed references | Section 14 requires typed references, separated grounding candidates and Core validation of type/scope/mapping/allow-list. |
| `AiTask.contextSnapshot` is currently mutated while preparing submission | Section 13 and the migration strategy require the final snapshot to be assembled before submission and immutable after `SUBMITTED`. |

The review also requested and this revision supplies:

* hard limits distinguishing the internal envelope from a new retrieval/domain model;
* canonical JSON serialization rules and digest test vectors;
* separation of composition budgets from projection-only budgets;
* an endpoint/service migration table and explicit legacy scope mapping;
* projection snapshot versus full prompt snapshot semantics.

The repository does not yet satisfy these requirements. They are acceptance
conditions for the follow-up implementation Story, not claims that the current
implementation is already compliant.
