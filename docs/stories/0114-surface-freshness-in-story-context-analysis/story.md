## Problem

The Story Context Analysis produces structured, grounded analysis for
Discuss/Plan preparation. Its output — `StoryContextAnalysisResult` — is the
primary artifact consumed by engineering agents making implementation
decisions.

However, the analysis result contains no freshness metadata. When the
repository evolves after the engineering context was last refreshed, the
analysis can silently present stale knowledge as current truth. The consumer
has no mechanism to distinguish:

```text
analysis produced from fresh context
```

from:

```text
analysis produced from potentially stale context
```

This is a concrete instance of the broader temporal knowledge gap described
in ADR-059 (Proposed).

### Repository Evidence

**REPOSITORY FACT**: `EngineeringContext.metadata().freshness()` already
carries authoritative deterministic freshness: aggregate status (`CURRENT`,
`STALE`, `PARTIALLY_FRESH`, `NO_BASELINE`, `UNKNOWN`), repository revision,
context revision, per-source breakdown with observed and baseline revisions,
and aggregate warnings (`PROJECT_CONTEXT_STALE`,
`PROJECT_CONTEXT_PARTIALLY_FRESH`). This is constructed by
`EngineeringContextContractMapper.buildFreshness()` from persisted
`ProjectSourceFreshness` rows and live evidence revisions. It is purely
deterministic — never generated by AI.

**REPOSITORY FACT**: `AnalyzeStoryContextUseCase.buildSelectedKnowledge()`
discards `EngineeringContext.metadata()` entirely. The selectedKnowledge map
passed to the AI engine contains only `contextDigest` (a SHA-256 hash) and
raw evidence — no freshness status, no repository revision, no warnings.

**REPOSITORY FACT**: `StoryContextAnalysisResult` (the AI output contract in
`devlog-contracts`) is a Java record generated by the Python AI engine via
structured output. It is the AI-produced analysis payload. It has no field
for freshness status, repository revision, or staleness indication.

**REPOSITORY FACT**: `StoryContextAnalysis` (the JPA entity) persists the
AI output as `analysisSnapshot` (JSONB `Map<String, Object>`) with no
freshness metadata beyond `createdAt`.

**REPOSITORY FACT**: The freshness semantics are synchronization-state
metadata, not knowledge-item temporal validity. `CURRENT` proves the
knowledge baseline was derived from the observed repository revision. It
does NOT prove that every Fact, Insight, Decision, or relationship is
semantically current. `STALE` proves the repository has advanced beyond the
knowledge baseline. It does NOT identify which specific knowledge items are
affected.

**SUPPORTED CONCLUSION**: Authoritative freshness information exists in the
system at the EngineeringContext level but is not captured with the Story
Context Analysis result. The consumer therefore cannot determine the
synchronization state of the source context that produced the analysis.

### Concrete Staleness Scenario

```text
1. Analysis A produces EngineeringContext at revision R1
2. Story Context Analysis consumes EngineeringContext, produces analysis
3. Repository evolves to R2 (material changes)
4. ProjectSourceFreshness becomes STALE
5. New Story Context Analysis request arrives
6. EngineeringContext is built from stale knowledge (R1) + live structure (R2)
7. Story Context Analysis produces result from mixed-revision context
8. Consumer receives analysis with no staleness indication
9. Consumer makes implementation decisions based on stale architectural context
```

The `EngineeringContext.metadata.freshness` would correctly report `STALE`
but this information is never captured with the analysis result.

## Goal

Preserve and expose the authoritative `EngineeringContextFreshness` snapshot
used to produce each Story Context Analysis, allowing consumers to determine
the synchronization state of the source context without requiring AI to
infer temporal validity.

Freshness is deterministic metadata owned by the Core/context pipeline. The
AI must NOT become the authority that generates, reconstructs, or interprets
this freshness state.

## Current Behavior

### EngineeringContext Freshness (already present)

```java
EngineeringContextFreshness(
    status: "STALE",
    repositoryRevision: "abc123...",
    contextRevision: "def456...",
    sources: [SourceFreshness(
        sourceId, name, status, guidance,
        observedRevision, contextRevision, checkedAt
    )]
)
```

This is embedded in `EngineeringContext.metadata().freshness()`. It is
constructed deterministically by `EngineeringContextContractMapper` from
persisted `ProjectSourceFreshness` rows and live evidence revisions.

### Story Context Analysis Pipeline (current)

```text
EngineeringContext (includes metadata.freshness)
    ↓
AnalyzeStoryContextUseCase.execute()
    ↓ buildSelectedKnowledge()
selectedKnowledge (NO freshness — metadata discarded)
    ↓
AI Engine generates StoryContextAnalysisResult (AI output — no freshness)
    ↓
handleCallback() persists StoryContextAnalysis (NO freshness column)
    ↓
Consumer receives result (NO freshness)
```

### StoryContextAnalysisResult (current AI output)

```java
StoryContextAnalysisResult(
    objectiveUnderstanding: ...,
    architectureFindings: ...,
    decisionFindings: ...,
    evidenceFindings: ...,
    historicalContext: ...,
    constraintFindings: ...,
    impactedComponentFindings: ...,
    uncertainties: ...,
    missingInformation: ...,
    implementationQuestions: ...,
    confidence: ...,
    provenance: ...,
    outputClassification: ...
    // NO freshness — this is the AI-owned contract
)
```

## Desired Behavior

### Authoritative Freshness Propagation

```text
EngineeringContext (includes metadata.freshness)
    ↓
AnalyzeStoryContextUseCase.execute()
    ↓
    ├─ buildSelectedKnowledge()        → AI receives evidence (NO freshness in prompt)
    ├─ capture freshness snapshot       → deterministic, from metadata.freshness()
    └─ store snapshot in AiTask context → carried to callback
    ↓
AI Engine generates StoryContextAnalysisResult (AI-owned — unchanged)
    ↓
handleCallback()
    ↓
    ├─ Core extracts freshness snapshot from AiTask contextSnapshot
    ├─ Core persists snapshot in StoryContextAnalysis.contextFreshness column
    └ Core persists AI analysisSnapshot (unchanged)
    ↓
Consumer receives result
    ↓
    ├─ analysisSnapshot  → AI-produced analysis (unchanged)
    └─ contextFreshness  → authoritative deterministic snapshot
```

### Ownership Invariant

```text
AI owns:   analysis output (StoryContextAnalysisResult)
Core owns: freshness metadata (EngineeringContextFreshness snapshot)
```

The freshness snapshot is captured at context construction time and persisted
with the analysis. It is NOT generated by the AI, NOT echoed by the AI, and
NOT part of the AI output contract.

### StoryContextAnalysis Entity (desired)

```java
StoryContextAnalysis(
    // ... existing fields ...
    analysisSnapshot: Map<String, Object>,    // AI output — unchanged
    contextDigest: String,                     // unchanged
    promptExecutionMetadata: Map<String, Object>, // unchanged
    contextFreshness: Map<String, Object>      // NEW: authoritative deterministic snapshot
)
```

The `contextFreshness` column stores the `EngineeringContextFreshness` values
(status, repositoryRevision, contextRevision, sources, warnings) as JSONB at
the time the analysis context was constructed.

### Mixed-Revision Visibility Preserved

The existing `EngineeringContextContractMapper.buildFreshness()` already
handles the case where live evidence revisions differ from the knowledge
baseline revision. The freshness snapshot captures this mixed-revision state
honestly:

```text
freshness.repositoryRevision = "R2"  (from live evidence)
freshness.contextRevision    = "R1"  (from knowledge baseline)
freshness.status             = "STALE"
```

This allows consumers to understand that the analysis was produced from a
context containing live structure at R2 alongside knowledge derived from R1.

## Design

### 1. Freshness Snapshot Capture

In `AnalyzeStoryContextUseCase.execute()`, after building the
`EngineeringContext`, capture the freshness snapshot:

```java
EngineeringContext engineeringContext = engineeringContextFacade.getEngineeringContext(...);
Map<String, Object> freshnessSnapshot = captureFreshnessSnapshot(engineeringContext);
```

The snapshot is a Map representation of `EngineeringContextFreshness`:
status, repositoryRevision, contextRevision, sources (with per-source
observedRevision, contextRevision, status, guidance, checkedAt), and
warnings from `EngineeringContextMetadata`.

### 2. Freshness Snapshot Carried Through Task Lifecycle

The freshness snapshot is stored in `AiTask.contextSnapshot` alongside the
existing `analysisId`, `intentId`, and `intentVersion` keys. This requires
no schema change to `AiTask` — `contextSnapshot` is already a JSONB map.

```java
Map<String, Object> contextSnapshot = new LinkedHashMap<>(Map.of(
    "analysisId", analysis.getId().toString(),
    "intentId", intentId,
    "intentVersion", intentVersion
));
if (freshnessSnapshot != null) {
    contextSnapshot.put("contextFreshness", freshnessSnapshot);
}
```

### 3. StoryContextAnalysis Entity Extension

The `StoryContextAnalysis` entity adds a `contextFreshness` JSONB column:

```java
@JdbcTypeCode(SqlTypes.JSON)
@Column(name = "context_freshness", columnDefinition = "jsonb")
private Map<String, Object> contextFreshness;
```

A Flyway migration adds this nullable column. Existing rows have NULL
(freshness unavailable for historical analyses).

### 4. Callback Persists Freshness Snapshot

In `AnalyzeStoryContextUseCase.handleCallback()`, extract the freshness
snapshot from `AiTask.contextSnapshot` and persist it with the analysis:

```java
Map<String, Object> contextFreshness = null;
if (task.getContextSnapshot() != null) {
    contextFreshness = (Map<String, Object>) task.getContextSnapshot().get("contextFreshness");
}

StoryContextAnalysis analysis = StoryContextAnalysis.builder()
    // ... existing fields ...
    .contextFreshness(contextFreshness)
    .build();
```

### 5. Query Service Exposes Freshness

`StoryContextAnalysisQueryService.toResult()` deserializes the persisted
`contextFreshness` and returns it alongside the analysis result. This may
require extending the response type or returning the freshness as a
companion field. The exact representation depends on existing API patterns.

### 6. No Prompt Changes

The Story Context Analysis prompt is NOT modified. The AI does not receive
freshness information and does not produce freshness output. This is
intentional: the system currently lacks the deterministic granularity to
identify which individual findings are affected by staleness, and asking the
LLM to infer this would produce unreliable results.

### 7. No AI Output Contract Changes

`StoryContextAnalysisResult` (the Java record and Python Pydantic model) is
NOT modified. It remains the AI-owned analysis payload. Freshness is
associated at the application level, not the AI generation level.

## Acceptance Criteria

### AC1 — Freshness Snapshot Captured at Context Construction

When `AnalyzeStoryContextUseCase.execute()` builds an `EngineeringContext`,
the `EngineeringContext.metadata().freshness()` snapshot is captured and
stored in the `AiTask.contextSnapshot`.

### AC2 — Freshness Persisted with Analysis

When `handleCallback()` persists a `StoryContextAnalysis`, the freshness
snapshot from `AiTask.contextSnapshot` is persisted in the
`contextFreshness` JSONB column.

### AC3 — STALE Preserved Exactly

Given a context whose freshness is `STALE`, the persisted
`StoryContextAnalysis.contextFreshness` contains `status = "STALE"` with
the full authoritative snapshot (repositoryRevision, contextRevision,
sources, warnings). No LLM qualification is required or performed.

### AC4 — PARTIALLY_FRESH Preserved Exactly

Given a `PARTIALLY_FRESH` context, the persisted `contextFreshness` contains
`status = "PARTIALLY_FRESH"`. It is NOT reinterpreted as "some knowledge is
stale."

### AC5 — CURRENT Preserved Exactly

Given `CURRENT`, the persisted `contextFreshness` contains `status =
"CURRENT"`. The Story does not claim this proves semantic validity.

### AC6 — Missing Freshness Handled

When `EngineeringContext.metadata().freshness()` is null or absent, the
`contextFreshness` column is NULL. The analysis proceeds without error.
Consumers interpret NULL freshness as "freshness unavailable."

### AC7 — Historical Analyses Unaffected

Existing persisted `StoryContextAnalysis` records retain NULL
`contextFreshness`. No backfill is performed. Historical freshness cannot
be reconstructed honestly.

### AC8 — Existing AI Analysis Unchanged

The existing `StoryContextAnalysisResult` fields, evidence grounding, and
analysis quality are unchanged. The AI does not receive, process, or produce
freshness information. No regression in existing test suites.

### AC9 — Per-Source Information Preserved

The persisted `contextFreshness` preserves per-source breakdown:
sourceId, name, status, guidance, observedRevision, contextRevision,
checkedAt. This enables consumers to identify which source caused staleness
and which revisions are involved.

### AC10 — Scope And Quality Gates Hold

Targeted tests for the freshness capture and persistence, the full
`mcp-server` verification suite, and `git diff --check` pass without
unrelated architectural or domain changes.

## Unresolved Questions

### Q1 — Freshness Exposure Format

The query service needs to expose `contextFreshness` to consumers. Should
this be:
- (a) A separate field in the REST/MCP response alongside the analysis
  result?
- (b) An extension to the existing response envelope?
- (c) A separate endpoint?

The investigation recommends (a) for simplicity, but the exact API surface
should be validated during implementation against existing REST/MCP patterns.

### Q2 — Historical Analysis Compatibility

Existing REST/MCP consumers expect `StoryContextAnalysisResult` without
freshness. Adding a new field to the response envelope may require API
versioning or backward-compatible construction. The implementation should
verify that existing consumers are not broken by a NULL or absent
`contextFreshness` field.

## Implementation Boundary

not change:

- how EngineeringContext is constructed;
- how knowledge is selected;
- how insights or decisions are temporal-assessed;
- how maintenance findings are generated;
- how the MCP server exposes freshness;
- how the frontend displays context;
