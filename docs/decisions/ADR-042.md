# ADR-042 — Agent Job Orchestration

* **Status:** Accepted
* **Date:** 2026-07-23

## Context

Passive Project Monitoring introduces background work triggered by repository and project events.

Multiple specialized agents may eventually participate:

* repository ingestion;
* commit-history analysis;
* diff analysis;
* project-state reporting;
* architecture analysis;
* documentation generation;
* roadmap interpretation;
* Codeglyphe relevance analysis;
* notification generation.

Executing these processes directly inside event listeners or controllers would create tight coupling, poor retry behaviour and limited observability.

The Workspace therefore requires a durable orchestration model for asynchronous agent work.

## Decision

The Developer OS introduces an **Agent Job Orchestrator** based on durable `AgentJob` records.

Every passive or asynchronous agent execution is represented as an explicit job.

The orchestrator owns:

* job creation;
* scheduling;
* prioritization;
* capability resolution;
* context preparation;
* execution lifecycle;
* retries;
* deduplication;
* observability;
* traceability.

Agents execute bounded capabilities.

They do not control their own lifecycle.

## Agent Job Model

An `AgentJob` should retain information equivalent to:

* job identifier;
* project identifier;
* agent capability;
* trigger type;
* trigger reference;
* priority;
* requested context profile;
* Intent identifier and version when applicable;
* User Guidance snapshot when applicable;
* status;
* creation time;
* scheduled time;
* start time;
* completion time;
* attempt count;
* failure information;
* correlation identifier;
* causation identifier.

The exact implementation may evolve, but every job must remain traceable to its trigger and outputs.

## Job Status

Initial job states should include:

* `PENDING`;
* `RUNNING`;
* `COMPLETED`;
* `FAILED`;
* `CANCELLED`;
* `SKIPPED`.

Additional states may be introduced if required, but the lifecycle must remain explicit and deterministic.

## Job Sources

Jobs may originate from:

* domain events;
* repository synchronization;
* schedules;
* manual user actions;
* another completed job;
* Workspace orchestration;
* external integrations.

Manual and passive executions should use the same job infrastructure whenever they invoke the same capability.

## Capability-Based Execution

Jobs target a capability rather than a concrete implementation class.

Examples include:

* `IMPORT_REPOSITORY_HISTORY`;
* `ANALYSE_COMMIT_DIFFS`;
* `REFRESH_PROJECT_STATE`;
* `DETECT_ARCHITECTURE_CHANGE`;
* `PREPARE_DOCUMENTATION`;
* `GENERATE_NOTIFICATION`.

This keeps orchestration independent from agent implementations.

## Priority

Jobs support explicit priorities.

Typical categories include:

* critical operational work;
* user-requested active work;
* position or security alerts;
* normal passive analysis;
* low-priority maintenance.

User-requested work should generally take precedence over non-critical passive work.

Priority must not bypass business validation or trust boundaries.

## Deduplication

Equivalent jobs should not execute repeatedly without new evidence.

Deduplication may use:

* project;
* capability;
* trigger reference;
* context version;
* repository state hash;
* time window.

A duplicated job may be marked `SKIPPED` while retaining traceability.

## Retry Policy

Retries are owned by the orchestrator.

Retry behaviour should distinguish:

* transient infrastructure failures;
* external-provider failures;
* deterministic validation failures;
* permanent input errors;
* AI output-contract failures.

Retries must be bounded and observable.

A retry creates a new execution attempt but does not silently erase previous failure information.

## Context Preparation

The orchestrator requests context from the Repository Context Engine.

Agents must not independently scan the complete repository or bypass Context Intelligence.

The job retains references to:

* selected Context Profiles;
* evidence snapshot or version;
* Intent version;
* User Guidance snapshot.

This preserves reproducibility.

## Communication Strategy

Explicit user commands continue to use REST application services.

Passive workflows should progressively use domain events and durable jobs.

The preferred evolution is:

```text
Business transaction
        ↓
Transactional outbox
        ↓
Domain event
        ↓
AgentJob creation
        ↓
Agent execution
```

A message broker may be introduced later.

The domain model must not depend directly on a specific broker.

## Concurrency

The orchestrator must support:

* per-project concurrency limits;
* capability-specific concurrency limits;
* prevention of conflicting jobs;
* safe parallel execution of independent jobs.

Jobs modifying the same trusted aggregate must not be promoted concurrently without appropriate locking or transaction control.

## Observability

Every job should expose:

* current status;
* duration;
* attempt history;
* trigger;
* generated proposals;
* generated deliverables;
* failure reason;
* logs or trace correlation.

The Workspace may display simplified agent activity while preserving detailed operational information for diagnostics.

## Consequences

### Advantages

* durable background execution;
* centralized retry and scheduling;
* consistent active and passive workflows;
* better observability;
* controlled concurrency;
* easier future agent integration.

### Trade-offs

* additional persistence and orchestration complexity;
* lifecycle management;
* cleanup and retention requirements;
* eventual need for queue scaling.

These trade-offs are accepted because autonomous modules require explicit orchestration.

## Alternatives Considered

### Execute Agents Directly From Event Listeners

Rejected.

This would create fragile transactions, poor retries and limited traceability.

### Let Each Agent Manage Its Own Queue

Rejected.

Scheduling, retries and priorities must remain centralized.

### Introduce a Message Broker Immediately

Rejected for the initial implementation.

The architecture should first validate the durable `AgentJob` model and transactional outbox. A broker may be added when operational needs justify it.
