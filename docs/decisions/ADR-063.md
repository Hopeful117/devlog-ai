# ADR-063 — Engineering Context Retrieval and Composition Architecture

## Status

Accepted (proposed in `70e2ea3`; accepted after architectural review;
Human Context Supremacy amendment approved 2026-08-27)

## Date

2026-08-26

## Context

The investigation
`docs/investigations/context-composition-trusted-knowledge.md`
(re-verified at `main @ 04d0887`, after Story 0094) established how DevLog
currently supplies engineering context to its consumers. Its measured
findings:

- DevLog persists substantial engineering knowledge: 44,235 Facts (39,317 for
  devlog-ai), 345 Observations, 18 ACTIVE Insights, 21 Engineering Stories,
  1 Decision, 44 knowledge relations, full commit/changed-path history, and
  the Story 0093 freshness checkpoints.
- Five partially independent context mechanisms serve this knowledge:
  **A** RepositoryContextEngine / `get_engineering_context`; **B**
  KnowledgeSelectionService / SelectedKnowledge (Understanding + Engineering
  Event); **C** documentation generation (Insight rows only); **D**
  `search_project_history` (lexical commit/path recall); **E** MCP Resources.
  Beyond the underlying repositories they share no retrieval, reference,
  scoring or grounding primitives.
- System A's candidate pool is fixed (~238) and Git-dominated (~70 of 60-item
  budget); category starvation is measured, not anecdotal: 18 insight
  candidates → ≤1 selected; 21 story candidates → 0 selected in every run.
- Selection is effectively intent-insensitive: five materially different
  intents produced near-identical compositions.
- System A projects Facts/Observations as structurally empty
  (`RepositoryContextAdapter.synthesizeAnalysisContext` passes `List.of()`),
  drops `ingestedRevision` from its freshness block, and recomputes STALE,
  overriding the canonical PARTIALLY_FRESH classification.
- System B alone implements strict grounding: explicit allow-lists validated
  subset-style. Story 0094 proved the model can still fail when the *same*
  knowledge object is visible under two syntaxes — bare changed-file paths in
  `commitDiff.changedFiles[].newPath` versus citable prefixed references
  (`git:{sourceId}:{sha}:{path}`) — a visible-vs-citable mismatch, not model
  misuse.
- System C receives only human-promoted Insight prose; it cannot reach any
  repository-derived knowledge that was not first narrated into an Insight.
- System D provides genuine deterministic lexical recall (mechanism concepts:
  9–17 commit matches where context returned 0), but its results are orphaned
  from composition.
- Naïvely adding all persisted Facts to System A would grow the candidate pool
  from ~238 to ~40,000 — total starvation under any realistic budget.

Related accepted/proposed decisions frame parts of this space: ADR-041
(passive monitoring), ADR-055 (context enrichment/projection), ADR-059
(temporal knowledge, safe degradation), ADR-060 (deterministic core vs
probabilistic intelligence, governed effects), ADR-061 (observation baselines,
`(Source, immutable revision)` identity), ADR-062 (detect/synchronize/
understand lifecycle; freshness observability). What none of them defines is
**how retrieved engineering knowledge should be identified, trusted, composed,
projected and grounded across multiple consumers** — the layer those decisions
implicitly presuppose.

## Problem

Each DevLog consumer answers "what does this consumer know?" differently
because each owns a private pipeline from persistence to prompt. The result is
measured fragmentation: knowledge DevLog owns is invisible to consumers that
need it; budgets starve trusted categories; identical intents yield identical
context regardless of question; grounding works only where someone hand-built
it; and the future hybrid Retrieval Layer has no seam to plug into without
becoming yet another parallel mechanism.

The architectural question:

> How should DevLog architect engineering-context retrieval and composition so
> that multiple consumers can access relevant trusted knowledge through shared
> capabilities while retaining consumer-specific selection, budgeting,
> projection, and grounding semantics?

## Decision

### 1. Capability parity, not payload parity

Different consumers do not receive identical context payloads. The invariant
is: **whenever a consumer's task requires a category of engineering knowledge,
that consumer can obtain it** — directly in its initial context, or
deterministically through canonical references into retrieval/detail
capabilities. Payload equality is explicitly rejected: an MCP agent benefits
from bounded context plus expansion, documentation benefits from narrative
composition, and neither is served by one monolithic blob.

### 2. Five distinct responsibilities

"Context retrieval" is not one concern. The architecture separates:

```text
Retrieval    = find potentially relevant knowledge for a project, source,
               revision and intent. Returns candidates, never final answers.

Composition  = choose the bounded subset appropriate to ONE consumer
               (budgets, floors/ceilings, weights, required categories).

Projection   = represent the chosen subset in that consumer's contract
               (EngineeringEvidence, SelectedKnowledge JSON, deliverable
               input, …).

Grounding    = define what may be cited as supporting evidence, under which
               exact identifier, enforced by validation.

Expansion    = navigate from bounded initial context toward deeper knowledge
               through canonical references (resources, search, relations).
```

Retrieval and the metadata below are shared; composition, projection and
grounding-contract construction remain consumer-owned.

### 3. Canonical KnowledgeReference semantics

DevLog adopts a canonical reference semantic for engineering knowledge. Every
candidate surfaced by shared retrieval carries metadata sufficient for any
consumer to trust, filter, cite or expand it:

```text
KnowledgeReference (architectural semantic, not a mandated DTO)
- stable identity within (Project, Source?, revision scope);
- knowledge category (commit, changed-path, fact, observation, insight,
  story, decision, relation, document, structure item, …);
- provenance: originating source/persistence owner;
- revision provenance: resolved revision(s) the item represents;
- temporal metadata: event time, knowledge creation time, validation time
  where applicable;
- trust tier (see §4);
- citability: whether this reference is a valid grounding target;
- expansion target: detail view / search capability / related references.
```

Identity guarantees required: stable enough to cite and re-retrieve within a
revision scope; unambiguous across consumers (one knowledge object must not
present two competing citation syntaxes — the Story 0094 defect class).
Existing evidence IDs (`git:{sourceId}:{hash}`, `diff:{sha}:{path}`,
fact/observation UUIDs) and resource URIs are *representations* of
references, not replacements; convergence happens per projection, additively.
Not every visible context element requires a reference (untrusted blobs may
remain opaque), but **every citable element must carry exactly one canonical
reference**, and visible-but-non-citable elements must be deterministically
distinguishable from citable ones by the consumer contract.

### 4. Trust tiers survive retrieval

Shared retrieval must transport, never flatten, DevLog's existing governance
semantics (ADR-060 lineage):

```text
TRUSTED              human-promoted knowledge (Insights, accepted proposals)
HUMAN_AUTHORED       human context inputs; repository documents (ADRs,
                     stories markdown, roadmap)
TECHNICAL_EVIDENCE   commits, changed paths, Facts, Observations, structure,
                     profiles
SYSTEM_METADATA      freshness checkpoints, diagnostics
UNVALIDATED          pending ValidatableProposals — excluded from context
                     candidates entirely
TRANSIENT_AI         raw LLM interpretation outside persisted knowledge —
                     never a retrieval citizen
```

A vector or lexical hit never becomes TRUSTED by similarity; trust is a
property of origin, preserved end-to-end. AI-generated unvalidated proposals
never silently equal project knowledge.

HUMAN_AUTHORED describes provenance/origin only. It must not be read as
*currently authoritative*, *factually true*, *currently applicable*, *accepted
architecture*, or *non-superseded*: a SUPERSEDED ADR remains HUMAN_AUTHORED
while being inappropriate evidence for "what is the current architectural
decision?". The invariant is:

```text
trust/provenance tier != current authoritative status
HUMAN_AUTHORED        != automatically true
```

Where available, retrieval metadata must therefore preserve the additional
document attributes needed to interpret repository-authored artifacts —
document type, status, supersession/replacement relation, revision, temporal
provenance. This ADR does not define a document lifecycle model.

### 5. Shared retrieval primitives; consumer-owned composition

The following become **shared capabilities** (implemented once, consumed by
any engine):

- lexical historical recall (the capability behind
  `search_project_history`, reusable as a primitive — the MCP tool itself
  remains a thin contract over it);
- windowed/recency candidate polling over persisted collections;
- reference/trust/temporal metadata assembly;
- relation-based expansion lookups;
- grounding identity syntax and validation helpers.

The following remain **consumer-specific composition policy**:

- total budget; category floors and ceilings; ranking weights;
  intent-specific requirements; truncation strategy;
- prompt/output projection; citation allow-list construction.

This boundary is deliberate anti-god-service design: the shared layer returns
*annotated candidates*; it never decides what a consumer receives.

### 6. Intent feeds both stages, differently

Intent is a retrieval input (recall shaping: terms, temporal hints, scope) and
a composition input (which categories deserve budget for this task). It does
not mandate an LLM intent classifier; deterministic term extraction — already
present in the ranker, the structure collector and history search — is the
initial mechanism, now applied consistently instead of three different ways.

### 7. RepositoryContextEngine becomes a composition consumer

RepositoryContextEngine is **not** the universal engine and does not become
the shared retrieval layer. Its future responsibility: one composition policy
(MCP engineering-context briefing) consuming shared retrieval primitives —
gaining category-aware selection with availability-aware floors so trusted
knowledge can no longer be starved to zero — while remaining the owner of its
contract, budget and enrichment behavior. Its collector set becomes clients of
shared candidates rather than private pollers, incrementally.

### 8. Engineering Event keeps strict grounding; gains shared references

Engineering Event analysis keeps its own bounded composition policy and its
strict allow-list validation (Story 0094 semantics are preserved verbatim).
Its migration obligation is narrower: visible context and citable identifiers
must converge on canonical references (or be explicitly marked non-citable),
eliminating the dual-syntax ambiguity. No change to its comparison policy,
bounded selection, or validation strictness.

### 9. Documentation generation joins as a composition consumer

Documentation generation belongs to the target architecture as a consumer:
it may eventually compose from shared candidates (trusted insights plus
referenced technical evidence per its own policy). This ADR only fixes its
membership and direction; its narrow current path is acknowledged debt, not
mandated change.

### 10. Progressive expansion is adopted

Initial contexts stay bounded; canonical references plus expansion targets
(detail resources, targeted retrieval, relation lookups) let consumers go
deeper on demand. Invariant: **expansion must resolve through canonical
references to the same trust/revision metadata as initial context** —
expanded knowledge is never second-class. This is what makes capability
parity practical for MCP agents without inflating payloads.

### 11. Repository-authored documents are retrievable, not auto-trusted

ADRs, Engineering Story markdown, roadmap and other repository documents
become first-class retrieval candidates as HUMAN_AUTHORED items with
provenance (path, commit). They are never copied into trusted domain knowledge
as a side effect of retrieval; promotion remains governed by existing flows.

### 12. Relations are expansion metadata

Knowledge relations (44 persisted today) and implicit links (story↔commits,
proposal↔supporting evidence, fact↔analysis) participate as reference-level
expansion metadata. Graph traversal infrastructure is not required now;
consumers expand one hop at a time through canonical references.

### 13. Hybrid retrieval readiness without RAG

Future channels — structured/domain queries, lexical scoring, temporal
search, relation expansion, vector similarity — plug into the shared
retrieval-primitive seam as additional candidate producers emitting canonical
references with trust/tier metadata. Invariants: domain knowledge and trusted
projections remain authoritative; indexes are rebuildable technical
projections; similarity never elevates trust. No infrastructure choice is made
by this ADR.

### 14. ContextPack is deferred

No first-class ContextPack now. Trigger for revisiting: **two or more
consumers actually share composed-context structures** such that a common
representation removes duplication instead of forcing consumer-specific fields
into a bloated object. Until then each projection contract stands alone.

### 15. Rejected practices

The following are explicitly rejected as architecture, regardless of
implementation attractiveness:

- one giant context payload containing all project knowledge;
- loading all persisted Facts/Observations into every request;
- identical payloads for every consumer;
- RepositoryContextEngine (or any layer) owning composition for all consumers;
- weakening grounding validators to tolerate ambiguous reference syntaxes;
- treating everything visible to a model as automatically citable;
- introducing vector/RAG infrastructure before retrieval semantics stabilize;
- premature first-class ContextPack;
- big-bang migration of all consumers.

### 16. Validation against representative questions

For each class, how the target architecture lets a consumer obtain evidence
without loading the whole knowledge base:

```text
Historical    "When was RepositoryContextEngine introduced?"
              → lexical retrieval primitive recalls the introduction commits
                (today: history search finds 9); context cites them as
                references with commit-time provenance.

Architectural "Why separate deterministic services from AI proposals?"
              → trusted insights + HUMAN_AUTHORED ADR candidates compose into
                MCP context; expansion follows ADR references to documents.

Recent        "What changed recently in repository synchronization?"
evolution     → recency-shaped retrieval over commit/path candidates with
                revision provenance per item (0093 checkpoints).

Implementation "How does DevLog persist repository knowledge?"
              → bounded fact/observation candidates + changed-path candidates
                carry canonical references; expansion opens commit-context
                detail.

Decision      "Which ADR governs proposal validation?"
              → document-category candidates surface candidateAdrReferences;
                expansion resolves the ADR document by reference.
```

## Consequences

### Positive

- One place implements recall, reference identity, trust/temporal metadata
  and grounding syntax; consumers stop drifting apart.
- Trusted knowledge can no longer be starved invisibly — floors make
  omissions explicit and measurable.
- Grounding ambiguity (visible-vs-citable) gets an architectural fix rather
  than per-prompt patches.
- MCP agents gain honest progressive depth via expansion instead of payload
  bloat.
- The future hybrid Retrieval Layer plugs into a defined seam without
  becoming authoritative.
- Composition policies become independently testable against annotated
  candidates.

### Negative

- A new abstraction (references/metadata) must be designed and versioned;
  poorly scoped, it could ossify wrong boundaries.
- Transitional period with old per-collector polling coexisting alongside
  shared primitives in System A.
- Every candidate grows slightly (metadata), costing bytes and discipline.
- Consumers must now declare composition policies explicitly — more upfront
  decisions, less accidental behavior.
- Risk of over-generalization if reference categories multiply speculatively.

### Accepted trade-offs

- Payload parity is sacrificed deliberately.
- Some duplication between projections persists by design (contracts differ).
- Facts/Observations enter System A only through bounded retrieval and/or
  bounded projection of relevant items; raw inclusion is rejected regardless
  of future budgets. "Bounded" constrains *what reaches the candidate pool*,
  not the mechanism: deterministic pre-filtering, structured aggregation,
  grouped projections, bounded representative selection or another
  evidence-supported approach are all admissible. LLM summarization is not
  required by this ADR.

## Alternatives Considered

### Option A — Independent consumer fixes

Each consumer evolves alone. Rejected: it institutionalizes the measured
fragmentation (five systems today), repeats the same retrieval logic with
drift, leaves grounding inconsistent, and offers no RAG seam — the next
retrieval mechanism would become a sixth system.

### Option B — RepositoryContextEngine as universal engine

One engine composes for everyone. Rejected: Engineering Event needs closure-
based bounded grounding, documentation needs narrative composition, MCP needs
expansion-friendly briefing — one policy cannot serve all three without
becoming configurable to the point of opacity; concentrates budget/scoring
ownership in a single choke point; god-service risk explicit and high.

### Option C — Shared retrieval primitives + consumer-specific composition

**Adopted.** Shared: discovery, canonical references, trust/provenance/
temporal metadata, expansion. Consumer-owned: composition, budgets, weights,
projection, grounding-contract construction. Best correctness/coupling/
flexibility balance; incremental adoption; direct RAG compatibility.

### Option D — Central retrieval AND composition platform

Centralizes composition too. Rejected: same choke-point concerns as B with
higher migration cost; composition policy is precisely where consumers
legitimately differ.

### Option E — Do nothing; patch symptoms

Rejected: Story-0094-class mismatches and starvation regressions recur per
consumer; evidence already shows five systems diverging.

## Relations

- Extends ADR-062's detect/synchronize/understand lifecycle with the read-side
  consumption architecture.
- Realizes the projection concerns sketched in ADR-055 under concrete
  retrieval/composition boundaries.
- Preserves ADR-060 authority split and ADR-061 baseline identity inside
  reference metadata.
- Depends on Story 0093 checkpoint semantics for revision provenance; on
  Story 0094 grounding semantics for citability rules.
- Leaves ADR-041 monitoring, Maintenance (ADR-053/054), and all MCP tool
  contracts unchanged.

## Implementation Notes

First implementation step (single Engineering Story, derived from the
investigation): **"Project trusted knowledge into engineering context with
category-aware composition"** — RepositoryContextEngine registers ACTIVE
insights, engineering stories and bounded fact/observation candidates as
first-class candidates carrying reference/trust/temporal metadata, adds
availability-aware per-category floors alongside the global budget, and maps
canonical reference fields through the MCP contract additively. Measurable
before/after: knowledge-layer items selected from ≤1/0 to floor-satisfying
minimums without reducing git coverage below usefulness. Later steps, in
evidence-derived order: align freshness projection (ingestedRevision, stop
STALE override) · progressive-expansion links · Engineering Event canonical
reference convergence · documentation composition adoption · hybrid retrieval
channels.

Explicitly NOT decided here: vector/embedding technology; ContextPack schema;
concrete budget/floor numbers; final scoring formulas; consumer migration
dates; UI concerns; agent orchestration.

## Amendment - Human Context Supremacy (2026-08-27)

### Amendment Status and Basis

This amendment is **Accepted** following human architecture review of the P0
investigation
`docs/investigations/human-engineering-context-supremacy.md`, which reached
`READY_FOR_ARCHITECTURE_DECISION` at `main @ 10e0e45`.

It strengthens and clarifies this ADR. It does not replace the original
decision, change the adopted Option C boundary, or create a competing retrieval
architecture. Where this dated amendment clarifies broader prospective wording
in the original text, the amendment controls interpretation while preserving
the original decision history.

The investigation established that:

- the human Analysis AI is not limited to Validated Knowledge;
- `AnalysisWorkflowServiceImpl` and `KnowledgeSelectionService` already build
  rich `SelectedKnowledge`, including Facts, Observations, Insights,
  Engineering Events, human context, evolution context and bounded
  `RepositoryContext` evidence;
- that selected context is primarily an AI input and persisted `AiTask`
  snapshot, not a human evidence-exploration capability;
- Deliverable generation intentionally receives a narrower Insight-only
  projection;
- MCP provides a richer supported discovery and navigation path through
  `EngineeringContextFacadeImpl`, `RepositoryContextAdapter`,
  `EngineeringContextContractMapper`, history search and resources;
- `RepositoryContextEngine` is reused and transport-neutral internally, but it
  is a bounded composer rather than the canonical retrieval universe;
- Story 0095 delivered the intended first bounded composition slice while
  shared retrieval, canonical expansion, human exploration, document bodies,
  freshness alignment and authorization remain incomplete;
- current authorization is a systemic limitation, not an intentional
  human-versus-agent scope difference.

### 17. Human Context Supremacy is a governance invariant

DevLog adopts **Human Context Supremacy**:

> Within the same authorization scope, every canonical engineering-evidence
> category available to an AI agent must be retrievable and inspectable by the
> human engineer supervising it.

This is capability supremacy, not payload equality. Human and agent payloads,
ranking, initial selection and budgets may differ. Those differences must not
create a richer authorized evidence universe for the agent.

For equivalent project, source, revision, authorization scope and engineering
query:

```text
agent automatically selected evidence
    subset of
human explorable authorized evidence universe
```

This subset relationship concerns evidence accessibility, not authorization.
The human has no implicit permission to cross the authorization boundary, and
the agent has no implicit transport-derived permission to do so.

The original capability-parity rule in section 1 remains the minimum shared
capability. Human Context Supremacy strengthens it by requiring the human to
explore authorized evidence that automatic machine composition excluded due to
ranking or model-context limits.

### 18. Retrieval, composition and presentation remain separate

The responsibilities in section 2 are clarified for human and agent
consumers:

```text
Authorization scope
        |
        v
Retrieval
  What authorized evidence can be found and inspected for this
  project, source, revision and query?
        |
        v
Composition
  Which ordered or bounded subset should this consumer receive
  automatically?
        |
        v
Presentation / projection
  How does this consumer inspect, navigate, cite, select or use it?
```

Retrieval defines the accessible evidence universe and shared evidence
semantics. Composition remains consumer-owned. Presentation and projection
remain consumer-owned.

Shared retrieval does not require a shared payload, shared ranking order,
shared context budget or shared user interface. Consumer-owned composition does
not permit a consumer to redefine evidence identity, authorization, provenance
or freshness semantics privately.

### 19. Shared authorized engineering-evidence retrieval

The target architecture is:

```text
Authorized project / source / revision / query
                        |
                        v
       Shared Engineering Evidence Retrieval
       canonical identity, trust, provenance,
       temporal metadata, freshness, expansion
                        |
                +-------+-------+
                |               |
                v               v
       Agent composition    Human exploration
       rank / floor /       search / filter /
       finite budget        page / inspect /
                |           expand / select
                v               v
       EngineeringContext   Human evidence
       MCP projection       presentation
                |               |
                v               v
             AI agent       Human engineer
```

The shared capability is owned by the backend application/retrieval boundary.
No new microservice is introduced or implied.

Consumer-neutral retrieval capabilities must incrementally cover:

- authorization-scoped candidate retrieval;
- project, source and revision identity;
- canonical evidence references;
- evidence-type-appropriate trust and citability metadata;
- provenance and temporal metadata;
- compatible freshness semantics;
- category and temporal filtering;
- pagination and bounded polling;
- deterministic search and recall;
- progressive reference expansion;
- related-evidence navigation.

This is an architectural capability set, not a prescribed class, service name
or universal evidence-body DTO. Facts, Observations, Insights, Decisions,
Engineering Events, repository history, source code, repository documents and
other evidence retain their authoritative domain models.

### 20. Authorization precedes retrieval

The mandatory ordering is:

```text
Authorization scope
        -> evidence retrieval
        -> consumer composition
        -> consumer projection
```

Transport does not determine authorization scope. MCP must not receive broader
evidence access because it is MCP; the human application must not receive
broader access because it is interactive.

The repository does not yet implement a complete application-user
authorization model. This amendment does not invent one. It establishes the
constraint that future authorization is enforced at or before the shared
retrieval boundary and is reused by human routes, MCP routes, history search
and direct reference expansion.

Future security tests must prove that no consumer or expansion path can escape
the authorized project/source scope.

### 21. Canonical references unite identity, not evidence bodies

Section 3 remains authoritative. Human and agent projections must ultimately
refer to the same underlying canonical evidence identity where applicable.

A canonical reference must be sufficient to:

- scope evidence to its project and, where applicable, source and revision;
- retrieve or expand the evidence deterministically;
- link related evidence;
- audit which evidence informed a composition, investigation or proposal;
- preserve compatible trust, provenance and revision semantics across
  projections.

Canonical identity does not require all evidence bodies to be normalized into
one object. Expansion resolves the authoritative or observed source according
to evidence type.

The exact reference representation remains an implementation design question.
Existing Git, diff, Fact, Observation, Insight, Decision, Story and MCP resource
identifiers are migration inputs, not automatically the final universal
syntax.

### 22. RepositoryContextEngine remains a bounded composer

Section 7 is reaffirmed and strengthened:

- `RepositoryContextEngine` remains a bounded engineering-context composer;
- it may consume candidates from shared retrieval capabilities;
- it continues to own planning, ranking, diversity, category floors, context
  budgeting, bounded selection and composition-specific enrichment;
- its finite selected set is not the canonical universe of retrievable
  evidence;
- it must not become the universal retrieval platform;
- human exploration must not be implemented by wrapping it with a larger
  budget.

For example, 253 authorized candidates may still be composed into 60 items for
an agent. Human Context Supremacy does not increase the agent payload to 253.
It requires the human capability to search, filter, page and expand the
authorized candidates beyond that selected 60 when needed.

### 23. Agent composition remains bounded

Agent consumers continue to own deterministic composition policy, including:

- relevance and recency ranking;
- category floors and ceilings;
- diversity rules;
- finite item and token budgets;
- bounded enrichment and truncation;
- projection and grounding allow-lists.

Automatic exclusion due to an agent budget is not evidence deletion and does
not remove the item from the human explorable universe.

### 24. The human workflow is a first-class context consumer

The human engineering workflow is now an explicit first-class consumer of
engineering context. It consumes backend application capabilities directly,
not MCP.

Its presentation may provide a bounded or ranked initial page for performance
and usability, but that initial page does not define the evidence universe. The
human capability must be able, subject to authorization and actual source
availability, to:

- browse and search;
- filter by category and relevant temporal/revision dimensions;
- paginate beyond the initial ranked view;
- inspect evidence provenance and freshness;
- expand canonical references to deeper source material;
- navigate related evidence;
- inspect evidence excluded from an automatic composition when diagnosable;
- compare relevant revisions;
- eventually select and attach/reference evidence in an auditable human
  investigation.

This amendment decides the capability direction, not Angular screen design or
the persistence model for human evidence attachment.

### 25. MCP remains a transport and consumer boundary

MCP does not become the shared retrieval architecture. The required direction
is:

```text
shared retrieval
    -> agent composition
    -> EngineeringContext projection
    -> MCP
```

The following is rejected:

```text
human application -> MCP -> EngineeringContext
```

MCP tools and resources project backend capabilities for agents. The human
application uses the underlying backend application capabilities through its
own projection.

### 26. Provenance and freshness use compatible semantics

Every evidence type exposes the provenance needed to answer, as applicable,
"Why does DevLog know this?". Relevant provenance may include project,
repository source, revision, commit, file, domain object, Analysis, extraction
origin and related evidence. The architecture does not invent fields that are
meaningless for a particular evidence type.

Human and agent projections need not serialize identical provenance or
freshness payloads, but they must preserve compatible semantics for the same
canonical evidence.

Relevant freshness semantics include, where applicable:

- observed/current repository revision;
- deterministically ingested revision;
- Understanding/baseline revision;
- the evidence's own revision and temporal identity.

A human must be able to determine whether evidence supporting an engineering
decision may be stale. This amendment does not resolve the existing
EngineeringContext freshness projection debt; it makes semantic compatibility
and human inspectability mandatory outcomes.

### 27. Progressive expansion supports both consumers

Section 10 remains adopted and is strengthened. Initial retrieval and
composition may return summaries and canonical references. Expansion then
supports:

```text
summary
    -> authoritative or observed source
    -> related evidence
    -> deeper source
```

Expansion must preserve the reference's project/source authorization, evidence
identity, trust, provenance and revision semantics. A resource or human detail
view is a projection of the same expansion capability, not an independent
retrieval implementation.

Progressive expansion avoids both a giant initial payload and a model-budget
ceiling on human investigation.

### 28. Repository documents remain required retrieval work

Section 11 remains the target: ADR markdown, Engineering Story artifacts,
roadmap markdown and other repository documents become retrievable
`HUMAN_AUTHORED` evidence with path, revision/commit and relevant document
status metadata.

The current system does not yet retrieve these document bodies as complete
first-class evidence. Persisted Decision or Engineering Story registry rows do
not substitute for repository document bodies.

`HUMAN_AUTHORED` remains provenance, not automatic truth or current authority.
Document type, status, revision, supersession/replacement and temporal
provenance determine interpretation. This amendment does not define the
repository-document lifecycle or implement retrieval.

### 29. Trust and proposal governance remain evidence-type-specific

Shared retrieval must preserve the distinctions in section 4 among:

- deterministic Facts;
- Observations;
- human-promoted Insights;
- Decisions and Engineering Events;
- repository commits and changed paths;
- source code and technical structure;
- human-authored repository documents;
- unvalidated AI proposals.

Human Context Supremacy is fully compatible with ADR-006. Retrieved evidence is
not an AI proposal. AI synthesis remains an untrusted `ValidatableProposal`;
human acceptance authorizes the Core's atomic promotion workflow. The resulting
Insight, Decision, Engineering Event or other promoted domain object is trusted
knowledge. The accepted proposal remains immutable proposal/validation history
and does not itself become trusted domain knowledge. This explicitly corrects
the shorthand "accepted proposals" in section 4 without changing ADR-006. The
AI cannot promote its own interpretation into trusted knowledge.

The amendment strengthens ADR-006 in practice by giving the validating human a
supported path to independently inspect underlying evidence.

### 30. Narrow downstream projections remain legitimate

Human Context Supremacy governs the human's ability to retrieve and inspect
authorized evidence. It does not require every downstream synthesis consumer
to receive the entire evidence universe.

Deliverable generation may continue to use its intentionally narrow
Validated-Insight projection. If that policy changes later, Deliverables remain
a separate composition consumer under section 9. A narrow Deliverable payload
does not violate this amendment while the supervising human can independently
retrieve and inspect the relevant evidence.

### 31. Human evidence attachment is recognized but not designed

An auditable human investigation may eventually select and attach evidence.
This is a human-consumer capability over canonical references, not a reason to
duplicate retrieval.

This amendment does not decide whether persistence uses canonical references
only, reference plus revision/digest, immutable snapshots or a hybrid. Any
future design must preserve evidence identity, revision and provenance and must
distinguish an investigation-time snapshot from current retrieval.

### 32. Capability and supremacy contracts

Future conformance must establish:

```text
Given
  the same authenticated principal,
  project,
  source,
  revision,
  authorization scope,
  and equivalent engineering query,

When
  an agent composition returns evidence category K
  with canonical reference R,

Then
  the human engineering-context capability can retrieve or expand K/R,

And
  both projections preserve compatible trust, provenance and revision
  semantics,

Even if
  ranking order, initial selection, presentation and budgets differ.
```

The stronger supremacy condition is:

```text
Evidence excluded from the agent's automatic selection solely by composition
policy or context budget remains manually searchable/retrievable by the human
when it is within the same authorized evidence universe.
```

Tests must target capability reachability and compatible semantics, not
byte-identical payloads.

### 33. Performance and observability constraints

Human Context Supremacy does not mean loading all project evidence at once.
Human presentation must support bounded initial views, pagination, filtering
and lazy/progressive expansion. Retrieval implementations must remain bounded
at expensive source boundaries and avoid N+1 expansion behavior.

Retrieval must eventually be diagnosable across consumers using concepts
such as consumer, project/source/revision, retrieval channels, candidate and
category counts, exclusion/truncation, freshness, duration and expansion
failure. The ADR does not prescribe telemetry technology. Sensitive evidence
bodies and credentials must not be logged.

### 34. Future hybrid retrieval remains deferred

Section 13 remains unchanged in direction. Structured and lexical retrieval
stabilize before vector infrastructure. A future vector channel may produce
candidates through the same governed retrieval seam only when it preserves
canonical identity, project/source/revision scope, trust and provenance.

A vector index remains a rebuildable projection and never becomes the source
of truth. This amendment introduces no RAG or vector technology.

### 35. No universal ContextPack

Section 14 remains unchanged. Human Context Supremacy concerns shared evidence
capabilities, not one giant DTO. `AnalysisContext`, `SelectedKnowledge`,
`RepositoryContext`, `EngineeringContext` and `ProjectContext` retain their
distinct semantics.

No universal `ContextPack` is introduced by this amendment.

### 36. Story 0095 remains a successful incremental slice

Story 0095, documented in
`docs/stories/0095-trusted-knowledge-category-composition/story.md` and its
`engineering-report.md`, successfully implemented its intended bounded
composition increment:

- intent-relevant bounded Fact/Observation polling before the candidate pool;
- availability-aware aggregate knowledge-kind floors;
- continued enforcement of relevance, item and token budgets;
- richer category representation while keeping Git evidence useful.

It did not claim or complete shared candidate retrieval, final canonical
references, generic expansion, human evidence exploration, repository document
bodies, complete freshness alignment or an authorization boundary. Those are
later ADR-063 implementation responsibilities, not Story 0095 failures.

For clarity, Story 0095 implemented one availability-aware aggregate floor over
eligible knowledge kinds, not an independent guaranteed floor for every kind.
Individual categories may still be absent from a bounded composition. The
prospective "per-category floors" and "cannot be starved to zero" wording in
sections 7, Consequences and Implementation Notes is therefore interpreted as
the broader ADR-063 direction toward explicit category-aware composition, not
as a claim that Story 0095 guaranteed every individual category. Human Context
Supremacy does not require every category in an agent's initial bounded set; it
requires those authorized categories to remain human-retrievable.

### 37. Paper Account acceptance benchmark

The Trading OS Paper Account investigation is retained as a concrete future
acceptance benchmark. Once the relevant retrieval and human-consumer slices are
implemented, a human engineer must be able to discover and inspect authorized
evidence concerning:

- `TradingAccount`;
- `BrokerAccount`;
- `AccountRiskConfiguration`;
- Risk Engine inputs;
- `ExecutionIntent`;
- `ExecutionPipeline`;
- `BrokerSubmissionStep`;
- Story 0030;
- relevant commits and changed files;
- relevant Decisions and ADRs;
- relevant source and symbol evidence.

The human must also be able to inspect Facts/Observations describing relevant
relationships, compare evidence against observed, ingested and Understanding
baseline revisions, distinguish source evidence from AI synthesis, and select
or attach/reference the evidence needed for an auditable investigation. Any AI
interpretation remains governed by ADR-006 validation.

The benchmark requires human inspectability of underlying evidence, not
loading every artifact into one LLM prompt.

### 38. Amendment consequences

#### Positive

- Humans can independently inspect and verify evidence used by agents.
- One authorized retrieval universe reduces human/agent evidence divergence.
- Canonical identity and expansion improve investigation and validation
  auditability.
- Consumer-specific machine and human experiences remain possible.
- Authorization, provenance and freshness gain one architectural enforcement
  seam.
- The future hybrid-retrieval seam serves both humans and agents without
  becoming authoritative.
- Agent contexts remain bounded without imposing model-token limits on human
  exploration.

#### Negative and costs

- Existing private collectors and search/detail paths require incremental
  convergence around shared retrieval capabilities.
- Canonical evidence identity and reference migration require design and
  contract testing.
- A complete principal/project authorization model must eventually be
  introduced at the shared boundary.
- Progressive expansion and related-evidence navigation add application
  complexity.
- Repository documents require lifecycle/status/supersession semantics before
  they can reliably answer current-authority questions.
- Capability-supremacy, security, freshness and projection tests add ongoing
  maintenance cost.
- Transitional duplication remains until consumers migrate incrementally.

### 39. Rejected amendment alternatives

#### A. Permanently expose the existing EngineeringContext facade to humans

Rejected as the target architecture. It exposes only a model-bounded selected
set, carries MCP-oriented resource semantics, and has incomplete expansion. It
may inform an incremental projection slice but cannot define the human evidence
universe.

#### B. Create a separate human retrieval path around RepositoryContextEngine

Rejected. It would create divergent retrieval, ranking, freshness,
authorization and reference semantics, and would misuse a bounded composer as
the retrieval universe.

#### C. Make Angular call MCP

Rejected. MCP is an agent transport/consumer boundary. The human application
must consume backend application capabilities directly.

#### D. Increase RepositoryContextEngine's budget for humans

Rejected. A larger composition budget is still a composition boundary, not a
retrieval and exploration capability. It also risks performance problems
without establishing search, pagination or canonical expansion.

#### E. Add RAG/vector search now

Rejected. Vector search does not establish canonical identity, authority,
freshness, authorization, expansion or human/agent capability governance. It
would risk becoming another retrieval system before the shared seam is stable.

#### F. Introduce a universal ContextPack or new context microservice

Rejected. Existing context objects have distinct semantics, and no new
deployment boundary is justified by the evidence.

### 40. Open questions preserved by this amendment

- What principal/project authorization model will scope shared retrieval?
- Should the first human slice expose the agent EngineeringContext selection,
  the Analysis `SelectedKnowledge` snapshot, or both as separately labelled
  evidence views?
- What concrete canonical reference representation best supports additive
  migration from current identifiers?
- What lifecycle and status model governs repository documents?
- How can pinned-revision file expansion avoid hidden read-side
  synchronization and preserve multi-source identity?
- Should human evidence attachment store a canonical reference, a reference
  plus revision/digest, an immutable snapshot or a hybrid?
- How should multi-source commit and file identity be represented where current
  resource URIs omit source identity?
- Which ranking exclusion diagnostics are safe and useful to expose to humans?

### 41. Amendment relations and implementation boundary

This amendment:

- is derived from
  `docs/investigations/human-engineering-context-supremacy.md`;
- extends section 1 capability parity with Human Context Supremacy;
- reinforces sections 2, 3, 5, 7, 10, 11, 13 and 14;
- preserves ADR-006 proposal validation and promotion boundaries;
- preserves Story 0095 as the first successful bounded-composition increment;
- requires future human and MCP capability/security conformance tests;
- creates no Engineering Story and chooses no first implementation slice;
- changes no production code, endpoint, service, DTO, retrieval algorithm,
  security mechanism or user interface.

Implementation planning begins only after human review of this amendment.
