# ADR-055 — Engineering Context Enrichment and Projection

## Status

Proposed

## Date

2026-08-16

## Context

DevLog has progressively established the foundations required to maintain reliable
project knowledge.

The context-stabilization phase introduced or strengthened:

* trusted project Knowledge;
* duplicate prevention and remediation;
* Knowledge lifecycle management;
* deterministic context-maintenance analysis;
* grounding consistency and reference validation;
* provenance;
* semantic similarity awareness during Knowledge promotion;
* explicit separation between deterministic facts and AI interpretation.

These capabilities make project memory increasingly reliable.

However, reliable project memory is not sufficient for DevLog's long-term role.

Engineering consumers such as Kiko currently need context that may span:

* trusted Knowledge;
* ADRs;
* Engineering Stories;
* repository structure and code;
* Git history and commits;
* milestones and project state;
* risks and constraints;
* transversal engineering knowledge stored outside DevLog.

A consumer should not need to independently query each source, reconstruct their
relationships, determine relevance, and assemble its own engineering context.

This responsibility belongs naturally to DevLog because DevLog already owns the
understanding and maintenance of project memory.

The next architectural challenge is therefore no longer primarily:

> How does DevLog maintain reliable project memory?

It becomes:

> How does DevLog transform reliable engineering memory into relevant,
> structured and task-specific context?

This requires two complementary capabilities:

1. **semantic enrichment** — increase the meaning, relationships and engineering
   usefulness represented by project memory;
2. **context projection** — select and organize the smallest reliable context
   useful for a specific consumer and engineering intent.

This ADR defines the transition from context stabilization toward these
capabilities.

## Decision

DevLog evolves toward an **Engineering Context Engine**.

It remains responsible for building and maintaining reliable project memory, but
also becomes responsible for enriching, selecting and projecting engineering
context for consumers.

### 1. Reliable Project Memory Remains the Foundation

Context projection does not replace the existing Knowledge model.

Trusted project memory remains the authoritative foundation from which richer
context is constructed.

The existing guarantees around:

* provenance;
* Knowledge lifecycle;
* grounding;
* duplicate prevention;
* deterministic validation;
* human validation where required;

remain applicable.

Semantic enrichment must build on these guarantees rather than bypass them.

### 2. DevLog Introduces Semantic Context Enrichment

DevLog should progressively represent relationships between engineering elements
rather than treating them only as isolated records.

Relevant relationships may include:

* Knowledge ↔ Knowledge;
* Knowledge ↔ ADR;
* Knowledge ↔ Engineering Story;
* Engineering Story ↔ commit;
* decision ↔ implementation history;
* Knowledge ↔ code component;
* requirement ↔ architectural decision;
* risk or constraint ↔ affected project area;
* project context ↔ transversal engineering knowledge.

The objective is not to maximize the number of relationships or stored records.

The objective is to increase the **semantic density and engineering usefulness**
of project memory.

Each enrichment must therefore justify how it improves project understanding or
context projection.

### 3. Context Is Requested Through Consumer Intent

Consumers should not orchestrate DevLog's internal knowledge sources directly.

They express their need through a context request describing the engineering
intent.

Conceptually:

    ContextRequest
          ↓
       DevLog
          ↓
    ContextPackage

The request describes what the consumer is trying to accomplish.

DevLog determines which available engineering information is relevant to that
intent.

The consumer should not need to know where each piece of information is stored.

### 4. DevLog Owns Context Composition

DevLog is responsible for composing project context from relevant engineering
sources.

Conceptually:

    Project Knowledge
          +
         ADRs
          +
    Engineering Stories
          +
      Git History
          +
      Code Context
          +
    Project State
          +
    Relevant Transversal Knowledge
          ↓
    Context Selection
          ↓
    Context Projection
          ↓
      ContextPackage

Consumers receive the resulting projection rather than independently assembling
these sources.

Source abstraction must not remove source provenance.

### 5. Context Projection Must Be Bounded and Task-Specific

More context is not automatically better context.

A projected context must be:

* project-scoped;
* relevant to the requested intent;
* structured;
* provenance-preserving;
* grounding-consistent;
* bounded by an explicit context budget;
* directly exploitable by its consumer.

DevLog should prefer the **smallest reliable context sufficient for the task**.

Context projection must therefore optimize relevance and usefulness rather than
raw context volume.

### 6. Kiko Is the First Reference Consumer

Kiko will be the first consumer used to validate the context-projection model.

Kiko's responsibility is to prepare high-quality Engineering Stories.

Kiko should provide DevLog with the engineering intent and relevant request
constraints.

DevLog should return the project context required to prepare that story.

The target responsibility boundary is:

    Kiko
      ↓
    ContextRequest
      ↓
    DevLog
      ↓
    ContextPackage
      ↓
    Kiko reasoning

Kiko should not need to independently retrieve project memory and transversal
engineering knowledge.

This integration provides a concrete way to evaluate whether semantic enrichment
actually improves an engineering workflow.

### 7. Transversal Knowledge Remains Independently Owned

DevLog does not replace the transversal Knowledge Vault.

The Vault remains an independent source of shared engineering knowledge such as:

* Engineering Philosophy;
* Quality standards;
* Workflow practices;
* AI Engineering;
* Knowledge Engineering.

The responsibility boundary is:

    Project Memory
        → owned by DevLog

    Transversal Memory
        → owned by the Vault

    Context composition
        → owned by DevLog

DevLog may retrieve relevant transversal knowledge and include it in a
ContextPackage when applicable.

Its external origin and provenance must remain explicit.

### 8. Deterministic Context Construction Remains the Primary Path

The first implementation of context projection should maximize deterministic
mechanisms.

The deterministic Core remains responsible for:

* authoritative project facts;
* retrieval boundaries;
* source provenance;
* permissions;
* explicit relationships;
* context budgets;
* reference validity;
* grounding closure;
* final ContextPackage assembly.

Semantic enrichment does not imply that AI becomes responsible for constructing
engineering reality.

### 9. AI Interpretation Is Introduced Only Where It Adds Measurable Value

A future DevLog **Context Analyst** may assist where semantic interpretation is
required.

Potential responsibilities include:

* semantic relevance assessment;
* implicit relationship detection;
* engineering-significance detection;
* historical interpretation;
* missing-Knowledge detection;
* project-to-transversal-Knowledge relevance;
* consumer-specific selection recommendations.

The Context Analyst operates on a bounded candidate context established by
DevLog.

Its output is structured interpretation or selection proposals.

It does not directly create authoritative project facts or construct the final
ContextPackage without deterministic validation.

The fundamental boundary remains:

> Known facts → deterministic systems  
> Interpretation and reasoning → AI

### 10. Context Projection Must Preserve Grounding Closure

Every reference exposed to a consumer must remain valid within the projected
context contract.

Context transformations must not expose references to facts or sources that the
consumer is not authorized to use.

If semantic selection removes a supporting element, dependent context must be
removed, transformed, or accompanied by the required support.

Grounding correctness is therefore an end-to-end property of context projection,
not only an output-validation concern.

### 11. Enrichment Is Driven by Real Consumer Needs

DevLog must not attempt to model every possible semantic relationship upfront.

New relationships and context capabilities should be introduced when they
improve a concrete projection or engineering workflow.

Kiko provides the first validation loop.

For each proposed enrichment, the guiding question is:

> What additional useful context does this allow DevLog to provide to Kiko?

If an enrichment has no demonstrated consumer value, it should remain outside the
initial scope.

### 12. Context Projection Becomes a Reusable DevLog Capability

Although Kiko is the first reference consumer, context projection must not become
Kiko-specific business logic.

The capability should eventually support different projections for:

* Engineering Story preparation;
* coding agents;
* code review agents;
* documentation agents;
* maintenance agents;
* human project understanding.

Consumers may require different projections of the same underlying engineering
memory.

The underlying facts and provenance remain consistent.

## Consequences

### Positive

* DevLog evolves from passive project memory toward an actionable engineering
  context capability;
* consumers receive context through a single boundary;
* Kiko no longer needs to orchestrate multiple memory systems;
* project history, architecture and trusted Knowledge can be projected together;
* transversal engineering principles can be applied to project-specific work;
* context quality becomes an explicit capability that can be tested;
* the same context infrastructure can support future engineering agents;
* semantic enrichment is tied to real workflow value rather than abstract
  knowledge modeling.

### Trade-offs

* DevLog gains responsibility beyond project-memory persistence;
* ContextRequest and ContextPackage become important public contracts;
* semantic relationships require explicit modeling and lifecycle rules;
* different consumers may eventually require different projection strategies;
* integration with external knowledge introduces freshness and provenance
  concerns;
* context-quality evaluation becomes a new engineering problem.

### Risks

* semantic enrichment could grow into an unnecessarily complex knowledge graph;
* projection logic could become consumer-specific if boundaries are not
  preserved;
* excessive context could reduce rather than improve agent performance;
* AI-assisted relevance could introduce unsupported relationships or references;
* external transversal knowledge could accidentally become indistinguishable
  from authoritative project facts;
* DevLog could gradually become responsible for reasoning that belongs to
  consumer agents rather than context construction.

## Alternatives Considered

### Keep DevLog as Project Memory Only

Rejected.

This would require each consumer to independently retrieve and compose project
context.

Kiko and future agents would duplicate context-selection logic and would need to
understand DevLog's internal knowledge topology.

### Let Kiko Compose Project and Transversal Context

Rejected as the long-term architecture.

This works during the current development phase but assigns memory retrieval and
context composition to an agent whose primary responsibility is Engineering Story
preparation.

Context composition is reusable infrastructure and belongs closer to the memory
system.

### Move Transversal Knowledge Into DevLog

Rejected.

The Vault and project memory serve different purposes and ownership models.

DevLog should consume transversal knowledge when relevant without becoming its
source of truth.

### Use an AI Agent to Build Context Directly

Rejected as the primary architecture.

An AI agent should not independently retrieve arbitrary sources and construct the
authoritative context presented to downstream consumers.

Deterministic retrieval, grounding, provenance and final assembly remain required.

### Build a Complete Engineering Knowledge Graph Before Projection

Rejected.

This would introduce speculative modeling without evidence that every
relationship improves real engineering workflows.

Semantic enrichment should evolve incrementally from actual projection needs.

## Explicit Non-Goals

This ADR does not define:

* replacement of the Obsidian Vault;
* migration of transversal knowledge into DevLog;
* autonomous mutation of trusted project Knowledge by AI;
* a complete engineering ontology;
* a universal knowledge graph;
* autonomous project strategy or architectural decision-making;
* implementation details of the future Context Analyst;
* automatic writing to the transversal Vault;
* consumer-specific reasoning inside DevLog;
* removal of human validation requirements established by existing ADRs.

## Implementation Direction

The next implementation phase should focus on proving context enrichment and
projection through Kiko before expanding the model.

A suitable progression is:

1. formalize the minimal semantic information Kiko requires;
2. identify gaps between current DevLog context and that required information;
3. introduce the first high-value semantic relationships;
4. formalize `ContextRequest`;
5. formalize `ContextPackage`;
6. implement deterministic context projection for Kiko;
7. evaluate real Engineering Stories produced from projected context;
8. refine enrichment and selection based on observed gaps;
9. integrate relevant transversal Vault knowledge;
10. introduce the Context Analyst only where deterministic projection proves
    insufficient.

The implementation must remain incremental and consumer-driven.
