# ADR-047 — Proposal-Type-Aware Intents and Validated Engineering Events

## Status

Accepted

## Date

2026-08-09

## Context

Intent was introduced for Insight generation, while ADR-006 deliberately defines a generic
proposal-to-knowledge workflow. DevLog now needs its first historical interpretation: an Engineering
Event proposed from bounded Git evidence and promoted only after human validation. Encoding that
event as an Insight would erase the distinction between generic interpretations and project-history
knowledge. Reusing `KnowledgeEvent` would also violate ADR-016 because that object is a raw
occurrence below Facts and Observations.

## Decision

Intent declares one `outputProposalType` and an execution mode in addition to its existing versioned
schema, constraints, prompt template, and Context Profiles. Existing Intent versions output
`INSIGHT`. Dedicated Engineering Event execution outputs `ENGINEERING_EVENT`.

The trusted historical object is a new immutable `EngineeringEvent`. It is produced atomically from
one accepted Event proposal and retains Project, Analysis, Validation, Source, revision-boundary,
and evidence provenance. `KnowledgeEvent` remains the raw occurrence layer.

The initial Event boundary is one non-root commit against its first parent. Core resolves and stores
that boundary, builds deterministic evidence, validates provider output, owns proposal state and
promotion, and exposes validated Events. The AI Engine interprets only selected immutable context.

## Consequences

* Intent can govern multiple proposal families without weakening existing Insight contracts.
* Event, Insight, raw activity, Decision, and Challenge remain distinct.
* Unsupported accepted proposal types fail instead of silently producing no trusted knowledge.
* The first slice cannot group commits, analyze root commits, infer code semantics, or run passively.
