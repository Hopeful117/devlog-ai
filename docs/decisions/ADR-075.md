# ADR-075 - User AI Configuration and Runtime State Ownership

## Status

Proposed - requires human architecture approval.

## Date

2026-10-30

## Context

DevLog AI needs a product configuration model that can represent both OAuth
and API-key provider setup. The current AI Engine configuration is primarily
process-scoped, while Core already owns authenticated principals, projects,
tasks, associations and task-scoped credential bindings.

The product must separate user preferences from secret material, authorization
capabilities and temporary provider state.

## Problem

Without an explicit ownership boundary:

- a provider configuration may accidentally become a credential store;
- runtime failures may mutate user preferences silently;
- the frontend may be given authority to select credentials;
- project-level complexity may be introduced without a product need;
- Simple and Advanced flows may produce incompatible representations.

## Decision

Core owns the non-secret user AI configuration and its product-level state.
The initial preference scope is global per authenticated user. Project-level
overrides are not introduced in V1.

The configuration contains only non-secret choices and permitted parameters:

```text
ProviderConfiguration
  principalId
  provider
  authenticationMethod
  selectedModel
  modelSelectionOrigin
  allowedParameters
```

The configuration does not contain an API key, OAuth token, refresh token,
authorization code or provider secret.

The following concepts remain separate:

- Catalog metadata: what DevLog supports;
- Provider configuration: what the user selected;
- Credential: secret or authorization held by the AI Engine;
- Credential association: Core-owned relation to an opaque AI Engine handle;
- Credential binding: short-lived task authorization issued by Core;
- Runtime state: current provider, credential and model condition.

Simple and Advanced configuration must converge on the same
`ProviderConfiguration` model. The UI mode cannot change authorization
semantics.

## Runtime State

Runtime state is derived or synchronized from checks and does not silently
rewrite user preferences. It may include:

- `NOT_CONFIGURED`;
- `CONFIGURATION_INCOMPLETE`;
- `READY`;
- `REAUTH_REQUIRED`;
- `PROVIDER_UNAVAILABLE`;
- `MODEL_UNAVAILABLE`;
- `CREDENTIAL_INVALID`;
- `REVOKED`.

The exact public state names may follow existing API conventions, but the
semantics must remain explicit.

`READY` means that the selected provider, authentication method, credential
association, selected model and required compatibility checks are currently
usable. It is not a permanent guarantee and is not an authorization grant.

## Model Rules

An explicit model selection is persistent user intent. It must never be
replaced automatically.

If that model becomes unavailable:

1. the configuration leaves `READY`;
2. the runtime state reports model unavailability;
3. the catalog recommendation may be displayed;
4. the user must explicitly select and accept a replacement.

Changes to the catalog recommendation do not mutate existing configurations.

## Authorization Boundary

Core remains the sole authority for:

- principal and project authorization;
- credential association ownership;
- task/provider compatibility;
- task-scoped credential binding.

A frontend configuration request expresses user intent. It is not authorization
to use a credential. REST, MCP and background execution must use the same Core
decision.

## Invariants

1. Core persists preferences, never provider secrets.
2. AI Engine owns secret storage and provider secret resolution.
3. Preferences are global per user in V1.
4. No project override exists in V1.
5. A configuration never authorizes a task by itself.
6. A task requires a valid Core-issued `AiCredentialBinding` where applicable.
7. Simple and Advanced modes use the same internal configuration model.
8. Runtime state may become invalid without changing explicit user intent.
9. There is no automatic model fallback.

## Consequences

### Positive

- Secret and preference ownership are explicit.
- The frontend can remain a thin user-intent adapter.
- The model is simple enough for V1.
- Runtime failures do not destroy user choices.

### Costs and Risks

- Core must expose product-oriented configuration capabilities.
- Runtime state may require provider checks and synchronization.
- A future project override would require a new decision.

## Out Of Scope

- Project-level configuration overrides in V1.
- Multi-credential selection in V1.
- Automatic model or provider fallback.
- Secret storage in Core.

## Implementation Boundary

This ADR defines ownership and state semantics. It does not authorize
production implementation. The User AI Configuration and State Story is the
bounded implementation vehicle after approval.
