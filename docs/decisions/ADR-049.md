# ADR-049 — Semantic Preservation During Knowledge Promotion

## Status

Accepted

## Date

2026-08-12

## Context

DevLog AI maintains project knowledge through a controlled pipeline that separates AI-generated interpretation from trusted project knowledge.

The current lifecycle is broadly composed of two stages:

1. acquisition and proposal generation;
2. human validation and promotion into durable knowledge.

The acquisition stage can produce relatively rich structured information through `AiProposalResult` and `ValidatableProposal.payload`.

This information may include elements such as:

* semantic type;
* rationale;
* confidence;
* evidence;
* source context;
* interpretation of repository changes.

After human validation, accepted proposals are promoted into durable knowledge represented primarily through Insights and Fields.

The Knowledge Usability Audit (see `docs/knowledge-usability-audit.md`) identified that this promotion is currently lossy.

Important semantic information available before promotion is either discarded, simplified or not represented in the resulting trusted knowledge.

Observed examples include:

* `confidence` not preserved;
* `evidence` not preserved;
* rationale/context being reduced;
* domain type reduction during `InsightPromotionService.toDomainType`;
* `ValidatableProposal.decidedAt` not being populated;
* validation-related information not always surviving the lifecycle.

As a consequence, DevLog can possess richer information before validation than after validation.

This reduces the usefulness of trusted knowledge for both:

* human project understanding;
* structured context consumed by future machine/agent workflows.

The problem must therefore be addressed at the knowledge lifecycle level before attempting to solve it only through richer frontend projections.

## Decision

Promotion from an accepted `ValidatableProposal` into trusted project knowledge **must preserve all semantically useful information necessary to understand, justify and trace the resulting knowledge**.

Promotion is a trust transition.

It must not implicitly become a semantic compression step.

Conceptually:

AI Interpretation
→ ValidatableProposal
→ Human / Business Validation
→ Trusted Knowledge

The transition to Trusted Knowledge may normalize or restructure data, but it must not discard information required to answer:

* What do we know?
* Why does it matter?
* Why do we believe it?
* Where did it come from?
* How trustworthy was the originating interpretation?
* Which validation accepted it?

### 1. Proposal and Knowledge Have Different Trust Levels, Not Necessarily Different Semantic Richness

`ValidatableProposal` represents untrusted or not-yet-trusted interpretation.

Trusted Knowledge represents information that has successfully passed the required validation lifecycle.

The primary difference between the two is therefore:

**trust status**

not:

**amount of useful semantic information**.

An accepted proposal may be transformed into a different domain representation, but that representation must retain the information necessary to preserve its meaning and provenance.

### 2. Accepted Knowledge Must Preserve Rationale

When available and relevant, the reasoning or rationale explaining a knowledge statement must survive promotion.

Example:

Weak knowledge:

> Project Timeline introduced.

Useful knowledge:

> DevLog exposes recent project evolution through a deterministic Timeline projection so humans can inspect project history without requiring LLM reconstruction.

The second form contains information that can influence future engineering decisions.

The system must not systematically reduce it to the first form during promotion.

### 3. Accepted Knowledge Must Preserve Evidence

Trusted knowledge should retain traceable evidence when that evidence exists in the validated proposal.

Evidence may originate from:

* repository facts;
* commits;
* diffs;
* Engineering Stories;
* ADRs;
* analysis results;
* repository context;
* other trusted engineering entities.

The exact evidence persistence model is intentionally not defined by this ADR.

However, promotion must preserve enough provenance to allow future consumers to understand why the knowledge exists.

### 4. Confidence Must Not Be Silently Discarded

If the AI analysis or proposal contains a meaningful confidence assessment, promotion must not silently remove it.

Confidence does not transform uncertain AI interpretation into deterministic fact.

It remains metadata describing the originating interpretation.

Trusted status means:

> the proposal was accepted according to the DevLog validation lifecycle.

It does not necessarily mean:

> the originating interpretation had absolute certainty.

Trust state and confidence therefore remain distinct concepts.

### 5. Semantic Types Must Not Be Reduced Without an Explicit Domain Reason

Promotion must not collapse richer semantic categories into broader categories merely because the trusted knowledge model currently supports fewer types.

For example, a mapping equivalent to:

many proposal categories
→ small number of generic Insight categories

is acceptable only when that reduction is intentional and does not remove information required by downstream consumers.

If normalization is necessary, the original semantic classification should remain recoverable where it provides engineering value.

The final type taxonomy will be addressed during implementation design.

### 6. Validation Provenance Must Be Preserved

Trusted knowledge should be traceable to the validation decision that allowed its promotion.

Where supported by the domain lifecycle, relevant information may include:

* proposal identity;
* acceptance decision;
* decision timestamp;
* validation actor or mechanism;
* validation-related severity or classification.

The exact persistence schema is outside the scope of this ADR.

However, accepted knowledge must not become disconnected from the process that established its trusted status.

### 7. Promotion Must Remain Atomic

This decision does not alter the existing principle that acceptance and promotion into trusted knowledge must form a controlled domain transition.

The existing guarantees around proposal lifecycle and trusted knowledge promotion remain in force.

The goal is to make the promoted result richer, not to weaken validation boundaries.

### 8. Trusted Knowledge Must Remain Structured

Semantic preservation does not mean storing the entire original AI response as an opaque text blob.

Prefer structured representations for information that downstream systems need to query or reason about.

Potential semantic dimensions include:

* statement;
* rationale;
* evidence;
* confidence;
* provenance;
* type;
* source;
* validation metadata.

The final model will be defined during implementation.

Avoid introducing unrestricted `Map<String, Object>` structures as a substitute for domain modeling.

### 9. Raw AI Output Is Not Automatically Trusted Knowledge

Preserving semantic richness must not result in blindly copying the complete AI payload into trusted persistence.

The Java Core remains responsible for:

* schema validation;
* domain validation;
* normalization;
* lifecycle enforcement;
* accepted knowledge construction.

Only validated and explicitly promoted information becomes trusted knowledge.

### 10. Knowledge Must Support Both Human and Machine Consumption

Trusted knowledge is a shared engineering asset.

It should support at least two classes of consumer.

#### Human

The engineer should eventually be able to understand:

* what was learned;
* why it matters;
* supporting context;
* provenance;
* related engineering work.

#### Machine / Agent

Structured consumers should eventually be able to:

* select relevant knowledge;
* reason from supporting context;
* distinguish trusted facts from interpretation metadata;
* retrieve provenance;
* construct targeted engineering context.

This ADR does not define consumer-specific APIs.

It establishes that the underlying trusted knowledge must retain enough semantic information for those consumers to be useful.

### 11. Frontend Projection Must Not Compensate for Missing Knowledge

The frontend must not reconstruct semantic richness that was discarded earlier in the lifecycle.

If the trusted knowledge model stores only a superficial summary, the UI cannot reliably infer:

* rationale;
* evidence;
* impact;
* provenance.

Therefore:

Knowledge Generation
→ Validation
→ Promotion
→ Persistence

must preserve the semantic information before:

Project State
→ Timeline
→ Knowledge UI

attempt to display it.

This ADR intentionally places the responsibility at the knowledge lifecycle layer.

### 12. Project State and Timeline Remain Projections

This decision does not turn `ProjectState` or `ProjectTimeline` into knowledge storage systems.

They remain deterministic read models.

They may consume richer trusted knowledge once it becomes available.

They must not independently invent missing rationale, evidence or confidence.

### 13. Events and Knowledge Remain Distinct Concepts

An Engineering Event represents something significant that happened.

Trusted Knowledge represents something the project now knows or understands.

An event may contribute to knowledge.

It is not automatically equivalent to knowledge.

Example:

Engineering Event:

> Story 0034 completed.

Potential Knowledge:

> Project history is exposed through a deterministic bounded Timeline projection aggregating validated project events without requiring LLM analysis.

This ADR preserves this conceptual distinction.

It does not redesign `EngineeringEvent` or `KnowledgeEvent`.

### 14. KnowledgeEvent Is Not Redefined by This Decision

The audit identified that `KnowledgeEvent` currently appears disconnected from the primary Insight/Proposal promotion pipeline.

This is an important architectural issue, but it is not resolved by this ADR.

A future decision may clarify:

* whether `KnowledgeEvent` represents a knowledge-domain event;
* whether it should participate directly in promotion;
* whether its current naming/responsibility remains appropriate.

Story 0035 must not silently redefine `KnowledgeEvent` unless an explicit architectural decision is made.

### 15. Knowledge Relations Are a Separate Evolution

The audit also identified limitations in `KnowledgeRelation`, including restricted entity types.

Semantic preservation should be addressed before significantly expanding the relation model.

A rich graph of shallow knowledge would still provide limited value.

The preferred sequence is:

Rich Trusted Knowledge
→ Better Human/Machine Projection
→ Richer Relationships
→ Knowledge Graph capabilities when justified

This ADR therefore does not require a Knowledge Graph or graph database.

### 16. Detailed Diff Persistence Is Out of Scope

The audit identified loss of detailed line-by-line diff evidence.

This ADR establishes the general requirement that useful evidence should remain traceable, but it does not mandate persistence of complete Git diffs.

Detailed diff retention has separate storage, lifecycle and cost implications and must be evaluated independently.

## Consequences

### Positive

* Trusted knowledge retains more engineering value after validation.
* Human-facing Knowledge views can expose meaningful rationale and evidence.
* Future agents receive better structured engineering context.
* Validation becomes a trust transition rather than a semantic compression step.
* Provenance and explainability improve.
* Future Project Knowledge Artifact generation receives better source material.
* Knowledge relations and future graph capabilities can operate on richer nodes.

### Negative

* Trusted knowledge persistence becomes richer and therefore more complex.
* Existing entities, DTOs or mappings may require migration.
* Additional fields increase API and testing responsibilities.
* Historical knowledge created before this change may remain less rich than newly promoted knowledge.
* Some AI output fields may need stronger schema/domain validation before they can be promoted.

### Risks

* Storing raw AI output instead of modeling trusted semantics.
* Treating confidence as equivalent to truth.
* Duplicating proposal payloads unnecessarily.
* Expanding Story 0035 into a complete Knowledge Graph redesign.
* Attempting to solve all historical knowledge inconsistencies in one migration.
* Introducing fields whose semantics are unclear merely because they exist in an AI payload.

## Explicit Non-Goals

This ADR does not define:

* the final Java Knowledge entity;
* final DTOs;
* database migration details;
* final type taxonomy;
* Knowledge Graph architecture;
* graph database technology;
* detailed diff persistence;
* KnowledgeEvent redesign;
* frontend visual design;
* AI prompt redesign unless required by Story 0035;
* automatic knowledge obsolescence;
* complete knowledge relationship modeling;
* document/artifact generation.

## Implementation Direction

The first implementation slice should focus on the highest-value semantic loss identified by the audit.

Recommended initial dimensions:

* rationale;
* evidence/provenance;
* confidence where available;
* validation decision metadata;
* preservation of useful semantic classification.

The implementation should follow the data end-to-end:

AI / Proposal
→ ValidatableProposal
→ Validation
→ Promotion
→ Trusted Knowledge
→ Read API
→ Human projection

The goal is not to make every knowledge concern perfect in one Story.

The goal is to prove that accepted knowledge can retain enough semantic richness to become genuinely useful.

## Compatibility With Existing Decisions

This decision preserves the existing principle that AI-generated output is not trusted knowledge directly.

AI continues to produce proposals.

The Java Core continues to own:

* validation;
* lifecycle;
* trusted knowledge construction;
* persistence.

Human or deterministic validation remains the gate between proposal and trusted knowledge.

This ADR strengthens that model by requiring that validated semantic value survive the transition.

The implementation should remain compatible with the separation between evidence, knowledge, facts and observations established in ADR-016, and with the evidence/knowledge separation of ADR-040.

## Guiding Principle

Validation should remove uncertainty about whether information is accepted into project memory.

It should not remove the information that made the knowledge useful.

Therefore:

**Promotion changes trust status, not semantic value.**
