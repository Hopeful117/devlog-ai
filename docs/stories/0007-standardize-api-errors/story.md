# Story 0007 — Standardize API Error Semantics

## Story ID
0007

## Title
Return explicit, stable and traceable API errors

## Status
Draft

## Priority
High

## Date
2026-08-08

---

## User Story

As an API consumer such as Kiko,
I want DevLog failures to preserve their correct HTTP semantics and expose stable, traceable error information,
So that I can distinguish invalid requests, missing routes, conflicts, provider failures and unexpected server errors without parsing human-readable messages.

---

## Context

The first live DevLog integration test from the `engineering-story` workflow called an incorrect route while discovering projects:

```text
GET /api/projects
```

The actual project collection endpoint is:

```text
GET /api/v1/projects
```

Spring MVC correctly raised a missing-resource exception, but `GlobalExceptionHandler` handled it through the generic unexpected-exception path. DevLog therefore returned `500 Internal Server Error` instead of `404 Not Found`.

Additional live checks showed the same classification problem for unsupported HTTP methods:

```text
DELETE /api/v1/projects
→ 500 Internal Server Error
```

DevLog already returns structured `ApiErrorResponse` bodies for validation failures, malformed JSON, invalid typed parameters, missing entities and known conflicts. It also produces an `X-Correlation-ID` response header. The gap is incomplete exception coverage and the absence of a stable machine-readable error code and correlation identifier in the common error body.

This Story should strengthen the existing error contract rather than replace it with a broad API redesign.

---

## Objective

Ensure that DevLog API failures:

* retain the correct HTTP status;
* expose a stable machine-readable error code;
* include the request correlation identifier for diagnostics;
* keep internal exception details out of public responses;
* remain consistently testable through the real Spring MVC exception-resolution path.

---

## Acceptance Criteria

### AC-1: Unknown API routes return 404

Requests to an unmapped API route must return:

* HTTP `404 Not Found`;
* the common API error representation;
* a stable error code identifying an unknown route;
* a useful public message that does not expose internal details;
* the requested path and correlation identifier.

An unknown route must not be logged or reported as an unexpected `500` error.

### AC-2: Unsupported HTTP methods return 405

Requests using an unsupported HTTP method on an existing route must return:

* HTTP `405 Method Not Allowed`;
* the common API error representation;
* a stable error code identifying the unsupported method;
* the request path and correlation identifier.

### AC-3: Existing request-validation errors remain explicit

Existing handling for invalid typed parameters, malformed JSON and Bean Validation failures must continue to return `400 Bad Request` with the common error representation and an appropriate stable error code.

### AC-4: Entity and conflict semantics remain correct

Existing missing-entity errors must continue to return `404 Not Found`.

Known business conflicts must return `409 Conflict`. In particular, attempting to create a project whose generated slug already exists must not fall through to the generic `500` handler.

### AC-5: Stable error code

The common API error representation must expose a stable machine-readable code that consumers can use without parsing `message` or `error` text.

Error codes must be deterministic and documented by tests. Their exact representation should follow the smallest convention consistent with the current backend architecture.

### AC-6: Correlation identifier in the response body

The common API error representation must include the same correlation identifier exposed through the `X-Correlation-ID` response header and used in server logs.

An accepted client-supplied correlation identifier must be preserved. An invalid or missing identifier must use the identifier generated by `CorrelationIdFilter`.

### AC-7: Safe unexpected-error response

Unhandled server failures must continue to return `500 Internal Server Error` with a neutral public message, a stable internal-error code and the correlation identifier.

Stack traces, exception class names and sensitive internal messages must remain server-side only.

### AC-8: Exceptions are classified deliberately

The implementation must not globally map every `IllegalArgumentException` to `400 Bad Request`, because this exception currently represents both input problems and internal invariant violations.

Provider, Git and collection exceptions must not receive arbitrary public statuses merely to increase handler coverage. Only exceptions that can cross an HTTP boundary and whose semantics are established by Repository Analysis and Implementation Planning should receive explicit mappings in this Story.

### AC-9: Specialized conflict response remains compatible

The existing AI task conflict response may retain its additional domain fields, but its common error fields and machine-readable code semantics must remain compatible with the standardized error contract.

### AC-10: End-to-end MVC tests

Tests must exercise Spring MVC exception resolution rather than only calling handler methods directly.

Coverage must include at least:

* unknown route;
* unsupported method;
* invalid UUID or typed path parameter;
* unknown entity;
* malformed or invalid request;
* duplicate project slug;
* unexpected exception;
* correlation identifier consistency between header and body.

### AC-11: Existing consumers and tests remain compatible

Existing backend and frontend consumers of error responses must be inspected and adapted only where the intentional contract extension requires it.

All relevant existing tests must continue to pass.

## Scope

### In Scope

* Audit and complete Spring MVC exception mappings used by DevLog's HTTP API.
* Correct missing-route and unsupported-method status handling.
* Correct the known duplicate-project-slug conflict classification.
* Extend the common error contract with a stable error code and correlation identifier.
* Reuse the existing correlation filter and structured error response infrastructure.
* Preserve safe public messaging for unexpected failures.
* Add controller-level or application-level MVC tests for the complete error path.
* Adapt directly affected consumers and tests if required by the contract extension.

### Out of Scope

* Migrating all endpoints to RFC 9457 `ProblemDetail`.
* Redesigning every domain exception hierarchy.
* Mapping every runtime or `IllegalArgumentException` to a client error.
* Changing DevLog's successful response contracts.
* Changing the Engineering-Skills fallback contract.
* Changing DevLog context collection, ranking or selection.
* Adding persistence, database migrations or new infrastructure.
* Exposing stack traces or internal exception details to clients.
* General logging or observability redesign.

---

## Impacted Components

Likely affected components include:

* `shared/exception/handler/GlobalExceptionHandler`;
* `shared/response/ApiErrorResponse`;
* `shared/logging/CorrelationIdFilter` or its public correlation-context contract;
* project conflict exception handling;
* specialized AI task conflict error representation where compatibility requires it;
* handler unit tests and Spring MVC controller tests;
* directly affected frontend error models or consumers, if any are found.

Repository Analysis must confirm the exact affected set before planning.

---

## Architectural Boundaries

* Controllers remain thin and do not construct ad hoc error bodies.
* Domain and application services express established failure semantics through typed exceptions.
* The shared HTTP error boundary owns translation to status, safe public detail, stable code and traceability metadata.
* Internal diagnostics remain in structured logs and are linked to public errors through the correlation identifier.
* Unknown internal failures remain server errors; they must not be disguised as invalid client requests.
* The change should extend the current contract with minimal disruption rather than introduce a second competing error format.

---

## Risks

### Contract compatibility

Adding fields is normally backward compatible for JSON consumers, but strict deserializers or frontend models may require adaptation. Repository Analysis must inspect actual consumers.

### Over-classification

Broad exception mappings can hide programming defects or mislabel infrastructure failures as client errors. Mappings must be explicit and evidence-based.

### Correlation context availability

The handler must obtain the exact identifier chosen by `CorrelationIdFilter`, including client-supplied valid identifiers, without generating a second unrelated value.

### Framework behavior

Spring Boot 4 and Spring MVC may route framework exceptions through different resolver paths. Tests must pass through MockMvc or the running HTTP stack rather than relying only on direct handler invocation.

---

## Validation

Validation should include:

* targeted `GlobalExceptionHandler` and correlation-filter tests;
* MockMvc tests covering the real dispatcher and exception advice;
* live read-only HTTP checks for unknown routes, unsupported methods, invalid UUIDs and unknown projects;
* relevant backend test suite and coverage checks;
* frontend validation only if an affected consumer is identified;
* confirmation that no database migration is introduced.
