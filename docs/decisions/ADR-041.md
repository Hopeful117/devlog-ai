# ADR-041 — Passive Project Monitoring

* **Status:** Accepted
* **Date:** 2026-07-23

## Context

DevLog AI currently supports active analyses explicitly requested by a user.

The long-term Developer OS vision also requires DevLog to maintain project awareness when the user is not actively interacting with the Workspace.

Relevant project changes may occur continuously:

* new commits;
* repository synchronizations;
* ADR additions or modifications;
* roadmap updates;
* documentation changes;
* completed analyses;
* accepted or rejected proposals;
* generated deliverables.

Requiring the user to manually request a complete analysis after every project change would reduce the value of DevLog as a living technical memory.

However, continuously running every available analysis would create unnecessary computational cost, duplicate work and excessive AI usage.

## Decision

DevLog AI introduces a **Passive Project Monitoring** mode.

Passive monitoring observes project changes, updates deterministic repository state and schedules targeted analyses when meaningful changes are detected.

It does not continuously execute every Intent.

Passive monitoring is selective, incremental and event-driven.

## Passive Monitoring Responsibilities

Passive monitoring may:

* detect new repository activity;
* import new commits;
* analyse commit metadata and code diffs;
* update deterministic repository evidence;
* detect modified ADRs and roadmap documents;
* identify stale project knowledge;
* schedule relevant agent jobs;
* update operational Workspace projections;
* create notifications or pending-review items.

Passive monitoring does not automatically promote AI interpretations into Trusted Knowledge.

## Trigger Sources

Passive processing may be triggered by:

* repository synchronization;
* new Git commits;
* branch updates;
* changed ADR files;
* changed roadmap files;
* completed deterministic analyses;
* accepted proposals;
* generated deliverables;
* scheduled consistency checks;
* manual refresh requests.

The architecture should not depend on one specific Git hosting provider.

Webhook integrations may be added later, but repository synchronization remains a valid trigger source.

## Incremental Processing

Passive monitoring should process only information that changed since the last successful execution.

Examples include:

* commits after the last imported hash;
* files changed since the previous analysis;
* newly accepted ADRs;
* newly validated knowledge;
* outdated reports affected by recent changes.

The system should avoid rebuilding the complete project context for every event.

## Significance Detection

Not every repository change requires AI interpretation.

Deterministic rules should first classify the change.

Examples of low-significance changes include:

* formatting-only changes;
* generated files;
* dependency lock-file noise;
* minor documentation corrections.

Examples of potentially significant changes include:

* new domain models;
* changed REST contracts;
* modified architecture;
* new ADRs;
* new services;
* major dependency changes;
* test failures;
* roadmap milestone completion.

Only meaningful changes should generate deeper passive work.

## Relationship With Active Analyses

Passive and active modes share the same repository evidence, project history and Trusted Knowledge.

Passive monitoring prepares and maintains context.

Active analyses may later reuse this work for deeper, user-requested interpretation.

Active analyses must not restart repository understanding from zero when valid passive results already exist.

## Workspace Integration

Passive monitoring updates the Workspace through user-oriented projections such as:

* recent activity;
* repository freshness;
* newly detected changes;
* pending validations;
* available documentation;
* agent execution status;
* project notifications.

Internal objects such as `AgentJob`, `Analysis`, `Proposal` or raw repository records should not dominate the user interface.

## Cost Control

Passive monitoring must support configurable operational limits, including:

* minimum delay between equivalent analyses;
* maximum concurrent jobs per project;
* maximum AI jobs per period;
* context-size limits;
* deduplication windows;
* retry limits.

Deterministic updates should be preferred over AI execution whenever possible.

## Failure Behaviour

A passive failure must not invalidate existing Trusted Knowledge.

Failures should:

* remain traceable;
* expose a controlled operational status;
* support retry;
* avoid duplicate promotion;
* preserve previously successful repository state.

## Consequences

### Advantages

* continuously updated project awareness;
* reduced manual work;
* faster active analyses;
* incremental project-memory construction;
* better Workspace notifications;
* controlled AI usage.

### Trade-offs

* additional lifecycle complexity;
* significance-classification rules;
* job deduplication requirements;
* background-processing observability.

These trade-offs are accepted because passive monitoring is essential to the Developer OS vision.

## Alternatives Considered

### Manual Analysis Only

Rejected.

Manual analysis prevents DevLog from becoming a living project memory.

### Continuously Execute Every Intent

Rejected.

This would create excessive cost, duplicate work and irrelevant output.

### Reanalyse the Entire Repository After Every Commit

Rejected.

Incremental processing provides better scalability and traceability.
