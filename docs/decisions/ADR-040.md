# ADR-040 — Knowledge and Evidence Separation

* **Status:** Accepted
* **Date:** 2026-07-23

## Context

DevLog AI currently relies primarily on validated Insights when generating analyses and documentation.

This approach guarantees that AI consumes trusted project knowledge.

However, it also introduces an important limitation.

Many documentation tasks require access to factual repository information that should not necessarily become validated knowledge.

Examples include:

* project structure;
* modules;
* dependency descriptors;
* configuration files;
* README contents;
* build configuration;
* source code organization;
* Git history;
* commit diffs;
* roadmap items.

Requiring every repository fact to become a validated Insight before it can be used by the AI would create unnecessary friction and significantly reduce documentation quality.

Repository facts and validated knowledge represent different concepts.

---

## Decision

DevLog AI distinguishes **Repository Evidence** from **Trusted Knowledge**.

Repository Evidence represents deterministic facts extracted from the repository.

Trusted Knowledge represents validated project understanding.

Both participate in AI analyses, but they play different roles.

Repository Evidence provides factual context.

Trusted Knowledge provides validated interpretation.

---

## Repository Evidence

Repository Evidence consists of deterministic information extracted directly from the project.

Examples include:

* source code;
* package structure;
* dependency graph;
* Git history;
* commit diffs;
* configuration files;
* tests;
* roadmap items;
* ADR documents;
* repository metadata.

Repository Evidence is not interpreted knowledge.

It represents facts.

---

## Trusted Knowledge

Trusted Knowledge consists of information that has completed the normal validation workflow.

Examples include:

* validated Insights;
* accepted architectural interpretations;
* validated historical analyses;
* promoted project knowledge.

Trusted Knowledge represents the project's trusted memory.

---

## Analysis Context

The AI should receive an `AnalysisContext` composed of multiple complementary layers.

Typical context includes:

* Intent;
* User Guidance;
* Repository Evidence;
* Trusted Knowledge.

The Repository Context Engine and Context Intelligence remain responsible for selecting the most relevant information.

---

## Knowledge-Producing Analyses

Analyses whose objective is to create project knowledge continue to follow the existing proposal workflow.

```text
Repository Evidence
        +
Trusted Knowledge
        ↓
AI Interpretation
        ↓
ValidatableProposal
        ↓
Human Validation
        ↓
Trusted Knowledge
```

No AI-generated interpretation becomes trusted knowledge without validation.

---

## Documentation Generation

Documentation generation differs from knowledge generation.

The AI may directly consume selected Repository Evidence together with Trusted Knowledge to produce documentation drafts.

Examples include:

* README;
* Architecture Overview;
* Release Notes;
* Project State Reports;
* Technical Articles.

Documentation generation does not require every repository fact to become a validated Insight.

---

## Repository Facts

Simple repository facts should not require AI interpretation.

Examples include:

* project language;
* build tool;
* repository structure;
* dependency list;
* module names.

These facts may be extracted deterministically and included directly in the AnalysisContext.

---

## Human Validation

Human validation remains mandatory whenever generated outputs become:

* Trusted Knowledge;
* official documentation;
* published deliverables.

Repository Evidence itself does not require validation because it originates from deterministic extraction.

---

## Responsibilities

The Repository Context Engine selects repository evidence.

Context Intelligence determines which evidence is relevant.

The AI interprets or generates content using the resulting AnalysisContext.

Promotion into Trusted Knowledge continues to follow ADR-006.

---

## Consequences

### Advantages

* richer AI context;
* higher-quality documentation;
* reduced unnecessary Insight creation;
* clearer separation of facts and interpretations;
* improved scalability of documentation workflows.

### Trade-offs

* larger AnalysisContext;
* additional distinction between repository facts and project knowledge;
* more sophisticated context selection.

These trade-offs are accepted because they improve both documentation quality and architectural clarity.

---

## Alternatives Considered

### Insights as the Only AI Context

Rejected.

Validated Insights alone do not contain enough factual information to generate complete documentation.

---

### Repository Facts Must Become Insights

Rejected.

This would unnecessarily overload the knowledge validation workflow with deterministic information that already exists in the repository.

---

### AI Reads the Entire Repository

Rejected.

Repository Context should remain bounded and selected by the Repository Context Engine according to ADR-038 and ADR-039.
