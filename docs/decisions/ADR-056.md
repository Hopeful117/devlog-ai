# ADR-056 — DevLog MCP Integration Boundary and Module Placement

## Status

Proposed

## Date

2026-08-16

## Context

DevLog is evolving toward an Engineering Context Engine capable of maintaining,
enriching and projecting reliable engineering context for different consumers.

ADR-055 established that context projection must become a reusable DevLog
capability rather than Kiko-specific business logic.

Potential consumers include:

* Kiko;
* coding agents;
* IDE agents;
* code review agents;
* documentation agents;
* maintenance agents;
* human developers;
* future Developer OS workflows.

This creates a new integration requirement.

Consumers need a standardized mechanism for discovering and accessing DevLog
engineering context without depending on DevLog's internal implementation or on
the conversational memory of a particular AI agent.

A concrete example is engineering continuity.

If Kiko becomes temporarily unavailable because of provider availability, token
limits or another operational constraint, another compatible agent should be
able to continue the engineering task using project context maintained by
DevLog.

This is not a Kiko-specific fallback mechanism.

It demonstrates a broader architectural requirement:

> Engineering context must belong to the project, not to the agent currently
> consuming it.

The Model Context Protocol (MCP) provides a potential standardized boundary
between DevLog and external AI-enabled engineering tools.

The architectural question is therefore:

> Where should the DevLog MCP integration live, and what responsibility should
> that integration boundary own?

Two main placement strategies are possible:

1. create an independent MCP repository or service;
2. introduce MCP as a dedicated adapter inside the DevLog repository.

This ADR defines the initial boundary and placement decision.

## Decision

DevLog will introduce MCP as a **dedicated inbound integration adapter inside
the DevLog repository**.

The initial implementation will live in a dedicated `devlog-mcp` module.

Conceptually:

```
IDE / Agent
    ↓
MCP Client
    ↓
devlog-mcp
    ↓
DevLog Application
    ↓
Engineering Context capabilities
```

MCP does not become a new business or knowledge layer.

### 1. MCP Is an External Protocol Adapter

The primary responsibility of `devlog-mcp` is to translate between MCP concepts
and existing DevLog application capabilities.

Its architectural position is comparable to another inbound adapter.

Conceptually:

```
          External Consumers
             ↓         ↓
           REST       MCP
             ↓         ↓
        REST Adapter  MCP Adapter
              \       /
               \     /
          DevLog Application
                 ↓
            DevLog Domain
```

MCP-specific protocol concerns remain at the system boundary.

DevLog's domain and application model must remain independent from MCP.

### 2. MCP Must Depend on DevLog Application Capabilities

The expected dependency direction is:

```
devlog-mcp
    ↓
application ports / services
    ↓
domain capabilities
    ↓
infrastructure through existing ports
```

The MCP adapter may invoke application queries and use cases.

It must not reproduce those use cases internally.

MCP-specific types must not leak into the domain model.

Conceptually:

```
MCP Request
    ↓
MCP Adapter
    ↓
Application Contract
    ↓
DevLog
    ↓
Application Result
    ↓
MCP Response
```

### 3. MCP Must Not Access Persistence Directly

The physical proximity of the MCP module to other DevLog modules must not allow
it to bypass application boundaries.

The following paths are forbidden:

```
MCP → JDBC repository

MCP → database

MCP → internal persistence implementation
```

The expected path remains:

```
MCP
  ↓
Application Port / Service
  ↓
Domain / Projection
  ↓
Infrastructure
```

If a required MCP capability cannot be implemented without directly accessing
persistence, this indicates that the DevLog application boundary is missing an
appropriate capability.

The application boundary should be improved rather than bypassed.

### 4. MCP Capabilities Must Remain Consumer-Agnostic

DevLog MCP must not become coupled to Kiko, OpenCode or any specific AI provider.

Capabilities should describe engineering intent.

Prefer concepts such as:

```
get_engineering_context
search_project_context
search_project_history
get_architectural_constraints
```

rather than:

```
get_context_for_kiko
get_context_for_opencode
```

Kiko may be an early consumer used to validate the integration, but MCP is not
owned by Kiko.

The same capability should be reusable by another authorized consumer.

### 5. Engineering Context Continuity Is an Initial Validation Use Case

One initial use case is continuation of engineering work when the primary agent
is unavailable.

Conceptually:

```
Engineering Task
      ↓
    Kiko
      ↓
provider unavailable
      ↓
alternative IDE agent
      ↓
  DevLog MCP
      ↓
Engineering Context
      ↓
 work continues
```

MCP does not select the replacement agent.

It only ensures that another compatible consumer can access DevLog capabilities.

Future provider selection and agent fallback belong to the Agent Orchestrator
or Engineering Workflow layer.

### 6. MCP Does Not Replace Context Projection

ADR-055 establishes that DevLog owns context composition and projection.

MCP must expose that capability rather than reimplement it.

Initially:

```
MCP
 ↓
Existing Application Queries
 ↓
Existing Projections
```

As context projection evolves:

```
MCP
 ↓
ContextRequest
 ↓
DevLog
 ↓
ContextPackage
```

MCP should remain independent from how DevLog internally constructs that
ContextPackage.

### 7. MCP Must Remain Compatible With the Future Retrieval Layer

The future Retrieval Layer may introduce:

* structured retrieval;
* lexical retrieval;
* semantic/vector retrieval;
* temporal retrieval;
* relationship expansion;
* reranking.

These mechanisms remain internal DevLog concerns.

Conceptually:

```
Consumer
   ↓
  MCP
   ↓
DevLog Application
   ↓
Retrieval Layer
   ↓
Context Projection
   ↓
ContextPackage
```

Consumers must not need to know whether DevLog used SQL queries, deterministic
projections, hybrid retrieval or future RAG infrastructure.

This allows retrieval capabilities to evolve without breaking MCP consumers.

### 8. The Initial MCP Boundary Should Be Primarily Read-Only

The first MCP implementation should minimize mutation capabilities.

Initial value should come from exposing reliable engineering context rather than
allowing agents to modify DevLog state.

Potential initial capabilities include access to:

* project context;
* trusted Knowledge;
* ADR context;
* Engineering Story context;
* project history;
* architectural constraints;
* projected engineering context.

Exact MCP Resources and Tools are intentionally deferred to a dedicated
capability-model ADR.

### 9. MCP Must Preserve Existing Knowledge Governance

MCP must not create an alternative path around DevLog validation rules.

In particular, an external agent must never be able to directly promote
information into trusted project Knowledge through MCP.

The following path is forbidden:

```
Agent
  ↓
MCP
  ↓
Trusted Knowledge
```

If future MCP tools allow agents to submit engineering findings, the existing
proposal lifecycle remains applicable.

Conceptually:

```
Agent
  ↓
MCP
  ↓
ValidatableProposal
  ↓
Validation
  ↓
Knowledge Promotion
  ↓
Trusted Knowledge
```

ADR-006 remains authoritative for this workflow.

### 10. MCP Must Not Replace Local Engineering Tools

DevLog MCP provides project memory and engineering context.

It is not intended to replace the IDE agent's local capabilities.

The IDE or coding agent remains responsible for operations such as:

* reading working-tree files;
* modifying source code;
* executing Git commands;
* running builds;
* running tests;
* producing implementation diffs.

The initial responsibility boundary is:

```
IDE / Coding Agent
    → local engineering execution

DevLog MCP
    → access to DevLog engineering context

DevLog
    → project memory and context construction
```

This avoids turning DevLog MCP into an unrestricted remote development
environment.

### 11. The MCP Module Must Remain Extractable

Although MCP starts inside the DevLog repository, the module must remain
architecturally extractable.

This requires:

* no domain logic inside `devlog-mcp`;
* no direct persistence access;
* explicit application contracts;
* protocol-specific models isolated inside the adapter;
* consumer-independent capabilities;
* no dependency from DevLog Core toward MCP.

The objective is not to predict a future extraction.

It is to avoid architectural coupling that would make extraction unnecessarily
expensive.

### 12. A Developer OS MCP Gateway Remains a Future Option

DevLog MCP initially serves DevLog-specific capabilities.

If MCP later becomes a common integration boundary for several Developer OS
modules, a different architecture may become justified.

Conceptually:

```
             Developer OS MCP
                    ↓
      ┌─────────────┼─────────────┐
      ↓             ↓             ↓
   DevLog       Workspace     Codeglyphe
                                  ↓
                       Engineering Workflows
```

At that point, an independent `developer-os-mcp` repository or service may
provide a meaningful system boundary.

That decision must be driven by demonstrated cross-product requirements rather
than introduced prematurely.

## Consequences

### Positive

* DevLog gains a standardized integration boundary for AI-enabled engineering
  tools;
* project context becomes less dependent on the conversational state of a
  particular agent;
* Kiko, OpenCode and future consumers can potentially access the same DevLog
  context capabilities;
* MCP can validate whether existing application boundaries expose sufficiently
  useful engineering context;
* the implementation can reuse existing DevLog application capabilities;
* no additional distributed-service boundary is required initially;
* the future Retrieval Layer can evolve independently from MCP consumers;
* engineering workflows gain a path toward provider and agent portability;
* the architecture remains compatible with a future Developer OS MCP gateway.

### Trade-offs

* MCP initially shares DevLog's repository and application lifecycle;
* module boundaries must be enforced despite physical proximity;
* additional application ports may be required to expose useful context cleanly;
* MCP introduces another public integration contract that will require
  compatibility management;
* the module may require later extraction if its responsibility expands beyond
  DevLog.

### Risks

* developers could bypass the application layer and access persistence directly
  from the MCP module;
* MCP capabilities could become tailored specifically to Kiko or OpenCode;
* too many low-level MCP capabilities could expose DevLog's internal topology;
* write-capable tools could accidentally bypass Knowledge governance;
* MCP could grow into an agent orchestration layer rather than remaining an
  integration adapter;
* premature support for multiple Developer OS modules could introduce an
  unnecessary distributed gateway;
* protocol concerns could leak into DevLog application or domain models.

## Alternatives Considered

### Create a Dedicated DevLog MCP Repository Immediately

Rejected for the initial implementation.

The current MCP responsibility is tightly associated with exposing DevLog
application capabilities.

A separate repository would introduce additional concerns such as:

* deployment;
* service communication;
* authentication between services;
* contract versioning;
* DTO duplication;
* distributed failure modes.

There is currently no demonstrated requirement that justifies this additional
service boundary.

### Expose DevLog Only Through the Existing REST API

Rejected as the only long-term integration mechanism.

REST remains appropriate for existing application and frontend use cases.

However, MCP provides a standardized capability-discovery and invocation model
for AI-enabled engineering consumers.

MCP should complement REST rather than replace it.

### Embed MCP Logic Directly in the Existing REST Module

Rejected.

MCP and REST are different protocol boundaries.

Combining them inside the same adapter would unnecessarily couple protocol
concerns and make the MCP boundary less explicit.

A dedicated module provides clearer architectural ownership.

### Build a Developer OS-Wide MCP Gateway Immediately

Rejected.

The immediate requirement is DevLog-specific.

Introducing a cross-product gateway before concrete Workspace, Codeglyphe or
Workflow MCP requirements exist would create speculative architecture.

The DevLog MCP module should first validate the integration model.

### Let Each Agent Integrate Directly With DevLog Internals

Rejected.

This would couple consumers to DevLog's storage model, internal APIs and
knowledge topology.

It would also cause context retrieval and composition logic to be duplicated
across consumers.

## Explicit Non-Goals

This ADR does not define:

* the exact MCP SDK or Java library;
* the MCP transport mechanism;
* exact MCP Resources;
* exact MCP Tools;
* MCP Prompts;
* authentication implementation;
* IDE-specific configuration;
* Kiko-specific integration;
* OpenCode-specific integration;
* automatic provider fallback;
* agent selection or orchestration;
* implementation of the future Retrieval Layer;
* RAG infrastructure;
* vector databases or embeddings;
* direct code execution through MCP;
* unrestricted filesystem access;
* autonomous modification of trusted project Knowledge;
* a Developer OS-wide MCP gateway.

## Implementation Direction

The MCP integration should be introduced incrementally.

A suitable progression is:

1. formalize the MCP capability model;
2. define security and governance requirements;
3. identify the minimal DevLog application ports required by the first MCP
   capabilities;
4. define the `devlog-mcp` module boundary;
5. select the Java MCP implementation technology;
6. initialize the module without business logic;
7. expose one minimal read-only capability;
8. connect an external IDE agent;
9. validate retrieval of real DevLog engineering context;
10. evaluate whether the returned context is sufficient to continue an
    engineering task without agent-specific conversational memory;
11. refine the application/context boundaries from observed gaps;
12. expand MCP capabilities only when justified by real engineering workflows.

The first prototype should optimize for learning and architectural validation,
not capability volume.
