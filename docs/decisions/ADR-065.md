# ADR-065 — Analysis Synthesis and Knowledge Proposal Separation

## Status

Accepted

## Date

2026-09-01

## Context

The post-0106/0107 canonical benchmark (`docs/investigations/post-0106-0107-canonical-analysis-product-benchmark.md`) executed `architecture-overview-v1` three times against one stable project state.

Every execution received stable, meaningful architecture information:

```text
40 Facts
4 Observations
10 Insights
5 trusted architecture knowledge items
60 repository-evidence items
50 ARCHITECTURE Semantic Section memberships
```

All three executions correctly generated no new or enriching architecture proposals.
The canonical result did not explain the current architecture or explicitly
explain the no-delta conclusion.

```text
ARCHITECTURE_BENCHMARK_USEFUL_RATE = 0/3
PRIMARY_BOTTLENECK = OUTPUT_SYNTHESIS
```

The product conflates two different outcomes:

```text
CURRENT-STATE SYNTHESIS   = What is the architecture now?
KNOWLEDGE DELTA           = What new or enriching knowledge should be proposed?
```

`architecture-overview-v1` currently generates only `NEW` or `ENRICHES` Insight
proposals. When no material delta exists, `proposals = []` is contract-valid but
leaves the user without an architecture overview.

Existing ADRs already govern adjacent concerns:

- ADR-006 — AI proposal lifecycle and governed promotion;
- ADR-020 — callback contract and atomicity;
- ADR-028 — Intent versioning and immutable semantic contracts;
- ADR-030 — Intent execution and user guidance;
- ADR-063 section 29 — AI synthesis remains untrusted `ValidatableProposal`;
- ADR-064 — preserved proposal governance.

What none of them defines is the architectural distinction between an AI answer
about existing project knowledge and an AI proposal to create new project
knowledge.

## Problem

When no new or enriching architecture delta exists, the user receives an empty
proposal list instead of a coherent current-state architecture overview. The
result is technically valid but functionally useless.

The architectural question is:

> How should DevLog represent an AI-generated current-state synthesis that
> describes existing project knowledge, without conflating it with
> `ValidatableProposal` objects that propose new project knowledge?

## Decision

DevLog introduces **Analysis Synthesis** as a distinct architectural category
separate from `ValidatableProposal`.

### 1. Analysis Synthesis is a new AI output category

An Analysis Synthesis is an AI-generated answer about what DevLog already knows.

It is NOT:

- a `ValidatableProposal`;
- trusted project knowledge;
- a promoted domain object;
- an Insight, Decision, or Engineering Event.

A `ValidatableProposal` proposes new or enriched knowledge that does not yet
exist in the trusted knowledge base.

Analysis Synthesis describes knowledge that already exists, organized by the AI
for human consumption.

```text
ValidatableProposal  → proposes NEW knowledge
                      → requires human validation
                      → may be promoted to trusted knowledge

Analysis Synthesis   → DESCRIBES existing knowledge
                      → does not require human validation
                      → cannot be promoted to trusted knowledge
```

### 2. Trust semantics

Analysis Synthesis is non-trusted by construction.

```text
SYNTHESIS != TRUSTED KNOWLEDGE
SYNTHESIS != VALIDATABLE PROPOSAL
SYNTHESIS != AUTOMATIC KNOWLEDGE PROMOTION
```

The synthesis represents the AI's interpretation of the selected
point-in-time context. It is not authoritative. It cannot create or modify
`Insight`, `EngineeringDecision`, or other trusted domain objects.

The human developer reads the synthesis to understand the current state. The
human developer reviews proposals separately to decide whether new knowledge
should be accepted.

### 3. Persistence ownership

The Java Core owns synthesis persistence.

The synthesis is persisted as an immutable, execution-scoped, non-trusted
snapshot on the existing `AiTask` entity or equivalent execution boundary.

Invariants:

- one Analysis execution produces one synthesis snapshot;
- the snapshot is immutable after callback persistence;
- the snapshot is scoped to the Analysis execution, not the project;
- no cross-run reuse without explicit future ADR authorization;
- the Core remains the source of truth for workflow state and persistence.

### 4. Callback contract extension

The AI Engine delivers synthesis and proposals through a single atomic
callback.

Conceptually:

```text
AiTaskResultRequest
├── correlationId
├── externalJobId
├── status
├── completedAt
├── synthesis              ← NEW: optional, non-trusted AI answer
│   ├── content
│   └── groundingReferences[]
├── proposals[]            ← existing: zero or more ValidatableProposal
└── error
```

The synthesis field is optional because not all Intent types require
synthesis. The proposal array remains governed by ADR-006 and ADR-020.

The callback is atomic: synthesis and proposals persist together or not at
all. This preserves ADR-020's transaction boundary requirement.

### 5. Intent versioning

The output schema change for `architecture-overview` requires a new Intent
version under ADR-028.

```text
architecture-overview-v1  → current semantics: delta-only proposals
architecture-overview-v2  → new semantics: mandatory synthesis + optional delta proposals
```

Existing `architecture-overview-v1` semantics remain immutable. The version
transition is a new Intent registration, not a mutation of the existing one.

`describe-project-v1` and `analyze-engineering-decision-v1` remain
behaviorally unchanged.

### 6. Grounding and provenance

Every substantive architecture claim in the synthesis must be grounded in the
selected point-in-time context.

Grounding requirements:

- claims reference selected evidence where applicable;
- unsupported categories are omitted or represented as uncertainty;
- the synthesis does not invent components, relationships, boundaries,
  principles, or causality;
- provenance traces to the Analysis execution context.

This extends ADR-064's grounding-support architectural capability to the
synthesis category.

### 7. Failure and atomicity semantics

The one-call design creates a deliberate question when synthesis and proposal
validation diverge.

For V1, the conservative baseline is one atomic governed output:

- validate synthesis and proposals before callback persistence;
- use the existing bounded corrective-generation behavior for invalid output;
- do not persist a partially validated callback;
- fail the task if the combined output remains invalid.

This preserves current callback atomicity. Partial success is explicitly
rejected for V1 to avoid inventing local partial-output semantics. A future
ADR may introduce governed partial-success behavior if evidence requires it.

### 8. Scope boundary

This ADR introduces a minimal architectural distinction for the
architecture-specific synthesis use case.

It does NOT introduce:

- a generic free-form Analysis answer framework;
- a new AI task type;
- frontend rendering changes;
- retrieval or context-composition architecture changes;
- ADR-064 resumption;
- RAG, embeddings, or vector infrastructure;
- MCP-specific result construction;
- automatic trust or knowledge promotion.

## Architectural Invariants

1. Analysis Synthesis is a distinct category from `ValidatableProposal`.
2. Synthesis is non-trusted and non-promotable.
3. The Java Core owns synthesis persistence.
4. Callback atomicity is preserved: synthesis and proposals persist together.
5. Synthesis is immutable and execution-scoped.
6. Every substantive claim must be grounded in selected context.
7. Partial success is rejected for V1.
8. Existing Intent semantics are immutable under ADR-028.
9. Synthesis does not enter the `ValidatableProposal` lifecycle.
10. One-call target: synthesis and delta detection use one structured model
    call in the valid path.
11. Analysis Synthesis is excluded from automatic future `SelectedKnowledge`
    and from trusted project evidence unless a future ADR explicitly defines
    a governed reuse mechanism with provenance, trust tier, retrieval
    semantics, authorization, and cycle prevention.

## Consequences

### Positive

- the user receives a coherent current-state architecture overview even when
  no new knowledge is proposed;
- synthesis and proposals are clearly separated at the architectural level;
- the existing proposal lifecycle is preserved without modification;
- callback atomicity and idempotency are maintained;
- the Core remains the source of truth;
- the change is incremental and architecture-specific.

### Negative

- a new AI output category to maintain;
- callback contract becomes slightly more complex;
- the AI Engine must produce two distinct output structures in one call;
- Intent versioning adds a catalog entry;
- execution-scoped snapshots increase persistence volume.

### Risks

- synthesis quality depends on model interpretation of selected context;
- over-broad synthesis could overlap with proposal content;
- grounding correctness must be validated end-to-end;
- the atomic failure policy may suppress otherwise useful synthesis when an
  optional proposal remains invalid.

## Rejected Alternatives

### Reuse synthesis as a ValidatableProposal

Rejected. Synthesis describes existing knowledge; proposals propose new
knowledge. Conflating them forces human validation on answers that do not
require it and pollutes the proposal lifecycle with non-actionable items.

### Mutable synthesis with knowledge promotion

Rejected. Allowing synthesis to promote into trusted knowledge would bypass
ADR-006's governed promotion workflow and permit AI-generated interpretations
to enter the knowledge base without human validation.

### Separate callbacks for synthesis and proposals

Rejected. Two callbacks would break ADR-020's atomic transaction boundary
and introduce ordering, partial-failure, and idempotency complexity without
measurable V1 benefit.

### Generic Analysis answer framework

Rejected. The current evidence justifies an architecture-specific fix. A
generic framework would introduce premature abstraction without demonstrated
cross-Intent need.

### Partial-success persistence

Rejected for V1. Persisting synthesis while failing proposals would require
new partial-output semantics, callback partitioning, and result-projection
complexity. The conservative atomic baseline is simpler and safer.

## Relations

- ADR-006 — partially refines the scope of AI-output governance. AI-generated
  outputs whose semantic purpose is to propose creation or enrichment of
  trusted project knowledge remain `ValidatableProposal` objects and continue
  through the existing human-validation and promotion lifecycle. Execution-scoped
  Analysis Synthesis is explicitly outside that promotion category because it is
  a non-trusted, non-promotable answer artifact. The trusted-knowledge safety
  invariant established by ADR-006 remains unchanged.
- ADR-020 — extends callback contract with optional `synthesis` field;
  preserves atomic transaction boundary.
- ADR-028 — requires new Intent version `architecture-overview-v2` due to
  output schema change; existing `v1` semantics immutable.
- ADR-030 — no change; Intent execution model preserved.
- ADR-063 §29 — corrects the shorthand "AI synthesis remains an untrusted
  `ValidatableProposal`" by establishing synthesis as a separate non-trusted
  category. Does not supersede ADR-063's trust-tier model.
- ADR-064 — acknowledges relationship; ADR-064 remains `KEEP_PAUSED`. This
  ADR does not resume ADR-064's context-composition sequence.
