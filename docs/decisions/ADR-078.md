# ADR-078 - DevLog Internal Agent and External Agent Client Identity

## Status

ACCEPTED - approved by the human project owner on 2026-10-31.

## Context

DevLog has two distinct agent roles that were previously conflated at the MCP
boundary:

1. The **DevLog Agent** is an internal DevLog capability. It maintains and
   analyzes projects and executes Story Agent work through the AI Engine.
2. The **OpenCode Agent** is an external client that calls DevLog through MCP
   while helping a user work.

The default DevLog provider configuration is `openai_chatgpt` authenticated by
ChatGPT OAuth. That credential belongs to the DevLog Agent execution boundary;
ChatGPT access and refresh tokens remain owned by the AI Engine. OpenCode must
not carry or select that provider credential.

ADR-077 correctly separated a technical MCP actor from a human identity, but
made human delegation the effective path for MCP use. That is appropriate when
an external agent acts on behalf of a human, but it is not required for the
normal autonomous DevLog capability. Requiring a human delegation for every
OpenCode call makes the product unusable across multiple projects and creates
one credential or delegation setup per project in practice.

## Decision

### 1. Separate the actors

The system distinguishes:

```text
Human User
    -> OpenCode Agent (external MCP client)
    -> DevLog Core
    -> DevLog Agent (internal capability)
    -> AI Engine / ChatGPT OAuth
```

OpenCode is never interpreted as the DevLog Agent and a technical
`client_credentials` token is never interpreted as `HUMAN`.

### 2. Autonomous agent mode is the default

The normal MCP path is:

```text
OpenCode technical actor
    -> stable AI_AGENT principal
    -> Core project authorization
    -> DevLog Agent execution
```

No human delegation is required for this mode. The stable agent principal is
configured once per DevLog installation/runtime and may be authorized for many
projects. `projectSlug` selects the requested target; it never selects an
identity or credential.

Core evaluates the agent principal against project authorization before context
retrieval, Story Agent execution, snapshot reads, or provider binding issuance.

### 3. Human delegation is optional

The ADR-077 delegation model remains available only when OpenCode must act on
behalf of a human:

```text
OpenCode AI_AGENT + explicit Core grant
    -> delegated HUMAN execution context
```

Delegation is not a prerequisite for autonomous DevLog use and must not be
silently created, renewed, or inferred from conversation state.

### 4. Multi-project authorization

An OpenCode Agent uses one technical identity and one transport credential for
all authorized projects. Core may represent authorization as explicit project
memberships or as an organization/workspace policy that covers multiple
projects. No provider credential, MCP bearer, or human delegation is created
per project.

The effective authorization remains:

```text
authenticated actor
    + project policy
    + capability policy
    + task/provider policy
```

### 5. Provider ownership

The default execution provider is:

```text
provider: openai_chatgpt
authentication: OAUTH
```

The DevLog Agent's provider association is resolved by Core and represented to
the AI Engine only through the existing opaque, task-scoped
`AiCredentialBinding`. ChatGPT access tokens, refresh tokens, authorization
codes, and provider sessions remain inside the AI Engine boundary.

Human delegation may select a human-owned provider association only in the
explicit delegated mode. It must not replace the autonomous agent association
in the default flow.

### 6. Transport lifecycle

The OpenCode MCP runtime obtains and renews a short-lived technical bearer.
Bearer renewal is independent from human delegation and provider OAuth
renewal. An expired bearer fails closed; restarting a conversation is not an
identity recovery mechanism.

## Invariants

- `OpenCode Agent != DevLog Agent != Human User`.
- A technical client is classified as `AI_AGENT`, never implicitly as `HUMAN`.
- A valid transport bearer does not by itself authorize a project.
- Project authorization is evaluated by Core and is not inferred from a slug.
- One agent identity and credential boundary can serve many projects.
- Human delegation is optional and explicit.
- OpenCode never receives or stores the DevLog Agent's ChatGPT credential.
- AI Engine receives only opaque task-scoped provider bindings.
- REST, MCP, and internal callers use the same Core authorization decision.
- Autonomous and delegated modes have distinct audit and failure categories.

## Consequences

### Positive

- DevLog is usable by OpenCode without a per-call human delegation.
- A single installation can serve many projects without 50 credentials.
- Internal DevLog execution is separated from external agent consumption.
- ChatGPT OAuth remains in the existing secure AI Engine boundary.
- Human delegation remains available without defining the default product path.

### Costs

- DevLog must provision and authorize a stable agent principal.
- Existing ambiguous MCP principal data requires explicit migration or refusal.
- Runtime diagnostics must distinguish autonomous and delegated execution.
- ADR-077 and Story 0171 documentation must be reconciled to this two-mode model.

## Implementation Boundary

This ADR authorizes the implementation of the autonomous agent path and its
reconciliation with the delegated path. It does not authorize moving provider
secrets, inventing human identities, or weakening Core authorization.
