# ADR-061 — Deterministic Repository Observation Baselines

## Status

PROPOSED

## Context

DevLog AI is evolving from a documentation assistant into an engineering
context and technical-memory system used by Developer OS and engineering
agents.

For this role, repository-derived knowledge must remain auditable over time.

ADR-059 introduced the separation between:

- knowledge authority,
- temporal freshness,
- and context eligibility.

ADR-060 established that deterministic facts must remain owned by
deterministic services and that probabilistic systems must not become the
authority for facts that can be established deterministically.

Story 0083 introduced deterministic temporal assessment for Insights.

Temporal assessment compares repository evidence between:

1. the repository state originally observed by the Analysis that produced
   the Insight;
2. the current known repository state for the same Source.

This requires reliable historical provenance for repository-backed Analyses.

The investigation preceding this ADR established that the current system does
not consistently persist this provenance.

Several Analysis creation/execution paths currently exist.

### Standard Analysis path

The standard Analysis creation path does not persist a selected Source and
does not persist a target revision.

When no selected Source exists, repository collection operates over all active
Sources of the Project.

This means the Analysis may observe several independent repositories.

A single:

    Analysis.targetRevision

cannot correctly represent such an observation.

### Project Understanding path

Project Understanding is source-scoped.

Repository synchronization resolves the exact immutable Git revision actually
observed by the workspace.

However, the Analysis currently persists the caller-provided target revision
rather than the resolved revision.

If the caller does not specify a revision, the Analysis may therefore persist
a null targetRevision even though the repository was successfully observed at
a known immutable revision.

### Engineering Event path

Engineering Event execution already demonstrates stronger semantics.

The requested commit is:

1. explicitly provided;
2. resolved by repository synchronization;
3. verified against the workspace resolved revision;
4. persisted as the Analysis targetRevision.

This establishes an existing precedent for deterministic repository
provenance.

### Repository observation

GitWorkspaceManager synchronizes a Source and resolves the repository to an
immutable Git commit.

The workspace is then checked out in detached mode and reset to that exact
revision.

The resulting:

    SynchronizedWorkspace.resolvedRevision

therefore represents the exact repository state observed by collectors.

KnowledgeCollectionService already receives this information and records
resolved revisions in diagnostic information.

The missing architectural concept is not revision discovery.

The system already knows the revision.

The missing concept is the explicit treatment of:

    Source + observed revision

as repository observation provenance.

## Problem

DevLog must be able to answer deterministically:

> Which exact repository state was observed when this knowledge was produced?

Without this guarantee, temporal reasoning can become misleading.

In particular, the system must never infer repository provenance from:

- the latest ProjectCommit;
- the current repository HEAD;
- timestamps;
- commit chronology;
- evidence similarity;
- AI interpretation;
- or another repository state that merely appears likely.

A revision that was not actually observed must never be recorded as if it had
been observed.

At the same time, the current Analysis model supports two fundamentally
different observation cardinalities:

### Single-source Analysis

A single Source is observed at one immutable revision.

Conceptually:

    Analysis
        |
        +-- Source A
        |
        +-- Revision abc123

This can be represented by the existing:

    selectedSource
    targetRevision

fields.

### Multi-source Analysis

Several Sources may be observed by one Analysis.

Conceptually:

    Analysis
        |
        +-- Source A @ abc123
        |
        +-- Source B @ def456
        |
        +-- Source C @ ghi789

A single targetRevision cannot represent this state correctly.

Forcing one revision into Analysis.targetRevision would destroy provenance
rather than improve it.

The architecture therefore needs explicit semantics for both cases.

## Decision

DevLog will introduce the architectural concept of a:

    Repository Observation Baseline

A Repository Observation Baseline identifies the immutable repository state
actually observed during repository-derived analysis.

Repository observation provenance is deterministic infrastructure/domain
information.

It MUST NOT be inferred probabilistically.

### 1. Baseline identity

The fundamental identity of a repository observation is:

    Source + immutable Git revision

Neither element is meaningful as temporal provenance without the other.

A revision MUST always be interpreted in the context of its Source.

Therefore:

    (Source, Revision)

forms one logical baseline identity.

### 2. Source and revision must describe the same observation

The persisted revision MUST correspond to the repository state actually
observed for the associated Source.

The authoritative revision is the revision produced by repository
synchronization and used by repository collectors.

In the current Git implementation this is:

    SynchronizedWorkspace.resolvedRevision

The following MUST NOT be used as substitutes unless independently proven to
be the exact observed revision:

- current HEAD;
- remote HEAD;
- latest persisted ProjectCommit;
- caller-provided branch name;
- timestamps;
- commit ordering;
- repository state observed at another time.

### 3. Single-source repository analyses

For a repository-backed Analysis that observes exactly one Source, the
existing fields are sufficient for V1:

    Analysis.selectedSource
    Analysis.targetRevision

They represent one Repository Observation Baseline.

For such an Analysis:

    selectedSource != null
    targetRevision != null

must hold once repository observation has successfully occurred.

The targetRevision MUST contain the exact immutable revision actually observed
for selectedSource.

### 4. Multi-source repository analyses

An Analysis that observes several Sources has several independent Repository
Observation Baselines.

Conceptually:

    Analysis
        |
        +-- ObservationBaseline(Source A, Revision A)
        +-- ObservationBaseline(Source B, Revision B)
        +-- ObservationBaseline(Source C, Revision C)

Analysis.targetRevision MUST NOT be overloaded to represent this state.

DevLog MUST NOT:

- select an arbitrary Source;
- persist the first observed revision;
- persist the last observed revision;
- persist the latest ProjectCommit;
- or collapse several Source/revision pairs into one targetRevision.

The current resolved-revisions diagnostic demonstrates that the runtime
already observes these Source/revision pairs.

However, this ADR does NOT require introducing a persisted multi-source
baseline entity immediately.

Multi-source persistence will be handled separately when required.

### 5. Hybrid V1 model

DevLog therefore adopts a hybrid approach.

#### Source-scoped Analysis

Use:

    selectedSource + targetRevision

as the persisted Repository Observation Baseline.

This model is immediately usable by deterministic temporal assessment.

#### Project-wide / multi-source Analysis

Do not fabricate a single baseline.

Existing multi-source execution may continue where required, but its
repository provenance MUST be treated as multi-source.

Such an Analysis MUST NOT be considered compatible with single-source
temporal assessment merely because Analysis.targetRevision could technically
store a String.

A future story may promote the existing runtime Source/revision observations
into an explicit persisted multi-source provenance model.

### 6. Observation time vs Analysis creation time

Repository provenance becomes authoritative when the repository state is
actually resolved for observation.

Analysis creation time is not necessarily repository observation time.

Therefore the architecture does NOT require targetRevision to be guessed or
resolved before an Analysis object can exist.

A temporary Analysis lifecycle state may exist before repository observation.

However, once repository-backed analysis successfully observes a Source, the
exact resolved revision must become its provenance before repository-derived
knowledge can be considered fully attributable to that Analysis.

The important invariant is:

    persisted provenance == actually observed repository state

not:

    provenance must always exist at initial object construction.

### 7. Immutability

Once captured, a Repository Observation Baseline is immutable historical
provenance.

Changing the baseline would change the meaning of the Analysis itself.

A new repository observation therefore requires a new Analysis or new
observation record rather than mutation of historical provenance.

Analysis.targetRevision remaining non-updatable is consistent with this
principle.

### 8. Failure semantics

Repository provenance MUST fail closed.

If DevLog cannot determine the repository revision actually being observed,
it MUST NOT invent one.

Failures such as:

- repository unavailable;
- synchronization failure;
- invalid revision;
- Git command failure;
- Source mismatch;
- unresolved repository state;

must result in an explicit inability to establish provenance.

They MUST NOT result in a guessed targetRevision.

For new source-scoped repository analyses, successful production of
repository-derived trusted knowledge requires a valid Repository Observation
Baseline.

The exact lifecycle behavior — FAILED, pending, retryable, or rejected — may
be defined by the implementation story according to the existing Analysis
workflow.

### 9. Legacy knowledge

Existing Analyses with:

    targetRevision = null

will not be retroactively repaired unless deterministic provenance can be
proven.

Current investigation shows that the existing legacy revision cannot be
reconstructed safely from timestamps or repository history alone.

Therefore legacy Analyses remain:

    targetRevision = null

and temporal assessment may legitimately classify knowledge derived from them
as:

    UNKNOWN

This is preferable to fabricated provenance.

No migration timestamp, capability version, or artificial historical revision
is required merely to distinguish legacy knowledge.

The presence or absence of deterministic provenance is itself meaningful.

### 10. ProjectCommit semantics

ProjectCommit represents persisted Git history and current-known repository
information.

It does not automatically represent the repository state observed by a
historical Analysis.

Therefore:

    latest ProjectCommit != Analysis baseline

unless an independent invariant proves that they refer to the same
observation.

ProjectCommit may continue to provide currentKnownRevision for temporal
comparison.

It MUST NOT be used to manufacture historical targetRevision values.

### 11. AI boundary

Repository observation provenance is fully deterministic.

AI MUST NOT:

- select targetRevision;
- infer a missing revision;
- choose between candidate commits;
- repair legacy provenance;
- decide which Source/revision pair was probably observed.

AI may explain existing provenance or uncertainty.

It may not create provenance authority.

### 12. Trusted knowledge boundary

Repository-derived trusted knowledge should ultimately be attributable to a
known repository observation.

For new source-scoped repository analyses:

    known Source
        +
    known observed revision

is therefore a prerequisite for strong repository provenance.

This ADR establishes the invariant.

The exact enforcement point in proposal promotion or Analysis lifecycle may
be introduced incrementally through dedicated stories.

This ADR does not modify ADR-006 proposal validation semantics.

## Consequences

### Positive

- Temporal assessment gains a trustworthy historical baseline.
- Repository provenance becomes deterministic and auditable.
- Agents can explain which exact repository revision knowledge came from.
- Story 0083 can operate correctly for newly generated source-scoped
  knowledge.
- Legacy uncertainty remains explicit instead of being hidden.
- Multi-source analyses are not forced into an incorrect single-revision
  representation.
- Existing Git synchronization already provides the required deterministic
  fact.
- No AI inference is required for baseline capture.
- The design remains compatible with future lineage, retrieval and RAG
  capabilities.

### Negative

- Source-scoped and project-wide Analyses cannot share identical temporal
  semantics without additional modelling.
- Some existing Analysis creation paths require correction.
- Multi-source repository provenance may eventually require a dedicated
  persisted model.
- Legacy knowledge may remain UNKNOWN indefinitely.
- targetRevision alone cannot solve provenance for project-wide analyses.

### Accepted trade-off

DevLog prefers explicit incomplete provenance over fabricated complete
provenance.

UNKNOWN is an acceptable representation of missing historical knowledge.

Incorrect provenance is not.

## Alternatives Considered

### Alternative A — Use latest ProjectCommit as targetRevision

Rejected.

The latest known commit represents current repository knowledge, not
necessarily the state observed by the Analysis.

This would conflate current state with historical provenance.

### Alternative B — Use timestamps to reconstruct historical revision

Rejected.

Database timestamps and Git commit timestamps represent different clocks and
different events.

Temporal proximity does not prove repository observation.

### Alternative C — Persist caller-provided targetRevision directly

Rejected as a general rule.

A requested revision is not sufficient provenance unless repository
synchronization proves that the requested revision is the revision actually
observed.

Engineering Event execution already demonstrates the correct verification
pattern.

### Alternative D — Use local or remote HEAD

Rejected.

HEAD is mutable context.

Historical provenance requires an immutable commit identifier corresponding
to the observed state.

### Alternative E — Force all Analyses to be single-source immediately

Rejected for now.

Existing standard Analysis behavior supports project-wide collection over
multiple Sources.

Changing this would alter broader Analysis semantics and exceed the scope of
temporal baseline capture.

### Alternative F — Introduce a persisted RepositoryObservation entity now

Deferred.

A dedicated model may eventually be appropriate, particularly for
multi-source Analyses, lineage and retrieval.

For V1, selectedSource + targetRevision already represent single-source
baselines adequately.

Introducing additional persistence before it is required would increase
complexity without improving the immediate temporal-assessment path.

### Alternative G — Infer legacy baselines using AI

Rejected.

Repository provenance is deterministic factual information.

Probabilistic reconstruction cannot become historical authority.

## Implementation Guidance

This ADR does not prescribe an exact implementation.

The first implementation story should remain narrowly focused on
source-scoped Analysis paths.

It should investigate and correct paths where:

    workspace.resolvedRevision()

is already known but is not persisted as the corresponding Analysis
targetRevision.

The implementation MUST verify that the persisted Source and revision belong
to the same repository observation.

The implementation MUST NOT attempt to solve multi-source persistence by
writing an arbitrary revision into Analysis.targetRevision.

The standard multi-source Analysis path should either remain outside the first
implementation slice or receive a separately designed provenance model.

The implementation should reuse the existing synchronization result rather
than introducing another independent revision-resolution mechanism.

No AI component is required.

No legacy backfill is required.

## Follow-up Work

Expected follow-up work includes:

1. Implement deterministic baseline capture for new source-scoped Analyses.
2. Verify Story 0083 against newly generated knowledge with valid baselines.
3. Decide whether project-wide multi-source Analyses require a persisted
   Repository Observation model.
4. Address Insights with empty evidenceReferences independently.
5. Implement Current Engineering Context temporal eligibility policy
   (Story 0084) after baseline capture is operational.
6. Later expose repository provenance to lineage, retrieval and agent context
   where useful.

## Invariants

The following invariants are mandatory:

1. Repository provenance is deterministic.
2. AI never chooses repository provenance.
3. A repository baseline is identified by Source + immutable revision.
4. The persisted revision must be the revision actually observed.
5. Caller intent is not equivalent to observed repository state.
6. Latest ProjectCommit is not automatically historical provenance.
7. Single-source and multi-source observations must not be conflated.
8. Multi-source provenance must never be collapsed into an arbitrary
   targetRevision.
9. Historical provenance is immutable.
10. Missing provenance remains explicit.
11. Legacy provenance is never fabricated.
12. Repository-state verification failure never becomes false certainty.
13. Trusted repository-derived knowledge should ultimately be attributable to
    deterministic repository provenance.
14. Probabilistic systems may explain provenance but may not establish it.

## Decision Summary

DevLog adopts deterministic Repository Observation Baselines.

The atomic identity of an observation baseline is:

    Source + immutable observed Git revision

For source-scoped Analyses, the existing:

    selectedSource + targetRevision

fields represent this baseline.

The authoritative revision is the immutable revision actually resolved and
observed by repository synchronization, currently exposed as:

    SynchronizedWorkspace.resolvedRevision()

Project-wide Analyses may observe multiple Source/revision pairs and therefore
cannot be represented safely by a single targetRevision.

DevLog will not fabricate such a baseline.

Legacy Analyses without deterministic provenance remain UNKNOWN.

Repository provenance is a deterministic fact and is never chosen or inferred
by AI.
