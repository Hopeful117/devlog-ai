# ADR-068 - Typed AI-Facing References and Grounding Namespace Isolation

## Status

Accepted

## Date

2026-09-14

## Context

DevLog exposes deterministic project context to AI components for structured
interpretation. The Java Core constructs and authorizes that context, while the
AI Engine interprets it and returns structured output. This boundary is defined
by ADR-006, ADR-060, ADR-063, ADR-064, ADR-065 and ADR-067.

The current Analysis projection exposes several entity namespaces using raw
UUID-shaped values. Facts, Observations, Insights, Analysis and Project
identities, profile identities, semantic-section item identifiers, relationship
endpoints and repository evidence references can therefore appear in the same
AI-facing prompt without one universal identity contract.

The relevant implementation path is:

```text
domain entities
    -> AnalysisContext / SelectedKnowledge
    -> SelectedKnowledgePromptProjectionService
    -> AiTask selectedKnowledgeSnapshot
    -> PromptRequest
    -> AI Engine prompt builder
    -> structured model output
    -> Python validation
    -> Java Core validation and domain lookup
```

The current implementation is concrete evidence of this shape:

- `SelectedKnowledge` contains Facts, Observations, Insights, profile data,
  events, human context, relationships and repository context.
- `SemanticSectionComposer` projects Facts, Observations, Insights and other
  entities as `itemType` plus `itemId`.
- `SelectedKnowledgePromptProjectionService` projects relationship endpoints as
  `entityType` plus `entityId`, but the entity identifier remains a raw value.
- `InsightPromptBuilder` constructs separate allow-lists for Fact IDs,
  Observation IDs and evidence references.
- `InsightGenerationService` performs Python-side subset validation.
- `AiProposalContractValidator` performs Core-side contract validation.
- `AiTaskResultServiceImpl` verifies that resolved Fact and Observation IDs
  exist and belong to the task Analysis before proposal persistence.

Story 0126 and its persisted interaction traces made it possible to reproduce a
real-provider failure in which the model emitted an Insight identity in a
grounding-specific field. The identity was visible in the prompt and was not a
newly hallucinated value. The confirmed failure classes are:

```text
CROSS_NAMESPACE_IDENTITY_AMBIGUITY
PROMPT_GROUNDING_CONTRACT_AMBIGUITY
SEMANTIC_SECTION_IDENTITY_LEAK
RETRY_CONTEXT_AMPLIFICATION
```

The investigation did not establish `TRUE_LLM_ID_HALLUCINATION`. The problem is
therefore not solved by weakening validation or by removing useful semantic
context. It requires an explicit identity contract at the Core-to-AI boundary.

ADR-063 already establishes the architectural requirement that citable elements
have one canonical, unambiguous reference and that visible-but-non-citable
elements are distinguishable from citable elements. This ADR specializes that
requirement for AI-facing contexts and grounding outputs.

## Problem

The current contract relies on field names and surrounding JSON structure to
communicate namespace semantics. The identifiers themselves do not communicate
their namespace. A model can therefore copy a valid visible identifier into a
field for which that identifier is not authorized.

This creates an avoidable distinction between:

```text
visible identity
```

and:

```text
identity valid for this output field
```

The Core correctly rejects invalid grounding output, but the contract gives the
model insufficiently explicit identity boundaries before generation. Corrective
retries can amplify the problem when validation messages and candidate blocks
repeat additional raw identifiers.

The architectural question is:

> What identity contract should DevLog use when projecting engineering context
> to AI components so that semantic context remains rich, grounding namespaces
> remain isolated, Core retains identity authority, and future retrieval and
> relationship projections can use the same reference semantics?

## Decision

DevLog adopts a **Core-owned structured AI reference abstraction** for
AI-facing context and structured output.

An AI reference explicitly contains:

```text
type   = entity namespace
ref    = opaque reference token
scope  = identity scope
```

Conceptually:

```json
{
  "type": "FACT",
  "ref": "F12",
  "scope": "ANALYSIS_CONTEXT"
}
```

The exact Java record, Python model and serialized field names are implementation
details for a future Engineering Story. This ADR decides the semantics and
authority boundary, not the concrete DTO classes.

### 1. Reference namespaces are explicit

Every AI-facing citable reference MUST identify its namespace. At minimum, the
architecture must distinguish:

- `FACT`;
- `OBSERVATION`;
- `INSIGHT`;
- `ANALYSIS`;
- `PROJECT`;
- `PROJECT_PROFILE`;
- `HUMAN_CONTEXT`;
- `REPOSITORY_EVIDENCE`;
- relationship endpoint entities;
- future citable Story, Decision, ADR and roadmap entities.

Bare UUIDs MUST NOT be used as the sole AI-facing identity of a citable entity.

An AI-facing reference identifies a projected context item. It does not grant
authority to the AI component and it is not itself a trusted domain object.

### 2. Reference scope is explicit

The reference scope distinguishes identity that is valid only for one projected
context from identity that is stable within a project or external source.

Analysis-local entities SHOULD use opaque context-local references, including:

- Facts;
- Observations;
- Analysis records;
- Analysis-associated project profiles.

Project-scoped or externally retrievable entities MAY use typed stable
references, including:

- Insights;
- Decisions;
- Engineering Events;
- Human Context inputs;
- Projects;
- repository evidence.

The use of a stable reference does not make AI output authoritative. It only
allows deterministic identification and future expansion within its declared
scope.

### 3. Core owns reference creation and resolution

Java/Core remains the sole authority for AI reference creation, scope, mapping,
resolution and acceptance.

The Core MUST be able to determine for every AI reference:

```text
reference exists
reference namespace is valid
reference scope is valid
reference belongs to the current task/context
reference is allowed for the output field
reference maps to exactly one domain entity
mapped entity belongs to the required project/Analysis scope
```

The AI Engine MUST NOT resolve AI references through direct database access,
repository access or an independently maintained identity registry. It may
perform defensive structural and subset validation, but Core validation remains
authoritative.

### 4. Context-local references are deterministic and auditable

Context-local references MUST be generated deterministically from the Core
projection ordering and MUST be scoped to the originating AI task/context.

The mapping from an AI reference to its domain identity MUST be retained at the
execution boundary sufficiently to reconstruct:

```text
AI reference
    -> projected context item
    -> domain identity
    -> model output
    -> validation result
```

The mapping is execution metadata, not trusted project knowledge. It MUST NOT be
used as a second domain identity system or as a source of cross-analysis truth.

### 5. Grounding candidates are structurally isolated

AI-facing context MUST distinguish semantic context from authorized grounding
candidates.

The conceptual shape is:

```text
CONTEXT
  project
  analysis
  projectProfile
  insights
  humanContext
  semanticSections
  relationships
  repositoryContext

GROUNDING_CANDIDATES
  facts
  observations
  evidence
```

Grounding candidate collections MUST contain typed AI references. Output fields
MUST accept only references from the corresponding authorized candidate set.

An Insight MAY remain fully visible and semantically useful in context, including
inside multiple semantic sections, but visibility MUST NOT authorize it as a
Fact or Observation grounding reference.

Semantic sections are indexes or perspectives over canonical context. Their
membership MUST NOT independently authorize grounding.

### 6. Output references use the same identity abstraction

Grounding output MUST use the same typed reference semantics as input context.

The implementation may choose names such as:

```text
supportingFactRefs
supportingObservationRefs
evidenceRefs
```

or an equivalent unified reference field. The current `*Ids` names and raw-ID
semantics MUST NOT be extended as the long-term contract.

The output contract MUST be versioned under the existing Intent versioning
rules. Existing persisted proposals remain domain records and do not need to
adopt the AI-facing representation when the Core resolves references before
persistence.

### 7. Relationships use the same reference abstraction

Relationship endpoints MUST use the same AI reference model as grounding and
semantic sections. Relationship semantics and identity are separate concerns:

- the reference identifies the endpoint;
- `relationType` describes the relationship category;
- confidence does not promote an inferred relationship to an explicit one.

This preserves ADR-067 D8. The identity contract applies equally to explicit
knowledge relations, temporal relationships, possible relevance and AI
hypotheses.

### 8. Retrieval compatibility is preserved

This ADR does not introduce Retrieval, vector infrastructure or a ContextPack.

Future retrieval projections MUST be able to expose candidates through the same
AI reference abstraction. A retrieval layer remains a reconstructible projection
and candidate source, not a source of domain truth.

Canonical references may carry stable project/source/revision semantics for
retrieval and expansion. Context-local AI handles may be used when a bounded
projection needs to hide persistence-local identity. Both are represented by the
same typed abstraction with explicit scope.

Expansion MUST resolve through Core-owned canonical references and preserve the
same trust, provenance and revision metadata as the initial context.

### 9. Retry correction preserves namespace isolation

Provider-facing corrective retries SHOULD describe namespace and authorization
failures semantically rather than repeating an invalid raw identifier when the
identifier is not needed for correction.

Human-facing diagnostic traces MAY retain the exact invalid reference,
classification and mapping result. Provider correction text and persisted
diagnostic data are separate concerns.

Retry context MUST use the same typed reference contract as the initial context.
Retries MUST NOT broaden the authorized grounding candidate set or introduce a
second identity syntax.

## Architectural Invariants

1. **AI_REF_NAMESPACE_EXPLICIT** — Every AI-facing citable reference has an
   explicit namespace/type.
2. **AI_REF_SCOPE_EXPLICIT** — Every AI-facing reference declares whether its
   identity is context-local or stable within a declared project/source scope.
3. **DOMAIN_IDENTITY_AUTHORITY_REMAINS_IN_CORE** — Java/Core owns creation,
   mapping, resolution and authoritative validation.
4. **GROUNDING_REFERENCES_MUST_BELONG_TO_ALLOWED_CONTEXT_SET** — A reference is
   valid for an output field only when Core authorizes it for that task and
   field.
5. **CONTEXTUAL_ENTITIES_CANNOT_BECOME_GROUNDING_BY_IDENTIFIER_REUSE** —
   Visibility in context or semantic sections never grants grounding permission.
6. **AI_REFERENCES_MAP_DETERMINISTICALLY** — Each accepted reference maps to one
   and only one domain entity within the declared scope.
7. **AI_REFERENCES_ARE_VALIDATED_BEFORE_DOMAIN_USE** — No AI reference reaches
   proposal persistence or another domain operation before Core resolution and
   validation.
8. **SEMANTIC_CONTEXT_REMAINS_AVAILABLE** — Useful contextual entities are not
   removed solely because they are not valid grounding sources.
9. **RELATIONSHIP_IDENTITY_IS_SHARED** — Relationship endpoints, semantic
   section items, grounding candidates and retrieval candidates use one typed
   reference abstraction.
10. **RETRIEVAL_COMPATIBILITY_PRESERVED** — Future retrieval projections may
    evolve independently but must remain compatible with the reference
    abstraction and Core authority boundary.
11. **TRUST_IS_NOT_GRANTED_BY_REFERENCE_VALIDITY** — A valid reference identifies
    evidence; it does not make AI output trusted knowledge.
12. **RETRY_DOES_NOT_BROADEN_AUTHORITY** — Corrective retries preserve context,
    namespace and grounding boundaries.

## Failure Semantics

The implementation MUST expose deterministic classifications equivalent to:

| Failure | Meaning |
|---|---|
| `UNKNOWN_AI_REFERENCE` | No reference with the supplied value exists in the task mapping. |
| `REFERENCE_NAMESPACE_MISMATCH` | The reference exists but its type does not match the output field. |
| `REFERENCE_SCOPE_MISMATCH` | The reference belongs to a different identity scope. |
| `REFERENCE_NOT_ALLOWED_FOR_GROUNDING` | The reference is contextual or otherwise not authorized for grounding. |
| `REFERENCE_OUTSIDE_CONTEXT` | The reference is valid elsewhere but not in this task/context. |
| `REFERENCE_MAPPING_FAILURE` | Core cannot resolve the reference to exactly one domain entity. |

The exact exception class and transport representation are implementation-level
decisions. The failure must remain a hard validation failure; confidence,
prompt wording or retry success cannot substitute for resolution.

## Migration Direction

Implementation Stories must preserve a coherent contract at each deployed
boundary. The intended sequence is:

1. Introduce the Core-owned AI reference abstraction and deterministic mapping.
2. Project typed references through context, semantic sections and relationships.
3. Add structurally isolated grounding candidate collections.
4. Version the AI output contract and migrate Python schemas and prompt builders.
5. Resolve references in Core before proposal persistence and retain mapping
   metadata for traceability.
6. Update corrective retries and diagnostic classifications.
7. Remove legacy raw-ID grounding acceptance after supported producers and
   consumers use the new contract.

Existing persisted proposals remain domain records. Historical AI task snapshots
may require compatibility handling, but the implementation must not silently
reinterpret historical raw identifiers under a new namespace.

## Testing Obligations

The implementation MUST include deterministic tests for:

- Fact reference to Fact UUID resolution;
- Observation reference to Observation UUID resolution;
- Insight reference to Insight UUID resolution;
- unknown reference rejection;
- Insight reference submitted as Fact grounding rejection;
- Observation reference submitted as Fact grounding rejection;
- Fact reference submitted as Observation grounding rejection;
- valid reference from another AnalysisContext rejection;
- semantic-section repetition not granting grounding permission;
- relationship endpoint namespace preservation;
- retry preservation of the typed reference contract.

Existing test areas include:

- `SelectedKnowledgePromptProjectionServiceTest`;
- `SemanticSectionComposerTest`;
- `AiProposalContractValidatorTest`;
- `AiTaskResultControllerTest`;
- `ai-engine/tests/test_prompt_builder.py`;
- `ai-engine/tests/test_insight_generation_service.py`;
- `ai-engine/tests/test_retry.py`.

Repeated real-provider execution may provide regression evidence, but provider
success is not the architectural correctness criterion. Core mapping and
namespace tests MUST prove the invariant independently of model behavior.

## Consequences

### Positive

- Cross-namespace identity reuse becomes deterministically rejectable before
  domain use.
- Useful Insight and relationship context remains available to the AI.
- Analysis-local persistence UUIDs are no longer required as the AI-facing
  identity representation.
- Grounding, semantic sections, relationships and future retrieval projections
  share one identity abstraction.
- Story 0126 traceability can reconstruct identity mapping and validation.
- Core authority and existing trust boundaries remain unchanged.

### Negative

- AI-facing context and output contracts require versioned migration.
- Core must retain an execution-scoped mapping for context-local references.
- Python and Java validation contracts must evolve together.
- Historical task snapshots require explicit compatibility handling.
- Structured references may consume more serialized space than a single UUID,
  although context-local handles may reduce repeated identity token cost.

## Alternatives Considered

### Option A - Typed stable references

Use values such as `fact:<uuid>` and `insight:<uuid>`.

This improves namespace safety and direct debugging, but continues exposing
persistence identity and Analysis-local volatility to the model. It is not the
long-term contract by itself.

### Option B - Typed context-local handles

Use values such as `fact:F12` and `insight:I07` with Core-owned mapping.

This provides strong isolation and lower token cost, but a string-only contract
does not sufficiently express scope and is less extensible for relationships
and future retrieval.

### Option C - Structured typed references

Use structured values containing type, opaque reference and scope.

This is selected because namespace and scope become schema-level properties,
Core can validate them deterministically, and the same abstraction can support
context-local handles and stable retrieval references.

### Remove non-grounding context

Rejected. Insights, relationships and semantic sections provide useful project
understanding and are not invalid merely because they are not grounding
sources. Removing them would reduce context quality instead of fixing identity
authority.

### Rely on prompt wording and existing field names

Rejected. The reproduced failure occurred despite field-level grounding
contracts and strict validation. Prompt wording is supplemental guidance, not a
namespace guarantee.

### Let the AI Engine resolve domain identities

Rejected. This would violate ADR-006, ADR-060 and ADR-067 by moving identity and
domain authority outside Java/Core.

## Scope Boundary

This ADR decides:

- AI-facing reference semantics;
- namespace and scope requirements;
- Core-owned mapping and validation authority;
- grounding candidate isolation;
- shared identity semantics for relationships and future retrieval projections;
- output contract versioning direction;
- retry and traceability constraints related to identity.

This ADR does not decide or implement:

- Retrieval ranking, vector search or embeddings;
- a generic ContextPack;
- provider selection or provider-specific behavior;
- general retry policy;
- a complete trace observability redesign;
- trust promotion or proposal lifecycle changes;
- exact Java class names;
- exact Python class names;
- exact DTO field names;
- database schema details;
- the first Engineering Story.

## Implementation Boundary

This ADR does not authorize production implementation or create an Engineering
Story. A future, separately authorized Story must derive its acceptance criteria
from this decision and preserve all invariants above.

The implementation Story must determine the smallest repository-consistent
representation for:

- the Core reference abstraction;
- deterministic context-local handle generation;
- execution-scoped mapping persistence;
- versioned Java/Python contracts;
- Core resolution and validation;
- retry correction and trace metadata.

The implementation must not introduce Retrieval infrastructure, modify unrelated
AI behavior, weaken existing grounding validation or remove useful semantic
context.
