# ADR-048 — Project Knowledge Artifact Generation

## Status

Accepted

## Date

2026-08-12

## Context

DevLog AI was initially conceived partly as a system capable of analyzing repository activity and generating documentation, particularly Markdown content that could later be used for portfolio and blog articles.

The project has since evolved significantly.

DevLog is no longer primarily a documentation generator.

It now acts as a living technical memory capable of progressively building and maintaining structured project knowledge from sources such as:

* repository history;
* commits and code changes;
* Engineering Stories;
* ADRs;
* engineering events;
* knowledge events;
* decisions;
* milestones;
* analyses;
* validated proposals;
* relationships between engineering entities.

This knowledge is increasingly consumed through two main projections:

* human-facing project views;
* structured context for AI agents.

Document generation remains valuable, but its role must now be reconsidered in this architecture.

Rather than treating generated documents as the primary output of DevLog, generated artifacts should become another way of projecting trusted project knowledge for a specific purpose and audience.

## Decision

DevLog will support, in a future phase, a **Project Knowledge Artifact Generation** capability.

This capability will transform trusted project knowledge into human-consumable artifacts without making those artifacts a new source of project truth.

Conceptually:

Trusted Project Knowledge
→ Context Selection
→ Content Intelligence
→ Presentation Intelligence
→ Rendering
→ Validation
→ Knowledge Artifact

Generated artifacts are projections of project knowledge.

They do not replace the underlying knowledge.

### 1. Knowledge Remains the Source of Truth

Generated documents, presentations and other artifacts must not become independent authoritative representations of project state.

The authoritative information remains in the relevant project domains:

* Engineering Stories;
* ADRs;
* decisions;
* milestones;
* Engineering Events;
* Knowledge Events;
* repository history;
* validated knowledge;
* relationships;
* other trusted project entities.

Artifacts consume these sources.

They do not redefine them.

Conceptually:

Source Knowledge
→ Artifact

not:

Artifact
→ Source Knowledge

Changes made manually to an exported artifact must not silently mutate trusted project knowledge.

### 2. Artifact Lifecycle and Generation Strategy Are Independent

Two separate dimensions must be modeled conceptually.

#### Lifecycle

An artifact may represent either:

##### Snapshot

A snapshot represents project knowledge at a particular moment for a particular purpose.

Examples:

* onboarding document generated for a new contributor;
* blog article draft;
* technical audit;
* project case study;
* release retrospective;
* architecture presentation;
* recruitment presentation.

A snapshot remains historically valid as a representation of the knowledge available at generation time.

It is not automatically rewritten when the project evolves.

A future request produces a new snapshot.

##### Living

A living artifact represents the current state of an evolving body of project knowledge.

Examples may include:

* current architecture overview;
* developer guide;
* current technical documentation;
* current component overview;
* project engineering handbook;
* API overview.

A living artifact has a stable conceptual identity but may evolve through multiple versions.

### 3. Living Artifacts Are Knowledge-Driven

Living artifacts should not primarily rely on arbitrary periodic regeneration.

Prefer:

Knowledge Change
→ Impact Detection
→ Artifact Freshness Evaluation

over:

Scheduled Time
→ Regenerate Everything

When knowledge relevant to a living artifact changes, the system should eventually be capable of determining that the artifact may no longer represent the current project state.

Conceptually:

Relevant Knowledge Changed
→ Living Artifact
→ STALE

The exact freshness model and lifecycle states will be defined during implementation design.

This ADR intentionally does not prescribe the final status enum.

### 4. Artifacts Must Preserve Source Relationships

Where practical, generated artifacts should retain relationships to the project knowledge used to produce them.

Potential sources include:

* ADRs;
* Engineering Stories;
* commits;
* decisions;
* components;
* Engineering Events;
* Knowledge Events;
* milestones;
* validated knowledge.

This enables future capabilities such as:

* traceability;
* regeneration;
* freshness detection;
* explanation of artifact provenance;
* impact analysis.

The exact persistence model will be defined separately.

### 5. Deterministic Facts and AI Presentation Are Separate Concerns

The use of AI is not determined by whether an artifact is Snapshot or Living.

A living artifact may require substantial AI generation.

A snapshot may be almost entirely deterministic.

The generation pipeline should distinguish between:

#### Trusted factual input

Obtained from deterministic project knowledge.

#### Content intelligence

Potential AI responsibilities include:

* selecting relevant information;
* synthesis;
* explanation;
* narrative construction;
* audience adaptation;
* information hierarchy.

#### Presentation intelligence

Potential AI responsibilities include:

* document structure;
* slide composition;
* visual hierarchy;
* diagram selection;
* layout recommendations;
* visual storytelling;
* presentation adaptation.

#### Rendering

Deterministic tooling should produce the final technical artifact whenever practical.

Examples may include:

* Markdown;
* HTML;
* PDF;
* DOCX;
* PPTX;
* diagrams;
* other supported formats.

AI may strongly influence content and presentation without becoming the source of factual project state.

### 6. High-Quality Presentation Is a First-Class Goal

Generated artifacts are not limited to internal technical documentation.

Some artifacts may have significant external value.

Examples include:

* portfolio case studies;
* blog articles;
* architecture presentations;
* technical presentations;
* recruitment material;
* client-facing technical reports;
* professional project documentation.

For these artifacts, visual quality, narrative quality and audience adaptation are legitimate product requirements.

The system should therefore not assume that artifact generation consists only of converting structured data into plain Markdown.

### 7. Audience and Purpose Influence Generation

Artifact generation should be driven by explicit intent.

The same project knowledge may need very different representations depending on the audience.

Potential audiences include:

* project engineer;
* engineering team;
* new contributor;
* technical management;
* recruiter;
* client;
* public audience.

For example:

Trusted Project Knowledge
→ Engineering Audience
→ Detailed Architecture Report

Trusted Project Knowledge
→ Recruiter
→ Project Case Study

Trusted Project Knowledge
→ Public Audience
→ Blog Article

The underlying facts remain consistent.

The selection, explanation, depth and presentation may change.

### 8. AI-Generated Artifacts Are Proposals Until Validated

Artifacts involving AI-generated content must follow the existing Human + AI engineering principles.

Conceptually:

Trusted Knowledge
→ AI Generation
→ Artifact Proposal
→ Human Review
→ Accepted Artifact

AI-generated content must not automatically become trusted project knowledge.

The system should preserve the distinction between:

* trusted source knowledge;
* generated interpretation;
* accepted artifact.

This follows the existing proposal and validation philosophy already used by DevLog.

### 9. Automatic Generation Must Be Risk-Aware

Automation level may depend on artifact characteristics.

A deterministic internal status report may potentially be regenerated automatically.

An AI-generated public blog article should not automatically replace published content.

Conceptually:

Low-risk deterministic artifact
→ Automatic regeneration may be allowed

High-value AI-generated artifact
→ Proposal
→ Human review

Automation policies will be defined separately.

### 10. Published Content Has Its Own Source of Truth

External systems may own the final published version of an artifact.

For example:

DevLog
→ Blog Article Proposal
→ Human Editing
→ Portfolio Publication

The published Portfolio article belongs to the Portfolio domain.

DevLog may preserve:

* generation intent;
* source knowledge;
* generated proposal;
* relationships;
* resulting artifact reference.

It should not silently assume ownership of content managed by another system.

### 11. Artifact Generation Must Support Multiple Output Types

The capability should not be designed specifically around Markdown.

Potential output families include:

#### Documents

* Markdown;
* HTML;
* PDF;
* DOCX.

#### Presentations

* PPTX;
* presentation-oriented PDF.

#### Visual artifacts

* diagrams;
* architecture visualizations;
* other project communication assets.

The architecture should allow new renderers without redefining the trusted knowledge model.

### 12. Rendering Is Separate From Knowledge and Content Generation

The system should avoid coupling project knowledge directly to a specific rendering technology.

Prefer:

Project Knowledge
→ Artifact Model
→ Renderer

rather than:

Project Knowledge
→ PDF-specific implementation

This separation allows the same generated content to potentially support several output formats.

### 13. Existing DevLog Concepts Must Be Evaluated Before Implementation

DevLog already contains concepts related to:

* Deliverable;
* Documentation;
* Artifact;
* Source.

Before introducing new domain entities, implementation design must analyze these existing models.

The future capability should:

* reuse them when their semantics remain correct;
* evolve them when appropriate;
* replace them only with explicit justification.

A parallel competing document model must not be introduced accidentally.

### 14. Artifact Generation May Consume Shared Engineering Knowledge

Future artifact generation may consume knowledge beyond project-specific DevLog data.

For example, an onboarding document may require:

Project Knowledge

* Shared Engineering Standards
  → Onboarding Artifact

Shared engineering standards may eventually come from an Engineering Knowledge source such as the Engineering Vault.

This ADR does not define that integration.

It only preserves the architectural possibility.

### 15. Visual Standards May Become an Independent Input

High-quality generated artifacts may eventually consume a shared visual language or Design System.

Conceptually:

Project Knowledge

* Engineering Knowledge
* Visual / Brand Standards
  ↓
  Artifact Generation
  ↓
  Professional Artifact

The artifact generator should therefore not embed all visual conventions directly into project knowledge.

The integration mechanism will be decided separately if the requirement becomes concrete.

### 16. Relationship With the Knowledge Graph

Artifact provenance and freshness will likely require relationships such as:

Artifact
→ basedOn → ADR

Artifact
→ basedOn → EngineeringStory

Artifact
→ basedOn → Component

Artifact
→ basedOn → KnowledgeEvent

Knowledge Change
→ affects → Component

Component
→ referencedBy → Artifact

These relationships may become important use cases for the future Project Knowledge Graph.

However:

**this ADR does not require a graph database or a Knowledge Graph implementation.**

Artifact generation should initially consume the existing relational knowledge model where sufficient.

### 17. Relationship With Human Overview

The Human Project Overview may eventually expose artifact state.

Possible capabilities include:

Living Documents

* current;
* stale;
* update available.

Snapshot Generation

* generate onboarding;
* generate project report;
* prepare blog article;
* prepare presentation.

Recent Artifacts

* recently generated snapshots;
* recently updated living documents.

This ADR does not define the final UI.

### 18. Relationship With Agents

Artifact generation should eventually be available as a controlled engineering capability rather than requiring agents to independently reconstruct project context.

Conceptually:

Agent / Human Intent
→ Artifact Generation Capability
→ Context Builder
→ Trusted Knowledge
→ Generation Pipeline

This allows future agents to request artifacts while preserving the same validation and knowledge boundaries.

## Consequences

### Positive

* Restores document generation as a meaningful DevLog capability without returning to the original document-centric architecture.
* Reuses the trusted project memory already built by DevLog.
* Supports both internal engineering documentation and high-value external communication.
* Separates factual trust from AI-generated narrative and presentation.
* Enables future document freshness detection.
* Supports multiple audiences and output formats.
* Provides a foundation for blog, portfolio, onboarding and presentation automation.
* Creates another concrete use case for project knowledge relationships.
* Remains compatible with Human + AI engineering principles.

### Negative

* Introduces a potentially large new product surface.
* Artifact lifecycle, provenance and freshness can become complex.
* High-quality visual generation may require specialized AI capabilities and rendering infrastructure.
* Multiple output formats increase testing and maintenance requirements.
* AI-generated external content requires strong human review.
* Existing Deliverable/Documentation/Artifact models may require significant evolution.

### Risks

* Recreating project knowledge inside documents instead of projecting it.
* Treating AI-generated interpretation as factual knowledge.
* Building an overly generic document platform.
* Coupling generation too tightly to specific formats.
* Attempting automatic freshness before knowledge relationships are sufficiently reliable.
* Expanding scope into generic office/document automation unrelated to engineering.

## Explicit Non-Goals

This decision does not require immediate implementation.

It does not define:

* final domain entities;
* database schema;
* final lifecycle enums;
* renderer technology;
* LLM provider;
* visual generation technology;
* graph database;
* scheduling infrastructure;
* Portfolio integration protocol;
* Engineering Vault integration;
* final Human Overview UI.

These decisions should be made when concrete implementation Stories are prepared.

## Implementation Timing

This capability should not interrupt the current Human Overview / Project State work.

Before implementation, DevLog should continue strengthening:

Project State
→ Human Overview
→ Project History / Timeline
→ Knowledge Relationships

These capabilities will provide better foundations for artifact provenance, context selection and freshness detection.

## Guiding Principle

DevLog does not generate truth.

DevLog maintains trusted project knowledge and transforms that knowledge into representations adapted to different consumers.

Human UI
→ interactive representation

Agent Context
→ machine-oriented representation

Knowledge Artifact
→ human communication representation

The representation may change.

The underlying trusted knowledge remains authoritative.
