# ADR-084 - Cross-Platform Agent Integration Architecture and Compatibility Guarantees

## Status

ACCEPTED - explicitly approved by the human project owner on 2026-11-25.
Acceptance does not authorize implementation or live experiments.

## Date

2026-11-25

## Context

DevLog exposes platform-independent capabilities through MCP and REST. Claude
already has a native [Companion mod](../../claude-mod/devlog-companion/), with an
activity indicator, Now, Context and History views, and a Context Trace
Inspector. OpenCode already integrates with DevLog through MCP and the
engineering preflight workflow; it does not have a native Companion in this
repository.

The OpenCode Companion feasibility audit reached a **CONDITIONAL GO**, not a
runtime certification. The published `@opencode/plugin@2.4.0` and
[tagged runtime](https://github.com/anomalyco/opencode/tree/v2.4.0) expose
server tool hooks and typed RPC, experimental Desktop contributions, and TUI
slots and panels. A before-hook observes an attempt, not confirmed dispatch;
the corresponding after-hook is not guaranteed. The audit distinguished a V2
CLI at `2.4.0`, a shell-default CLI at `1.18.11`, and a Desktop package at
`2.4.1`. It did not verify an exact `2.4.0` Desktop/sidecar pairing, live RPC
or presentation behavior, or an authorized server-side trace read.

Repository history records the Claude mod implementation in `49240264`,
although Story 0193 still has a pre-implementation status heading. The files,
not that heading, establish the implementation baseline; neither proves
runtime behavior or constitutes human acceptance. The current implementation
uses timestamp-based operation keys, does not explicitly scope its atoms by
session, and passes credentials through subprocess arguments for trace
retrieval. These are findings to address separately, not behaviors to preserve
for parity.

**Evidence boundary.** `DEVLOG_CONTEXT_ERROR`: the Story Agent and direct
DevLog context tools were unavailable for this ADR task. The earlier audit's
bounded Story Agent result was fresh at revision `7ecc1680` but truncated and
terminally rejected with `GROUNDING_REQUESTED_FILE_SCOPE`. It produced no
usable grounded synthesis. The earlier deterministic history references were
checked against Git. The existing requirements below come from accepted
repository ADRs and current contracts, not a new live validated-knowledge
retrieval.

## Problem

How can DevLog evolve a native integration for one agent platform without
regressing another, while preserving truthful observations, stable backend
contracts, and independent deployment? A single host-shaped implementation
would make platform-specific behavior and failure modes leak across boundaries.
Fully separate implementations would leave both consumers to interpret common
DevLog contracts independently.

## Architectural Drivers

- Preserve existing Claude workflows while introducing OpenCode independently.
- Use native presentation and lifecycle capabilities without claiming equal host
  semantics, wire coverage, or visual fidelity.
- Keep DevLog Core authoritative for identity, context, authorization, and
  trusted knowledge. Keep presentation failures out of tool execution and
  governance.
- Support a local Desktop experience and intentional terminal, SSH, and remote
  workflows from the same OpenCode server projection.
- Make compatibility claims versioned, testable, reproducible, and reviewable.

## Decision

**Multi-platform by design, native by implementation.** Adopt **shared
Companion domain semantics with native platform adapters**, incrementally.
Claude and OpenCode MUST be first-class supported integration platforms.
OpenCode Desktop MUST be the primary OpenCode presentation target; OpenCode TUI
MUST be an intentional secondary target, including remote workflows. OpenCode
MUST NOT replace Claude. A first-class support commitment is not a declaration
that an unbuilt feature or untested version is already supported.

**Compatibility** means avoiding unintended regressions in supported behavior on
either platform. **Feature parity** means offering equivalent functionality
where technically and operationally appropriate. Full visual or technical
parity is not required. A platform-specific feature MAY ship independently if
its behavior is isolated, shared semantics remain accurate, affected support
claims are validated, and limitations and fallbacks are documented. Missing
capabilities MUST NOT be simulated with fabricated events, inferred success, or
misleading status.

The MUST, MUST NOT, SHOULD and MAY statements define the accepted requirements.
Existing governance and security requirements remain binding. Implementation
approaches, version combinations and paths identified as candidates are not
approved by this decision.

## Architecture and Responsibility Boundaries

```text
Claude Presentation              OpenCode Desktop     OpenCode TUI
        |                               |                   |
Claude Adapter                          +---------+---------+
        |                                         |
        |                                  OpenCode RPC
        |                                         |
        |                                OpenCode Server Adapter
        |                                         |
        +-------------> Shared Companion Core <---+
                                  |
                        DevLog integration contracts
                                  |
                         DevLog MCP / REST / Core
```

This is a logical dependency view, not a process or package diagram. The
Shared Companion Core is client-side domain logic, **not** Java/Core, a
transport client, or an authorization authority. Native adapters own IO. Each
integration MUST run without installing, starting, or communicating with the
other. The OpenCode server observer MUST be able to run without a presentation
adapter.

| Responsibility | Owner and boundary |
|---|---|
| Shared Companion Core | MAY contain stable operation identity types, activity and presence reducers, DevLog response decoding, trace DTOs, error classification, validation/redaction, pure formatting and shared fixtures. Compatible assets or design tokens MAY be shared separately. Logic SHOULD be deterministic and independently testable. Only extract demonstrated common semantics; do not require a common event shape, state store, or UI renderer. |
| Claude | The native adapter owns hook registration, tool interception, Claude session lifecycle and state bindings. Claude presentation owns rendering, commands and panes. The adapter retains native discovery, packaging and installation unless a separate migration is validated and approved. |
| OpenCode server | The native adapter owns plugin lifecycle, tool hooks, session/location events, MCP status observation, correlation, cleanup and RPC registration. It produces the authoritative **OpenCode Companion projection** and gates any approved trace read; it does not author DevLog business facts. |
| OpenCode Desktop and TUI | Native presentation entries consume the same scoped server projection where applicable. Desktop MAY use panels, commands, presence indicators, graphical views, and interactive components. TUI SHOULD use terminal-native slots, panels or routes, and text/glyphs. Neither duplicates the domain reducer or acquires DevLog credentials. |
| DevLog | Java/Core remains the source of truth for project identity, task state, context, trace authorization, grounding and accepted knowledge. MCP and REST remain transport adapters over Core capabilities. |

The Shared Companion Core MUST NOT import Claude or OpenCode SDKs, SolidJS,
OpenTUI, Electron, native hook or UI primitives, packaging/installation APIs,
or platform credential stores. Platform SDK types, connectivity, and event
delivery belong in adapters. Shared contracts and fixtures MAY precede any
shared executable artifact.

## Platform Capability Strategy

| Capability | Claude Companion baseline | OpenCode target and evidence limit |
|---|---|---|
| Lifecycle and dispatch | `tool.call` wraps the host continuation for matching MCP tools. A wrapper is not complete wire telemetry. | `execute.before`/`execute.after` observe ordinary registered tool paths, including nested Code Mode from tagged source. A start is an attempt; a missing terminal event is possible. |
| Correlation and cancellation | The current name/time key can collide; there is no explicit cancellation observation. | Host session, message and call identifiers support scoped correlation. Session interruption is not per-call or Core cancellation. Validate background and cancellation paths; do not synthesize terminal success. |
| Session and subagents | `session.start` exists; teardown, per-session isolation and subagent coverage are not established by the current mod. | Session/location events and child session identity are available. Parent roll-ups are optional and MUST NOT erase child ownership. Runtime isolation still needs validation. |
| Connectivity and background work | Trace-fetch errors currently drive a heuristic disconnect state. | `mcp.status.changed` and MCP inventory describe host-visible connection status, not all events inside a wrapper or background task. Client RPC, MCP transport and trace REST health are separate. |
| Presentation | Native AbovePrompt, pane and command; graphical SVG and terminal text fallback in the source. | Desktop panel, command, session header/composer contributions and graphics are experimental. TUI uses native slots and text. Exact UI and packaging behavior requires a pinned runtime check. |
| Authentication and Context Inspector | Current mod reads the task-scoped trace REST route using local credential plumbing; this is not a reference security design. | A trusted server MAY offer authorized, on-demand trace retrieval. A valid RPC connection or task ID is not authorization. Trace correlation and live access remain unverified. |
| Remote | No remote support claim is made by this ADR for the Claude mod. | Support TUI running on an SSH host and a compatible local TUI connected to an authenticated remote OpenCode server. Install the presentation artifact where it executes. Do not load UI code or retrieve secrets from a remote filesystem as a fallback. |

Capability records MUST distinguish **supported**, **partial** and
**unsupported** capabilities, and identify **experimental** or **unverified**
surfaces. At runtime, unknown, incomplete and unavailable observations MUST be
explicit. An unsupported capability is not a transient outage; a missing event
is not evidence of either. Adapters SHOULD prefer native evidence and graceful
degradation over emulation.

## Operation and Presence Semantics

The domain projection MUST keep four independent facts:

1. **Platform tool execution:** observed attempt, dispatched/in progress only
   where evidenced, reported completion/error, evidenced interruption, or
   incomplete/unknown. Activity may expire from the live view without gaining
   a terminal outcome.
2. **DevLog business/AI task:** an explicit known state or unknown/not
   applicable. Preserve pending outcomes; a poll deadline with last-known
   `SUBMITTED` is not a terminal AI task failure. A platform success may carry
   a failed DevLog result.
3. **Context Trace:** not applicable, candidate/not checked, available,
   unavailable, or unknown, with safe diagnostics when appropriate. A valid
   task ID is only a candidate. Even an authorized trace response may report
   unavailable context. A task-scoped trace MUST NOT be labeled as the exact
   observed invocation unless that join is established.
4. **Connectivity:** distinguish the platform/server connection, the DevLog
   MCP connection and trace-service reachability. Sign-in required, disabled,
   pending and unknown MUST NOT be collapsed into network disconnection.

Presence is a scoped summary, not a second source of truth:

| State | Meaning |
|---|---|
| `IDLE` | No observed active DevLog work or recent outcome requiring attention. It does not assert service health. |
| `WORKING` | A current observed attempt, confirmed execution, or explicitly pending DevLog task. The display MUST distinguish an unconfirmed attempt from actual dispatch when claiming progress. Stale attempts leave the active view as incomplete/unknown, not as success. |
| `READY` | A recent, positively evidenced applicable DevLog outcome is ready to present. It MUST NOT imply Context Trace availability; “context ready” requires evidence of the relevant context. Recency SHOULD be measured from completion, not start. |
| `ERROR` | A relevant observed execution or business failure. A trace-read failure MUST NOT retroactively change the recorded tool/task outcome. |
| `DISCONNECTED` | The connection required for the displayed capability is known to be lost. The UI MUST identify the affected boundary; a request timeout, hidden resource, or missing trace alone does not prove disconnection. |

An adapter MAY use an auxiliary loading/unknown presentation or badges for
pending, interrupted and unavailable facts. Under concurrency, aggregate active
work separately from recent terminal results. A derived label MUST NOT discard
the underlying facts. Each supported derivation and fallback MUST have fixtures.

## Stable DevLog Backend Contracts

MCP tool names and schemas, structured envelopes, task identifiers and lifecycle
semantics, Context Trace DTOs, error provenance, authorization requirements, and
observability metadata MUST be treated as consumer contracts. DevLog MUST NOT
embed host tool display names, layout rules, or unrelated host lifecycle in
business services. Host correlation metadata, when justified, SHOULD be opaque,
optional and separate from authorization. Backend changes require a genuine
backend responsibility, not merely a less convenient adapter.

- Prefer additive, backward-compatible changes. New optional fields and statuses
  MUST be assessed against real supported consumers; additive syntax is not
  proof of semantic compatibility. Unknown values MUST degrade without implying
  success or access.
- Distinguish platform call IDs, MCP operation/instance IDs and task IDs. A
  resumed task can have several invocations. The current task trace lookup
  selects a correlated operation without a deterministic ordering guarantee;
  do not base exact invocation attribution on it.
- Preserve project-scoped authorization and existing error semantics. In
  particular, a masked missing/unauthorized trace MUST NOT be reinterpreted as
  proof of existence or service loss. Trace access MAY use existing authorized
  routes; missing/unsafe authorization leaves the feature unavailable.
- A breaking change MUST have explicit impact analysis, affected platform and
  version identification, a documented migration (including coexistence,
  deprecation and rollback as applicable), updated contract tests, validation of
  affected consumers, and human approval before release.

## Compatibility, Versioning and Distribution

1. **Non-regression.** A change MUST NOT introduce unintended regression in
   supported behavior, authorization or installation on any affected platform.
   A deliberate change to supported behavior is a reviewed compatibility change,
   not a waived test.
2. **Shared change validation.** Shared contracts, Core rules, backend
   integration semantics, and packaging inputs MUST trigger the relevant
   validation on every affected supported combination. One platform passing is
   not evidence that another passes.
3. **Platform change isolation.** A change confined to one native adapter MUST
   run its adapter checks and relevant shared tests. It SHOULD NOT require an
   unrelated adapter change or release. Broaden validation if the ostensibly
   local change affects a common contract, authorization, or shipped artifact.
4. **Independent distribution.** Each integration MUST be packageable,
   installable, upgradable and removable without disturbing the other or its
   configuration. A shared artifact, if introduced, MUST be bundled or resolved
   at a compatible version with no runtime dependence on the other plugin.
5. **Version evidence.** Releases MUST record supported platform builds, plugin
   and SDK versions, shared artifact version or build provenance where
   applicable, backend contract compatibility, verified workflows, known
   limitations, experimental features, and evidence date/revision. Include the
   OpenCode Desktop/sidecar/CLI pairing and remote topology where claimed. No
   future host release is assumed compatible. Pin experimental APIs for initial
   validation; broaden support only with evidence.
6. **Failure isolation.** Runtime errors or absence of one integration MUST
   NOT affect another, DevLog business operations, policy, MCP authorization,
   or normal platform operation beyond the affected contribution. An
   incompatible presentation MUST degrade independently of server observation.

## Security, Governance and Session Isolation

- The Companion MUST be observational by default. It MUST NOT alter tool
  input/output, authorization or preflight decisions; approve or promote
  unvalidated AI output; retry or resume DevLog tasks; or make additional MCP
  calls merely to simulate observability. This does not change existing retry
  and renewal policy owned by the authorized MCP runtime. An explicit Inspector
  action MAY make a separately authorized, read-only request.
- The OpenCode Preflight Gate MUST remain independent. The installed Gate's
  explore matcher uses legacy argument aliases while the tagged native
  `subagent` tool uses `agent`; its completion classifier is also permissive.
  These are source-level compatibility findings, not a live verdict. Validate
  independently and correct only through a separately approved Engineering
  Story. Do not bypass the Gate to demonstrate Companion behavior.
- Credentials MUST stay inside the trusted execution/credential boundary, not
  in the presentation process, client-bound options, process arguments,
  persisted projections, or logs. Platforms MAY use different approved
  mechanisms with equivalent scope, delegation, expiry and revocation
  guarantees. The Claude baseline's credential path is not grandfathered into
  a new design. No unrestricted backend proxy, arbitrary task lookup, or
  cross-project access is permitted. If the caller cannot be authorized for the
  selected scope, trace access MUST fail closed.
- Observation state MUST be scoped by platform/server instance, project and
  workspace/location, session (including child sessions) and call identity as
  applicable. Frontends MUST scope selected state to the owning window/route
  and reconcile late responses on switches. Host IDs and paths are selectors,
  not proofs of authority. Module-level state does not prove isolation.
  Authorize reads and notification delivery at the server boundary; if event
  subscriptions cannot enforce that scope, use authorized snapshots without
  broadcasting project or session data.
- Hooks SHOULD do bounded, non-blocking bookkeeping and MUST NOT propagate
  observer failures into tool execution. Active state and history MUST be
  bounded separately. Cancel stale view requests, detach listeners on unload,
  reconcile dropped/reordered notifications, and enforce retention. Persist
  only necessary sanitized metadata, never raw sensitive inputs, outputs, or
  credentials. Remote workflows MUST provide equivalent confidentiality and
  authorization; headless execution MUST NOT depend on a GUI or TUI.

## Validation Requirements

| Layer | Required evidence |
|---|---|
| Shared domain | Deterministic state transitions, presence, decoding and error classification, trace independence, unknown/incomplete outcomes, concurrent same-tool and out-of-order cases, scope and sanitization. |
| Contracts | MCP schema and envelope fixtures, REST DTOs, task lifecycle and ID semantics, error and authorization behavior (including project isolation), old/new consumer compatibility. |
| Native adapters | Per-platform fixtures for event translation, terminal gaps, permission/cancellation behavior, connection loss/recovery, child sessions, unknown inputs, and failure isolation. |
| Packaging | Independently build/package each affected artifact; inspect shipped dependencies and shared artifacts. Prove discovery and installation without the other integration, and verify upgrades/removal do not change it. |
| Runtime | On supported versions, observe loading, hook behavior, concurrent calls, session/worktree/window isolation, panel/indicator rendering, errors and cleanup. Validate OpenCode RPC/reconnect and at least the claimed remote modes; prove co-existence with the Gate without changing it. |
| Claude regression | Capture the existing supported Claude behavior before any refactor that could affect it: discovery/install and removal, presence states, panel and commands, Now/Context/History, observation/error paths, and Inspector where authorized. Reproduce on the same declared baseline after shared changes. OpenCode passing never proves Claude compatibility. |

Use [existing pull request quality automation](../../.github/workflows/quality.yml)
progressively: first add deterministic contract, shared and adapter checks under
separately authorized work, then independent packaging jobs and runtime checks
as reproducibility permits. Shared changes MUST run affected suites across both
platforms. Runtime checks not yet automatable MUST have a versioned manual
protocol with prerequisites, steps, expected results, failure criteria and
sanitized evidence. Record automated results, actual runtime evidence and
explicit human acceptance separately. A missing, skipped, blocked or unexecuted
required check MUST NOT be reported as passing or as evidence of support. A
release MUST NOT claim compatibility on an affected combination until the
required checks for that combination pass and the applicable human gate is met.

## Repository Organization and Incremental Adoption

The current canonical Claude path is `claude-mod/devlog-companion/`; the
installer copies the manifest, hooks and types into the Claude marketplace.
There is no verified shared-package loading or bundle contract in that
installer. Preserve it as-is until a separately approved migration.
`opencode-mod/devlog-companion/`, `integrations/{companion-core,shared-assets,compatibility-tests}/`
and `docs/integrations/` are **candidate** locations, not approved paths. Test
Claude's ability to consume a shared module or an independently distributable
build-time artifact before requiring extraction. If neither is viable, start
with shared contracts and compatibility fixtures and keep the native
implementations independent. No directory or packaging migration is decided here.

Recommended sequence; each executable step requires its own authorization:

1. Approve the architecture and compatibility contract.
2. Establish a reproducible Claude Companion regression baseline.
3. Validate OpenCode native capabilities in an isolated, version-pinned spike.
   This may proceed independently of step 2 if it does not change Claude.
4. Verify packaging feasibility for both hosts, including shared artifacts.
5. Validate the Preflight Gate independently and correct it under a separate
   Story if required. Do not use an ineffective Gate as a passing baseline.
6. Identify common semantics from evidence, not from similar UI labels.
7. Extract only verified common logic in small steps protected by the Claude
   baseline and both platforms' applicable checks. No big-bang Claude refactor.
8. Implement the OpenCode server observer and shared server projection.
9. Deliver the native OpenCode Desktop experience incrementally.
10. Introduce Context Inspector only after scoped trace access passes.
11. Deliver the native OpenCode TUI, including the claimed SSH/remote paths.
12. Strengthen compatibility CI, packaging and independent distribution.

Useful observer or Desktop improvements need not wait for full parity, shared
packaging, or all TUI features. They MUST NOT bypass their own validation or
weaken the commitment to the other platform.

## Alternatives Considered

- **A — Independent native implementations, no shared implementation.** Good
  starting point when semantics or packaging are not yet proven. Long term,
  duplicated response decoding, identity, and status classification can drift
  after a backend or platform change. Independent implementations may still
  share contracts and fixtures, but offer fewer safeguards against rule drift.
- **B — Fully unified cross-platform framework.** Maximizes nominal reuse but
  would impose a common lifecycle, UI and credential abstraction over materially
  different hosts. It risks suppressing native features or fabricating symmetry
  where evidence is partial. Rejected as premature abstraction.
- **C — Shared domain Core with native adapters (accepted).** Share only
  demonstrated invariants while keeping platform capability, rendering, state
  integration and deployment native. Shared code can propagate a defect to both
  consumers; independent runtime regressions and contract tests remain mandatory.

## Consequences

**Positive:** Claude can evolve without requiring an OpenCode release, and vice
versa. OpenCode can use native Desktop presentation while retaining a genuine
TUI path. Verified shared semantics reduce inconsistent status and error
interpretation, without moving business authority out of DevLog Core.

**Costs:** Maintain explicit capability and version records, fixture sets for
both native adapters, independently shippable artifacts, and manual runtime
evidence until automation is practical. Shared evolution costs more validation;
platform-specific presentation intentionally duplicates some work. Not every
DevLog or host feature will look or behave identically on both platforms.

## Risks and Open Questions

- Exact supported runtime/SDK/sidecar combinations, experimental GUI
  installation, TUI packaging, live RPC isolation and recovery remain to be
  measured. Lossless MCP wire coverage is not a supported assumption.
- Claude shared artifact discovery/packaging, actual session isolation and the
  baseline on supported builds need evidence before extraction. Any mitigation
  for current credential, concurrency or state weaknesses is separate work.
- The Gate's effective behavior and exact credential provider for authorized
  trace requests remain open. Determine whether task-scoped trace inspection is
  sufficient before proposing new backend correlation or shared-server
  authorization. Set concrete retention budgets and subagent presentation
  behavior through future Stories.
- The accepted architecture does not certify any specific platform version.
  Target version matrix, packaging paths, adoption scope and any new auth or
  backend work remain subject to later validation and authorization.

## Non-Goals and Implementation Boundary

This decision authorizes no plugin, spike, Claude refactor, Gate change, backend
API or authentication change, dependency installation, or global OpenCode
configuration change. It establishes no mandatory feature parity, generic
plugin framework, Companion SDK, or common cross-product runtime.

Trading OS and other Developer OS components MAY use these principles as
reference. This ADR governs **DevLog** only and does not authorize work in
another repository or sharing product domain models, business rules, or
authorization. Any future cross-product mutualization requires demonstrated
need and a separate decision.

After human approval, the recommended next Engineering Story is a
**Claude Companion regression baseline and cross-platform compatibility
evidence** Story. A separately approved OpenCode compatibility spike can
proceed without modifying Claude. Neither is created or authorized by this ADR.

## Amendment - Native OpenCode GUI Observation and Isolated Sequencing (2026-11-27)

### Amendment Status and Basis

**ACCEPTED by the owner on 2026-11-27.** This amendment is effective as an
architectural clarification to ADR-084. It does not itself authorize
implementation, runtime experiments, or a compatibility claim.

This focused amendment follows the repository's dated-amendment lifecycle. It
preserves the original decision history and its requirements for Core-owned
business authority, truthful evidence, privacy, failure isolation, independent
platform adapters, and validated compatibility claims. This amendment clarifies
the interpretation of the responsibility boundary,
security/session-isolation section, and incremental-adoption sequence below; it
does not replace the original decision or generally weaken its security rules.

The owner approved GUI-only native observation as the preferred Story 0252
direction and formally accepted this amendment and the revised Story plan on
2026-11-27. OpenCode v2.4.0 exposes the routed GUI
session, its server's native data cache, transcript tool parts, and typed
session events. This makes a narrow presentation-only implementation possible
without a Companion RPC or server observer. The host treats GUI plugin bundles
as trusted application code; this amendment explicitly accepts that trust model
for this limited feature, not as a claim of plugin sandboxing or per-session
authorization.

### 1. Native platform implementations may differ

Cross-platform functional compatibility does not require identical internal
implementations, event sources, state stores, or presentation plumbing.
Platform-native GUI observation and an in-memory presentation projection are
acceptable when the host already exposes the relevant data to that GUI and the
feature consumes only the data needed for the currently routed session.

The existing shared domain semantics and evidence requirements remain in force.
An adapter must not turn missing, ambiguous, stale, or incomplete evidence into
a successful outcome. Platform-specific implementation is not evidence of
cross-platform parity or support.

### 2. Narrow presentation-only projection exception

Server-side projection is not mandatory for every presentation-only feature.
An OpenCode Desktop GUI adapter MAY derive a bounded, sanitized, in-memory
presence view from the host's already-exposed native session cache, transcript
tool parts, and supported session events for its currently routed session.
This is a presentation projection only; it is not a new business authority,
authorization authority, or durable record.

For this exception:

- The OpenCode trusted GUI plugin model is an explicit trust assumption. This
  feature is not isolated from other trusted/enabled GUI plugin code.
- Filtering observations to the currently routed session is **presentation
  scoping**, not a server-side authorization boundary and not proof that a
  session ID belongs to a window.
- The adapter MUST read/process only data necessary for the current route,
  MUST NOT enumerate unrelated sessions or retain their activity, and MUST
  clear route-specific state on session/server-location changes and teardown.
- Presence state MUST remain local and in memory. The adapter MUST NOT retain
  raw transcripts, prompts, tool arguments/results, credentials, or error
  payloads in Companion-specific storage or logs.
- A feature requiring data beyond what the host already exposes to the GUI,
  broader session enumeration, cross-window delivery, persistence, or external
  transmission MUST establish its own appropriate authorization and privacy
  guarantees before implementation.

This exception does **not** authorize a new Companion RPC endpoint, activation
of the existing snapshot RPC, a server observer dependency, additional MCP or
REST requests, broader data access, persistence, external transmission, or any
change/weakened interpretation of DevLog backend authorization. Existing
backend/Core authorization remains authoritative and unchanged.

### 3. OpenCode sequencing without a Claude regression claim

OpenCode-specific development MAY proceed before full Claude runtime regression
qualification only when the work is isolated to OpenCode and all of the
following hold:

- Claude implementation files remain unchanged.
- Shared runtime components and shared Companion code remain unchanged.
- Existing Claude behavior is not intentionally changed.
- Backend and integration contracts remain unchanged.
- Outstanding Claude runtime validation and its unqualified capabilities remain
  explicitly documented.

Claude runtime regression qualification remains required before claiming full
cross-platform compatibility. OpenCode-only tests or manual checks do not
establish Claude compatibility. Shared changes or changes capable of affecting
Claude continue to require the applicable Claude baseline and cross-platform
validation before a compatibility claim.

This clarifies the prospective sequence in section 12: the Claude baseline
remains recommended and required for shared evolution and cross-platform
qualification, but is not a prerequisite for a separately authorized,
OpenCode-only GUI presentation change meeting the constraints above.

### Preserved invariants and implementation boundary

This amendment preserves:

- DevLog Core authority over business task semantics, project identity,
  authorization, context, trace access, grounding, and trusted knowledge.
- No fabricated success, failure, dispatch, connectivity, or missing event.
- No weakening of authorization for backend, MCP, REST, trace, or future data
  access.
- Independent platform adapters and explicit compatibility evidence.
- Separate owner approval of the amended ADR, Story/plan, implementation,
  runtime validation, and final acceptance.

The amendment authorizes no production change by itself. Story 0252 still
requires owner approval of its revised implementation plan and explicit
implementation authorization; Desktop validation requires the applicable
separate owner authorization.
