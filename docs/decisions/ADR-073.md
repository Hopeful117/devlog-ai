# ADR-073 - Core-Owned Binding Between Principal, AI Task and User Credential

## Status

Proposed - requires human architecture approval.

## Date

2026-10-30

## Context

ADR-072 introduces user-authorized Sign in with ChatGPT credentials inside the
AI Engine. The current task path is not user-scoped: Java/Core creates an
`AiTask`, sends a `PromptRequest` and the AI Engine uses a process-scoped
provider. `PromptRequest.metadata` is transport input and is not an
authorization decision.

A raw OAuth token must remain inside the AI Engine provider boundary. However,
the AI Engine still needs to know which user credential may be used for a given
task. A caller-provided credential reference would be forgeable unless Core
authorizes and binds it to the authenticated principal and task.

ADR-070 already separates authenticated principal, project membership and
transport identity. This ADR specializes that boundary for user-authorized AI
provider credentials.

## Problem

Without a Core-owned binding:

- one user's task could use another user's ChatGPT credential;
- a caller could inject a credential reference in arbitrary task metadata;
- Core would have no deterministic authorization evidence;
- the AI Engine could select credentials independently of project scope;
- task snapshots and callbacks could accidentally become credential stores.

## Decision

Core will be the sole authority that authorizes and binds a user-authorized AI
credential to an AI task. The binding is an immutable, opaque, short-lived
capability reference with no secret material:

```text
AiCredentialBinding
  bindingId
  principalId
  provider
  credentialOwnerSubject
  allowedTaskId / task scope
  issuedAt
  expiresAt
  status
```

The access token and refresh token are never stored by Core and never cross the
Core boundary. The AI Engine owns the mapping from its internal credential
handle to the OpenAI tokens. Core stores only the opaque binding metadata and a
hash or non-sensitive identifier sufficient to validate the binding.

The normative flow is:

```text
authenticated principal
  -> Core authorizes project/task and requests a provider binding
  -> AI Engine verifies the binding exchange through authenticated service auth
  -> AI Engine associates bindingId with its local ChatGPT credential
  -> Core emits the task with the Core-issued bindingId
  -> AI Engine accepts only that bindingId for that task
```

The exact browser authentication mechanism remains governed by ADR-070 and a
future identity-provider decision. The binding protocol must not infer a
principal from a project slug, task ID, OAuth token, cookie or caller metadata.

## Normative Invariants

1. A `bindingId` is an opaque capability reference, never an access token,
   refresh token, ID token, client secret or authorization code.
2. Only Core may issue, bind, revoke or authorize a binding for a task.
3. The binding is scoped to one principal, one provider and one task or
   explicitly bounded task capability; it is not a general project token.
4. The AI Engine rejects missing, expired, revoked, foreign or task-mismatched
   bindings before calling OpenAI.
5. A valid binding does not grant project access, context access or trusted
   knowledge rights. Those remain Core decisions.
6. Core does not receive or persist OpenAI access/refresh tokens.
7. AI Engine does not choose a principal, project or task scope from OAuth
   claims or arbitrary task metadata.
8. The binding is never included in prompts, model output, Core callbacks,
   interaction traces or user-visible MCP results unless a non-sensitive audit
   identifier is explicitly required.
9. Binding creation, use, refresh and revocation are auditable with redacted
   identifiers and categorized outcomes only.
10. REST, MCP and background task paths use the same Core binding capability;
    transport does not change authorization semantics.

## Service Authentication

The Core-to-AI Engine binding exchange must use an authenticated service
boundary independent from the user's ChatGPT credential. The implementation
must select one approved mechanism before production enablement, such as
mutual TLS or a rotated service credential managed outside repository
configuration.

The service mechanism authenticates the AI Engine as a service. It does not
replace the user principal or project authorization checks. A service
credential must not be accepted as a user credential or as proof of project
membership.

## Failure Semantics

- missing or invalid principal: `401` at the authenticated Core boundary;
- principal without project/task authorization: `403` or the existing
  non-disclosing outcome required by the capability;
- unknown, expired, revoked or task-mismatched binding: fail closed without
  invoking the provider;
- binding exchange failure: task is not submitted to the provider;
- credential refresh failure: AI Engine revokes the local credential mapping
  and requests reauthorization; it does not ask Core to accept a new scope;
- all failures expose bounded categories and never secret-bearing payloads.

## Persistence and Retention

Core may persist the non-secret binding metadata for the task lifetime and
configured audit retention. AI Engine may persist the encrypted credential
according to ADR-072. Binding expiry must not extend token or project access.
Revocation must invalidate future provider use without rewriting historical
task snapshots.

## Out of Scope

- Selecting or replacing the identity provider for all DevLog users.
- Moving OAuth token storage to Core or PostgreSQL Core persistence.
- Allowing MCP clients to provide arbitrary binding IDs.
- General-purpose delegated authorization or service-account impersonation.
- Provider fallback, billing or ChatGPT conversation access.

## Consequences

### Positive

- User credentials cannot be selected by untrusted task metadata.
- Core retains authoritative project/task authorization.
- AI Engine can keep OAuth secrets isolated from Core and MCP.
- Binding use is bounded, revocable and testable.

### Costs and Risks

- Core and AI Engine require a new authenticated binding protocol.
- Existing task creation paths must obtain a principal or remain API-key/mock
  only until they do.
- Service authentication and key rotation become deployment responsibilities.
- A binding table and lifecycle must be maintained without confusing it with
  project membership or trusted knowledge.

## Implementation Boundary

This ADR does not authorize implementation. Story 0161 defines the binding
capability and contract. Story 0160 depends on Story 0161 for user-authorized
task execution and must not work around this boundary.
