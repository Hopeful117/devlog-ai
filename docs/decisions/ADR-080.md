# ADR-080 — Hybrid Retrieval Architecture

## Status

**ACCEPTED** — Accepted by the human project owner on 2026-11-18.
Implementation remains bounded by individual Engineering Stories and their
separate authorization gates.

## Date

2026-11-18

## Context

### Prerequisite evaluation

Story 0177 built a replayable offline evaluation comparing four retrieval
conditions:

| Condition | Candidate recall | Final recall | Noise |
|-----------|-----------------|--------------|-------|
| `LEXICAL_CONTROL` | 0.875 | 0.875 | 0.250 |
| `STRUCTURAL_CONTROL` | 1.000 | 1.000 | 0.229 |
| `SEMANTIC_EXPERIMENT` | 1.000 | 1.000 | 0.313 |
| `HYBRID_EXPERIMENT` | 1.000 | 1.000 | 0.313 |

The synthetic semantic condition recovered a semantically indirect target
that lexical retrieval missed. The evaluation report concluded: *"No
production retrieval change is recommended from this report … A future
hybrid retrieval Architecture Story may be considered only if live captures
reproduce a material lexical recall gap after strict revision/trust
filtering."*

This ADR is that Architecture Story. The gap has been confirmed at the
fixture level and the project has decided that the RAG foundation is the
next major workstream.

### Current pipeline

`RepositoryContextEngine` runs deterministic collection (7 collectors),
term-frequency scoring (`DeterministicEvidenceRanker`), budgeted diverse
selection (`BudgetedDiverseEvidenceSelector`), and enrichment. Semantic
relevance is computed by a term model: tokenize the query, count how often
each discriminating term appears in candidate text, sum contributions. This
scoring is vocabulary-bound: an ADR about "dependency inversion" cannot
score against the query "decoupling strategy."

Measured gaps (ADR-063):

- 18 Insight candidates → ≤1 selected per run.
- 21 Engineering Story candidates → 0 selected.
- Five materially different intents produced near-identical compositions.
- Facts/Observations from past analyses unreachable unless anchored by an
  exact file path or commit hash.

### Infrastructure state

- **PostgreSQL 17** — vanilla, no extensions installed.
- **No pgvector** extension, no embedding service, no full-text index.
- Python AI Engine is an HTTP service with stateless generation endpoints.
- `InsightSimilarityService` implements TF-IDF + cosine similarity in Java
  but is not wired to the context pipeline.
- `KnowledgeSelectionService` (System B) implements strict grounding with
  allow-lists independently of System A.

## Problem

The existing `RepositoryContextEngine` is deterministic and correct, but its
recall is bounded by vocabulary matching. When a developer asks about
"how is isolation enforced between analysis runs," the relevant ADR may use
"bounded context" and "project scope," scoring near zero against the query
terms. The system cannot surface what it cannot spell-match.

The architectural question:

> How should DevLog add a semantic retrieval channel that improves
> evidence recall across vocabulary boundaries while preserving Java
> Core authority, trust semantics, project isolation, and reproducibility?

## Decision

### D1 — Hybrid retrieval: three complementary channels

The Retrieval Layer combines three mechanisms. None alone is sufficient.

| Channel | Mechanism | Strength | Weakness |
|---------|-----------|----------|----------|
| Structured | Reference, type, project, status filters | Exact, zero noise | Vocabulary-bound, not fuzzy |
| Lexical | Term model (existing), optionally PostgreSQL full-text | Exact terms, symbols | Vocabulary-bound |
| Semantic | Vector cosine similarity (pgvector) | Cross-vocabulary | Noisy, expensive |

The semantic channel is **additive**: it supplements the structured and
lexical channels, it does not replace them. Structural constraints (project
isolation, trust tier, status) are applied as hard filters before any
similarity computation.

### D2 — Vector technology: PostgreSQL + pgvector

**Decision: PostgreSQL + pgvector is the retrieval index technology.**

Rationale:

- Same operational unit as the existing DB; no new service to operate.
- Transactional consistency: an index update is atomic with the knowledge
  update that triggered it.
- Project isolation is enforced by the same SQL permission model already
  in place.
- The `pgvector` extension ships with standard Postgres distributions and
  is installable with `CREATE EXTENSION IF NOT EXISTS vector`.
- An HNSW or IVFFlat index on `vector(1536)` (OpenAI) or `vector(768)`
  (smaller models) is sufficient for DevLog's document volumes (ADRs,
  Stories, Insights: orders of magnitude below the operational threshold
  requiring a dedicated vector store).
- Embeddings can be stored in the same `retrieval_documents` table that
  holds provenance metadata, eliminating a cross-service join.

**Rejected alternatives:**

- *Qdrant/Chroma/Weaviate*: introduces a new operational service with
  separate persistence, backup, and authentication; Java Core would need
  a new client; project isolation becomes a cross-service concern.
- *Elasticsearch*: substantial operational overhead for the access
  patterns needed; overlaps PostgreSQL full-text capabilities.
- *Python-side retrieval*: violates ADR-067; Python must not access the
  database, repository, or retrieval index independently.

### D3 — Retrieval Layer placement: Java Core, RepositoryContextCollector

The semantic retrieval channel is implemented as a new
`RepositoryContextCollector` (or a set of them) in Java Core. It follows
the existing extension point: implement `RepositoryContextCollector`,
register as a Spring component, and the engine collects its candidates
alongside structural candidates.

This placement preserves:

- Java Core as the sole authority for project scope, revision scope,
  authorization, trust tier, and grounding.
- Existing pipeline (collect → rank → select → enrich) unchanged.
- The semantic collector returns `RepositoryEvidence` items with the same
  provenance contract as any other collector; the ranker and selector
  apply identically.

The semantic collector is **disabled by default** and activated by
configuration. A missing index, a failed embedding call, or a disabled
flag causes the collector to return an empty list; the pipeline continues
with the remaining collectors.

### D4 — Embedding generation: Python AI Engine, stateless endpoint

Java Core owns the embedding lifecycle: it decides what to embed, when
to request embeddings, where to store them, and when to invalidate them.

Python AI Engine provides a **new stateless endpoint** (`/api/v1/embeddings`)
that accepts a list of texts and returns a list of float vectors. It has
no access to the database, vector index, or retrieval state.

This boundary:

- Keeps Python in its authorized role (probabilistic generation, stateless
  computation).
- Keeps Java Core as the authority over what knowledge is embedded and
  stored.
- Allows the embedding model to be changed (a migration concern for Java
  Core, opaque to Python).

Embedding calls for indexing are made from an asynchronous Java service,
not from the hot retrieval path. Query embedding at retrieval time is
synchronous but bounded.

### D5 — Retrieval index as reconstructible projection

The `retrieval_documents` table and its vector index are a **technical
projection**, not authoritative knowledge. Governed by:

- Every indexed document traces back to a canonical source entity
  (ADR, Insight, Story, Fact).
- The index can be fully reconstructed from the authorized source tables.
- The index stores no knowledge that is not already in an authoritative
  entity; it stores no AI-generated content.
- Embedding model version is recorded; a model change triggers
  re-indexing, not a knowledge change.

### D6 — Similarity score never changes trust

A vector similarity score is a retrieval hint. It does not:

- Change a document's `TrustTier`.
- Change a document's `currentness` or `status` (CURRENT/SUPERSEDED).
- Change a document's grounding eligibility.
- Promote an UNVALIDATED or TRANSIENT_AI document into the context.

Trust tier assignment remains exclusively under Java Core authority
(`TrustTierClassifier`). The semantic collector assigns to each evidence
the same trust tier that the source entity carries in the knowledge model.

### D7 — Graceful degradation

If pgvector is unavailable, the semantic collector returns an empty list
and logs a bounded warning. The existing deterministic pipeline continues
unaffected. The degradation is fail-safe: the context is smaller but
complete with respect to the available channels.

If the Python AI Engine embedding endpoint is unavailable, the indexing
job retries with exponential backoff and records a bounded diagnostic.
Live retrieval queries for a document without an embedding fall back to
lexical scoring.

### D8 — Candidate fusion: Reciprocal Rank Fusion (RRF)

Lexical and semantic retrievals produce independently ranked lists. RRF
combines them without requiring that scores from different models be
comparable:

```
RRF_score(d) = Σ_r 1 / (k + rank_r(d))
```

where `k = 60` (standard constant), `r` iterates over retrieval lists,
and `rank_r(d)` is the 1-based rank of document `d` in list `r`.

RRF output is used as the `SEMANTIC_RELEVANCE` criterion input for the
existing `DeterministicEvidenceRanker`. The other five criteria
(ARCHITECTURAL_RELEVANCE, HISTORICAL_RELEVANCE, RECENCY, CONFIDENCE,
USER_GUIDANCE_BOOST) remain unchanged, preserving temporal and authority
scoring.

### D9 — Indexable document types (Phase F scope)

**Indexed in Phase F:**

| Type | Entity | Granularity | Why |
|------|--------|-------------|-----|
| ADR | Markdown file | Decision + rationale | Most retrieved architectural constraint |
| Engineering Story | `EngineeringStory` | Objective + acceptance criteria | Consistently zero-selected |
| Insight | `Insight` | Title + content | Starved (≤1/18 selected) |
| Decision | `EngineeringDecision` | Title + choice + rationale | Explicit knowledge |

**Deferred:**

- Commits and Diffs: high volume, changing content, better served by
  lexical recall on subjects; re-indexing cost is significant.
- Raw Facts: 44k+ items; volume requires a selective strategy (Phase G+).
- Project Notes and Milestones: low retrieval value relative to indexing cost.

### D10 — Multi-project isolation

Every `retrieval_documents` row carries a `project_id`. All vector queries
apply `WHERE project_id = :projectId` as a **pre-filter**, not a
post-filter. The pgvector index is created with `project_id` as a leading
column in composite indexes where the query planner supports it.

No embedding is ever returned for a project other than the requested
project, regardless of similarity score.

### D11 — Source provenance and status

Every indexed document carries:

| Field | Purpose |
|-------|---------|
| `source_type` | ADR / INSIGHT / STORY / DECISION |
| `source_id` | UUID of the originating entity |
| `source_revision` | Commit hash or analysis ID anchoring the content |
| `trust_tier` | Trust tier of the source entity at indexing time |
| `status` | CURRENT / SUPERSEDED at indexing time |
| `content_hash` | SHA-256 of indexed text — detects drift without re-embedding |
| `embedding_model` | Model identifier + version — detects stale embeddings |

SUPERSEDED documents remain in the index but their candidates are scored
down in the `DeterministicEvidenceRanker` (existing ARCHITECTURAL_RELEVANCE
logic). They are never excluded: a superseded ADR may still be contextually
relevant as historical reference.

### D12 — Synchronization: event-driven + scheduled backfill

**On knowledge change:**

Events emitted by the domain model (Insight accepted, Story status changed,
ADR file updated) trigger an async Java listener that queues the affected
document for re-indexing. Invalidation on project deletion cascades via
the existing project lifecycle.

**Backfill:**

A one-time scheduled job indexes all existing documents of supported types.
The job is idempotent (uses `content_hash` to skip unchanged documents)
and can be restarted safely.

**Re-indexing on model change:**

Changing the embedding model version triggers a full re-index of the
affected document types. This is a planned operation, not an automatic
background migration.

## Boundaries Not Changed by This ADR

- Java/Core remains the sole authority for project scope, context
  construction, selection, trust, grounding, and acceptance.
- Python remains responsible for probabilistic generation and stateless
  embedding computation only.
- MCP and REST remain thin adapters over the same Core capability.
- AI output (including embedding vectors) remains non-trusted knowledge.
- The `ValidatableProposal` lifecycle and ADR-006 governance are unaffected.
- No RAG framework, generic agent runtime, or autonomous Python retrieval
  is introduced.
- The existing `RepositoryContextEngine` pipeline (collect → rank →
  select → enrich) is extended, not replaced.

## Options Considered

### A. Add a dedicated vector store (Qdrant, Chroma)

Rejected. It introduces operational complexity (new service, backup,
authentication, network), breaks Java Core's SQL-first authority model,
and requires cross-service consistency for project isolation. The scale
of DevLog's retrieval corpus does not justify this overhead.

### B. Full-text search only (PostgreSQL tsvector)

Partial. PostgreSQL full-text search improves lexical recall significantly
(stem matching, stop words, language-aware ranking). It does not cross
vocabulary boundaries. This path is not an alternative to semantic
retrieval; it is a preparatory lexical improvement that can be implemented
independently and benefits the pipeline regardless of whether pgvector is
eventually adopted. It should be delivered first.

### C. Rerank with an LLM

Explicitly out of scope. LLM reranking introduces provider cost, latency,
and trust complexity on the critical retrieval path. This decision may be
revisited after the initial hybrid layer is measured.

### D. Python-side retrieval

Rejected. ADR-067 and ADR-069 forbid Python from independently accessing
the database, repository, or project context. This would require Python to
reconstruct context in parallel with Java Core, violating the established
boundary.

### E. Extend InsightSimilarityService to cover retrieval

Partial adoption. `InsightSimilarityService` already implements TF-IDF +
cosine similarity in Java and could serve as a lightweight semantic signal
for small corpora. Its approach is in-process and requires the full corpus
in memory. It is a useful supplement for Insights only; it cannot scale to
ADRs and Stories or support a persistent index. It is not adopted as the
primary semantic mechanism.

## Consequences

### Positive

- Vocabulary-independent evidence recall: "decoupling" matches ADRs about
  "dependency inversion."
- Engineering Stories and Insights recover from selection starvation.
- PostgreSQL remains the single persistence layer; no new operational
  service.
- Fail-safe degradation: the existing pipeline is never broken by a
  semantic component failure.
- The evaluation infrastructure from Story 0177 can be extended with live
  captures to measure the production impact.

### Costs

- pgvector extension must be installed and tested in the existing
  PostgreSQL setup (migration V82+).
- Python AI Engine gains a new endpoint; its contract must be versioned.
- Embedding cost: each document type requires one embedding API call per
  indexed document and per query. Batch embedding at index time amortizes
  the cost.
- Re-indexing on model change requires a planned migration window.
- Noise may increase at the candidate stage; the existing selection budget
  limits its impact on the final context.
