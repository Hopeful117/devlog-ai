# ADR-057 — DevLog MCP Capability Model

## Status

Proposed

## Date

2026-08-16

## Context

ADR-055 established DevLog as an Engineering Context Engine responsible for
transforming reliable project memory into bounded, structured and task-specific
engineering context.

ADR-056 established MCP as a dedicated inbound adapter inside DevLog.

The next architectural question is:

> What should DevLog expose through MCP, and at what level of abstraction?

MCP can expose different categories of capabilities.

For DevLog, the important distinction is between:

* engineering information that can be addressed and consumed as context;
* engineering operations that require DevLog to interpret a request, execute an
  application use case, or construct a task-specific result.

If this distinction is not explicit, the MCP interface risks becoming either:

* a low-level mirror of DevLog's internal data model;
* a collection of agent-specific endpoints;
* an unrestricted query interface;
* a second application layer containing duplicated business logic.

The initial MCP capability model must therefore preserve DevLog's existing
architectural boundaries while remaining useful to different engineering
consumers.

## Decision

DevLog MCP will expose **intent-oriented engineering capabilities** rather than
its internal storage or domain topology.

The initial capability model will primarily use:

1. **Resources** for addressable, contextual engineering information;
2. **Tools** for explicit DevLog application operations and task-specific
   context requests.

MCP Prompts are not required for the initial version.

The capability model remains consumer-agnostic and primarily read-only.

### 1. Resources Represent Addressable Engineering Context

Resources should expose engineering information that has a meaningful,
relatively stable identity from the consumer perspective.

Potential examples include:

```
project://{projectId}/context

adr://{adrId}

story://{storyId}

knowledge://{knowledgeId}
```

Resources may provide contextual representations of these concepts.

They must not expose persistence entities or database representations directly.

The boundary remains:

```
MCP Resource
    ↓
Application Query
    ↓
DevLog Projection
    ↓
Contextual Representation
```

A Resource represents a public engineering concept, not an internal table or
repository.

### 2. Tools Represent Explicit Engineering Context Operations

Tools should be used when the consumer expresses an engineering intent that
requires DevLog to perform an application-level operation.

Potential examples include:

```
search_project_context

get_engineering_context

search_project_history

get_architectural_constraints
```

The exact names and request contracts may evolve during implementation.

The important distinction is that a Tool represents a meaningful DevLog
capability rather than direct access to an internal service.

Conceptually:

```
Consumer Intent
      ↓
   MCP Tool
      ↓
Application Capability
      ↓
Context Selection / Projection
      ↓
    Result
```

### 3. Resources and Tools Must Not Mirror DevLog Internals

MCP consumers should not need to understand:

* repository implementations;
* projection tables;
* persistence identifiers that have no engineering meaning;
* enrichment jobs;
* internal event structures;
* database relationships;
* internal service topology.

Avoid capabilities such as:

```
query_knowledge_table

execute_projection_query

get_jdbc_repository_data

find_context_projection_row
```

Prefer capabilities describing engineering intent:

```
get_project_context

search_project_history

get_engineering_context
```

This preserves the ability to change DevLog internals without breaking MCP
consumers.

### 4. ContextRequest and ContextPackage Remain the Strategic Contracts

ADR-055 introduced `ContextRequest` and `ContextPackage` as the conceptual
boundary for engineering context projection.

MCP should progressively expose this capability rather than create a parallel
context model.

Conceptually:

```
MCP Client
    ↓
engineering intent
    ↓
MCP Adapter
    ↓
ContextRequest
    ↓
  DevLog
    ↓
ContextPackage
    ↓
MCP Representation
    ↓
  Consumer
```

The MCP representation may adapt the result for protocol requirements.

It must not redefine the semantics of the underlying engineering context.

### 5. `get_engineering_context` Is the Strategic High-Level Capability

The long-term central MCP capability should allow a consumer to request
engineering context for a specific intent.

Conceptually:

```
get_engineering_context(
    project,
    intent,
    constraints
)
```

Possible intents may eventually include:

* understanding an implementation;
* investigating a defect;
* preparing an Engineering Story;
* reviewing a change;
* understanding an architectural constraint;
* continuing an existing engineering task.

The capability should not become an AI reasoning endpoint.

Its responsibility is to provide the smallest reliable engineering context
sufficient for the expressed intent.

### 6. Search Capabilities Complement Context Projection

Context projection and search solve related but different consumer needs.

A consumer may sometimes know exactly what it wants to inspect.

For example:

```
search_project_history(
    project,
    "Project Notes Markdown"
)
```

or:

```
search_project_context(
    project,
    "ValidatableProposal"
)
```

Search capabilities may therefore remain useful alongside
`get_engineering_context`.

However, consumers should not be required to orchestrate many low-level
searches to reconstruct a ContextPackage.

The strategic direction remains:

```
engineering intent
      ↓
   DevLog
      ↓
context composition
```

rather than:

```
consumer
  ↓
search A
  +
search B
  +
search C
  ↓
consumer reconstructs context
```

### 7. The Initial Capability Set Must Remain Small

The first MCP implementation should not attempt to expose all DevLog features.

A suitable initial candidate set is:

```
Resources
---------
project context
ADR
Engineering Story
trusted Knowledge

Tools
-----
search_project_context
search_project_history
get_engineering_context
```

This list is intentionally small.

Capabilities should be added only when a real engineering workflow demonstrates
their value.

### 8. Initial Capabilities Are Read-Only

The initial MCP capability model must not allow external consumers to mutate
trusted project state.

The first version should optimize for:

* understanding;
* investigation;
* context retrieval;
* engineering continuity.

It should not optimize for autonomous modification.

The initial boundary is therefore:

```
Consumer
    ↓
  MCP
    ↓
Read / Query Capability
    ↓
  DevLog
```

not:

```
Consumer
    ↓
  MCP
    ↓
Project Mutation
```

### 9. Future Write Tools Must Use Existing DevLog Workflows

Read-only is an initial scope decision, not necessarily a permanent limitation.

Future MCP capabilities may eventually allow operations such as:

* submitting an engineering finding;
* requesting an analysis;
* creating a proposal;
* requesting context maintenance.

Such operations must invoke existing DevLog application workflows.

For AI-generated knowledge:

```
Agent
  ↓
MCP Tool
  ↓
Application Use Case
  ↓
ValidatableProposal
  ↓
Validation
  ↓
Trusted Knowledge
```

MCP must never provide a direct mutation path into authoritative Knowledge.

### 10. Capabilities Must Remain Consumer-Agnostic

Capability contracts must express engineering intent rather than consumer
identity.

The same capability should be usable by:

* Kiko;
* OpenCode;
* another coding agent;
* an IDE integration;
* a human-facing developer tool;
* a future Developer OS workflow.

For example:

```
get_engineering_context
```

is valid.

```
get_kiko_context
```

is not.

Consumer-specific presentation or reasoning belongs to the consumer.

### 11. MCP Does Not Own Engineering Reasoning

DevLog MCP may return structured engineering context.

It must not become responsible for performing the engineering task itself.

For example:

```
investigate_bug_and_fix_it
```

is outside the initial MCP responsibility.

A more appropriate interaction is:

```
Agent
  ↓
get_engineering_context
  ↓
DevLog
  ↓
ContextPackage
  ↓
Agent investigation
```

The agent remains responsible for reasoning about the implementation and
performing local engineering work.

DevLog remains responsible for context quality.

### 12. Capability Results Must Preserve Provenance

Context exposed through MCP must preserve enough source information for the
consumer to understand where important claims originate.

Relevant provenance may include:

* Knowledge identity;
* ADR identity;
* Engineering Story identity;
* commit identity;
* repository/file context;
* context projection origin;
* external transversal knowledge origin.

MCP adaptation must not flatten engineering context into unsupported prose that
loses traceability.

### 13. Capability Results Must Remain Bounded

MCP must not become a mechanism for dumping the entire DevLog project memory
into an agent context window.

ADR-055 requires projected context to remain bounded and task-specific.

The same rule applies through MCP.

Conceptually:

```
Project Memory
     ↓
Context Selection
     ↓
Context Budget
     ↓
MCP Result
```

Consumers should receive the smallest reliable context sufficient for the
requested engineering intent.

### 14. MCP Capabilities Must Be Retrieval-Implementation Agnostic

The initial implementation may rely on deterministic queries and existing
projections.

Future implementation may use:

* richer projections;
* lexical search;
* hybrid retrieval;
* vector search;
* temporal retrieval;
* relationship expansion;
* RAG.

These are implementation details behind DevLog's application boundary.

The public capability should remain conceptually stable:

```
get_engineering_context
```

regardless of whether the internal implementation evolves from:

```
deterministic projections
```

to:

```
hybrid retrieval + ContextPackage
```

This prevents MCP consumers from becoming coupled to future RAG infrastructure.

### 15. Prompts Are Deferred

MCP Prompts are not required for the initial DevLog MCP prototype.

Prompt templates could eventually help consumers perform standardized workflows
such as:

* Engineering Story preparation;
* architecture investigation;
* code review preparation;
* project-history analysis.

However, prompt ownership introduces additional questions around:

* consumer reasoning responsibilities;
* prompt versioning;
* model/provider differences;
* workflow ownership.

These concerns are not necessary to validate the initial MCP integration.

Resources and Tools should therefore be validated first.

## Consequences

### Positive

* MCP exposes engineering intent rather than DevLog internals;
* consumers remain independent from DevLog persistence and retrieval topology;
* Resources provide addressable engineering context;
* Tools provide explicit application-level capabilities;
* ContextRequest and ContextPackage remain the strategic context contracts;
* the same capabilities can serve Kiko, OpenCode, humans and future agents;
* MCP remains compatible with future Retrieval/RAG evolution;
* the initial read-only surface reduces implementation and security risk;
* provenance and bounded context remain part of the integration contract;
* capability growth remains driven by real engineering workflows.

### Trade-offs

* defining high-level capability contracts requires more design than exposing
  internal queries directly;
* some consumers may still require lower-level search capabilities;
* Resource and Tool boundaries may require refinement after real IDE usage;
* ContextRequest and ContextPackage may need to evolve before
  `get_engineering_context` reaches its intended form;
* protocol adaptation introduces mapping between MCP contracts and DevLog
  application contracts.

### Risks

* too many Tools could recreate DevLog's internal service topology through MCP;
* Resources could accidentally expose persistence-oriented models;
* consumers could begin orchestrating low-level searches instead of using
  context projection;
* `get_engineering_context` could grow into an unbounded catch-all capability;
* context results could become too large for practical agent consumption;
* MCP-specific requirements could distort ContextPackage design;
* future write capabilities could bypass proposal and validation workflows if
  governance is not preserved;
* DevLog could accidentally perform consumer reasoning rather than context
  construction.

## Alternatives Considered

### Expose Only Low-Level Resources

Rejected as the complete capability model.

Resources are useful for directly addressable engineering information.

However, requiring consumers to independently retrieve ADRs, Stories, Knowledge
and history would reproduce the context-composition problem ADR-055 is intended
to solve.

### Expose Only One `get_engineering_context` Tool

Rejected for the initial architecture.

A high-level context capability is strategically important, but direct
addressable resources and search remain useful for inspection, debugging and
precise engineering workflows.

The model should support both projected context and focused retrieval.

### Mirror the Existing REST API Through MCP

Rejected.

REST endpoints reflect web/application integration needs and should not
automatically define the MCP capability model.

MCP capabilities should be designed around engineering-agent intent.

Duplicating every REST endpoint would create protocol redundancy without
providing a meaningful MCP abstraction.

### Expose Internal Query Services Directly as Tools

Rejected.

This would couple MCP consumers to DevLog implementation details and make
internal refactoring part of the external compatibility surface.

### Introduce Write Capabilities Immediately

Rejected.

The immediate problem is engineering-context accessibility and continuity.

Mutation introduces substantially greater concerns around authorization,
validation, auditability and Knowledge governance.

Read-only capabilities are sufficient to validate the first MCP use case.

### Introduce MCP Prompts in the First Version

Rejected.

Prompt templates are not required to validate context interoperability.

They can be introduced later if standardized engineering workflows demonstrate
a concrete need.

## Explicit Non-Goals

This ADR does not define:

* exact MCP Resource URI formats;
* final Tool names;
* exact Tool input/output schemas;
* MCP transport;
* MCP SDK or Java implementation;
* authentication implementation;
* IDE-specific configuration;
* Kiko-specific behavior;
* OpenCode-specific behavior;
* automatic provider fallback;
* agent orchestration;
* coding-agent execution;
* filesystem access;
* Git execution;
* build or test execution;
* full Retrieval Layer implementation;
* vector search;
* embedding models;
* RAG infrastructure;
* MCP Prompt templates;
* direct mutation of trusted Knowledge.

## Implementation Direction

The first capability implementation should validate the smallest useful
read-only MCP surface.

A suitable progression is:

1. inventory existing DevLog application queries and projections that can support
   MCP without architectural bypasses;
2. identify the minimal project-context representation useful to an IDE agent;
3. define one initial Resource backed by an application capability;
4. expose and validate that Resource through an MCP client;
5. define one focused read-only search Tool;
6. validate search against real DevLog project context;
7. introduce the first minimal `get_engineering_context` capability using
   deterministic context construction;
8. connect an IDE agent such as OpenCode or another MCP-compatible consumer;
9. attempt a real engineering investigation using DevLog MCP context;
10. evaluate context relevance, provenance, size and missing information;
11. improve enrichment/projections only where observed MCP usage demonstrates a
    real context gap;
12. expand the MCP capability set incrementally.

The first prototype should answer a practical question:

> Can an external engineering agent retrieve enough reliable DevLog context to
> understand and continue a real project task without depending on another
> agent's conversational memory?
