# ADR-043 — Passive Agent Autonomy and Workspace Update Boundaries

* **Status:** Accepted
* **Date:** 2026-07-23

## Context

The Developer OS vision allows DevLog and future modules to work autonomously in the background.

Agents may analyse repository activity, reconstruct project history, generate documentation drafts and keep the Workspace operationally current.

Autonomy creates value only if agents can update visible project state without requiring manual intervention for every deterministic operation.

However, allowing agents to directly modify Trusted Knowledge, roadmap commitments or official documentation would violate the existing proposal-validation architecture and reduce user control.

A clear boundary is required between:

* autonomous operational updates;
* proposed semantic changes;
* trusted project state.

## Decision

Passive agents operate under **bounded autonomy**.

Agents may autonomously update deterministic and operational Workspace projections.

Agents may not directly modify Trusted Knowledge or publish official deliverables.

Semantic interpretations and authoritative changes continue to require the existing proposal and validation lifecycle.

## Autonomy Levels

The Developer OS defines progressive autonomy levels.

### Level 1 — Observation

Agents may:

* read repository evidence;
* import commits;
* calculate deterministic facts;
* update execution status;
* detect changes;
* create activity events;
* create notifications.

No semantic project knowledge is modified.

### Level 2 — Proposal

Agents may additionally:

* create immutable `ValidatableProposal` objects;
* prepare documentation drafts;
* suggest roadmap relationships;
* suggest ADR relationships;
* identify candidate significant project events;
* suggest Workspace actions.

Human or business validation remains required.

### Level 3 — Controlled Reversible Actions

Future agents may perform explicitly authorized, reversible actions such as:

* creating a draft document;
* opening a draft roadmap item;
* preparing a pull request;
* scheduling a non-critical analysis;
* updating a temporary Workspace projection.

Each action must be permission-controlled, traceable and reversible.

### Level 4 — Authoritative Autonomous Changes

Not accepted as a default architecture.

Agents must not autonomously:

* promote Trusted Knowledge;
* accept proposals;
* modify accepted ADRs;
* publish official documentation;
* merge code;
* execute destructive repository actions.

Any future exception requires a separate architectural decision.

## Operational Workspace Updates

Agents may autonomously update operational projections including:

* last repository synchronization;
* analysed commit count;
* recent activity;
* agent status;
* pending validation count;
* stale-analysis indicators;
* generated draft availability;
* notification state;
* deterministic coverage indicators.

These projections describe current system state and do not constitute Trusted Knowledge.

## Trusted Knowledge Boundary

Trusted Knowledge remains owned by the Java Core.

An agent cannot directly:

* create accepted Insights;
* alter validated historical interpretations;
* change trusted architectural relationships;
* promote a proposal;
* delete trusted knowledge.

Promotion continues to occur atomically through application services enforcing business rules.

## Documentation Boundary

Agents may generate draft deliverables from Repository Evidence and Trusted Knowledge.

Drafts may be stored and displayed autonomously.

A draft becomes official documentation only after explicit validation or publication.

The distinction between draft and official output must remain visible and traceable.

## Roadmap Boundary

Agents may:

* detect possible roadmap progress;
* propose completion of an item;
* suggest a new item;
* identify divergence between code and roadmap.

Agents may not autonomously commit the organization to a roadmap change.

Accepted roadmap modifications require user or business validation.

## Permissions

Agent capabilities must be explicitly permissioned.

Permissions may include:

* repository read;
* deterministic evidence write;
* proposal creation;
* draft creation;
* notification creation;
* external integration access;
* reversible action execution.

Agents receive only the capabilities required for their job.

Credentials and permissions must not be embedded in prompts.

## Traceability

Every autonomous action must retain:

* agent identity;
* capability;
* job identifier;
* trigger;
* affected project;
* evidence references;
* timestamp;
* output identifiers;
* authorization level.

The user must be able to understand what changed and why.

## Workspace Presentation

The Workspace should present autonomous work using user-oriented language.

Examples:

* “Three new commits were analysed.”
* “An architecture change was detected.”
* “A documentation draft is ready for review.”
* “Two findings require validation.”

The UI should not require users to understand internal job or proposal models unless they open diagnostic details.

## Human Control

The user remains the final authority.

The user may:

* approve or reject proposals;
* cancel pending jobs;
* disable passive capabilities;
* configure monitored repositories;
* define operational limits;
* review agent evidence;
* publish or discard drafts.

## Consequences

### Advantages

* useful autonomous maintenance;
* preserved trust and human control;
* clearer Workspace behaviour;
* safe evolution toward more capable agents;
* compatibility with ADR-006.

### Trade-offs

* distinction between operational and trusted state;
* additional permissions model;
* more explicit lifecycle states;
* some workflows remain manual.

These trade-offs are accepted because bounded autonomy is safer than unrestricted agent action.

## Alternatives Considered

### Agents Cannot Update Anything Without Validation

Rejected.

This would make passive monitoring too burdensome and prevent the Workspace from remaining operationally current.

### Agents Directly Update Trusted Knowledge

Rejected.

AI interpretation must never bypass validation and atomic promotion.

### Fully Autonomous Developer Agent

Rejected as the default model.

Autonomous code, roadmap or publication changes introduce unacceptable trust and governance risks without additional architectural decisions.
