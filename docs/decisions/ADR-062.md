# ADR-062 — Repository Synchronization Lifecycle and Freshness Checkpoints

## Status

Proposed

## Date

2026-08-26

## Context

The investigation `docs/investigations/repository-synchronization-freshness.md`
established the current synchronization reality of DevLog:

- DevLog knowledge advances **only** through explicit user-triggered refreshes.
  No scheduler, watcher, hook or event listener exists anywhere in the system.
- At the same time, `get_engineering_context` performs a hidden live Git
  synchronization (`fetch --prune` + forced checkout) on every read for the
  repository-structure layer, while all other evidence layers
  (`GIT_HISTORY`, `COMMIT_DIFF`, `ROADMAP`, `VALIDATED_INSIGHT`) are served
  from persisted state frozen at the last manual refresh.
- The result is **mixed-revision context returned silently**: file contents at
  HEAD beside knowledge several days old, with no freshness warning of any
  kind. This was observed live against DevLog itself (its own newest PR was
  invisible to `search_project_history` while structure evidence carried
  current-HEAD revisions).
- A baseline-comparability drift exists between story 0021
  (`findLatestComparable` selecting snapshots whose analysis has
  `targetRevision IS NULL`) and story 0085 (which now always persists the
  resolved revision as `Analysis.targetRevision`). New understanding snapshots
  could therefore never become freshness baselines.

Several accepted/proposed ADRs already frame parts of this space:

- ADR-041 — Passive Project Monitoring (Accepted): selective, incremental,
  event-driven observation; provider independence; significance detection;
  cost control. It defines *why* DevLog must observe change autonomously.
- ADR-053 / ADR-054 — Internal Context Maintenance (+ Agent): diagnosis and
  remediation surfaces.
- ADR-055 — Context Enrichment and Projection (Proposed).
- ADR-059 — Temporal Engineering Knowledge and Safe Freshness Degradation
  (Proposed): separates knowledge authority, temporal freshness and context
  eligibility.
- ADR-060 — Deterministic Core, Probabilistic Intelligence, Governed Effects
  (Proposed): deterministic facts owned by deterministic services.
- ADR-061 — Deterministic Repository Observation Baselines (Proposed):
  identity of an observation is `(Source, immutable revision)`; provenance is
  deterministic and must equal the actually observed state.

What none of them formalizes is the **lifecycle** between "the repository
changed" and "DevLog's persisted state reflects it", nor the obligation to
make freshness observable to readers.

## Problem

DevLog cannot answer honestly:

> Which repository revision does the context I am about to serve represent,
> and how far behind the repository is it?

Worse, it sometimes serves answers assembled from two different revisions
without declaring it. Before automatic synchronization can be introduced
(future stories), the architecture must first make observation, ingestion and
freshness explicit and separable.

## Decision

### 1. Three distinct concepts

```text
Change detection   = observing that a repository revision changed.
                     Produces a fact: observedRevision(source).

Synchronization    = advancing persisted DevLog source state toward a known
                     target revision (fetch, import, checkpoint update).
                     Cheap, deterministic, safe to automate.

Understanding      = building new derived knowledge from synchronized state
                     (collection snapshot, projections, AI work).
                     Expensive, gated by significance and policy.
```

These are separate concerns. Today they are fused inside one user action
("Refresh understanding") and, inversely, partially duplicated inside read
paths. Future stories will separate them operationally (detector, planner,
sync jobs). This ADR fixes the semantic boundaries so those stories have a
stable target.

### 2. Freshness checkpoints are per-source and explicit

Freshness state is keyed by `(Project, Source)` — consistent with ADR-061's
`(Source, immutable revision)` identity. Two revision notions are required:

```text
observedRevision  = latest repository revision actually observed for the
                    source (by a probe, a synchronization, or a recorded
                    pipeline observation). It describes the repository.

baselineRevision  = revision represented by the latest comparable knowledge /
                    profile snapshot for that source. It describes what
                    DevLog ingested knowledge represents.
```

`project_source_freshness.current_revision` physically stores
`observedRevision`; its meaning is hereby clarified (no rename, no migration).
`project_source_freshness.baseline_revision` stores `baselineRevision`.
Existing status enums are retained:

```text
ProjectFreshnessStatus: NO_BASELINE | CURRENT | STALE | UNKNOWN
ProjectRefreshGuidance: ESTABLISH_BASELINE | REFRESH_NOT_NEEDED |
                        REFRESH_RECOMMENDED | VERIFY_BASELINE
```

An aggregate `PARTIALLY_FRESH` state may be **derived** at contract level when
multiple sources disagree (or when content served at read time was resolved at
a revision different from the knowledge baseline). It is not a new persisted
state. Lifecycle states such as `SYNCING` or `FAILED` are deliberately NOT
introduced until an explicit synchronization lifecycle exists to produce them
honestly.

### 3. Checkpoints advance without re-probing

When a pipeline has already resolved `resolvedRevision = X` for a source, the
checkpoint may be advanced using X directly. Re-running `fetch + rev-parse`
merely to record freshness is prohibited: observations are reused, not
duplicated. After a successful understanding execution at X, the checkpoint
must be able to report CURRENT against X without any Maintenance remediation.

### 4. One ownership point for checkpoint writes

Checkpoint updates belong to a single service boundary
(`ProjectFreshnessService` / its persistence). Pipelines call this boundary;
they never manipulate freshness repositories directly. This prevents
scattered, inconsistent writers.

### 5. Reads declare freshness — no silent mixed revisions

`get_engineering_context` must expose, additively:

- an aggregate `freshnessStatus`;
- `repositoryRevision` / `contextRevision` where unambiguously derivable;
- a per-source breakdown;
- explicit warnings (`PROJECT_CONTEXT_STALE`,
  `PROJECT_CONTEXT_PARTIALLY_FRESH`) whenever the served context's knowledge
  baseline differs from the best-known observed revision.

Invariant (**no silent stale context**): if DevLog knows that its knowledge
baseline differs from the observed repository revision, it must say so in the
same response. It must never present a stale baseline as current by omission.

A dedicated MCP resource `devlog://projects/{slug}/freshness` exposes the
persisted per-source freshness projection as a read-only view.

### 6. Read paths must not mutate (direction)

Read operations should eventually operate against pinned/known revisions and
must not perform hidden synchronization (`fetch --prune`, forced checkout) as
a side effect. The current hidden workspace synchronization inside
`RepositoryContextEngine` builds is acknowledged debt: it stays until a
dedicated story can remove it without breaking enrichment correctness, and
its divergence effect must be made observable by the freshness metadata in
the meantime.

### 7. Polling is an adapter, not the architecture

Future automatic observation (scheduled probes today; Git hooks, webhooks or
Workspace events later) are **sources** feeding change detection. They are
not the synchronization model. Any scheduler-based detector must be a thin
adapter producing observations; it must never be a full-refresh loop.

An explicit synchronization lifecycle (planner, sync jobs, retries, coalescing)
is the intended long-term shape and will be specified in a future ADR once the
foundation proves stable. This ADR only fixes the intention and the semantic
vocabulary; it does not introduce job models prematurely.

## Consequences

### Positive

- Baseline comparability is restored for post-0085 revision-pinned snapshots.
- Freshness becomes observable by agents and users through the context
  contract and a dedicated MCP resource.
- Understanding refreshes leave freshness consistent without extra clicks.
- The semantic split (detect / sync / understand) prepares detector adapters,
  sync jobs and significance gating without rework.
- Multi-source projects get honest aggregate states instead of a fabricated
  single revision.

### Negative

- Read responses grow slightly (additive metadata fields).
- Until the hidden read-path synchronization is removed, freshness metadata
  exposes the divergence rather than eliminating it.
- `SYNCING`/`FAILED` honesty requires the future lifecycle; until then some
  transient conditions remain invisible.

### Accepted trade-offs

- Persisted freshness rows reflect the last observation, not a continuously
  polled truth; consumers see `checkedAt` and judge recency.
- Aggregate statuses are computed, not persisted; recomputation is cheap and
  avoids schema coupling.

## Alternatives Considered

### Manual-only (improve labels, do nothing else)

Rejected. Human memory is the failure mode under investigation; ADR-041
already rejects it.

### Scheduled full refresh (`@Scheduled refreshAllProjects()`)

Rejected as architecture. It burns the expensive resource (AI runs)
indiscriminately, ignores idle projects, multiplies zombie analyses after
crashes, and encodes the conflation of sync and understanding. A scheduled
*probe adapter* remains acceptable later precisely because of decision §7.

### Implicit synchronization triggered by reads

Rejected. A read would become unbounded-latency, budget-spending mutation;
violates read predictability and MCP tool semantics. Reads declare freshness;
explicit actions synchronize.

### Change detection + explicit synchronization lifecycle

Adopted as direction (not yet implemented here). Detection produces
observations; synchronization advances state deterministically; understanding
stays gated. This story implements only the foundation: repaired baselines,
recorded observations, observable freshness.

## Relations

- Extends ADR-041 (Passive Project Monitoring) with concrete semantics.
- Builds on ADR-060 (deterministic authority) and ADR-061 (observation
  identity) — checkpoint values follow their invariants.
- Unblocks ADR-059 follow-ups (safe freshness degradation needs a freshness
  signal to degrade from).
- Leaves Maintenance (ADR-053/054) untouched; maintenance benefits from the
  corrected baseline query without behavioral redesign.
