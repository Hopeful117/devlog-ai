# ADR-079 - Multi-Layer Context Budgets and Provider-Incomplete Diagnostics

## Status

**PROPOSED - AWAITING HUMAN REVIEW**

This proposal does not authorize implementation until accepted by the human
project owner.

## Context

The Story Context Agent has multiple bounded stages:

```text
Core candidates -> selected repository context -> serialized projection
                -> complete prompt -> provider output -> structured callback
```

The existing `truncated` flag describes Core selection reduction. A provider may
independently terminate with `response.incomplete` and
`incomplete_details.reason=max_output_tokens`. These events currently have
different owners but are easy to conflate in the caller experience.

The Core selection budget also does not account for system instructions,
grounding contract, output schema and output headroom. A valid bounded projection
can therefore still produce an incomplete provider response.

## Decision Proposed

DevLog shall model and diagnose execution budgets as distinct layers:

1. **Selection budget**: candidate/evidence count, content and repository-context
   tokens owned by Java/Core.
2. **Projection/prompt input budget**: serialized projection, instructions,
   grounding contract, guidance and output schema owned by the execution
   boundary.
3. **Provider output budget**: effective `max_output_tokens` sent to the provider.
4. **Model context capacity**: provider/model-specific input plus output ceiling.
5. **Safety margin**: reserved capacity required to avoid treating the hard limit
   as a normal response target.

An execution is budget-valid only when the effective policy can account for:

```text
prompt input + output allowance + safety margin <= model context capacity
```

The exact tokenization algorithm and model capacities remain implementation-level
details, but their provenance and certainty must be explicit. If the system
cannot establish a safe bound, it must fail closed before provider invocation
with an explicit `BUDGET_CAPACITY_UNKNOWN` diagnostic. An estimate may be used
for accounting, but it cannot authorize a provider call unless the configured
policy establishes that the estimate is safe for the provider/model.

## Normative Failure Semantics

- Core selection reduction remains valid behavior when explicitly marked.
- `truncated=true` means that the authorized candidate universe was reduced; it
  does not mean that the provider failed.
- `response.incomplete` is a provider failure, never a successful analysis.
- `max_output_tokens` must be distinguishable from context selection truncation,
  parsing failure, validation failure and transport failure.
- Incomplete provider content must not be parsed, retried as valid output,
  persisted as an analysis result or promoted to trusted knowledge.
- Corrective retry remains reserved for contract/validation failures unless a
  separately approved provider retry policy is introduced.

## Required Observability

Every Story Context execution must preserve bounded, non-secret accounting for:

- context/projection/grounding digests;
- candidate, selected and discarded counts;
- selection budget and effective usage;
- serialized projection and prompt size measurements where available;
- effective provider model and output limit;
- input/output/total usage when supplied by the provider;
- provider response status and bounded incomplete reason;
- terminal execution phase and failure category;
- task and correlation identity.

Full prompts, repository payloads, raw provider content, credentials and tokens
remain excluded from normal logs and bounded runtime diagnostics. The immutable
execution snapshot is a separate audit/grounding artifact: it may retain the
Core-authorized canonical context and exact projection required by ADR-069. That
retention is not diagnostic logging and keeps its existing access, immutability
and lifecycle controls. Normal traces retain metadata only; diagnostic traces
may retain existing prompt fields only under their configured short retention.

## Architectural Constraints Preserved

- Java/Core remains the sole authority for project scope, context construction,
  selection, trust, grounding and acceptance.
- Python remains responsible for probabilistic generation and defensive output
  validation only.
- MCP and REST remain thin adapters over the same Core capability.
- AI output remains non-trusted.
- No RAG, vector store, generic agent runtime, Python-side retrieval or automatic
  context expansion is introduced by this decision.

## Options Considered

### A. Increase all budgets immediately

Rejected. It can increase cost and provider failures without identifying which
stage is constrained.

### B. Hide truncation and let the model infer completeness

Rejected. It violates the existing abstention and grounding rules.

### C. Add accounting and preflight before changing limits

Selected. It makes retrieval failure, prompt-size failure and provider failure
measurable before tuning policy.

### D. Let Python retrieve omitted context

Rejected. It violates ADR-067 and ADR-069 Core authority boundaries.

## Consequences

### Positive

- Operators can distinguish context reduction from provider interruption.
- Budget changes become measurable and reversible.
- Incomplete output cannot be mistaken for a valid analysis.
- Live failures become replayable from bounded execution metadata.

### Costs

- Core and AI Engine contracts require additive versioned metadata.
- Provider adapters need bounded incomplete-response projections.
- Tests must cover multiple independent budget failure modes.
- Model-specific capacity knowledge must be configured or reported as unknown.

## Contract Compatibility

New Story Context budget and provider-diagnostic fields must use a versioned
Story Context contract or an additive envelope explicitly accepted by both Core
and AI Engine. Existing strict contracts with `extra="forbid"` must not receive
new fields silently.

The implementation must define and test this compatibility matrix before
deployment:

| Core | AI Engine | Required behavior |
|---|---|---|
| old | old | Existing Story Context behavior remains valid |
| new | new | New accounting and diagnostics are exchanged |
| new | old | Unsupported execution fails closed with a version diagnostic |
| old | new | New AI Engine downgrades to the old contract; new fields are not sent |

Provider-specific response details remain inside provider adapters. Core receives
only the normalized, bounded diagnostic contract.

## Implementation Boundary

The follow-up implementation Story may add accounting, preflight validation,
bounded provider diagnostics, metrics, snapshots, operator-facing errors and
regression/evaluation tests.

It may not change the Core/Python authority boundary, add autonomous retrieval,
introduce RAG, or increase production budgets without measured evidence and an
explicit review of the resulting cost and quality.
