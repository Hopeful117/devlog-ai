# ADR-064 — Hybrid Analysis Context Composition Architecture

## Status

Accepted (materialized after HUMAN architectural review; accepted 2026-08-30)

## Date

2026-08-30

## Context

Story 0098 resolved the previously measured `CATEGORY_SELECTION` bottleneck in
Analysis repository-context composition.

Real Analysis execution now receives materially more balanced selected evidence,
including:

- `COMMIT_DIFF`;
- `GIT_HISTORY`;
- `VALIDATED_INSIGHT`;
- `PREVIOUS_ANALYSIS`;
- `ROADMAP`;
- `ADR`;
- `CURRENT_ANALYSIS`;
- related source evidence where applicable.

The completed investigation
`docs/investigations/post-0098-analysis-quality-investigation.md` established
that this retrieval/composition improvement did not sufficiently improve
human-facing Analysis usefulness.

Observed failures after Story 0098:

- project understanding remains largely enumerative;
- architecture review can produce zero proposals despite rich selected context;
- engineering-decision analysis remains generic;
- proposal grounding can remain empty;
- selected history, roadmap, previous analyses, and human context are
  frequently ignored.

The completed design investigation
`docs/investigations/analysis-context-composition-design.md` traced the exact
current path from deterministic evidence selection to AI prompt construction and
found the strongest information loss after selection and before AI
interpretation.

The current pattern is:

```text
rich deterministic engineering knowledge
        ↓
selection
        ↓
projection / composition
        ↓
loss of hierarchy,
relationships,
chronology,
provenance,
salience
        ↓
large weakly structured AI-facing context
        ↓
weak synthesis
```

This is a different problem from retrieval/category selection.

Existing ADRs already govern adjacent concerns:

- ADR-006 — AI proposal lifecycle and governed promotion;
- ADR-038 — deterministic Repository Context Engine;
- ADR-044 — bounded enrichment remains post-selection and bounded;
- ADR-059 — temporal knowledge and safe freshness degradation;
- ADR-060 — deterministic core, probabilistic intelligence, governed effects;
- ADR-061 — deterministic repository observation provenance;
- ADR-062 — synchronization lifecycle and freshness observability;
- ADR-063 — shared retrieval/composition vocabulary and consumer-owned
  composition.

What none of them defines explicitly is the architecture of the deterministic
composition boundary that transforms already selected engineering knowledge into
an AI-facing Analysis context that remains semantically structured, bounded,
traceable, and useful for synthesis.

## Problem

DevLog can now select balanced engineering evidence, but the current Analysis
context projection largely flattens that selection into a weakly structured AI
payload. Important information remains technically present yet becomes
operationally weak for the model.

Specifically:

- semantic hierarchy is weak;
- explicit known relationships are partially lost before AI generation;
- chronology survives mostly as low-salience metadata;
- provenance and ranking context are weakened or discarded;
- selected evidence categories compete in one large low-hierarchy payload;
- objective-specific salience is not represented strongly enough.

The architectural question is therefore:

> How should DevLog deterministically compose already selected engineering
> knowledge into an AI-facing Analysis context that preserves usable semantic
> hierarchy, explicit trusted relationships, chronology, provenance, stable
> identity, and objective-aware salience without allowing the AI to control
> composition policy or deterministic truth?

## Decision

DevLog adopts a **Hybrid Analysis Context Composition Architecture** for
generic Analysis generation.

The deterministic layer SHALL transform selected engineering evidence into a
shared AI-facing Analysis context architecture conceptually organized as:

```text
Analysis Context
│
├── Objective / Scope
│
├── Semantic Sections
│   ├── Project State
│   ├── Architecture
│   ├── Decisions
│   ├── History
│   ├── Roadmap
│   ├── Validated Knowledge
│   └── Repository Changes
│
├── Relationship Highlights
│
├── Timeline Highlights
│
└── Grounding Support
```

These names are architectural concepts, not mandated final DTO field names.

### 1. Selection and composition are separate responsibilities

Selection and composition are distinct layers.

```text
Selection   = choose the bounded evidence set
Composition = organize the chosen evidence for AI interpretation
```

Story 0098 solved a selection bottleneck. This ADR governs the next layer:
composition.

### 2. Context composition remains deterministic

The Java/backend deterministic layer remains responsible for organizing what
DevLog already knows.

The AI layer does not control:

- evidence budgets;
- section construction;
- deterministic salience policy;
- relationship projection policy;
- timeline projection policy;
- grounding identity rules.

This extends ADR-038, ADR-060, and ADR-063.

### 3. Deterministic / AI responsibility boundary

DevLog formalizes the boundary:

```text
Java deterministic layer
→ organizes what DevLog knows

AI layer
→ interprets and synthesizes that context
```

The deterministic layer owns representation of already-known facts such as:

- Analysis objective;
- Analysis scope;
- evidence/category boundaries;
- stable identity;
- known provenance;
- deterministic salience/ranking information where relevant;
- timestamps and known chronology;
- explicit trusted relationships already represented by DevLog;
- bounded composition.

The deterministic layer MUST NOT manufacture unsupported semantic
relationships or causal conclusions.

For example:

- projecting `A occurred before B` is valid when supported by timestamps,
  commit ordering, or an explicit before/after model;
- projecting `A caused B` is NOT valid unless DevLog already has an explicit,
  trusted relationship or equivalent deterministic evidence model supporting
  that causal claim.

The AI layer owns:

- interpretation;
- synthesis;
- explanation;
- higher-level reasoning;
- proposal framing;
- inferred relationships where permitted by existing AI governance.

AI interpretations remain governed by ADR-006 and related proposal/validation
rules.

### 4. One shared context architecture, objective-specific deterministic emphasis

Generic Analysis objectives SHALL share one underlying composition
architecture.

Objective-specific behavior SHALL be expressed through deterministic emphasis,
not duplicated composition pipelines.

Conceptually:

```text
shared context architecture
        +
objective-specific deterministic emphasis
```

This means different objectives may receive different section ordering,
highlight emphasis, and bounded salience treatment while still consuming the
same architectural model.

The current generic objectives illustrate the pattern:

- Understand this project:
  - may emphasize project state, purpose, validated knowledge, and recent
    evolution;
- Review the architecture:
  - may emphasize architecture knowledge, ADRs, relevant source evidence,
    relationship highlights, and timeline/evolution cues;
- Analyze engineering decisions:
  - may emphasize decisions, ADRs, roadmap, history, explicit relationships,
    and grounding support;
- Prepare README information:
  - may emphasize project state, installation/usage signals, and validated
    project knowledge.

Exact weights, quotas, and ordering policies remain implementation policy
unless a future ADR elevates a specific constraint.

### 5. Semantic sections are the primary hierarchy

The shared Analysis context SHALL provide semantic hierarchy rather than one
undifferentiated evidence blob.

Architecturally relevant semantic concerns include:

- current project state;
- architecture;
- engineering decisions;
- project/history evolution;
- roadmap;
- validated knowledge;
- repository changes.

Sections MAY evolve over time.

Not every objective must populate every section equally.

### 6. Relationship Highlights preserve explicit trusted relationship semantics

`Relationship Highlights` are adopted as a bounded deterministic projection of
relevant explicit relationships already known by DevLog.

Important invariants:

- derived only from existing known relationships;
- bounded;
- deterministic;
- traceable to underlying entities/evidence;
- objective-aware where appropriate;
- not an AI-generated knowledge graph;
- not a replacement for canonical domain relationships.

Current examples of relationship sources that this architecture must be able to
preserve when relevant include:

- Observation -> supporting Facts;
- Insight -> Analysis / Proposal / validation lineage;
- EngineeringEvent -> Analysis / Proposal / Source;
- Decision -> Proposal;
- `KnowledgeRelation` edges such as:
  - `RESOLVES`;
  - `CAUSED_BY`;
  - `RELATES_TO`;
  - `DERIVED_FROM`;
  - `ADDRESSES`;
  - `INFORMED_BY`;
- repository `relatedReferences`;
- commit-parent relationships;
- architecture knowledge evidence references.

This ADR does not create a new graph database, graph runtime, or generic graph
source of truth. It governs projection of already-known relationship semantics.

### 7. Timeline Highlights preserve usable chronology

`Timeline Highlights` are adopted as a bounded deterministic representation of
relevant chronology.

Potential source signals already available include:

- facts;
- observations;
- Analysis timestamps;
- insights;
- decisions;
- challenges / context inputs;
- Engineering Events;
- commits / diffs;
- evolution scopes;
- Story / ADR / roadmap temporal information where supported.

Timeline projection MUST:

- preserve known chronology;
- remain bounded;
- remain traceable;
- avoid inventing causal relationships;
- avoid blindly privileging recency;
- support engineering evolution understanding.

This ADR does not introduce a full temporal knowledge graph.

### 8. Grounding support is an architectural capability

The composed Analysis context MUST preserve stable evidence identity
sufficiently for AI outputs to reference their supporting context.

Grounding support is therefore an architectural requirement of context
composition.

However, the currently observed engineering-decision grounding defect is
explicitly separate from this ADR's core design problem.

Current defect trace:

```text
selected evidence identity
→ grounding allow-list
→ decision output contract lacks grounding fields
→ decision service persists empty grounding arrays
```

That is a contract/mapping defect to be addressed separately. This ADR only
establishes the architectural invariant that grounding capability must remain
available end-to-end.

### 9. Architecture-review semantics remain separate

The current `Review the architecture` objective behaves operationally more like
`detect meaningful new architecture delta`, and zero proposals are explicitly
allowed.

This ADR does NOT redefine that product/Intent semantic.

The hybrid context composition architecture must be capable of supporting
architecture synthesis, but it must not silently change the current Intent
contract.

Any change to architecture-review output semantics requires separate HUMAN
product review.

### 10. Result projection remains separate

Canonical `/result` currently exposes only a limited evidence preview.

This can hide internal context diversity, but result projection is a separate
concern from AI generation context quality.

This ADR does NOT solve canonical result projection.

The invariant is:

```text
AI generation context quality
!=
human-facing result projection quality
```

### 11. Composition remains a projection, not a new source of truth

The composed AI-facing Analysis context is a projection.

It is not authoritative canonical project knowledge.

Canonical domain knowledge remains the source of truth in existing domain and
persistence models. Prompt-oriented composition MUST NOT create duplicated
persisted truth solely for AI consumption.

This extends ADR-006, ADR-059, ADR-060, and ADR-063.

### 12. Persistence and versioning direction

No persistence migration is required by this architectural decision.

Preferred direction:

- retain existing JSONB snapshot persistence where possible;
- evolve composition through versioned or backward-compatible projections;
- keep deterministic projections reconstructible from canonical state.

### 13. Compatibility with future retrieval architecture

This architecture must remain compatible with future Retrieval Layer / RAG work.

However, this ADR explicitly does NOT introduce:

- embeddings;
- vector databases;
- semantic retrieval infrastructure;
- ContextPack retrieval architecture;
- external graph databases;
- Engineering Query;
- new agents.

The current decision operates after evidence selection. Future retrieval
infrastructure may feed evidence into this composition architecture, but it is
outside this ADR's implementation scope.

## Architectural Invariants

1. Selection and composition are separate responsibilities.
2. Context composition remains deterministic.
3. AI does not control evidence budgets or deterministic composition policy.
4. Known explicit relationships should not be unnecessarily discarded before AI
   interpretation.
5. Chronology should be made operationally usable when relevant.
6. Provenance and stable evidence identity must remain available where needed
   for grounding.
7. Deterministic composition must not invent unsupported semantics.
8. One shared Analysis context architecture serves generic objectives.
9. Objective-specific behavior is expressed through deterministic emphasis
   rather than duplicated pipelines.
10. Composed AI context is a projection, not trusted canonical knowledge.
11. AI-generated interpretations remain governed by existing
   proposal/validation rules.
12. Composition must remain bounded and measurable.
13. Exact quotas, highlight counts, weights, and tuning parameters remain
   implementation policy unless they become architectural constraints.

## Consequences

### Positive

- stronger semantic hierarchy for AI-facing Analysis context;
- better preservation of explicit known relationships;
- better support for temporal reasoning and engineering evolution;
- stronger grounding potential through preserved stable identity;
- improved model attention over selected evidence;
- better future compatibility with DevLog Agent and future retrieval
  architecture;
- clearer architectural boundary between deterministic organization and AI
  synthesis.

### Negative

- larger and more complex composition contract;
- possible prompt-size growth;
- additional deterministic composition logic;
- greater need for objective-aware composition tests;
- backward-compatible projection readers may be required for historical
  snapshots.

### Risks

- relationship projection may introduce noise if poorly bounded;
- timeline projection may over-bias recency if not measured carefully;
- reintroducing provenance and hierarchy may increase payload cost;
- some objective underperformance may still come from separate product-contract
  issues rather than composition alone.

## Rejected Alternatives

### Flat selected-knowledge JSON as the long-term Analysis composition model

Rejected as the target architecture because observed evidence shows weak
hierarchy, weak relationship utilization, weak chronology salience, and poor
model attention over rich selected context.

This does NOT mean JSON serialization itself is inherently wrong. The rejected
approach is the current weak information structure, not the existence of JSON.

### Structured Sections only

Rejected as the recommended architecture because it improves hierarchy but is
insufficient on its own for preserving explicit relationships and temporal
semantics strongly enough.

### Generic Evidence + Relationship + Timeline model

Rejected as the recommended architecture because it maximizes raw information
preservation but introduces greater complexity and weaker direct model usability
than the hybrid approach.

### AI-driven composition

Rejected because deterministic composition and trusted-context governance belong
to backend policy, not to AI model behavior.

### Immediate RAG / vector solution

Rejected as premature because the evidenced bottleneck exists after current
selection and before AI interpretation. Retrieval infrastructure would not by
itself solve the current composition failure.

## Incremental Implementation Strategy

This ADR authorizes incremental implementation, not a big-bang replacement.

Recommended sequence:

```text
Context Composition ADR
        ↓
Relationship preservation
        ↓
benchmark
        ↓
Structured semantic sections
        ↓
benchmark
        ↓
Timeline highlights
        ↓
benchmark
        ↓
Objective-specific deterministic emphasis
        ↓
benchmark
```

Each slice must be independently measurable.

The following remain explicitly separate workstreams:

- engineering-decision grounding defect;
- architecture-review product/Intent semantics;
- canonical result preview behavior.

## Measurement Requirement

Composition changes MUST be benchmarked against stable Analysis scenarios.

Current benchmark objectives:

- Understand this project;
- Review the architecture;
- Analyze engineering decisions.

Deterministic measures should include:

- relationship survival;
- timeline-highlight presence;
- evidence identity preservation;
- grounding availability;
- objective-relevant section presence;
- usage of non-`COMMIT_DIFF` evidence.

Qualitative HUMAN review should assess:

- project-understanding depth;
- architecture synthesis;
- historical reasoning;
- causal-chain quality;
- engineering-decision quality;
- grounding quality.

Proposal count alone is NOT an acceptable quality metric.

## Relations

- Extends ADR-038 by refining the deterministic composition boundary after
  selection and before AI interpretation.
- Extends ADR-063 by defining the architecture of consumer-owned Analysis
  composition more precisely.
- Preserves ADR-006 governance: AI outputs remain proposals, not trusted
  knowledge.
- Preserves ADR-060 boundary: deterministic organization, probabilistic
  synthesis, governed effects.
- Builds on ADR-059 and ADR-061 by making chronology and provenance usable in
  composed context without inventing semantic authority.
- Leaves ADR-044 unchanged: enrichment remains bounded and post-selection.
- Leaves ADR-062 unchanged: freshness/synchronization remain separate concerns.
