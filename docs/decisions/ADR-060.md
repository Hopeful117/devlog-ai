# ADR-060 — Deterministic Core, Probabilistic Intelligence, and Governed Effects

## Status

Proposed

## Date

2026-08-18

## Context

DevLog AI is evolving from a documentation assistant into an engineering context and project-memory system capable of observing repository evolution, understanding engineering changes, maintaining project knowledge, and providing reliable context to humans and AI agents.

This evolution increasingly combines two fundamentally different forms of reasoning:

- deterministic processing based on observable repository and domain facts;
- probabilistic interpretation performed by AI models.

Both are valuable, but they do not provide the same guarantees.

Deterministic mechanisms are appropriate when DevLog can establish a fact objectively from repository state, persisted domain state, explicit relationships, or deterministic rules.

Examples include:

- a file exists or no longer exists;
- a commit modified a given file;
- a dependency version changed;
- a proposal has a given lifecycle status;
- an Insight is ACTIVE, SUPERSEDED, or ARCHIVED;
- a lineage relationship exists;
- an endpoint, symbol, or declaration disappeared;
- a deterministic invariant is violated.

AI-assisted reasoning is appropriate when DevLog must interpret meaning rather than merely establish facts.

Examples include:

- determining whether several changes represent one architectural evolution;
- evaluating whether a repository change invalidates an architectural assumption;
- understanding whether documentation still describes the current implementation;
- correlating commits, Engineering Stories, ADRs, Insights, and repository changes;
- identifying likely maintenance work;
- explaining why a knowledge item may have become semantically stale;
- proposing documentation or knowledge updates.

Trying to solve all of these problems deterministically would lead to increasingly complex rule engines that still cannot reliably perform semantic interpretation.

Conversely, delegating objectively observable facts to probabilistic models would reduce reproducibility, explainability, reliability, and auditability.

DevLog therefore requires an explicit architectural boundary between deterministic facts, probabilistic interpretation, and authoritative effects.

This requirement becomes especially important with Temporal Knowledge.

ADR-059 introduces a distinction between:

- Authority;
- Freshness;
- Context Eligibility.

A knowledge item may remain authoritative while its semantic freshness becomes uncertain.

For example:

    ACTIVE Insight
        +
    repository evolution
        ↓
    temporal suspicion

must not automatically imply:

    ACTIVE → SUPERSEDED

A deterministic signal may sometimes be sufficient to establish temporal degradation.

In other cases, determining whether a repository evolution actually invalidates the semantic meaning of a knowledge item requires interpretation.

The Temporal Knowledge architecture must therefore support both deterministic and probabilistic reasoning without allowing probabilistic conclusions to silently mutate trusted project knowledge.

The same architectural problem applies beyond Temporal Knowledge.

DevLog's three major responsibilities can be described as:

1. Observe
2. Understand
3. Maintain

Each responsibility requires a different balance between deterministic and probabilistic processing.

A common architectural policy is therefore required.

---

## Decision

DevLog AI SHALL follow the architectural principle:

> **Deterministic Core, Probabilistic Intelligence, Governed Effects.**

Deterministic processing SHALL be preferred whenever a result can be objectively established from available facts.

Probabilistic reasoning MAY be used when semantic interpretation, correlation, explanation, classification, or synthesis is required.

Probabilistic conclusions MUST NOT silently cross an authority boundary.

The closer an operation is to modifying authoritative project state, the stronger its deterministic and governance guarantees MUST become.

This decision applies across DevLog's Observe, Understand, and Maintain responsibilities.

---

## 1. Deterministic facts are preferred over probabilistic reconstruction

DevLog MUST NOT use AI reasoning to infer information that can be reliably established through deterministic mechanisms.

For example:

    Git diff
        → deterministic extraction

is preferred over:

    repository files
        → LLM guesses what changed

Likewise:

    persisted proposal status
    lineage relationships
    file existence
    commit metadata
    dependency changes
    repository structure

SHOULD be obtained through deterministic services whenever possible.

AI models MAY consume these facts, but SHOULD NOT replace their authoritative extraction.

The preferred processing direction is:

    deterministic extraction
        ↓
    structured evidence
        ↓
    probabilistic interpretation

rather than:

    raw project state
        ↓
    probabilistic reconstruction of facts

This improves:

- reproducibility;
- explainability;
- auditability;
- cost control;
- testability;
- reliability.

---

## 2. Observation distinguishes facts from interpreted signals

The Observe responsibility MAY contain both deterministic and probabilistic capabilities.

However, DevLog MUST distinguish between objectively observed facts and interpretive signals.

Conceptually:

    Observation
        ├── Observed Fact
        └── Inferred Signal

An Observed Fact represents information directly established from authoritative project or repository state.

Examples:

- file modified;
- dependency changed;
- symbol removed;
- proposal accepted;
- Insight superseded;
- commit introduced;
- lineage edge present.

An Inferred Signal represents an interpretation derived from one or more facts.

Examples:

- a change may affect an architectural boundary;
- documentation may have become inconsistent;
- an Insight may no longer describe current reality;
- several commits may represent one engineering evolution.

An inferred signal MUST NOT be presented as though it were an observed fact.

---

## 3. Understanding is intentionally hybrid

The Understand responsibility is expected to contain the strongest probabilistic component in DevLog.

Semantic understanding frequently requires reasoning that cannot be expressed efficiently or reliably through deterministic rules alone.

The preferred architecture is:

    deterministic facts
        +
    trusted project context
        +
    lineage
        +
    historical knowledge
        ↓
    AI interpretation
        ↓
    structured proposal / assessment
        ↓
    deterministic governance

AI reasoning MAY therefore:

- correlate evidence;
- identify semantic relationships;
- explain engineering evolution;
- detect likely contradictions;
- assess potential knowledge impact;
- classify engineering meaning;
- generate summaries;
- propose knowledge;
- propose maintenance actions.

However, an AI interpretation remains an interpretation until it crosses an explicitly governed validation boundary.

This preserves ADR-006.

AI-generated knowledge MUST continue to use the ValidatableProposal lifecycle where authoritative project knowledge is concerned.

---

## 4. Maintenance is not required to remain fully deterministic

DevLog's Maintain responsibility SHALL NOT be restricted to deterministic detection.

Maintenance MAY combine deterministic and probabilistic capabilities.

The maintenance pipeline SHOULD conceptually follow:

    Detect maintenance need
        ↓
    Assess impact
        ↓
    Propose remediation
        ↓
    Validate / govern
        ↓
    Execute controlled effect

Different stages may use different reasoning modes.

### Deterministic maintenance

Examples include:

- broken references;
- missing files;
- obsolete explicit endpoints;
- deterministic dependency mismatches;
- invalid persisted relationships;
- violated lifecycle invariants.

### AI-assisted maintenance

Examples include:

- documentation likely describing an obsolete architecture;
- ADR potentially requiring reconciliation;
- knowledge likely invalidated by repository evolution;
- documentation sections likely requiring rewriting;
- several artifacts likely describing conflicting states.

AI MAY detect, explain, prioritize, and propose maintenance work.

AI MAY generate candidate remediation artifacts.

AI MUST NOT silently mutate authoritative knowledge solely because a probabilistic analysis recommends doing so.

---

## 5. Authority boundaries govern effects

The critical architectural distinction is not whether AI participates in a workflow.

The critical distinction is whether a result can modify authoritative state.

Therefore:

> **No probabilistic conclusion may silently cross an authority boundary.**

Examples of authority boundaries include:

- promoting a ValidatableProposal into trusted knowledge;
- changing the authoritative lifecycle of an Insight;
- superseding trusted knowledge;
- modifying an accepted Decision;
- altering validated project knowledge;
- performing irreversible repository mutations;
- changing governance state.

Probabilistic reasoning MAY produce information used before such a boundary.

Crossing the boundary MUST require an explicitly defined governance mechanism.

Depending on the operation, that mechanism MAY include:

- deterministic validation;
- domain invariants;
- human approval;
- policy evaluation;
- controlled workflow execution;
- combinations of the above.

---

## 6. Governance strength increases with effect authority

DevLog SHALL apply progressively stronger guarantees as processing approaches authoritative mutation.

Conceptually:

    Observation
        ↓
    Interpretation
        ↓
    Proposal
        ↓
    Validation
        ↓
    Authoritative Effect

Probabilistic reasoning may increase during interpretation.

Governance and deterministic guarantees must increase as the system approaches an authoritative effect.

The architecture SHOULD therefore favor:

    Observation
        mostly deterministic

    Interpretation
        hybrid

    Proposal
        probabilistic reasoning allowed

    Validation
        strongly governed

    Authoritative mutation
        controlled and auditable

No global deterministic/probabilistic percentage is defined.

The appropriate balance depends on the semantic responsibility of each operation.

---

## 7. Reasoning origin must remain distinguishable

When a domain result depends on interpretation, DevLog SHOULD preserve enough information to distinguish how the conclusion was produced.

At minimum, future models SHOULD be capable of distinguishing conceptually between:

    DETERMINISTIC
    AI_ASSISTED
    HUMAN

This classification represents epistemic origin, not authority.

For example:

    origin = AI_ASSISTED

does not automatically mean that the result is untrusted.

Likewise:

    origin = DETERMINISTIC

does not automatically grant permission to mutate authoritative knowledge.

Origin and authority are separate concerns.

A confidence score SHOULD NOT be required for deterministic conclusions merely to force all reasoning into a probabilistic representation.

Confidence MAY be appropriate for probabilistic interpretations.

---

## 8. Temporal Knowledge applies this policy directly

ADR-059 Temporal Knowledge SHALL follow ADR-060.

Temporal assessment may therefore use multiple reasoning modes.

Example:

    Repository change
        ↓
    deterministic facts
        ↓
    temporal signals
        ↓
    deterministic or AI-assisted assessment
        ↓
    governed context eligibility

Some temporal conclusions may be objectively derived.

Example:

    knowledge explicitly depends on dependency version X
        +
    dependency X replaced
        ↓
    deterministic temporal signal

Other cases require interpretation.

Example:

    architectural Insight
        +
    multiple repository refactorings
        ↓
    AI-assisted semantic assessment

An AI-assisted temporal assessment MAY conclude that knowledge is likely stale or suspicious.

It MUST NOT automatically change the authoritative lifecycle of that knowledge solely from that conclusion.

In particular:

    ACTIVE + temporally suspect

MUST remain representable without requiring:

    ACTIVE → SUPERSEDED

Temporal freshness and knowledge authority remain separate dimensions as defined by ADR-059.

---

## 9. Context eligibility may use governed temporal conclusions

Context selection MAY use temporal assessments to prevent agents from receiving knowledge that is likely misleading.

However, context eligibility MUST be determined through an explicit policy.

For example, a future policy may distinguish between:

    deterministic stale
        → exclude

    AI-assisted suspected stale
        → degrade / warn / request review

    human-confirmed stale
        → exclude from current context

The exact policy is intentionally deferred to Temporal Knowledge implementation decisions.

ADR-060 establishes only that reasoning origin and authority MUST remain distinguishable.

---

## 10. AI-assisted maintenance produces proposals before authoritative effects

When AI identifies required maintenance, its preferred output SHALL be a structured proposal rather than an immediate authoritative mutation.

Examples include:

    DocumentationMaintenanceProposal
    TemporalAssessmentProposal
    KnowledgeReconciliationProposal
    ADRMaintenanceProposal

Exact domain types are deferred.

Where the proposed maintenance would create or modify trusted knowledge, ADR-006 governance SHALL remain applicable.

This allows DevLog to become increasingly proactive without becoming an uncontrolled autonomous editor of project truth.

---

## 11. Deterministic services remain first-class architecture

The introduction of AI-assisted reasoning MUST NOT cause deterministic domain services to be collapsed into generic agents.

Capabilities such as:

- repository extraction;
- lineage reconstruction;
- lifecycle diagnostics;
- validation;
- deterministic freshness signals;
- context budgeting;
- evidence ranking;
- governance rules;

SHOULD remain deterministic services where their semantics are objectively defined.

Agents MAY orchestrate or consume these capabilities.

They SHOULD NOT reimplement them probabilistically.

---

## 12. Probabilistic reasoning must consume structured context where possible

AI reasoning SHOULD receive curated engineering context rather than unrestricted raw repository state whenever practical.

The preferred direction is:

    repository / domain state
        ↓
    deterministic extraction
        ↓
    structured engineering context
        ↓
    probabilistic interpretation

This aligns ADR-060 with DevLog's evolution toward an Engineering Context Engine for agents.

It also reinforces the importance of DevLog's documentation-assistant responsibility.

High-quality AI interpretation depends on:

- accurate documentation;
- maintained ADRs;
- trusted knowledge;
- repository evidence;
- lineage;
- Engineering Stories;
- temporal state.

Improving context selection cannot compensate indefinitely for incorrect or abandoned project documentation.

Maintenance of project knowledge therefore remains a core DevLog responsibility.

---

## 13. Probabilistic outputs must remain explainable through evidence

AI-assisted conclusions SHOULD retain references to the evidence used to produce them whenever the domain operation supports such provenance.

A future consumer SHOULD be able to distinguish:

    conclusion
        ↓
    reasoning origin
        ↓
    supporting evidence
        ↓
    relevant project state

This is especially important for:

- Temporal Knowledge;
- maintenance proposals;
- architectural interpretation;
- security analysis;
- context eligibility decisions.

Data Lineage SHOULD be reused where applicable rather than introducing duplicate provenance systems.

---

## 14. Human absence must not force false certainty

DevLog must remain useful when a user does not actively maintain project knowledge.

The absence of human validation MUST NOT force DevLog to continue presenting questionable information as unquestionably current.

Likewise, absence of human intervention MUST NOT authorize DevLog to rewrite trusted project history.

The system SHOULD therefore support intermediate states such as:

    authoritative but temporally suspect

and:

    maintenance recommended but not validated

This allows DevLog to degrade confidence safely without fabricating certainty or silently rewriting authority.

This principle follows ADR-059:

> Unknown or explicitly uncertain knowledge is preferable to false certainty.

---

## Consequences

### Positive

- Establishes a common AI governance model across DevLog.
- Preserves deterministic guarantees where objective facts exist.
- Allows AI reasoning where semantic interpretation provides genuine value.
- Prevents probabilistic outputs from silently becoming authoritative truth.
- Supports proactive maintenance without uncontrolled autonomous mutation.
- Provides a clean foundation for Temporal Knowledge.
- Reinforces ADR-006 rather than bypassing it.
- Improves auditability by distinguishing reasoning origin.
- Avoids unnecessary deterministic rule-engine complexity.
- Avoids using expensive probabilistic reasoning for objectively calculable facts.
- Creates an architectural pattern reusable by future Developer OS capabilities.
- Supports future Security Audit and engineering workflow agents.
- Provides a natural foundation for increasingly autonomous but governed agents.

### Negative

- Hybrid workflows are more complex than purely deterministic pipelines.
- Some operations will require explicit classification of reasoning origin.
- AI-assisted assessments require governance and evidence handling.
- Context eligibility may eventually need different policies depending on assessment origin.
- Testing must distinguish deterministic correctness from probabilistic contract validation.
- Future agents cannot simply write directly to authoritative project state.
- Some maintenance actions will require additional proposal/validation workflows.

---

## Alternatives Considered

### Alternative A — Keep DevLog maintenance entirely deterministic

Rejected.

Deterministic mechanisms are appropriate for objectively observable maintenance problems but are insufficient for semantic documentation and knowledge maintenance.

This approach would eventually require increasingly complex rule engines while still failing to understand many architectural changes.

---

### Alternative B — Make AI the primary reasoning mechanism for all DevLog capabilities

Rejected.

Using probabilistic models to reconstruct objectively available facts would reduce:

- reproducibility;
- reliability;
- auditability;
- explainability;
- testability.

Deterministic extraction must remain preferred where possible.

---

### Alternative C — Allow sufficiently confident AI conclusions to directly mutate trusted knowledge

Rejected.

A confidence score is not an authority boundary.

Even high-confidence probabilistic conclusions may be wrong.

Trusted knowledge lifecycle changes require explicit governance.

---

### Alternative D — Require human validation for every AI-produced result

Rejected as a universal policy.

Some AI outputs are advisory or contextual and do not cross an authority boundary.

Requiring human validation for every interpretation would unnecessarily limit DevLog's usefulness and future autonomy.

Human validation SHOULD be required where governance policy determines it is necessary, particularly for authoritative effects.

---

### Alternative E — Treat deterministic and probabilistic conclusions identically

Rejected.

Their epistemic guarantees differ.

A deterministic conclusion derived from explicit repository facts and an AI interpretation based on semantic reasoning should not be represented as though they were produced by the same mechanism.

Reasoning origin must remain distinguishable.

---

## Explicit Non-Goals

ADR-060 does NOT:

- define a universal deterministic/probabilistic ratio;
- define specific LLM providers or models;
- define confidence thresholds;
- define Temporal Knowledge states;
- define the final TemporalAssessment schema;
- define context eligibility policy;
- introduce a new persistence table;
- implement autonomous documentation mutation;
- authorize AI to supersede trusted knowledge;
- replace ADR-006;
- replace Data Lineage;
- introduce Event Sourcing;
- define agent orchestration infrastructure;
- define the future Security Audit module;
- define generic workflow execution.

These concerns belong to dedicated decisions or implementation stories.

---

## Implementation Direction

ADR-060 should initially influence architecture rather than trigger a broad refactoring.

The first concrete consumer SHOULD be Temporal Knowledge.

The Temporal Knowledge design SHOULD investigate a model capable of representing, at minimum:

    TemporalAssessment
        knowledge reference
        conclusion
        reasoning origin
        supporting evidence
        evaluation time

Additional concepts such as:

- confidence;
- repository revision;
- persistence;
- transition history;
- governance requirement;

SHOULD be introduced only when justified by the Temporal Knowledge domain model.

The current preferred Temporal Knowledge direction is hybrid:

1. calculate current temporal state deterministically where possible;
2. use AI-assisted interpretation where semantic reasoning is necessary;
3. preserve reasoning origin;
4. persist meaningful temporal transitions when auditability requires it rather than blindly persisting every evaluation;
5. derive context eligibility through explicit deterministic policy;
6. never automatically mutate trusted knowledge authority from a probabilistic temporal conclusion.

The first Temporal Knowledge Story SHOULD remain small and establish the foundational domain semantics before introducing event-driven reevaluation, autonomous maintenance, or broad context integration.
