# ADR-072 - Sign in with ChatGPT for User-Authorized AI Usage

## Status

ACCEPTED - approved by the human project owner on 2026-10-30.

## Date

2026-10-30

## Context

DevLog AI currently authenticates model providers with server-side API keys.
That model is operationally simple, but it does not allow a user to authorize
AI execution with an eligible ChatGPT plan. OpenAI documents Sign in with
ChatGPT as two separable capabilities:

- identity: verified account information for application sign-in;
- ChatGPT plan usage: explicit permission to use eligible Responses API calls
  against the user's ChatGPT plan or available credits.

The two permissions do not grant access to ChatGPT conversations and must not
be treated as an API-key exchange. The authorization code flow uses PKCE,
state and nonce. For the open-source application flow, the first authorization
uses `dynamic_agent_client`; OpenAI returns an issued client ID that the
application persists per ChatGPT account. The resulting access token is a user credential and must be
handled as a secret.

The existing architecture requires Java/Core to remain authoritative for
project scope, deterministic context, trust, grounding and acceptance. Python
may execute probabilistic generation, but it must not persist trusted knowledge
or reconstruct project context. Introducing user-authorized model usage must
preserve those boundaries.

## Problem

DevLog needs to support a user-authorized OpenAI execution path without:

- embedding ChatGPT credentials in repository configuration;
- confusing ChatGPT identity with project authorization;
- silently falling back to an API-key path when the user did not authorize it;
- sending OAuth tokens to Java/Core, MCP clients, logs or callbacks;
- using unsupported ChatGPT-plan request semantics;
- allowing an expired, revoked or insufficiently scoped grant to produce an
  apparently successful AI task.

## Decision

DevLog will add a user-authorized OpenAI provider based on Sign in with
ChatGPT. The first implementation is an opt-in provider path in the Python AI
Engine, with the following flow:

```text
User browser
  -> OpenAI authorization endpoint (`https://auth.openai.com`)
  -> callback with code/state
  -> AI Engine exchanges code using PKCE
  -> encrypted/secure token storage owned by the deployment
  -> Responses API with user access token
  -> existing Core callback and validation path
```

The implementation will request identity scopes and the documented ChatGPT
plan usage permissions, including `openid`, `profile`, `email`,
`offline_access`, `resource.invoke` and `chatgpt.tokens.use.direct`, subject to
the scopes actually approved for the registered application. The resource is
`https://api.openai.com/v1`.

The initial open-source registration uses `dynamic_agent_client` without a
client secret. The client ID returned by OpenAI is stored with the encrypted
credential and reused for later authorization, ID-token audience validation
and refresh operations.

The provider will call only the public Responses API endpoint. Every
ChatGPT-plan inference request MUST set:

- `store=false`;
- `stream=true`;
- `Authorization: Bearer <user access token>`.

The provider considers a request successful only after `response.completed`.
`response.failed`, `response.incomplete`, an invalid token, a missing required
scope and an interrupted stream are explicit failures.

## Architectural Boundaries

1. OAuth identity is not project authorization. Java/Core continues to decide
   whether a principal may access a project or capability.
2. OAuth tokens remain inside the AI Engine provider boundary. They are never
   included in `AiTask`, Core callbacks, MCP responses, prompts, traces or
   ordinary logs.
3. The AI Engine receives the already authorized Core context exactly as it
   does for other providers. Sign in with ChatGPT changes model credentials,
   not context construction or grounding authority.
4. AI output remains transient and non-trusted until the existing Core-owned
   validation and promotion workflow accepts it.
5. The API-key provider remains available as a separately configured mode. No
   implicit fallback between user-authorized and server-key credentials is
   allowed.
6. Refresh tokens are stored only through an explicit deployment secret-store
   integration. Plaintext persistence, repository configuration and database
   logging are forbidden.
7. OAuth transactions are single-use, short-lived and bound to the browser
   session, redirect URI, state and PKCE verifier. Callback state mismatches,
   reuse and expiration fail closed.

## Scope and Consent

The application must distinguish these states:

- identity authorized;
- ChatGPT plan usage authorized;
- access token valid;
- refresh token available;
- requested model/usage eligible;
- provider request completed.

Identity success alone is insufficient to enable ChatGPT-plan inference. The
user must explicitly grant the plan-usage permission, and the implementation
must use the granted scope set returned by OpenAI rather than assuming that all
requested scopes were approved.

## Error and Revocation Semantics

- `access_denied` is a user-visible authorization cancellation, not a provider
  success or a retryable model failure.
- Missing or revoked plan-usage permission disables this provider path until
  the user reauthorizes.
- Expired access tokens may be refreshed only with a valid refresh token and
  the original authorization binding.
- Refresh failure requires reauthorization and must not fall back silently to
  another user's token or an API key.
- OpenAI subscription-sharing limits and usage-unavailable responses are
  provider failures with bounded diagnostics and no secret disclosure.
- The existing Java/Core callback contract remains the source of truth for
  task success, grounding and proposal validation.

## Security and Privacy

- Use HTTPS for production callbacks and secure cookie/session handling.
- Generate cryptographically random `state`, PKCE verifier and OIDC `nonce`.
- Validate issuer, audience, nonce, state, redirect URI, token response and
  granted scopes before storing or using credentials.
- Store only the minimum account identity required for the local session.
- Encrypt refresh tokens at rest or delegate storage to the deployment secret
  manager; define key rotation before production enablement.
- Redact authorization codes, access tokens, refresh tokens, ID tokens,
  prompts, repository content and full provider payloads from logs and traces.
- Provide explicit disconnect/revoke behavior and delete local credentials
  when the user disconnects.

## Out of Scope

- OAuth authentication for the remote MCP server.
- A generic identity provider or multi-tenant organization system.
- Access to ChatGPT conversations or ChatGPT internal endpoints.
- Automatic provider fallback or token sharing between users.
- Changes to Core context construction, grounding, trust promotion or MCP
  capability semantics.
- Billing, quota enforcement beyond surfacing provider responses, or a new
  conversation-memory system.

## Consequences

### Positive

- Users can opt into eligible ChatGPT-plan usage without providing an API key.
- OpenAI identity and model usage are explicit, auditable consent decisions.
- Existing Core authority and provider-independent task contracts remain intact.
- API-key and user-authorized execution can be tested independently.

### Costs and Risks

- OAuth callback/session lifecycle and secure token storage become operational
  responsibilities.
- The provider is subject to account eligibility, consent and subscription
  sharing limits outside DevLog's control.
- Local development needs an explicit secure credential strategy.
- Token refresh, revocation and disconnect behavior require integration tests.

## Implementation Boundary

This ADR defines the architecture and does not by itself authorize production
implementation. Story 0160 is the bounded implementation vehicle. It must
first implement the callback and provider contract with mockable OpenAI
boundaries, then enable live usage only after secrets, redirect URIs and
credential storage are explicitly configured for the deployment.

## Status Reconciliation

Story 0170 extends the existing configuration UX and reuses the provider revocation boundary; it
does not change this ADR's status or authorize a new OAuth architecture. The current header and
the historical reconciliation wording below are intentionally preserved as a human decision
boundary. Implementation evidence, tests, and Story closure must not be treated as an implicit
architectural status transition.

Story 0160 is marked `CLOSED - implemented, validated, and delivered` and the
repository contains the corresponding implementation. The `Proposed` status
of this ADR is intentionally not changed by that implementation status:
architectural acceptance remains an explicit human decision and must not be
inferred from code, tests or Story closure.

The configuration Epic references this ADR as an existing architectural
constraint and does not authorize OAuth changes while the status remains
`Proposed`.
