# ADR-052 — Internal Human Context Inputs for Analysis

## Status

Proposed

## Date

2026-08-13

## Context

DevLog AI currently derives most of its useful project context from
repository-based evidence and the trusted knowledge lifecycle built on top of
that evidence.

This architecture is valuable, but it leaves an important gap.

Some project information is highly relevant for analysis quality while remaining
absent or only weakly visible in repository evidence.

Examples include:

* medium-term project objectives;
* explicit architectural constraints;
* domain vocabulary;
* non-obvious assumptions;
* known limitations of the current system;
* intended future direction;
* important context behind roadmap priorities;
* clarifications provided directly by the project owner.

This information is often known by the human owner of the project but is not
naturally captured by:

* source code;
* Git history;
* ADRs already present in the repository;
* deterministic repository analysis.

As a consequence, DevLog may produce analyses that are technically grounded in
the repository yet still under-contextualized relative to the actual project
intent.

At the same time, this missing context should not be solved by weakening the
existing trust boundaries.

Human-authored contextual information is valuable, but it is not the same kind
of artifact as:

* repository evidence;
* deterministic observations;
* validated trusted knowledge.

DevLog therefore needs an internal mechanism allowing users to persist
project-level human context as a first-class analysis input without confusing
that input with validated project knowledge or repository-derived evidence.

## Decision

DevLog introduces **Internal Human Context Inputs** as a project-owned,
persistent, human-authored source of contextual information used to enrich
future analyses.

These inputs are stored inside DevLog.

They are not imported from repository files by default.

They are not generated artifacts.

They are not automatically promoted into trusted knowledge.

Conceptually:

```text
Human Author
    ↓
Internal Human Context Input
    ↓
Context Selection
    ↓
AnalysisContext
    ↓
AI Interpretation
    ↓
Validatable Proposal
    ↓
Validation
    ↓
Trusted Knowledge
```

The role of Internal Human Context Inputs is to improve analysis quality by
making explicit human project context available to the selection and
interpretation pipeline.

### 1. Internal Human Context Inputs Are a First-Class Project Resource

A project may own multiple Internal Human Context Inputs.

These inputs are persistent DevLog entities attached to a single project.

They exist independently from repository files and independently from trusted
knowledge entities.

Their purpose is to answer:

> What important project context has the human explicitly provided that may help
> DevLog better understand this project?

### 2. Internal Human Context Inputs Are Contextual, Not Automatically Trusted Knowledge

Internal Human Context Inputs must not bypass the existing proposal and
validation lifecycle.

They are human-authored context.

They are not automatically:

* Insights;
* Decisions;
* Engineering Events;
* validated facts;
* trusted knowledge.

They may influence analysis.

They may later contribute to proposals.

Only the existing DevLog lifecycle may promote derived knowledge into trusted
project memory.

### 3. Declarative Human Context Must Remain Semantically Distinct From Observed Evidence

DevLog must preserve the distinction between:

* repository-observed evidence;
* deterministic interpretation;
* human-authored contextual declarations;
* validated trusted knowledge.

For example:

* “The current backend uses Spring Boot” may be repository-grounded evidence.
* “The medium-term objective is to improve the semantic usefulness of knowledge
  for both humans and agents” is a human-authored contextual declaration.

Both are useful.

They are not the same category of truth.

Internal Human Context Inputs therefore require explicit provenance indicating
that the source is human-authored and internal to DevLog.

### 4. Inputs Must Be Structured Enough for Bounded Selection

Although the main content may be stored as Markdown, Internal Human Context
Inputs must not be modeled as an undifferentiated text dump.

They should expose enough structure to support bounded and relevant selection.

At minimum, the model should support dimensions such as:

* title;
* body content;
* input type;
* status;
* timestamps;
* author metadata;
* optional tags or priority signals.

The exact schema is an implementation concern.

However, the system must preserve the principle that human context remains
queryable and selectable rather than opaque.

### 5. Input Types Must Express Context Semantics

Internal Human Context Inputs should support explicit semantic categorization.

Illustrative categories may include:

* `GOAL`
* `CONSTRAINT`
* `ASSUMPTION`
* `KNOWN_GAP`
* `DOMAIN_CONTEXT`
* `DECISION_CONTEXT`
* `ROADMAP_CONTEXT`

This ADR does not prescribe the final enum.

It establishes that typed human context is preferable to a flat collection of
generic notes because context selection and downstream interpretation depend on
semantic intent.

### 6. Inputs Must Support Lifecycle Status

Human context changes over time.

An input may be current, obsolete, superseded, or archived.

DevLog must not assume every human-authored input remains equally relevant
forever.

The model should therefore support lifecycle states allowing the system and the
user to distinguish between:

* active context;
* historical context;
* deprecated context;
* archived context.

This ADR does not define the final state model.

It requires only that the lifecycle be explicit enough to avoid treating stale
human context as permanently current.

### 7. History Should Be Preserved

DevLog is a technical memory system.

Important human context should not silently lose historical trace when edited.

The system should preserve meaningful change history for Internal Human Context
Inputs, either through explicit versioning or another traceable historical
mechanism.

The exact persistence strategy is not defined here.

The architectural requirement is that DevLog should remain able to understand
that a contextual declaration changed over time.

### 8. Context Selection Must Remain Bounded and Relevant

Internal Human Context Inputs must not be injected wholesale into every
analysis.

They are subject to the same general bounded-context principles already
established for repository-derived context.

Selection should remain:

* project-scoped;
* intent-aware when relevant;
* bounded;
* explainable;
* biased toward useful context rather than maximum volume.

The existence of human context must improve analysis quality without recreating
prompt bloat or noisy context assembly.

### 9. Internal Human Context Inputs Do Not Turn DevLog Into a General Wiki

This capability exists to improve project understanding and analysis quality.

It is not intended to transform DevLog into a generic note-taking or
documentation platform.

The allowed conceptual scope is project understanding.

Examples include:

* goals;
* constraints;
* clarifications;
* intent;
* important non-code context;
* analysis-relevant explanations.

Broad unconstrained knowledge-base behavior is outside the scope of this
decision.

### 10. Repository-First Remains Valid

This decision is compatible with the existing repository-first strategy.

Repository evidence remains the primary technical grounding source for project
understanding.

Internal Human Context Inputs complement repository understanding where human
intent, terminology, or priorities are not recoverable from repository evidence
alone.

This decision does not replace repository-first with human-input-first.

It extends DevLog with a controlled internal human context layer.

### 11. Human Inputs and Trusted Knowledge May Later Interact Through Existing Lifecycle Boundaries

Future analyses may use Internal Human Context Inputs as part of their bounded
context and produce better proposals as a result.

For example:

* a project goal input may help an analysis prioritize relevant architecture
  trade-offs;
* a known-gap input may help explain repeated technical findings;
* a domain-context input may reduce ambiguity in generated insights.

However, any resulting knowledge must still pass through:

```text
Proposal
    ↓
Validation
    ↓
Trusted Knowledge
```

No direct promotion path is introduced by this ADR.

### 12. UI and API Should Expose Inputs as User-Owned Project Context

DevLog should present these inputs in user-facing terms such as project notes
or human project context rather than internal technical jargon.

The presentation should make clear that they are:

* authored by a human;
* attached to the project;
* part of analysis context;
* distinct from validated trusted knowledge.

This ADR does not define the final UI.

It establishes the conceptual boundary that the feature is user-owned project
context, not an internal diagnostic object.

## Consequences

### Positive

* analyses gain access to important human project context absent from the
  repository;
* both human and agent understanding can improve without weakening trust
  boundaries;
* DevLog gains a native way to persist project intent and clarifications;
* context quality improves while remaining explainable;
* future knowledge proposals can become more relevant and less
  under-contextualized.

### Negative

* a new project entity and lifecycle must be modeled;
* context selection becomes more complex;
* stale or poorly maintained human inputs may reduce analysis quality;
* versioning or historical trace introduces additional persistence complexity;
* UX constraints are needed to prevent the feature from becoming a generic
  dumping ground.

### Risks

* treating human-authored input as equivalent to validated knowledge;
* allowing unbounded note accumulation to pollute analysis context;
* creating a generic wiki instead of a focused project-context capability;
* introducing weakly typed notes that are difficult to reuse intelligently;
* failing to signal clearly to users and agents that this information is
  declarative human context.

## Alternatives Considered

### Store human notes only inside the repository

Rejected.

This would make the capability dependent on repository workflow and
version-control practices, while the goal is to provide an internal DevLog-native
mechanism.

It would also blur the distinction between project artifacts and DevLog-owned
contextual input.

### Treat human inputs as trusted knowledge immediately

Rejected.

This would bypass the existing proposal and validation architecture and weaken
trust boundaries.

Human-authored context is valuable without needing to be treated as
already-validated project knowledge.

### Keep human inputs as free-form temporary prompt additions only

Rejected.

Temporary prompt additions are not durable project memory and cannot be
consistently reused, curated, reviewed, or evolved over time.

### Expand generated documentation to capture this need

Rejected.

Generated artifacts are projections, not the authoritative internal
representation of project context.

This need concerns persistent input to analysis, not output rendering.

## Explicit Non-Goals

This ADR does not define:

* the final entity name;
* the final database schema;
* the final UI;
* the final API shape;
* the exact selection algorithm;
* the final type taxonomy;
* automatic conversion into trusted knowledge;
* repository import of Markdown notes as part of this feature;
* generic wiki or knowledge-base capabilities;
* external collaborative document integrations.

## Implementation Direction

The first implementation slice should focus on the smallest useful vertical
path:

1. persist project-owned human context inputs inside DevLog;
2. expose basic CRUD with explicit type and status;
3. make active inputs retrievable as bounded project context;
4. allow selected analyses to consume that context;
5. preserve the distinction between human context and trusted knowledge in read
   models.

A suitable seed use case is:

* storing the medium-term project objective that DevLog should improve the
  semantic quality and usefulness of information provided to both human users
  and AI agents.
