# ADR-054 — Context Maintenance Agent

## Status

Proposed

## Date

2026-08-14

## Context

ADR-053 introduced the Internal Context Maintenance Capability, establishing
deterministic evaluation as the primary layer for context-health maintenance.

The first implementation slice (Stories 0052–0058) delivered:

* deterministic freshness signals for project understanding and projections;
* duplicate-debt detection through TrustedKnowledgeDuplicateAuditService;
* stale human context detection;
* first-class maintenance findings with reviewable lifecycle;
* narrow AUTO_RESOLVE for unambiguous cleared conditions;
* human-reviewed remediation workflow for duplicate and stale cases.

This deterministic layer works well for clear-cut cases where staleness,
duplicates, or gaps can be detected through bounded system rules.

However, ADR-053 §4 explicitly identified a gap:

> Some maintenance questions are semantically ambiguous.
>
> For example:
>
> * whether two trusted knowledge records are meaningful enrichment or weak
>   duplication;
> * whether a context input is obsolete or still strategically relevant;
> * whether multiple signals together imply degraded project understanding.

These ambiguous cases currently fall through to human judgment by default, which
is appropriate for governance but does not scale when the volume of maintenance
findings grows or when cross-surface patterns require synthesis.

DevLog now needs a bounded AI-assisted agent capable of evaluating ambiguous
maintenance situations while remaining firmly within the governance model
established by ADR-053.

## Decision

DevLog introduces a **Context Maintenance Agent** that uses AI assistance to
evaluate ambiguous maintenance situations that deterministic rules cannot resolve
cleanly.

This agent is:

* internal to DevLog;
* project-scoped;
* maintenance-focused;
* advisory by default;
* governed by explicit scope boundaries.

It is not:

* a general-purpose autonomous analysis agent;
* a replacement for repository analysis;
* a replacement for human validation;
* a system that mutates trusted knowledge directly.

### 1. The Agent Exists Within ADR-053 Governance

The Context Maintenance Agent is an extension of the Internal Context
Maintenance Capability defined in ADR-053.

It does not replace the deterministic layer.

It complements it by handling cases where:

* deterministic signals are present but their severity or meaning is ambiguous;
* multiple weak signals together suggest a pattern that no single rule captures;
* the distinction between legitimate enrichment and weak duplication requires
  semantic interpretation;
* context inputs may be obsolete or still relevant based on project intent.

The deterministic layer remains the primary evaluation path. The agent activates
only when deterministic evaluation surfaces findings that benefit from
AI-assisted interpretation.

### 2. The Agent Is Advisory, Not Autonomous

The agent produces:

* interpreted maintenance assessments;
* prioritized remediation recommendations;
* semantic classifications of ambiguous findings;
* suggested actions with confidence indicators.

The agent does not:

* directly modify trusted knowledge;
* automatically resolve findings outside the AUTO_RESOLVE scope defined in
  ADR-053;
* delete, merge, or archive context without human approval;
* override human decisions on previously reviewed findings.

Human authority remains explicit for all destructive, ambiguous, or
historically-implicative actions.

### 3. The Agent Operates On Maintenance Findings, Not Raw Data

The agent consumes:

* existing maintenance findings produced by deterministic evaluation;
* the context surface and issue type of each finding;
* related findings that may form a pattern;
* bounded project context relevant to the finding.

The agent does not:

* independently scan repositories;
* generate findings from scratch without deterministic signal;
* replace the MaintenanceEvaluationService.

The deterministic layer remains the source of maintenance findings. The agent
interprets and enriches those findings when semantic ambiguity exists.

### 4. Scoped Maintenance Reasoning Domains

The agent's reasoning scope is bounded to:

#### Duplicate Ambiguity Resolution

When the deterministic layer produces `TRUSTED_KNOWLEDGE_SEMANTIC_DUPLICATE`
or `TRUSTED_KNOWLEDGE_OVERLAP_REVIEW` findings, the agent may:

* compare the semantic content of candidate records;
* assess whether overlap represents genuine duplication or legitimate
  enrichment;
* recommend RESOLVE (keep both), DISMISS (not actually duplicate), or
  escalate to human with structured rationale.

#### Cross-Signal Pattern Detection

When multiple findings exist across surfaces, the agent may:

* identify correlated staleness patterns;
* assess whether combined signals imply broader context degradation;
* rank maintenance priority across related findings.

#### Context Input Relevance Assessment

When `STALE_HUMAN_CONTEXT_INPUT` findings exist, the agent may:

* assess whether an input remains strategically relevant despite age;
* distinguish between genuinely obsolete inputs and inputs that are still
  valuable but not recently updated;
* recommend whether to dismiss, acknowledge, or escalate.

#### Maintenance Priority Ranking

When multiple findings compete for attention, the agent may:

* rank findings by estimated impact on context quality;
* surface the highest-value remediation actions first;
* reduce noise by grouping related findings.

### 5. The Agent Produces Structured Maintenance Assessments

Each agent assessment must be:

* tied to a specific maintenance finding or finding cluster;
* structured with explicit reasoning;
* tagged with a confidence indicator;
* traceable to the evidence and signals that informed it;
* reviewable by humans.

The assessment output model includes:

* finding reference;
* interpreted severity;
* semantic classification;
* confidence level;
* rationale;
* recommended action;
* supporting signals.

### 6. The Agent Integrates With Existing Workflow

The agent's assessments surface through the existing maintenance-finding
lifecycle:

* agent assessments attach to existing findings;
* human review remains available for all agent-influenced decisions;
* the audit trail records agent contributions alongside deterministic
  signals;
* the frontend surfaces agent assessments as additional context, not as
  automatic actions.

The agent does not introduce a parallel workflow or a separate UI surface.

### 7. The Agent Must Be Bounded and Explainable

Every agent assessment must be:

* explainable in terms of the signals and evidence that produced it;
* narrow enough to verify against specific maintenance scenarios;
* testable against known ambiguous cases;
* bounded to the scoped reasoning domains defined in this ADR.

The agent must not:

* produce opaque or unexplainable assessments;
* reason about project strategy, product direction, or business intent;
* generate broad architectural interpretations outside maintenance scope;
* infer user intent beyond what the evidence supports.

### 8. The Agent Respects Existing Lifecycle Rules

The agent does not create new lifecycle transitions.

It operates within existing transitions:

* OPEN → ACKNOWLEDGED
* OPEN → RESOLVED
* OPEN → DISMISSED
* ACKNOWLEDGED → RESOLVED
* ACKNOWLEDGED → DISMISSED

Agent-influenced transitions follow the same validation rules as
human-initiated transitions.

AUTO_RESOLVE remains limited to the deterministic cases defined in ADR-053 and
Story 0058. The agent does not expand AUTO_RESOLVE eligibility.

### 9. The Agent Must Not Create Noise

The agent exists to improve signal-to-noise ratio, not to create a second
layer of noise.

Therefore:

* the agent should not produce assessments when deterministic rules provide
  a clear answer;
* the agent should not restate what deterministic evaluation already
  determined;
* the agent should prefer silence over weak assessments;
* confidence thresholds should filter low-value assessments before they
  reach the UI.

### 10. The Agent Supports Future Capabilities Without Enabling Uncontrolled
Evolution

The agent architecture is designed to be extensible for future maintenance
reasoning domains.

However, each new reasoning domain requires:

* explicit scoping in this ADR or a follow-up ADR;
* deterministic signal dependency;
* bounded assessment output;
* test coverage against known scenarios;
* human review pathway.

The agent must not become a self-extending autonomous system.

## Consequences

### Positive

* ambiguous maintenance findings gain structured AI-assisted interpretation;
* duplicate ambiguity resolution becomes scalable without losing human
  authority;
* cross-surface pattern detection improves context quality awareness;
* maintenance prioritization becomes data-driven rather than ad hoc;
* the deterministic layer and AI layer remain cleanly separated.

### Trade-offs

* the agent adds AI inference cost to maintenance evaluation;
* confidence calibration requires careful tuning to avoid false-positive
  assessments;
* the boundary between deterministic and ambiguous cases requires ongoing
  definition;
* agent assessments must be validated against known scenarios to ensure
  quality.

### Risks

* the agent could gradually expand scope beyond maintenance if boundaries
  are not enforced;
* low-confidence assessments could degrade usability if not properly
  filtered;
* the agent could create a false sense of automation reliability in
  inherently ambiguous domains;
* cross-surface pattern detection could produce spurious correlations.

## Alternatives Considered

### Extend AUTO_RESOLVE to more finding types

Rejected.

AUTO_RESOLVE requires deterministic, unambiguous conditions. The ambiguous
cases targeted by this ADR are by definition not suitable for automatic
resolution without human review.

### Rely solely on human judgment for ambiguous cases

Rejected.

This does not scale as the volume of maintenance findings grows. Human
judgment remains authoritative but benefits from structured AI-assisted
interpretation to prioritize and contextualize.

### Build a general autonomous maintenance agent

Rejected.

This is too broad and risks collapsing boundaries between maintenance,
analysis, and project reasoning. The scoped agent model preserves
architectural clarity.

### Use AI to generate maintenance findings directly

Rejected.

This would bypass the deterministic layer that provides explainability and
trust. The deterministic-first model established in ADR-053 remains
foundational.

## Explicit Non-Goals

This ADR does not define:

* a general-purpose autonomous analysis agent;
* automatic expansion of AUTO_RESOLVE eligibility;
* AI-driven trusted knowledge mutation;
* automatic duplicate resolution without human review;
* cross-project maintenance reasoning;
* project strategy or product-direction interpretation;
* a replacement for repository analysis;
* a separate UI surface for agent assessments;
* confidence-score calibration automation.

## Implementation Direction

The first implementation slice should be intentionally narrow and should
validate the agent model against real ambiguous cases before broadening scope.

A suitable first vertical path would be:

1. define the agent assessment output model;
2. implement duplicate ambiguity resolution for semantic-overlap findings;
3. implement cross-surface pattern detection for correlated staleness;
4. integrate agent assessments into the existing maintenance-finding
   lifecycle;
5. add confidence thresholds and low-value assessment filtering;
6. validate against known ambiguous scenarios with test coverage.
