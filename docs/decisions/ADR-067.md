# ADR-067 — DevLog Engineering Story Context Agent — First Agent Capability

## Status

Accepted

## Date

2026-09-05

## Context

DevLog AI has established a mature architecture for deterministic engineering context composition (ADR-063, Story 0111), AI proposal governance (ADR-006), synthesis/proposal separation (ADR-065), and replayable evaluation (ADR-066). The `EngineeringContext` contract with trust-tier classification, deterministic scoping, and MCP/REST exposure is accepted and implemented.

Engineering Stories exist as a workflow primitive (REGISTERED → IN_PROGRESS → COMPLETED with base/target commits), but Kiko (the human developer) lacks automated tooling for the Discuss/Plan phases. The first useful agent capability should close this gap by consuming scoped `EngineeringContext` and producing structured analysis to help Kiko understand an Engineering Story before implementation.

The architecture preparation phase (docs/discovery/first-devlog-agent-architecture-preparation.md) identified 11 architectural decisions (A–K) and presented three alternatives. The human owner has now explicitly approved the decisions listed below.

## Problem

Engineering Stories are created and started, but Kiko has no automated way to gather relevant architecture, decisions, repository evidence, constraints, and open questions from DevLog's existing knowledge before implementation. This agent fills that gap using the now-accepted EngineeringContext architecture.

The agent must:

* consume deterministic, trust-classified `EngineeringContext`;
* produce structured, grounded analysis for human consumption;
* preserve all trust boundaries (ADR-006, ADR-065);
* reuse existing evaluation infrastructure (ADR-066);
* remain compatible with future Developer OS / OpenClaw runtimes without coupling DevLog to them.

## Decision

### D1 — Hybrid Agent Ownership (Decided)

**DevLog Core owns the agent capability and its governance. Python AI Engine owns agent execution and probabilistic behavior.**

#### Java/Core owns

* application capability / use-case semantics;
* authorization;
* Engineering Story/project scope;
* `EngineeringContext` construction and authorization;
* trust boundaries;
* capability governance;
* deterministic invariants;
* contractual acceptance/validation of results;
* exposure through application transports.

#### Python AI Engine owns

* agent execution;
* probabilistic reasoning;
* prompt orchestration;
* structured generation;
* uncertainty-aware interpretation;
* future agentic reasoning mechanisms within capabilities authorized by Core.

**Architectural principle:** Java owns capability, authority and governance. Python owns agent execution and probabilistic intelligence.

**V1 constraint:** Adopt this architectural boundary now, but implement only the minimum required one-shot execution model. V1 does NOT require tool loops, planning loops, autonomous runtime, persistent memory, capability registry infrastructure, or generic agent framework.

Conceptually: `EngineeringContext → Python agent execution → structured result → Core validation`

---

### D2 — MCP + REST Transport Adapters (Decided)

The same Java application capability must be consumable through **MCP and REST**. They are thin transport adapters over the same application capability.

**MCP** — Kiko, engineering assistants, machine/tool consumers, future compatible orchestrators.
**REST** — direct human-facing DevLog UI, future Developer OS UI, other HTTP consumers.

There must NOT be separate MCP-agent and REST-agent implementations.

**Architectural principle:** One capability, multiple transport adapters.

MCP is especially important for the current Kiko workflow, but MCP is not the architectural definition of the agent.

---

### D3 — Java/Core Is the Sole EngineeringContext Authority (Decided)

Java/Core exclusively constructs, scopes and authorizes `EngineeringContext`. The Python agent runtime consumes the resulting `EngineeringContext` as immutable authorized input.

Python must NOT independently reconstruct DevLog project context through:

* direct database access;
* direct repository access;
* `KnowledgeSelectionService` duplication;
* a parallel retrieval model;
* a new ContextPack;
* implicit project-context reconstruction.

The existing deterministic context composition rules remain authoritative.

Future agent-driven context expansion MAY eventually exist, but it must request additional context through authorized Core capabilities. It must not bypass the Core context boundary. This future mechanism is NOT part of V1.

---

### D4 — Rich V1 Story Context Analysis Contract (Decided)

The agent produces a **rich output contract for V1**. The contract must be capable of representing at least these semantic areas:

* objective understanding;
* relevant architecture;
* relevant decisions;
* relevant evidence;
* historical context;
* constraints;
* potentially impacted components;
* uncertainties;
* missing information;
* questions before implementation;
* confidence;
* provenance;
* output classification.

Exact production field names and implementation classes are not frozen by this ADR. The ADR defines semantic requirements rather than prematurely specifying every DTO/Pydantic implementation detail.

**Important rule:** Rich does NOT mean artificially populated. A section with no sufficiently relevant or grounded information may be empty. The model must never fabricate content merely to populate the rich schema. The purpose is to provide a durable structured foundation for DevLog and future Developer OS workflows.

---

### D5 — Hybrid Persistence Model (Decided)

Agent analyses are not simply disposable, but persistence must not turn AI analysis into trusted project knowledge.

* Each execution produces an immutable analysis snapshot.
* The snapshot is non-trusted AI output.
* Execution/history retention is permitted.
* It may be associated with the Engineering Story for audit/history purposes.
* A later execution must use a freshly constructed `EngineeringContext`.
* Previous analysis must NOT be implicitly reused as trusted context.
* Persistence does NOT mean promotion.
* Persistence does NOT mean cross-run memory.

**Architecturally decided:** Every successful agent execution produces an immutable, non-trusted analysis snapshot with traceable execution identity. The snapshot semantics are required; they are not optional.

**Deferred implementation detail:** ADR-067 does NOT prescribe the concrete durable storage model. The implementation Story must determine the smallest repository-consistent persistence representation. It may determine whether the approved snapshot semantics are represented through:

* an existing AI task/execution persistence mechanism;
* an extension of an existing entity;
* a dedicated persistence model;
* another repository-consistent durable representation.

Do NOT mandate a new database table. Do NOT invent a schema. Do NOT weaken D5 into purely transient output.

Conceptually:
```
EngineeringContext T1 → Analysis A1
Later:
EngineeringContext T2 → Analysis A2
```
A1 may remain available for audit/history, but A2 must not automatically reason from A1. Any future cross-run comparison, reuse or conversational memory requires explicit architecture authorization.

Align with ADR-065 execution-scoped, non-trusted snapshot semantics where applicable. Do not invent unnecessary persistence infrastructure in this ADR.

---

### D6 — Analysis and Recommendations, No ValidatableProposal in V1 (Decided)

The first agent is primarily an analysis capability. It MAY produce clearly classified recommendations. It MUST NOT create `ValidatableProposal` objects in V1.

Semantic separation:

| Category | Description |
|----------|-------------|
| **Factual extraction** | What repository/context evidence explicitly establishes. |
| **AI interpretation** | Grounded synthesis or interpretation produced by AI. |
| **Recommendation** | Advisory AI output that may suggest an investigation or potential direction. |
| **Proposal** | A formal project-evolution artifact governed by ADR-006. |

The Story Context Agent does NOT create formal proposals in V1.

If a human finds a recommendation valuable:
```
recommendation → explicit human action → separate proposal capability → ValidatableProposal → human validation
```
No automatic promotion is allowed.

---

### D7 — Strict Grounding by Output Category (Decided)

| Category | Requirement |
|----------|-------------|
| **Factual extractions** | MUST reference valid evidence. Unsupported factual claims are invalid. |
| **AI interpretations** | MUST be grounded in explicit evidence references. Interpretation must remain distinguishable from factual extraction. |
| **Recommendations** | MAY extend beyond explicit repository evidence, but MUST: be explicitly classified as recommendations; clearly indicate whether they are grounded; never masquerade as repository truth. An ungrounded recommendation must remain visibly ungrounded. |

**Critical invariant:** Confidence does not substitute for evidence. `HIGH confidence != grounded fact`. Unsupported factual or interpretative claims must fail grounding validation rather than merely being downgraded to lower confidence.

**Preserved invariant:** `known A + known B != A → B` unless evidence supports the relationship.

---

### D8 — Explicit Relationship Semantics (Decided)

Relationship semantics MUST be explicit. `relationType` and `confidence` represent different dimensions and must not be conflated.

The architecture must distinguish at least:

| Relation Type | Definition |
|---------------|------------|
| **EXPLICIT** | A relationship backed by persisted deterministic relationship evidence (`KnowledgeRelation` edge). An AI interpretation must NOT create an `EXPLICIT` relationship. |
| **TEMPORAL_PROXIMITY** | Elements are temporally related or occur within a relevant deterministic time/story window. This is not causal evidence. |
| **POSSIBLE_RELEVANCE** | Deterministic signals indicate possible relevance (shared symbols, files, components, or other supported evidence). This does not establish causality. |
| **INFERRED_HYPOTHESIS** | An AI-generated relational interpretation grounded in evidence but not explicitly established by repository truth. It must remain visibly an inference/hypothesis. |

**Invariant:** Confidence cannot promote one semantic category into another. For example: `POSSIBLE_RELEVANCE + HIGH confidence` does not become `EXPLICIT`.

Future human investigation may eventually convert an inferred relationship into formal project knowledge through an authorized workflow, but the agent cannot perform that promotion itself.

---

### D9 — Explicit Human/Kiko Invocation During Discuss/Plan (Decided)

The Story Context Agent is explicitly invoked. Its initial workflow position is primarily:

`Understand → Discuss → Plan → Implement → Test → Review → Improve`

with the agent assisting during **Discuss/Plan**.

V1 does NOT automatically run when a Story starts.

Each invocation:

1. receives explicit authorized scope;
2. operates on a freshly constructed `EngineeringContext`;
3. may receive optional human guidance;
4. produces an independently traceable analysis;
5. may be re-run later against a new context.

#### Human Guidance

Human guidance MAY influence:
* interpretation;
* focus;
* priorities;
* presentation/output emphasis.

Human guidance MUST NOT alter:
* trust-tier assignment;
* deterministic context-authority rules;
* security boundaries;
* evidence truth;
* relationship truth.

For V1, avoid making free-form guidance silently alter deterministic context selection. Explicit scope controls such as `project`, `storyId`, `files[]`, and intent remain the deterministic scope mechanism.

### No persistent conversation in V1

V1 is not a chatbot with persistent conversation memory. Conceptually: `EngineeringContext + optional Human Guidance → one analysis`. Persistent conversational memory is deferred.

---

### D10 — Extend ADR-066 Evaluation + Real Human Acceptance (Decided)

Do NOT create an independent generic agent-evaluation framework. Reuse and extend the **ADR-066 Replayable AI Intent Evaluation Harness**.

Agent evaluation must contain two complementary layers:

#### Deterministic gates (machine-verifiable)

At minimum evaluate:
* schema validity;
* grounding validity;
* trust safety;
* relationship-semantic safety;
* context integrity / digest consistency where applicable;
* forbidden output/capability violations.

These gates can fail evaluation automatically.

#### Human qualitative evaluation

At minimum assess:
* correctness;
* relevance;
* completeness;
* actionability;
* uncertainty honesty;
* usefulness for Engineering Story preparation.

A structurally valid but practically useless response is not sufficient.

#### Human usefulness gate

The V1 agent cannot be considered fully accepted merely because automated tests pass. Before final human acceptance, it must assist on at least one **real Engineering Story**, and the human owner must explicitly assess whether the analysis improved Discuss/Plan preparation.

**Architectural principle:** The first useful agent must prove usefulness in the actual engineering workflow, not only compliance with a schema.

---

### D11 — Runtime-Agnostic Developer OS / OpenClaw Boundary (Decided)

DevLog agent capabilities remain independently usable and runtime-agnostic. MCP and REST are adapters. They do not define the capability architecture.

Developer OS, Kiko, OpenClaw or another future orchestrator may invoke supported DevLog capabilities through approved contracts. They do NOT own:

* DevLog domain semantics;
* EngineeringContext construction;
* trust rules;
* Engineering Story semantics;
* DevLog agent governance.

ADR-067 introduces:

* NO OpenClaw dependency;
* NO OpenClaw-specific contract;
* NO selection of a general-purpose future agent orchestrator.

**Architectural principle:** Capabilities first, protocols/runtimes second.

The design must allow OpenClaw or another runtime to be introduced or replaced later without redesigning the DevLog domain capability.

## Failure Semantics

Architectural failure semantics are defined at the decision level; implementation policies are deferred to the Engineering Story.

| Failure Scenario | Architectural Response |
|------------------|------------------------|
| Empty EngineeringContext | Return analysis with `confidence=LOW`, `uncertainties` explaining no context; never fabricate. |
| Stale context (freshness=STALE) | Include freshness in provenance; add `uncertainty` with `reason=STALE_CONTEXT`. |
| Invalid/non-resolving story scope | Return analysis with empty `technical_evidence`; `requestEcho.storyId` echoes input; `uncertainties` explains (per Story 0111 AC5). |
| AI structured-output validation failure | Corrective retry per existing AI Engine patterns (max 1); then error response. |
| Grounding validation failure | Reject output; retry; if persists → error with `TRUST_SAFETY=VIOLATION`. |
| Relationship-semantic violation | Reject output; retry; if persists → error. |
| Trust-safety violation | Reject output immediately; no silent trust-boundary crossing. |
| Low-confidence output | Include `confidence=LOW`; human decides trustworthiness. |
| Partially useful output | Return valid sections; mark incomplete; include `uncertainties`. |
| AI Engine unavailable / timeout | Transport-level error; no partial trust-boundary relaxation. |
| Snapshot persistence failure | A caller must never be led to believe that an analysis was durably recorded when snapshot persistence failed. The implementation Story must determine whether successful delivery requires durable snapshot persistence first, whether generation and persistence form one logical success boundary, how persistence failure is surfaced, and whether a generated-but-not-persisted result may ever be returned. |

**Retry invariant:** A retry may regenerate AI output when generation/validation fails. It must NOT silently broaden context, change trust boundaries, or introduce unsupported evidence merely to obtain a successful response.

Where repository truth does not yet define a safe policy, the policy is marked as an implementation-level decision for the future Engineering Story.

## Consequences

### Positive

* First useful agent capability demonstrating EngineeringContext value.
* Clean ownership boundary: Core = capability/governance; AI Engine = execution/intelligence.
* Reuses all existing infrastructure: EngineeringContext, IntentCatalog, ADR-066 harness.
* No RAG, vector DB, embeddings, OpenClaw, autonomous coding, or trusted-knowledge mutation.
* MCP + REST transport adapters over single capability — no duplication.
* Rich output contract provides durable foundation for Developer OS.
* Human Context Supremacy preserved — agent evidence subset of human-explorable universe.
* Explicit relationship semantics prevent hallucinated causality.
* Evaluation extends ADR-066 without parallel framework.

### Negative

* Requires new Intent registration in AI Engine Catalog.
* Requires new Python generation service and output schema.
* Requires new Java capability orchestration (use case + validation).
* Requires MCP tool and REST endpoint as transport adapters.
* Hybrid persistence adds snapshot storage without promotion semantics.
* Grounding must be enforced across the generation and Core acceptance boundaries. The exact allocation of deterministic grounding-validation responsibilities between Python and Java is deferred to the implementation Story, provided Core retains authoritative acceptance and no AI-generated output can bypass the approved grounding invariants.
* Human qualitative evaluation gate requires manual verification before full acceptance.

### Risks

* Grounding validation complexity — deterministic checks in Java must align with Python generation expectations.
* Rich output schema evolution — additive changes only; breaking changes require new Intent version.
* Persistent snapshots may be misinterpreted as trusted knowledge — schema must clearly classify as non-trusted.
* Evaluation harness extension for agent scenarios must not drift from ADR-066 Intent-level focus.

## Alternatives Considered

### Option A — MCP-First Transient Analysis (Selected as preliminary recommendation)

Single MCP tool `analyze_story_context` → context → AI Engine → transient result. Rejected as sole architecture because it conflates transport with capability and leaves REST as second-class.

### Option B — Backend Application Capability with MCP/REST Adapters (Selected for ADR-067)

Java use case `AnalyzeStoryContext` owns capability; MCP tool and REST controller are thin transport adapters. Matches D1/D2 decisions.

### Option C — External Orchestration Only (Rejected)

DevLog provides only primitives; external runtime composes. Rejected because it violates D3 (Core must own context authority) and D11 (MCP/REST are adapters, not the only consumers). Also prevents Kiko from using the agent directly.

## Non-Goals (V1)

* RAG, vector database, embeddings.
* OpenClaw coupling or generic multi-agent runtime.
* Autonomous coding, code modification, repository modification.
* Persistent conversational agent memory.
* Automatic trusted-knowledge mutation.
* Generic ContextPack.
* Agent Presence Window / real-time collaboration.
* Review workflow entities (no review workflow exists yet).

## Implementation Boundary

This ADR does NOT authorize implementation. Once Accepted, this ADR provides the architectural basis for a future Engineering Story implementing the first DevLog Agent capability. The Engineering Story must be separately designed, reviewed and explicitly authorized before production implementation begins.

Anticipated implementation scope (architectural consequences, not authorization):

* Java: `AnalyzeStoryContextUseCase`, validation, MCP tool, REST controller, snapshot persistence representation.
* Python: `engineering-story-context-analysis-v1` Intent, `StoryContextAnalysisGenerationService`, output schema.
* Contracts: `StoryContextAnalysisResult` (semantic requirements defined here; exact DTO deferred).
* Evaluation: ADR-066 scenario for `engineering-story-context-analysis-v1` with deterministic gates + human qualitative assessment.
* Documentation: MCP tool description, REST API docs.

This ADR does NOT implement those files, create the Story, alter CI, or change production code. The Engineering Story must derive its acceptance criteria from this ADR and preserve all invariants above.
