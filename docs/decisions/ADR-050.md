# ADR-050 — Incremental Knowledge Evolution

## Status

Accepted

## Date

2026-08-12

## Context

DevLog AI progressively builds trusted project knowledge from repository evidence,
analysis, human validation, and controlled promotion into project knowledge.

This architecture already provides important guarantees:

* deterministic and bounded context selection;
* structured AI contracts;
* human validation before trust promotion;
* Java Core ownership of trusted-knowledge lifecycle (ADR-006);
* richer semantic preservation during promotion (ADR-049).

These guarantees make repeated analysis relatively stable, especially for
`ARCHITECTURE_REVIEW`.

That stability is desirable.

However, repeated architecture analyses currently tend to reconstruct the same
conclusions independently when the repository has not materially changed.

Conceptually, the current model still resembles:

Repository Evidence
→ Analysis
→ Knowledge Proposal
→ Validation
→ Trusted Knowledge

then again:

Repository Evidence
→ Analysis
→ Knowledge Proposal
→ Validation
→ Trusted Knowledge

This means DevLog can repeatedly restate architecture knowledge that is already
trusted, because existing trusted knowledge is not yet a first-class comparison
input for incremental evolution.

DevLog therefore needs a model in which new analysis asks not only:

> What does the project architecture look like?

but also:

> Given what DevLog already knows about the architecture, what does the new
> evidence add, confirm, contradict, or invalidate?

## Decision

DevLog will evolve toward an **incremental knowledge evolution** model in which
relevant existing trusted knowledge may become a bounded input to future
analyses.

Conceptually:

Current Trusted Knowledge

* New Repository Evidence
* Analysis Intent
  → Analysis
  → Proposed Knowledge Delta
  → Validation
  → Knowledge Evolution

The Core idea is:

* knowledge is cumulative;
* repeated scans should maximize marginal information value;
* trusted knowledge must not be rewritten implicitly;
* AI may propose evolution;
* Java Core owns lifecycle, validation, and persistence.

### 1. Knowledge Is Cumulative

Trusted project knowledge may be used as input to future analyses when it is
relevant to the current intent.

An analysis should not systematically restart from semantic zero when DevLog
already possesses relevant trusted knowledge.

This does not mean sending the full trusted corpus to every analysis.

It means the system may provide a bounded, structured, relevant subset of
existing trusted knowledge as context.

### 2. Idempotence Remains Required

Incremental evolution does **not** mean every scan must produce something new.

If:

* the evidence has not materially changed;
* no relevant new information is discovered;
* the trusted knowledge remains correct;

then the correct outcome may be:

* no significant knowledge delta;
* no new proposal;
* no new trusted-knowledge record.

DevLog must not invent new knowledge solely to demonstrate that a scan ran.

### 3. Knowledge Delta Is a First-Class Concept

Future analyses may produce knowledge outcomes that are semantically different
from “standalone new statement”.

The architectural delta categories are conceptually:

* `NEW`
* `ENRICHES`
* `CONFIRMS`
* `CONTRADICTS`
* `SUPERSEDES` / `INVALIDATES`

These categories are architectural semantics, not a commitment to a final Java
enum shape.

#### `NEW`

A genuinely new knowledge statement was discovered.

#### `ENRICHES`

An existing trusted knowledge statement remains valid, but meaningful additional
information allows it to be extended or refined.

#### `CONFIRMS`

New evidence strengthens existing trusted knowledge without materially changing
its semantic content.

`CONFIRMS` should not generally create a duplicate trusted-knowledge unit.

It may instead reinforce provenance, support, or future freshness evaluation.

#### `CONTRADICTS`

New evidence conflicts with existing trusted knowledge and must be surfaced
explicitly through an appropriate lifecycle.

#### `SUPERSEDES` / `INVALIDATES`

Previously valid knowledge may become historically true but no longer
representative of current project state.

The system must preserve historical truth rather than rewriting the past.

### 4. AI Proposes Evolution; Core Owns Lifecycle

The AI Engine may interpret:

* current repository evidence;
* bounded existing trusted knowledge;
* the relationship between them.

It may therefore propose outcomes such as:

* `NEW`
* `ENRICHES Insight K17`

The AI Engine must never directly modify trusted knowledge.

Per ADR-006, the Java Core remains responsible for:

* proposal identity;
* validation;
* lifecycle transitions;
* persistence;
* allowed relationships;
* promotion into trusted knowledge;
* transactional consistency.

### 5. Existing Knowledge Is Context, Not Prompt Noise

DevLog must not send the entire knowledge corpus to every analysis.

Existing trusted knowledge selection must be:

* project-scoped;
* intent-scoped;
* bounded;
* deterministic when practical;
* structured enough for Core-side validation.

Where possible, existing repository-context and knowledge-selection
infrastructure should be reused rather than introducing a second generic
selection engine.

### 6. Knowledge Evolution Must Remain Traceable

Enriched or evolved knowledge must remain traceable to:

* the prior trusted knowledge involved;
* the proposal that suggested the change;
* the validation that accepted it;
* the evidence supporting it.

Conceptually:

Knowledge K17
← Evidence A
← Proposal P1
← Validation V1

Knowledge K22
→ enriches / derives-from K17
← Evidence B
← Proposal P2
← Validation V2

This ADR does not require a graph database or a full knowledge graph.

It requires only that evolution remain structurally traceable.

### 7. Historical Truth Must Be Preserved

DevLog must not rewrite the past merely because the current state evolved.

For example:

* “Thymeleaf was used” may remain historically valid
* even if Angular is now the current UI technology

Detailed temporal modeling is intentionally deferred.

The first incremental slice should preserve history rather than attempt a full
temporal truth engine.

### 8. Repeated Analysis Should Maximize Marginal Information Value

The goal is not:

more scans → more records

The goal is:

more useful evidence → better project understanding

Repeated analyses should therefore prefer:

* meaningful additions;
* grounded enrichments;
* explicit contradictions when they matter;
* or no proposal when nothing materially new was learned.

### 9. This Benefits Both Humans and Machines

#### Human

Humans should eventually be able to see:

* current architecture understanding;
* important enrichments over time;
* evidence and rationale;
* the progression of trusted knowledge.

#### Machine

Machines and agents should eventually be able to consume:

* current trusted knowledge;
* targeted evolution context;
* provenance;
* less redundant prompt context.

### 10. Explicit Non-Goals

This ADR does not require immediate implementation of:

* a knowledge graph;
* a graph database;
* a complete redesign of `KnowledgeRelation`;
* a full temporal knowledge engine;
* vector search or embeddings;
* automatic mutation of trusted knowledge by AI;
* automatic acceptance of contradictions;
* a complete AI-engine rewrite;
* a frontend redesign;
* artifact generation.

## Consequences

### Positive

* repeated architecture analysis can become incrementally useful rather than
  repetitively descriptive;
* trusted knowledge can become a better input for future analysis;
* prompt context can improve signal-to-noise ratio;
* semantic idempotence can coexist with technical idempotence.

### Trade-offs

* AI and Core contracts become more explicit and therefore slightly more
  complex;
* trusted-knowledge selection requires stronger scoping and validation rules;
* the first slice must avoid overreaching into contradiction or temporal
  modeling.

### Implementation Direction

The first vertical slice will be intentionally narrow:

* `ARCHITECTURE_REVIEW` only;
* bounded relevant trusted architecture knowledge;
* structured delta semantics;
* support for `NEW`, `ENRICHES`, and no-significant-delta behavior only.
