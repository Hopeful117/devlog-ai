# ADR-074 - Provider and Model Catalog Boundary

## Status

ACCEPTED - approved by the human project owner on 2026-10-31.

## Date

2026-10-30

## Context

DevLog AI currently selects an AI provider and model primarily through process
configuration (`LLM_PROVIDER` and `LLM_MODEL`). The AI Engine already exposes a
provider-independent `LlmProvider` abstraction and supports `mock`, `openai`,
`openai_chatgpt`, `gemini`, `anthropic` and `openrouter`.

The product now needs a user-facing configuration flow. That flow must describe
providers, authentication methods, known models and recommendations without
making provider implementation details or secrets part of the user contract.

The repository does not currently define a structured Provider and Model
Catalog. A catalog is therefore needed, but it must not become a second
authorization system, a credential store or an unbounded dynamic discovery
framework.

## Problem

Without a catalog boundary:

- the frontend must know internal provider identifiers;
- authentication methods are not represented as product capabilities;
- recommended models cannot be versioned or explained;
- model availability and user-selected configuration can be confused;
- adding a provider can require provider-specific UI changes.

## Decision

DevLog AI will define a Core-owned, provider-independent Provider and Model
Catalog as the initial product source for supported provider metadata.

The catalog may represent:

- stable provider identifier;
- user-facing provider name;
- supported authentication methods;
- known model identifiers scoped by provider;
- recommended model;
- relevant DevLog capabilities and constraints;
- stable or experimental status;
- catalog version.

The V1 catalog is curated and controlled by DevLog AI. Complete dynamic model
discovery is not required. A future runtime discovery result may enrich or
qualify catalog information, but it does not become authoritative for user
authorization or silently rewrite existing configuration.

The initial catalog must represent at least:

- `openai_chatgpt` with OAuth;
- `anthropic` with API key;
- `mock` without authentication.

The remaining currently supported providers may be represented according to
their actual configuration support and readiness.

## Conceptual Boundary

The catalog describes what DevLog knows how to support:

```text
Provider
  -> Authentication Methods
  -> Known Models
  -> Recommended Model
  -> Capabilities
```

The catalog does not decide:

- whether a principal may use a provider;
- whether a project may run a task;
- which credential a task may use;
- whether a binding is valid;
- whether a provider request is currently authorized.

Those decisions remain Core authorization and credential-binding decisions under
ADR-070, ADR-072 and ADR-073.

## Model Recommendation Rules

The catalog distinguishes:

- recommended model;
- initial/default model;
- model explicitly selected by a user;
- model currently available at runtime.

A catalog recommendation is advisory. It must not silently replace an existing
user selection.

If a configured model becomes unavailable, the configuration leaves `Ready`
and enters a model-unavailable state. DevLog may present the current
recommendation, but the user must explicitly accept the new model.

There is no automatic model fallback.

## Invariants

1. Provider and model identifiers are stable and provider-scoped.
2. Catalog metadata contains no credentials, tokens or secrets.
3. Catalog metadata is not authorization evidence.
4. Dynamic discovery is optional and non-authoritative in V1.
5. A recommendation never silently changes an explicit user choice.
6. Unknown, unavailable or incompatible models are surfaced explicitly.
7. `LlmProvider` remains independent from catalog storage and UI concerns.

## Consequences

### Positive

- The frontend can consume one product-oriented contract.
- Provider additions do not require a new configuration flow for every provider.
- Recommendations can evolve without mutating existing user choices.
- Runtime discovery can be added later without changing authorization ownership.

### Costs and Risks

- Catalog metadata requires controlled maintenance.
- Provider and model availability can diverge from curated metadata.
- Catalog versioning and compatibility rules must be tested.

## Out Of Scope

- Full provider model discovery in V1.
- Model scoring or benchmarking.
- Credential storage or authorization.
- Automatic provider or model fallback.

## Implementation Boundary

This ADR defines the catalog boundary and does not authorize production
implementation. The Provider and Model Catalog Story is the bounded
implementation vehicle after this ADR is accepted.
