# ADR-082 - MCP-Orchestrated Preparation of Bounded Live Evaluations

## Status

ACCEPTED - implementation and live execution remain separately authorized.

## Date

2026-11-23

## Context

DevLog AI contains a bounded A/B/C evaluation harness for live comparison of
the current DevLog path, a direct investigator path, and a Core-authorized
engineering analyst path. The provider-free runner already validates manifests,
oracles, normalization, provenance and artifact integrity.

Live preparation remains operationally repetitive. It requires checking the
frozen source revision, the executable runtime revision, worktree state, native
contracts, adapters, provider configuration, OAuth binding, operational limits
and artifact destinations before any provider call is allowed.

The current evaluation uses ChatGPT OAuth. Monetary provider cost is not
measurable in this subscription context. The repository already contains an
approved non-metered pricing contract that represents this fact without
claiming that usage is free or that cost is zero.

The architectural question is:

> How can DevLog prepare a bounded live evaluation through MCP without manual
> preparation steps, while preserving Core authority, OAuth boundaries,
> provenance, idempotency and the existing live authorization gate?

## Decision

DevLog will provide a Core-owned capability for automatically preparing a
bounded live evaluation. The capability may be exposed through MCP as a thin
transport adapter. It will produce an immutable, redacted execution plan and
will not execute the provider evaluation.

The capability is preparation-only. It does not create, renew, broaden or
implicitly accept a campaign authorization. Live execution remains a separate
operation requiring the existing campaign-scoped authorization and all
technical preconditions.

The preparation capability SHALL return one of:

```text
READY
BLOCKED
NOT_AUTHORIZED
```

The result SHALL identify every blocking condition using bounded diagnostic
metadata. It SHALL distinguish technical readiness from authorization and from
semantic evaluation.

## Preparation Contract

For an explicitly selected benchmark and observation set, Core SHALL validate:

- benchmark, case and manifest identity;
- oracle identity and digest without placing oracle material in treatment input;
- frozen source revision;
- executable runtime revision;
- reproducible worktree state;
- A/B/C runtime identities and answer contracts;
- runner, normalization and adapter availability;
- operational budgets and stop conditions;
- provider and model identity;
- OAuth/MCP binding status through non-secret metadata;
- artifact destination isolation and retention policy;
- idempotency key and existing operation state.

The returned plan SHALL contain the validated identities, digests, bounded
limits, capability envelope, artifact destination reference and blockers. It
SHALL NOT contain credentials, access tokens, prompts, raw provider payloads,
full repository content or unbounded diagnostics.

Repeated preparation with the same request identity and equivalent inputs SHALL
return the existing authoritative plan rather than create a second preparation
operation. A changed request or changed identity SHALL produce a conflict or a
new explicitly identified operation; it SHALL not silently replace the first
plan.

## Non-Metered OAuth Contract

When the provider and authentication mode are ChatGPT OAuth, preparation SHALL
use the approved non-metered contract:

```text
billingModel       = CHATGPT_OAUTH_SUBSCRIPTION_NOT_METERED
currency           = NOT_APPLICABLE
costCeilingPolicy  = OPERATIONAL_LIMITS_ONLY
input/output rates = absent
```

`NOT_MEASURED` SHALL mean that monetary cost is not observable through this
provider boundary. It SHALL NOT be converted to zero and SHALL NOT remove the
operational ceilings.

The operational ceilings remain mandatory and include, where applicable:

- observations and repetitions;
- maximum model turns;
- maximum provider actions;
- maximum output tokens;
- maximum wall-clock duration;
- provider and model;
- authorization expiration;
- artifact retention and destination.

The pricing contract identity and digest SHALL be bound to the preparation
plan even when no monetary amount is calculated.

## Authority and Security Boundaries

1. Java/Core owns capability semantics, project scope, benchmark identity,
   authorization checks, deterministic validation and plan persistence.
2. MCP exposes the Core capability and does not implement a second preparation
   workflow.
3. OAuth identity and provider usage authorization remain distinct from project
   authorization.
4. OAuth credentials remain inside the AI Engine provider boundary and are not
   returned by MCP or persisted in evaluation plans.
5. Preparation cannot renew or expand a human delegation.
6. Preparation cannot authorize implementation, provider execution or trusted
   knowledge promotion.
7. A stale, mismatched, incomplete or ambiguous identity fails closed.
8. Error classification and retry behavior follow ADR-081. No automatic retry
   is permitted where idempotence or the previous operation result is unknown.

## Execution Boundary

The following operations remain outside this ADR's preparation capability:

- provider calls;
- live A/B/C treatment execution;
- campaign authorization creation or renewal;
- OAuth consent or reauthorization;
- modification of the frozen manifest or oracle;
- modification of repository or production state;
- semantic scoring or human qualitative adjudication.

The prepared plan may be consumed by the separately authorized live runner.
That runner must revalidate the plan, runtime identity, authorization and
expiration immediately before execution.

## Evaluation and Artifact Semantics

The preparation result is engineering metadata, not an evaluation result. It
must not be counted as a completed observation, semantic answer, quality score
or proof of provider success.

Live artifacts remain evaluation-only. Raw provider responses, if captured by a
later authorized execution, must follow the existing redaction, digest,
revision and terminal-outcome contracts. Preparation itself must perform zero
provider calls and zero external provider network calls.

## Alternatives Considered

### Option A - Keep live preparation manual

Rejected. Repeated manual checks create avoidable configuration drift and make
it harder to distinguish technical blockers from authorization blockers.

### Option B - Let MCP directly execute the live runner

Rejected for this decision. It would conflate preparation with provider
execution and weaken the existing campaign authorization boundary.

### Option C - Create a standing autonomous campaign authorization

Deferred. This would change the governance model for external provider usage and
requires a separate security, delegation, expiration, revocation and cost-risk
decision. It is not implied by ChatGPT OAuth's non-metered billing model.

### Option D - Core-owned preparation with MCP as an adapter

Accepted. This preserves the Core authority boundary, allows MCP automation and
keeps the capability usable by future REST or other authorized consumers.

## Consequences

### Positive

- Live evaluation preparation becomes reproducible and automatable.
- Technical readiness and authorization remain visibly separate.
- ChatGPT OAuth can be represented without inventing monetary cost data.
- Revisions, digests, budgets and artifact destinations are checked centrally.
- Preparation can be safely retried through an idempotent operation identity.
- MCP remains a transport adapter rather than a second authority.

### Costs and Risks

- Core must persist or otherwise expose preparation-plan identity and status.
- The runner and preparation capability must share exact contract versions.
- Operational ceilings remain necessary even when monetary cost is not measured.
- OAuth and provider readiness can change after preparation and must be rechecked
  before execution.
- This ADR does not eliminate the separate campaign authorization gate.

## Implementation Boundary

This ADR does not authorize implementation. A subsequent Engineering Story must
define and implement, at minimum:

- the Core application capability and immutable preparation-plan contract;
- the MCP adapter;
- idempotency and conflict behavior;
- non-secret OAuth/MCP readiness projection;
- manifest, oracle, revision and worktree validation;
- non-metered pricing-contract binding;
- redacted artifact metadata;
- deterministic unit and integration tests;
- revalidation requirements for the separately authorized live runner.

The Story must not implement autonomous live execution, authorization renewal,
provider fallback, budget expansion or trusted-knowledge mutation.
