# ADR-081 - MCP Error Classification, Retry and Idempotency Policy

## Status

ACCEPTED - approved by the human project owner on 2026-11-20.

L'acceptation de cet ADR formalise la decision architecturale. Son
implementation reste bornee par Story 0211 et ses gates d'autorisation
distinctes.

## Date

2026-11-20

## Context

Le runtime MCP local renouvelle un bearer de transport lorsqu'il reconnait
exactement une erreur JSON-RPC `-32600 / Authentication is required`. Le serveur
MCP Java utilise actuellement le meme code et le meme message lorsqu'un appel
au backend Core repond `401`.

Cette collision permet a une erreur d'authentification Core d'etre interpretee
comme une expiration du bearer transport. Le runtime peut alors renouveler le
processus MCP et rejouer une operation alors que le probleme concerne la couche
Core, la delegation ou une autre frontiere d'autorisation.

Les Stories 0172 et 0174 definissent deja des invariants importants pour les
operations en vol, les generations, le renouvellement borne et les transitions
terminales. Elles ne definissent pas une politique transversale pour les
erreurs Core, provider, `429`, timeouts, idempotence et resultats ambigus.

## Problem

Le systeme ne doit pas deduire la couche d'origine d'une erreur a partir du
seul message humain ou d'un code generique. Il doit aussi eviter les retries
illimites et les rejeux d'operations dont le resultat precedent est ambigu.

## Decision

DevLog adopte une classification structurelle et une politique commune pour les
erreurs MCP.

### 1. Provenance obligatoire

Chaque erreur exploitee par une decision de retry doit avoir une provenance
structurelle parmi :

- `TRANSPORT_AUTHENTICATION` ;
- `CORE_AUTHENTICATION` ;
- `CORE_AUTHORIZATION` ;
- `DELEGATION_AUTHENTICATION` ;
- `PROVIDER_AUTHENTICATION` ;
- `PROTOCOL` ;
- `FUNCTIONAL` ;
- `TRANSIENT_INFRASTRUCTURE` ;
- `RATE_LIMITED` ;
- `UNKNOWN`.

Le message destine a l'utilisateur peut rester non-divulgant, mais il ne peut
pas etre le discriminant interne de la politique. Un `401` Core ne doit jamais
etre encodable comme une erreur d'authentification transport uniquement parce
qu'il partage le message `Authentication is required`.

### 2. Taxonomie normative

Les codes internes doivent conserver la couche, la cause et le caractere
retryable. Les codes minimaux sont :

```text
CONFIGURATION_INVALID
TRANSPORT_UNAVAILABLE
TRANSPORT_AUTH_EXPIRED
TRANSPORT_AUTH_REJECTED
CORE_AUTHENTICATION_FAILED
CORE_AUTHORIZATION_FAILED
DELEGATION_FAILED
PROVIDER_FAILED
PROTOCOL_INVALID
PROCESS_FAILED
TIMEOUT
RATE_LIMITED
UNKNOWN
```

Un adaptateur peut exposer un code MCP generique pour ne pas divulguer de
details, mais il doit conserver la classification interne necessaire au runtime
et aux diagnostics.

### 3. Retry borne

Un retry est interdit par defaut. Il est autorise uniquement si la matrice de
politique identifie explicitement la categorie, le budget, le backoff, le
contexte et la condition d'idempotence.

Regles minimales :

- `TRANSPORT_AUTH_EXPIRED` : un renouvellement et un retry maximum ;
- `CORE_AUTHENTICATION_FAILED` : aucun renouvellement transport automatique ;
- `CORE_AUTHORIZATION_FAILED` et `DELEGATION_FAILED` : fail-closed ;
- `400`, `403`, `404` et `409` : aucun retry par defaut ;
- timeout et `5xx` : retry seulement lorsque la couche et l'idempotence
  l'autorisent ;
- `429` : retry conditionnel, borne et compatible avec `Retry-After` ;
- `PROTOCOL_INVALID` et `CONFIGURATION_INVALID` : echec immediat ;
- `UNKNOWN` : echec immediat, sans rejeu automatique.

Un retry global ne doit pas etre ajoute simultanement dans le runtime Python et
dans les clients Java sans budget partage et sans autorite unique de decision.

### 4. Idempotence et resultats ambigus

Une operation est rejouable uniquement si son idempotence est garantie par le
contrat metier ou par une cle de deduplication autoritaire cote serveur.

Une reservation locale d'`operationId` ne suffit pas a garantir l'idempotence
apres redemarrage ou perte de connexion.

La regle par defaut est :

```text
resultat precedent ambigu + absence de garantie d'idempotence
-> aucun rejeu automatique
```

### 5. Invariants du runtime

La mise en oeuvre doit preserver les invariants acceptes de Story 0172 :

- une seule reservation logique par operation ;
- `operationId` stable pendant un retry autorise ;
- generations anciennes ignorees ;
- une seule transition terminale ;
- barriere d'arret prioritaire pendant un renouvellement ;
- aucun payload sensible dans les evenements ;
- echec ferme quand le renouvellement ou l'autorisation ne peut pas etre
  prouve.

Le renouvellement du bearer transport reste independant de la delegation
humaine et des credentials provider, conformement aux ADR-077 et ADR-078.

### 6. Diagnostics

Les diagnostics peuvent contenir uniquement des metadonnees bornees :

- categorie et code ;
- couche d'origine ;
- retryable ou terminal ;
- tentative courante et budget ;
- `instanceId`, `operationId` et generation ;
- action recommandee.

Ils ne doivent contenir aucun bearer, credential, token de delegation, prompt,
payload JSON-RPC, reponse provider ou contenu repository sensible.

## Alternatives considered

### Option A - Reutiliser `-32600 / Authentication is required`

Rejetee. Cette option conserve la collision entre transport et Core et permet
un renouvellement ou un rejeu incorrect.

### Option B - Classifier uniquement par statut HTTP

Rejetee. Le statut HTTP est perdu ou transforme aux frontieres MCP et ne suffit
pas a distinguer transport, Core, delegation et provider.

### Option C - Ajouter un champ de provenance structurel

Retenue comme direction. Le format exact peut etre un code MCP enrichi, une
metadonnee interne ou une enveloppe normalisee, mais la provenance doit rester
machine-readable et separee du message humain.

### Option D - Retry generique de toute erreur temporaire

Rejetee. Une erreur temporaire ne prouve pas l'idempotence et peut produire un
double effet metier lorsque le resultat precedent est ambigu.

## Consequences

### Positives

- Un `401` Core ne declenche plus implicitement le renouvellement transport.
- Les frontieres d'authentification et d'autorisation deviennent observables.
- Les retries sont bornes et auditables.
- Les operations ambigues echouent de maniere sure.
- Les Stories 0172 et 0174 conservent leurs invariants.

### Cout

- Les adaptateurs Java et le runtime Python doivent partager une taxonomie.
- Les clients doivent definir explicitement leurs garanties d'idempotence.
- Les tests doivent couvrir les erreurs par couche et les scenarios concurrents.
- Une compatibilite transitoire peut etre necessaire si des clients attendent
  encore l'ancien message generique.

## Implementation boundary

Cet ADR ne constitue pas une autorisation d'implementation. Les changements
doivent etre realises dans Story 0211 et ses Stories derivees, apres approbation
de l'Implementation Plan et autorisation humaine explicite.
