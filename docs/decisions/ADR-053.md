# ADR-053 — Internal Context Maintenance Capability

## Status

Proposed

## Date

2026-08-14

## Context

DevLog AI is progressively evolving into a durable project-context system whose
value depends not only on analysis quality, but also on the quality of the
underlying maintained project memory.

Recent work has improved:

* trusted-knowledge lifecycle;
* duplicate policy;
* incremental knowledge evolution;
* internal human context inputs.

These decisions strengthen the architecture, but they also make a new gap more
visible.

DevLog can now accumulate useful project context across multiple internal
surfaces, yet it still lacks an explicit internal capability responsible for
maintaining the health of that context over time.

In practice, several classes of degradation can accumulate:

* timeline projections may become stale or fail to reflect recent project
  activity;
* project understanding may become outdated relative to newer evidence;
* trusted knowledge may contain duplicate or near-duplicate debt despite
  stronger prevention policy;
* internal human context may become stale, superseded, or low-value;
* context surfaces may drift apart in freshness or usefulness;
* humans and future agents may consume context that is technically present but
  operationally weak.

This problem is not the same as primary project analysis.

The issue is not:

> What new architecture or engineering truth should DevLog infer?

The issue is:

> Is DevLog’s existing project context still fresh, coherent, non-redundant,
> and operationally useful?

That distinction matters.

If DevLog models this concern too early as a broad autonomous “living agent,” it
risks blurring architectural boundaries between:

* deterministic system maintenance;
* AI interpretation;
* trusted-knowledge lifecycle ownership;
* human authority over destructive or ambiguous changes.

DevLog therefore needs an explicit internal capability focused on **context
maintenance** rather than general project analysis.

## Decision

DevLog introduces an **Internal Context Maintenance Capability** whose role is
to evaluate, surface, and assist the maintenance of project-context quality over
time.

This capability is internal to DevLog.

It is project-scoped.

It is not a replacement for repository analysis.

It is not a replacement for human validation.

It is not a second autonomous analysis engine.

Its purpose is to ensure that the context DevLog exposes to humans and future
agents remains:

* fresh;
* coherent;
* non-redundant;
* reviewable;
* operationally useful.

Conceptually:

```text
Project Context Surfaces
    ↓
Context Health Evaluation
    ↓
Maintenance Findings
    ↓
Suggested or Safe Maintenance Actions
    ↓
Human Review When Required
    ↓
Improved Context Quality
```

### 1. Context Maintenance Is a Distinct Architectural Responsibility

Context maintenance is not identical to repository analysis, proposal
generation, or trusted-knowledge promotion.

Its primary question is:

> What parts of the current project context require hygiene, refresh, review, or
> cleanup?

This responsibility exists because DevLog is not only an analysis engine.

It is also a persistent project memory system.

Persistent memory requires maintenance.

### 2. The Capability Must Focus on Context Health, Not Autonomous Project Reasoning

The Internal Context Maintenance Capability exists to improve context quality.

It does not exist to act as an unrestricted autonomous project agent.

Its scope is bounded to maintenance concerns such as:

* freshness;
* staleness;
* redundancy;
* inconsistency detection;
* low-signal context accumulation;
* missing or outdated projections.

It must not silently redefine product direction, generate broad strategic
interpretations, or mutate trusted knowledge outside existing lifecycle rules.

### 3. Deterministic Evaluation Should Be the Primary Layer

Where practical, maintenance evaluation should begin with deterministic or
bounded system rules rather than free-form AI judgment.

Examples include:

* detecting stale projection timestamps;
* detecting missing regeneration opportunities;
* detecting obviously outdated context age;
* detecting exact duplicate trusted records;
* flagging near-duplicate candidates for review;
* identifying inactive or superseded internal human context inputs.

This preserves explainability and reduces unnecessary AI-driven churn.

### 4. AI Assistance May Be Used for Ambiguous Maintenance Reasoning

Some maintenance questions are semantically ambiguous.

For example:

* whether two trusted knowledge records are meaningful enrichment or weak
  duplication;
* whether a context input is obsolete or still strategically relevant;
* whether multiple signals together imply degraded project understanding.

In such cases, AI may assist by:

* interpreting overlap;
* explaining likely staleness;
* ranking maintenance priority;
* proposing remediation options.

AI assistance remains advisory unless an existing validated lifecycle already
permits the action.

### 5. Safe Automatic Actions Must Be Narrow, Reversible, and Low-Risk

The capability may eventually perform certain automatic actions only when they
are:

* deterministic;
* low-risk;
* reversible;
* traceable;
* semantically unambiguous.

Illustrative examples may include:

* refreshing derived health indicators;
* creating maintenance findings;
* scheduling regeneration suggestions;
* marking a maintenance check as completed.

Automatic deletion, merge, archival, or semantic mutation of trusted context
must not occur silently.

### 6. Human Authority Must Remain Explicit for Destructive or Ambiguous Changes

Human approval remains required for actions such as:

* deleting trusted knowledge;
* merging semantically overlapping trusted records;
* archiving context whose ongoing relevance is ambiguous;
* resolving duplicate-remediation cases with historical implications;
* accepting maintenance actions that materially alter project memory.

This is consistent with DevLog’s existing human-in-the-loop architecture.

### 7. Maintenance Findings Must Be First-Class and Reviewable

The output of this capability should not be an invisible background side effect.

DevLog should expose explicit maintenance findings or tasks describing:

* what was detected;
* why it matters;
* what context surface is affected;
* what action is suggested;
* whether the action is automatic, reviewable, or blocked pending human
  judgment.

This keeps context hygiene visible and auditable.

### 8. The Capability Must Span Multiple Context Surfaces

The maintenance scope is not limited to one entity family.

It should be able to reason about the health of relevant DevLog context surfaces
including, at minimum:

* trusted knowledge;
* project understanding projections;
* timeline projections;
* internal human context inputs;
* future derived project-context artifacts where applicable.

This ADR does not require one unified implementation for every surface.

It establishes that context maintenance is cross-surface by nature.

### 9. Duplicate Remediation Must Respect Existing Duplicate Policy

Per ADR-051, trusted-knowledge duplication is unacceptable as a steady-state
target, but human review should not be the primary line of defense.

The Internal Context Maintenance Capability complements that policy by handling
existing or suspected duplicate debt through:

* detection;
* classification;
* review support;
* explicit remediation workflows.

It must not weaken the distinction between:

* prevention of new duplicates;
* downstream enforcement;
* remediation of historical duplicate stock.

### 10. Maintenance Must Improve Signal-to-Noise Ratio

This capability exists to reduce noise, not create a second layer of noise.

It should therefore optimize for:

* actionable maintenance findings;
* bounded review surfaces;
* useful prioritization;
* low false-positive churn;
* clear distinction between informational warnings and required action.

A maintenance system that floods the user with weak signals would undermine its
own purpose.

### 11. This Capability Supports Future Agent Work Without Becoming That Agent

Cleaner and fresher context will improve future human workflows and future agent
consumers.

That is an intended benefit.

However, this ADR does not introduce a general autonomous agent responsible for
project analysis, planning, or engineering execution.

The Internal Context Maintenance Capability is infrastructure for context
quality.

It is not the long-term analysis agent itself.

### 12. User Experience Must Preserve Human Control Over Project Memory Hygiene

DevLog should present maintenance in user-facing terms that communicate:

* context health;
* stale or duplicate candidates;
* suggested cleanup actions;
* what is safe to automate;
* what requires human judgment.

The user experience should make it easy for a human to keep DevLog’s project
memory healthy without forcing the human to manually discover every issue.

## Consequences

### Positive

* DevLog gains an explicit architectural owner for project-context hygiene.
* Context quality becomes a system concern rather than an accidental byproduct.
* Humans and future agents can rely on fresher and less redundant project
  context.
* Existing duplicate and staleness debt gain a principled remediation surface.
* The architecture remains aligned with repository-first and human-in-the-loop
  principles.

### Negative

* A new internal maintenance domain must be modeled.
* Additional health signals, findings, and workflows increase system
  complexity.
* Poorly tuned maintenance heuristics could create noisy or low-value findings.
* Cross-surface maintenance may expose lifecycle inconsistencies that require
  follow-up architectural work.

### Risks

* modeling maintenance too broadly and accidentally creating an uncontrolled
  autonomous agent;
* allowing AI assistance to bypass human authority on ambiguous or destructive
  actions;
* generating too many weak maintenance findings and degrading usability;
* conflating context freshness with semantic truth;
* silently mutating project memory in the name of hygiene.

## Alternatives Considered

### Introduce a broad autonomous “living agent” immediately

Rejected.

This is too ambiguous as a first architectural step and risks collapsing
important system boundaries between maintenance, analysis, and authority over
trusted project memory.

### Rely on humans to notice and clean stale or duplicate context manually

Rejected.

This does not scale, produces inconsistent outcomes, and contradicts the goal of
DevLog as a reliable project-context system.

### Handle each maintenance problem independently with isolated ad hoc logic

Rejected.

This would solve local symptoms while leaving DevLog without a coherent
architectural model for context-health ownership.

### Treat maintenance as part of the future analysis agent only

Rejected.

The maintenance problem exists now and has a narrower, more governable scope
than a general-purpose analysis agent.

## Explicit Non-Goals

This ADR does not define:

* a general autonomous analysis agent;
* automatic trusted-knowledge deletion or merge;
* the final health-score model;
* the final maintenance-finding schema;
* the final scheduler or triggering model;
* the final UI;
* a full contradiction-resolution engine;
* a full temporal truth engine;
* a replacement for repository analysis;
* a replacement for existing validation workflows.

## Implementation Direction

The first implementation slice should be intentionally narrow and should focus on
maintenance visibility before broad automation.

A suitable first vertical path would be:

1. define explicit context-health signals for one or two high-value surfaces;
2. persist reviewable maintenance findings;
3. expose findings in the UI;
4. support human-reviewed remediation for duplicate or stale-context cases;
5. allow only narrow safe automatic actions where semantics are unambiguous.
