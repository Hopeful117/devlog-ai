# ADR-076 - User-Provided API Key Credential Lifecycle

## Status

Proposed - requires human architecture approval.

## Date

2026-10-30

## Context

DevLog AI already stores ChatGPT OAuth credentials in the AI Engine through an
encrypted credential store. Core owns non-secret associations and issues
task-scoped `AiCredentialBinding` capabilities. The product now needs to
support a user-provided API key for the first API-key vertical slice, using
`anthropic` as the representative provider.

An API key has a different lifecycle from OAuth: it has no OAuth callback,
refresh token or authorization scope set. It must therefore reuse the secure
credential boundary without being forced into the OAuth protocol.

## Problem

Accepting an API key through a user-facing flow can accidentally:

- persist the key in Core;
- return the key to the frontend after registration;
- select a credential from arbitrary client metadata;
- bypass principal or project authorization;
- create a credential store separate from the existing AI Engine store;
- expose the key in logs, traces, exceptions or snapshots.

## Decision

The AI Engine remains the owner of API-key secret storage and resolution. Core
stores only non-secret association metadata and an opaque credential handle.
The existing encrypted credential-store boundary is reused and extended only
where needed to represent credential kind and API-key lifecycle semantics.

The API-key flow uses a Core-issued, one-time enrollment intent.

```text
authenticated principal
  -> Core authorizes an enrollment intent for provider and method
  -> frontend submits the API key to the AI Engine using that intent
  -> AI Engine validates the intent and encrypts the key
  -> AI Engine returns only an opaque handle and non-secret metadata
  -> Core persists the credential association
  -> Core issues a task-scoped AiCredentialBinding when needed
  -> AI Engine resolves the handle only after binding validation
```

The exact transport may use a short-lived opaque intent or a Core-signed
intent, but it must be authenticated and validated by the AI Engine through
the existing Core-to-AI service trust boundary. A new independent credential
infrastructure is not introduced.

## Enrollment Intent

An enrollment intent must be:

- short-lived;
- single-use;
- bound to the authenticated principal;
- bound to exactly one provider;
- bound to exactly one authentication method;
- unusable as a task binding;
- replay-resistant;
- invalidated after successful or failed consumption according to the
  documented lifecycle.

The intent contains no provider secret. Core must never receive the submitted
API key as part of the association callback or persistence operation.

The chosen V1 mechanism is a Core-signed, short-lived intent verified by the AI
Engine through the existing authenticated service boundary. The signed claims
are limited to a principal reference, provider, authentication method,
intent identifier, issued-at time, expiry and single-use identifier. The
intent is not accepted by task execution endpoints.

This choice reuses the existing Core-to-AI authenticated boundary and avoids
introducing a separate session or identity system. The AI Engine must still
consume the intent atomically and record its use to prevent replay.

## Credential Association

Core may persist:

- principal identifier;
- provider;
- authentication method;
- opaque AI Engine credential handle;
- non-secret status and timestamps;
- optional redacted/fingerprint metadata if required by the product contract.

Core must not persist:

- API key value;
- OAuth token;
- refresh token;
- authorization code;
- provider response containing secret material.

V1 permits one active association per principal and provider. Replacing a key
creates or activates the new association only after secure storage succeeds,
then invalidates the previous handle.

## Revocation and Runtime

Revocation must:

- invalidate the Core association;
- prevent future binding issuance;
- invalidate or delete the AI Engine credential mapping;
- preserve historical task records without rewriting them.

An API key may be invalidated by the provider without local knowledge. A
provider rejection transitions the runtime state to a bounded credential or
provider error and does not reveal the key.

No API-key fallback to OAuth, another provider or another association is
allowed.

## Security Invariants

1. Core never stores or receives the API key value.
2. The AI Engine encrypts the API key at rest.
3. The frontend never receives the key after intake.
4. The enrollment intent is not a task authorization.
5. A handle is not sufficient to invoke a provider.
6. A valid task binding is required before provider resolution.
7. Principal, provider, project and task scope are validated by Core.
8. The AI Engine rejects unknown, expired, consumed or mismatched intents.
9. API keys are absent from logs, traces, snapshots, prompts, callbacks and
   error payloads.
10. REST, MCP and background tasks use the same Core binding decision.
11. Replacement and revocation are explicit and auditable.
12. There is no automatic credential fallback.

## Consequences

### Positive

- The existing AI Engine secret boundary is reused.
- Core remains authoritative without becoming a secret store.
- OAuth and API key lifecycles remain semantically correct.
- The frontend can support secure one-time intake without rereading secrets.

### Costs and Risks

- Core and AI Engine need an enrollment-intent contract.
- The AI Engine needs atomic replay protection for consumed intents.
- The existing association model may need a provider-neutral extension while
  preserving ChatGPT-specific identity metadata.
- API-key validation introduces provider calls and bounded failure states.

## Out Of Scope

- Multiple active credentials per provider in V1.
- Secret storage in Core or PostgreSQL Core persistence.
- Browser persistence of API keys.
- Generic credential delegation or service-account impersonation.
- Automatic provider or credential fallback.

## Implementation Boundary

This ADR does not authorize production implementation. The User API Key
Credential Lifecycle Story is the bounded implementation vehicle after this
ADR is accepted.
