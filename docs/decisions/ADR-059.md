# ADR-059 --- Temporal Engineering Knowledge and Safe Freshness Degradation

## Status

Proposed

## Date

2026-08-18

## Context

DevLog is progressively becoming an Engineering Context Engine
responsible for transforming project activity, validated engineering
knowledge, architectural decisions, Engineering Stories, repository
history and project documentation into reliable, task-specific
engineering context for humans and engineering agents.

At the same time, DevLog remains an engineering documentation and
project-memory assistant. These two responsibilities are complementary:
high-quality context cannot be produced indefinitely from poorly
maintained project knowledge, and project documentation cannot remain
useful if DevLog has no mechanism for distinguishing current engineering
truth from historical or potentially obsolete information.

ADR-006 established that AI-generated outputs cannot directly become
trusted project knowledge. ADR-050 introduced incremental knowledge
evolution. ADR-058 introduced Engineering Knowledge Data Lineage so
DevLog can explain where governed knowledge came from, which lifecycle
transitions occurred and where a knowledge lifecycle is broken.

Recent context-consolidation work also established an important
current-context rule for Insights:

``` text
ACTIVE Insight
    ↓
eligible for current trusted context

SUPERSEDED / ARCHIVED Insight
    ↓
preserved historically
    ↓
excluded from current trusted context
```

This solves one part of the problem. It does not solve the broader
temporal problem.

An `ACTIVE` piece of knowledge may still become inaccurate, incomplete,
misleading or obsolete when the repository evolves:

``` text
Validated Insight
    "The project uses component X for responsibility Y."
        ↓
repository evolves
        ↓
component X is removed or replaced
        ↓
Insight remains ACTIVE
```

The knowledge remains historically valid and its original validation
remains auditable. However, using it silently as current engineering
truth may now be incorrect.

The same problem can affect Insights, Decisions, Engineering Stories,
project observations, architectural documentation, repository-derived
knowledge, future Codeglyphe-derived external knowledge, future
Retrieval/RAG context and engineering context exposed to external
agents.

This creates a fundamental distinction between:

``` text
Was this knowledge legitimately accepted?
```

and:

``` text
Should this knowledge still be treated as current?
```

The first question is governed by validation and knowledge authority.
The second is temporal. These concerns must not be collapsed into a
single status.

A second problem appears when the user does not actively maintain
repository documentation or manually review knowledge after every
meaningful code change. DevLog must not silently treat all previously
accepted knowledge as indefinitely current. At the same time, DevLog
must not allow AI agents to rewrite, supersede or invalidate trusted
engineering knowledge without the existing governance process.

The architectural question is therefore:

> How should DevLog represent and react to the temporal freshness of
> engineering knowledge so that stale information does not silently
> become current truth, while preserving historical knowledge, human
> governance, auditability and the prohibition against agents directly
> modifying trusted knowledge?

## Decision

DevLog will introduce a **Temporal Engineering Knowledge capability**
that separates:

1.  **Governed Authority** --- whether knowledge was legitimately
    accepted and what its authoritative lifecycle state is;
2.  **Temporal Freshness** --- whether available evidence still supports
    treating that knowledge as representative of current project
    reality;
3.  **Context Eligibility** --- whether the knowledge may safely
    participate in current engineering context.

The core principle is:

> DevLog must distinguish the governed authority of engineering
> knowledge from its temporal freshness and its eligibility for use as
> current engineering context.

Temporal Knowledge does not authorize DevLog or an external agent to
rewrite trusted knowledge. It gives DevLog a deterministic and auditable
mechanism for becoming more cautious about knowledge whose relationship
to current project reality has weakened.

### 1. Authority and Freshness Are Different Concepts

A knowledge artifact may have been correctly validated when it was
created and later become stale.

Therefore `VALIDATED` must not imply `CURRENTLY_TRUE`, and `STALE` must
not imply `WAS_NEVER_VALID`.

Conceptually:

``` text
Knowledge
    authority = authoritative
    freshness = fresh
```

and:

``` text
Knowledge
    authority = authoritative
    freshness = stale
```

The second artifact remains part of project history. Its original
validation remains valid as a historical fact. Its eligibility for
current context may change.

### 2. Temporal Knowledge Must Not Replace Existing Governance

ADR-006 remains authoritative for trusted knowledge creation and
promotion:

``` text
AI Result
    ↓
ValidatableProposal
    ↓
Validation
    ↓
Promotion
    ↓
Trusted Knowledge
```

Temporal Knowledge observes the relationship between trusted knowledge
and current project reality.

It must not introduce:

``` text
AI Agent
    ↓
automatic reinterpretation
    ↓
Trusted Knowledge modified
```

A temporal finding may trigger a diagnostic, maintenance recommendation,
proposal, request for review, context degradation or future governed
maintenance workflow. It does not itself create a new authoritative
engineering truth.

### 3. DevLog Must Degrade Safely When Knowledge Becomes Suspect

The absence of user intervention must not force DevLog into either
keeping potentially false knowledge forever or allowing an agent to
rewrite trusted knowledge automatically.

DevLog will support **safe freshness degradation**.

Conceptually:

``` text
FRESH
    ↓
evidence changes
    ↓
SUSPECTED_STALE
    ↓
stronger deterministic evidence / unresolved condition
    ↓
STALE
```

The exact state model is deferred. The semantic behavior is required.

When sufficient evidence indicates that knowledge may no longer describe
current project reality, DevLog must be able to reduce its confidence in
using that knowledge as current context without altering the
authoritative knowledge itself.

### 4. Context Eligibility Is Derived Separately From Authority

Temporal state must influence eligibility for current engineering
context.

Conceptually:

``` text
authoritative + fresh
    → CURRENT_CONTEXT

authoritative + suspected stale
    → CAUTION / reduced current-context eligibility

authoritative + stale
    → HISTORICAL_ONLY or EXCLUDED_FROM_CURRENT_CONTEXT
```

These names are conceptual and do not define final enums.

Current engineering context must not silently present knowledge known to
be stale as if it were current truth. Eligibility should be
deterministically derived from governed state, temporal state and
applicable context policy, without requiring an LLM.

### 5. Unknown Is Safer Than False Certainty

If all known information about an engineering concern is stale,
contradictory or insufficiently supported, DevLog should be able to
represent:

``` text
CURRENT KNOWLEDGE UNKNOWN
```

rather than silently falling back to obsolete knowledge.

For example:

``` text
The last validated knowledge states X,
but repository evolution indicates that this information may be stale.
No validated current replacement is available.
```

is preferable to asserting that X is the current architecture when
evidence no longer supports that claim.

Uncertainty is therefore a legitimate output of the knowledge system.

### 6. Historical Knowledge Must Be Preserved

Temporal degradation must not delete historical knowledge.

Stale or superseded artifacts may remain useful for understanding
previous architecture, explaining decisions, reconstructing evolution,
generating documentation history, diagnosing regressions, auditing
AI-assisted engineering, understanding migrations and future temporal
retrieval.

The lifecycle is:

``` text
current knowledge
    ↓
project evolution
    ↓
historical knowledge
```

not deletion.

### 7. Supersession and Staleness Are Different

`SUPERSEDED` means a newer authoritative artifact has replaced an older
one according to a governed lifecycle.

`STALE` means evidence indicates an artifact may no longer accurately
represent current project reality.

For example:

``` text
Insight A ACTIVE
    ↓
repository changes
    ↓
Insight A becomes stale
```

may occur before a replacement exists.

Later:

``` text
Insight B proposed
    ↓
validated
    ↓
promoted
    ↓
Insight A superseded by Insight B
```

The first transition is temporal. The second is governed knowledge
evolution. Temporal Knowledge must not manufacture the second merely
because the first occurred.

### 8. Temporal State Must Be Evidence-Based

Knowledge must not become stale merely because it is old.

A six-month-old architectural Decision may remain current. A
one-hour-old Insight may become obsolete immediately after a repository
change.

Temporal evaluation should prefer meaningful engineering evidence, such
as:

-   referenced source files changed;
-   referenced symbols disappeared;
-   dependencies changed;
-   configuration changed;
-   architecture boundaries changed;
-   relevant ADRs were superseded;
-   a newer governed artifact contradicts or replaces the old artifact;
-   related Engineering Stories completed;
-   relevant repository evidence changed materially;
-   external technical facts used by the knowledge changed;
-   lineage indicates that an upstream source is no longer current.

Time may participate in temporal policy, but it must not be the sole
definition of semantic freshness.

### 9. Deterministic Signals and Semantic Interpretation Must Be Separated

Some temporal changes can be established deterministically:

``` text
referenced file no longer exists
dependency version changed
referenced symbol disappeared
newer accepted artifact explicitly supersedes this artifact
```

Other changes require semantic interpretation, for example whether a
refactoring invalidates an architectural rationale.

AI may assist with semantic interpretation. Such interpretation must
produce governed outputs such as findings or `ValidatableProposal`
objects. It must not directly mutate authoritative knowledge or silently
decide supersession.

### 10. Temporal Knowledge Must Use Data Lineage Where Available

ADR-058 established Engineering Knowledge Data Lineage to preserve
provenance and diagnose knowledge lifecycles.

Temporal Knowledge should consume lineage relationships where they
provide meaningful evidence:

``` text
Knowledge
    ↓ derived from / related to
Source Evidence
    ↓
Source Evidence changes
    ↓
Temporal Evaluation
```

Lineage may help answer:

``` text
What changed since this knowledge was validated?
Which source evidence originally supported this Insight?
Which dependency change caused this knowledge to become suspect?
Which newer artifact superseded this one?
Why was this knowledge excluded from current context?
```

Lineage and Temporal Knowledge remain separate capabilities. Lineage
explains relationships and lifecycle history; Temporal Knowledge
evaluates their current temporal meaning.

### 11. Temporal Transitions Must Be Auditable

A freshness change may materially affect context delivered to an
engineering agent.

DevLog should eventually be able to identify:

-   the knowledge artifact;
-   previous temporal state;
-   resulting temporal state;
-   relevant time;
-   evidence or trigger;
-   evaluation mechanism;
-   project;
-   whether the transition affected current-context eligibility.

The exact persistence model is deferred. DevLog must nevertheless be
able to explain why knowledge stopped being treated as current.

### 12. Temporal State Should Prefer Reconstruction Before New Persistence

As with ADR-058 lineage, DevLog should not immediately introduce a large
temporal persistence model.

The implementation should first determine which temporal facts can be
derived reliably from existing state.

Explicit temporal persistence should be introduced when temporal state
is historically important, expensive to reconstruct, ambiguous without
preserving the evaluation, needed for auditability, required to trigger
future workflows or necessary to explain previous context outputs.

### 13. Temporal Evaluation Must Be Project-Scoped

A repository change in one project must not degrade knowledge in an
unrelated project.

Every temporal evaluation must directly carry project identity or be
deterministically resolvable to one project through the evaluated
artifact and its provenance.

Cross-project temporal knowledge is outside the initial scope.

### 14. Temporal Knowledge Must Not Depend on Retrieval or RAG

Temporal Knowledge solves a domain and context-integrity problem that
exists before semantic retrieval.

It must remain usable without embeddings, vector databases, semantic
search, RAG or LLM retrieval reasoning.

Future Retrieval may use temporal information for current-vs-historical
retrieval, freshness weighting, temporal filtering, ContextPack
construction, confidence and provenance explanation.

Temporal truth must not be owned by a vector index. Domain knowledge and
its temporal projections remain the source of truth; any future vector
representation must remain reconstructible.

### 15. Retrieval Must Eventually Become Temporally Aware

The architecture must support future queries such as:

``` text
What is currently known about X?
What was believed about X before migration Y?
Why did the current architecture replace the previous one?
Show the historical evolution of this engineering concern.
```

This requires a distinction between current retrieval and
historical/temporal retrieval.

A future Retrieval Layer must consume temporal semantics rather than
redefine them.

### 16. Documentation Is Part of Temporal Knowledge Quality

DevLog's evolution toward an Engineering Context Engine does not reduce
its documentation responsibility.

Documentation is one of the durable representations of project
knowledge. If it is not maintained, future context generation, retrieval
and agent reasoning will degrade.

Temporal Knowledge should support documentation maintenance:

``` text
Repository evolution
    ↓
knowledge / documentation impact detected
    ↓
temporal finding
    ↓
maintenance proposal
    ↓
human validation
    ↓
documentation update
```

This preserves DevLog as both a Project Memory / Documentation Assistant
and an Engineering Context Engine.

### 17. Lack of User Maintenance Must Produce Degradation, Not Fabrication

A project may remain unattended.

DevLog cannot assume absence of human review means existing knowledge is
still correct. It also cannot infer replacement truth without sufficient
governed evidence.

The required fallback is:

``` text
No maintenance
    +
repository evolution
    ↓
freshness degradation
    ↓
reduced context eligibility
    ↓
diagnostic / maintenance proposal
```

not indefinite use of old knowledge and not autonomous rewriting.

### 18. Temporal Findings May Trigger Governed Maintenance Workflows

Temporal evaluation may produce structured findings such as:

``` text
Knowledge X may be stale because source Y changed.
```

A future workflow may be:

``` text
Temporal Signal
    ↓
Temporal Diagnostic
    ↓
Maintenance Proposal
    ↓
Human / business validation
    ↓
Knowledge update / supersession / documentation change
```

Detection and proposal generation may become increasingly automated.
Authority-changing operations remain governed.

### 19. External Engineering Agents Consume Temporal Semantics but Do Not Own Them

External agents such as Kiko, OpenCode or future Developer OS
engineering agents need to know how safely knowledge can be treated as
current.

Future context may expose semantics such as:

``` text
current
potentially stale
historical
current state unknown
```

The exact contract is deferred.

External agents may consume temporal diagnostics. They must not directly
change temporal authority, supersede trusted knowledge or bypass DevLog
governance.

### 20. Temporal Knowledge Must Remain Compatible With Event-Driven Evolution

Future DevLog and Developer OS architecture may increasingly use domain
events, jobs and specialized agents.

Temporal evaluation should be compatible with events such as:

``` text
CommitIngested
EngineeringStoryCompleted
DecisionAccepted
KnowledgePromoted
DependencyChanged
RepositoryAnalyzed
```

These events may trigger reevaluation.

This ADR does not require Event Sourcing. Event-driven temporal
reevaluation and Event Sourcing are separate architectural questions.

A future Event Sourcing ADR may evaluate whether immutable event history
should become a stronger foundation for project-state reconstruction.
Temporal Knowledge must not depend on that future decision.

### 21. The Initial Temporal Scope Is Intentionally Small

The first implementation must not make every DevLog artifact temporally
aware.

The preferred starting point is trusted `Insight` knowledge because
DevLog already has:

``` text
ACTIVE
SUPERSEDED
ARCHIVED
```

semantics and current-context filtering.

`Decision` should then be evaluated because architectural decisions may
remain valid for long periods and therefore provide an important
counter-example to age-based freshness.

### 22. Temporal Knowledge Is a Domain Capability, Not a Context Projection Hack

Temporal behavior must not be implemented solely inside
`RepositoryContextEngine` or `AgentContextProjectionService`.

Those components may consume temporal eligibility. They must not own
temporal truth.

The conceptual architecture is:

``` text
Project / Repository Evolution
        ↓
Temporal Knowledge Capability
        ↓
Temporal Assessment
        ↓
Context Eligibility
        ↓
Knowledge Selection / Projection
```

not a projection service guessing whether knowledge looks old.

### 23. Temporal Knowledge Must Be Explainable Without an LLM

Core questions such as:

``` text
Why is this Insight excluded from current context?
When did this knowledge become stale?
Which evidence triggered reevaluation?
Is a validated current replacement available?
```

must be answerable from deterministic application state whenever the
underlying transition was deterministic.

AI may summarize or interpret the result. It must not be required to
reconstruct authoritative temporal state.

### 24. Temporal Knowledge Must Support Safe Current-State Queries

DevLog should progressively support an explicit distinction between:

``` text
current knowledge
```

and:

``` text
historical knowledge
```

Current-state consumers should eventually receive only artifacts
eligible under current temporal policy. Historical consumers must remain
able to inspect preserved artifacts and their temporal evolution.

This distinction should eventually be reusable by Engineering Context,
MCP, documentation workflows, DevLog Agent, Kiko, future Retrieval and
future Developer OS agents.

## Consequences

### Positive

-   DevLog can distinguish validated history from current engineering
    truth;
-   stale knowledge does not need to remain silently eligible for
    current context;
-   historical knowledge remains preserved and auditable;
-   lack of user maintenance can degrade context safely instead of
    producing false certainty;
-   external agents can receive uncertainty rather than misleading
    authoritative statements;
-   ADR-006 governance remains intact;
-   AI agents remain unable to directly rewrite trusted knowledge;
-   temporal diagnostics can trigger governed maintenance workflows;
-   documentation maintenance becomes part of the same project-memory
    integrity model;
-   Data Lineage gains a concrete downstream consumer;
-   future Retrieval can distinguish current and historical knowledge;
-   temporal reasoning can improve ContextPack quality without making
    RAG the source of truth;
-   age-based heuristics are avoided as the primary definition of
    freshness;
-   deterministic repository changes can drive deterministic temporal
    signals;
-   DevLog becomes more robust when projects are temporarily unattended;
-   current-state uncertainty becomes explicitly representable;
-   Developer OS agents can consume safer engineering context;
-   the architecture remains compatible with future event-driven
    processing and possible Event Sourcing.

### Trade-offs

-   knowledge now has multiple conceptual dimensions instead of a single
    lifecycle status;
-   context eligibility becomes dependent on temporal policy;
-   temporal signals and transitions require new tests;
-   some temporal state may eventually require persistence;
-   lineage and repository history may need to be queried during
    temporal evaluation;
-   semantic staleness is harder to determine than structural staleness;
-   documentation maintenance workflows may generate additional review
    work;
-   consumers must eventually understand current versus historical
    queries;
-   conservative degradation may temporarily hide useful knowledge when
    no current replacement exists;
-   uncertainty must be represented explicitly in user and agent-facing
    contracts;
-   temporal policies require careful tuning to avoid both false
    staleness and false freshness.

### Risks

-   conflating authority and freshness could accidentally bypass
    ADR-006;
-   automatically marking knowledge `SUPERSEDED` from temporal signals
    would create ungoverned mutation;
-   using age as the main freshness criterion could incorrectly
    invalidate stable architectural knowledge;
-   overly aggressive degradation could remove too much useful context;
-   overly conservative degradation could continue exposing stale
    information;
-   AI-based staleness detection could be mistaken for authoritative
    state;
-   context projection could accidentally become the owner of temporal
    semantics;
-   introducing too many temporal states immediately could create
    unnecessary complexity;
-   persisting every temporal observation could create excessive write
    amplification;
-   poorly linked provenance could make temporal explanations
    unreliable;
-   external agents could misinterpret `suspected stale` as `invalid`;
-   historical queries could accidentally be filtered by current-context
    rules;
-   temporal maintenance automation could become implicit auto-repair if
    governance boundaries are not preserved.

## Alternatives Considered

### Treat ACTIVE as Equivalent to Current

Rejected.

`ACTIVE` expresses governed knowledge lifecycle state. It cannot
guarantee that repository evolution has not invalidated the semantic
content of the artifact.

### Keep All ACTIVE Knowledge Current Until a Human Updates It

Rejected as the long-term approach.

This protects authority but not context quality. An unattended project
could continue exposing known-obsolete information indefinitely.

Human validation remains required for authoritative replacement. Human
activity must not be required merely for DevLog to stop presenting
strongly contradicted knowledge as current truth.

### Automatically Supersede Stale Knowledge

Rejected.

Staleness and supersession have different semantics. A stale artifact
may have no validated replacement. Automatic supersession would allow
temporal detection to mutate governed authority.

### Allow AI Agents to Rewrite Stale Knowledge

Rejected.

This would violate ADR-006 governance and undermine auditability.

AI may generate a proposal describing a replacement or maintenance
action. It may not directly convert that interpretation into trusted
knowledge.

### Delete Stale Knowledge

Rejected.

Stale knowledge remains valuable historical engineering memory. Deletion
would damage auditability, project-history reconstruction and future
temporal retrieval.

### Use Only Creation or Validation Time

Rejected.

Age is not semantic freshness. Long-lived architectural decisions may
remain current for years, while newly validated implementation knowledge
may become obsolete immediately.

### Introduce a Single Combined Knowledge Status

Rejected.

A combined status would mix governed authority, temporal freshness and
context eligibility. These dimensions evolve for different reasons and
must remain distinguishable.

### Let RepositoryContext Decide Freshness

Rejected.

RepositoryContext is a consumer and projection boundary. Making it
responsible for temporal truth would couple domain semantics to context
generation and prevent reuse by documentation, diagnostics and
Retrieval.

### Wait for Retrieval / RAG

Rejected.

The temporal problem exists in trusted project knowledge before
retrieval. RAG should consume temporal semantics rather than invent
them.

### Depend on Event Sourcing First

Rejected.

Event Sourcing may later improve historical reconstruction, but Temporal
Knowledge can be designed using current domain state, lineage and
repository history.

### Automatically Repair Temporal Findings

Rejected for the initial architecture.

Detection, diagnosis, proposal and authoritative modification remain
separate responsibilities.

## Explicit Non-Goals

This ADR does not define:

-   final temporal database tables;
-   final JPA entities;
-   final temporal enums;
-   final freshness scoring formulas;
-   final confidence scores;
-   final expiration durations;
-   arbitrary time-to-live rules for engineering knowledge;
-   automatic supersession;
-   automatic invalidation of trusted knowledge;
-   automatic rewriting of Insights, Decisions or Engineering Stories;
-   automatic documentation modification without governance;
-   bypass of `ValidatableProposal`;
-   bypass of validation;
-   modification of ADR-006 governance;
-   deletion of stale knowledge;
-   replacement of `ACTIVE`, `SUPERSEDED` or `ARCHIVED` lifecycle
    semantics;
-   complete temporal support for every DevLog domain concept;
-   final REST or MCP contracts;
-   frontend or timeline visualization;
-   final Retrieval architecture;
-   vector database selection;
-   embeddings or RAG implementation;
-   temporal vector-search algorithms;
-   LLM-based authoritative freshness evaluation;
-   Event Sourcing;
-   event-store technology;
-   CQRS;
-   generic project-state reconstruction;
-   Codeglyphe integration;
-   external news freshness;
-   cross-project temporal knowledge;
-   automatic security auditing;
-   automatic repository repair.

## Implementation Direction

The first implementation should validate Temporal Engineering Knowledge
against the smallest real knowledge lifecycle where current/historical
semantics already exist.

A suitable progression is:

1.  inventory existing temporal information for `Insight`, `Decision`,
    `EngineeringStory`, repository evidence and relevant lineage;
2.  document the exact current semantics of `ACTIVE`, `SUPERSEDED` and
    `ARCHIVED` rather than changing them immediately;
3.  identify which current knowledge types can become semantically stale
    while remaining authoritatively valid;
4.  identify deterministic repository changes that can invalidate or
    weaken freshness;
5.  define the minimal conceptual vocabulary required to distinguish
    authority, freshness and context eligibility;
6.  determine whether freshness should initially be reconstructed,
    persisted or represented through a hybrid model;
7.  define a first deterministic temporal diagnostic for an `ACTIVE`
    Insight;
8.  validate a real repository-evolution scenario:

``` text
ACTIVE Insight
    ↓
supported by repository evidence
    ↓
relevant source changes materially
    ↓
Insight becomes temporally suspect
```

9.  verify that DevLog can report the temporal concern without modifying
    the Insight's authoritative state;
10. define current-context behavior when the Insight becomes
    sufficiently stale;
11. verify that historical inspection still returns the original
    Insight;
12. verify that no automatic `SUPERSEDED` transition occurs;
13. define how a maintenance proposal can be generated without bypassing
    ADR-006;
14. determine which temporal transition information must be auditable
    and which can be reconstructed;
15. integrate ADR-058 lineage where it improves explanation of the
    freshness transition;
16. validate behavior when the user performs no maintenance;
17. ensure the safe result is uncertainty or exclusion from current
    context, not fabricated replacement knowledge;
18. evaluate `Decision` as a second knowledge type specifically to prove
    that age alone does not imply staleness;
19. only after these semantics are stable, extend temporal eligibility
    to Engineering Context;
20. expose temporal diagnostics through MCP only after the
    application-level capability is stable;
21. design future Retrieval integration so current and historical
    queries consume temporal semantics rather than redefining them;
22. evaluate event-driven temporal reevaluation after the deterministic
    model is proven;
23. evaluate Event Sourcing separately after Temporal Knowledge
    requirements make its potential value measurable.

The first implementation should answer:

> Given an ACTIVE trusted Insight whose supporting project reality has
> changed, can DevLog deterministically recognize that the Insight may
> no longer be safe to present as current engineering truth, explain
> why, and degrade its current-context eligibility without modifying or
> superseding the authoritative Insight?

A second validation question should be:

> If the user does not maintain repository knowledge after meaningful
> project evolution, can DevLog avoid serving known-stale information as
> current truth while also avoiding autonomous modification of trusted
> knowledge?

A third validation question should be:

> Can DevLog preserve the stale artifact as auditable historical
> knowledge and later connect it to a governed replacement when one is
> validated?

If these questions can be answered reliably, Temporal Engineering
Knowledge will have demonstrated immediate value before expanding into
Retrieval, event-driven maintenance and broader Developer OS automation.
