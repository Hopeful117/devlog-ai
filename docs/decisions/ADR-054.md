# ADR-054 — Contradiction and Supersession in Incremental Knowledge Evolution

## Status

Accepted

## Date

2026-08-14

## Context

DevLog AI builds trusted project knowledge through a controlled lifecycle in
which AI proposes, humans validate, and the Java Core owns promotion into
trusted knowledge (ADR-006).

Story 0037 implemented the first vertical slice of ADR-050 for
`ARCHITECTURE_REVIEW`. That slice introduced:

* a bounded, deterministic, project-scoped selection of existing trusted
  architecture knowledge;
* a structured architecture delta contract carrying `deltaType` and
  `targetInsightId`;
* strict Core-side validation of that contract;
* promotion in which an accepted `ENRICHES` proposal creates a new trusted
  Insight linked to its target through a `KnowledgeRelation`.

That slice deliberately supported only the following knowledge outcomes:

* `NEW`;
* `ENRICHES`;
* no-significant-delta, expressed as an empty `proposals` array.

It explicitly deferred:

* `CONFIRMS`;
* `CONTRADICTS`;
* `SUPERSEDES` / `INVALIDATES`;
* a temporal truth engine;
* a dedicated persisted delta entity.

The repository has therefore not yet satisfied the parts of ADR-050 that
require the system to retain the distinction between:

> this knowledge is historically true

and:

> this knowledge is currently true.

Today a knowledge statement is promoted as trusted and never changes trust
representation once it exists.

The current trusted model cannot represent the acquisition of new information
that invalidates or replaces previously valid knowledge without either:

* silently keeping both statements (which ADR-050 forbids when one supersedes
  the other); or
* rewriting/editing the prior trusted knowledge (which ADR-006 forbids because
  the Core owns lifecycle and history must be preserved).

The domain needs an architectural decision on how a trusted-knowledge
contradiction is surfaced, decided, and recorded while preserving historical
truth.

## Decision

DevLog will extend the incremental knowledge evolution model with an explicit,
Core-owned contradiction-and-supersession lifecycle.

Only the following outcome is added in this decision, in addition to those
already supported by ADR-050 implementation:

* `SUPERSEDES` / `INVALIDATES`.

`CONFIRMS` and `CONTRADICTS` are addressed conceptually below but are not
implemented as first-class outcomes by this ADR.

### 1. Contradiction and Supersession Are Distinct

A **contradiction** is the observation that new evidence is incompatible with an
existing trusted knowledge statement.

A **supersession** is a recorded outcome in which a previously valid statement
is no longer representative of the current project state, while remaining
historically true.

A contradiction is a detection and a trigger.

A supersession is a decided, persisted trust-state transition.

DevLog must not collapse the two:

* detecting a contradiction does not automatically supersede the existing
  knowledge;
* a supersession must be explicitly decided through the existing validation
  lifecycle.

### 2. The AI Proposes Supersession; It Never Mutates Trusted Knowledge

The AI Engine may propose that existing trusted knowledge should be superseded.

It expresses this through the structured delta contract, referencing the target
trusted knowledge it believes should be superseded.

The AI Engine never:

* edits, deletes, or rewrites an existing `Insight`;
* changes an existing trust state;
* or decides that supersession is final.

Per ADR-006 and ADR-050, the Java Core remains the owner of:

* proposal identity;
* validation;
* lifecycle transitions;
* persistence;
* trust-state changes.

### 3. Supersession Is a Fully Validated Proposal Outcome

A proposal of type `SUPERSEDES` follows the same lifecycle as `NEW` and
`ENRICHES`:

```text
AI Detects Contradiction / New Dominant Evidence
        │
        ▼
SUPERSEDES Proposal (targets Trusted Knowledge K17)
        │
        ▼
Existing Human Validation Lifecycle
        │
        ├── REJECTED → K17 remains current; proposal history preserved
        │
        └── ACCEPTED → Supersession recorded, K17 becomes historically valid
```

A rejected supersession leaves the existing trusted knowledge unchanged and
preserves the proposal history for traceability.

### 4. Historical Truth Is Preserved, Not Rewritten

When a supersession is accepted, DevLog does **not** delete, edit, or rewrite
the superseded insight.

Instead it changes the **trust-state representation** of the superseded
statement so that:

```text
K17  "Thymeleaf was used"
  └── remains historically true
      └── marked SUPERSEDED (no longer current)

K22  "Angular is now the UI technology"
  └── becomes the current trusted statement
```

The superseded statement remains queryable and traceable as historical truth.

This directly satisfies ADR-050 point 7 (historical truth must be preserved)
and ADR-051 (proposal history and trusted knowledge remain distinct).

### 5. The Chosen Mechanism Is a Trust-State on Trusted Knowledge

To distinguish historically valid from currently valid knowledge, DevLog adds a
first-class **trust-state marker** to the trusted knowledge entity.

The minimal states are:

```text
ACTIVE
SUPERSEDED
```

`ACTIVE` is the default and represents knowledge representative of the current
project state.

`SUPERSEDED` represents knowledge that remains historically true but is no
longer representative of the current project state.

The exact Java representation (enum field, nullability, migration) is an
implementation detail left to the Story.

DevLog does not introduce a full temporal truth engine in this decision.

### 6. Supersession Is Recorded as a Directional Relation

In addition to the trust-state marker, an accepted supersession records the
directional relationship between the successor and the superseded statement.

Conceptually:

```text
K22
  → SUPERSEDES → K17
```

The `KnowledgeRelation` domain already represents directional knowledge links.

This decision adds `SUPERSEDES` to the recognized relation vocabulary.

The predecessor (K17) and successor (K22) are both trusted knowledge records,
so the relation links two trusted-knowledge entities within the same project.

### 7. The Core Enforces Structural Constraints

The Java Core validates a supersession structurally, never by parsing free text:

* the target of a `SUPERSEDES` proposal must exist and be `ACTIVE`;
* the target must belong to the same project;
* the target must be present in the selected trusted knowledge;
* a `SUPERSEDES` proposal must not silently produce a second independently
  active statement for the same semantic claim unless that is an intentional,
  validated outcome.

This mirrors the existing scope-safety guarantees established in Story 0037 for
`NEW` and `ENRICHES`.

### 8. Contradiction Detection Remains an Explicit Input Concern

A supersession proposal is grounded in evidence that contradicts or dominates
the existing trusted knowledge.

The contradiction may be discovered:

* by the AI Engine during architecture analysis;
* or by deterministic comparison of new evidence against trusted knowledge.

This ADR does not require a separate deterministic contradiction engine.

The first slice may rely on the AI Engine surfacing a contradiction through the
structured supersession contract, validated and decided by the Core.

A full deterministic contradiction detector is deferred.

### 9. Repeated Analysis with No Material Change Remains Idempotent

Adding supersession does not weaken ADR-050 idempotence.

If no contradiction is detected and no dominant new evidence exists, the correct
outcome remains:

* no significant delta;
* no supersession proposal;
* no trust-state change;
* no new trusted-knowledge record.

### 10. Compatibility with the Duplicate Policy

Story 0038 / ADR-051 define an explicit knowledge-duplicate policy.

Supersession does not create a semantic duplicate:

* the superseding statement is a distinct, validated, current claim;
* the superseded statement is retained as distinct historical trust.

The duplicate policy continues to reject the creation of a second *ACTIVE*
statement that is semantically equivalent to existing *ACTIVE* trusted
knowledge.

Supersession therefore must not be used as a mechanism to bypass duplicate
detection by relabeling an equivalent statement as a "successor".

## Consequences

### Positive

* DevLog can represent that a project no longer uses a technology without
  erasing that it once did.
* Historical truth is preserved instead of rewritten.
* Proposed supersession passes through the existing trusted validation
  lifecycle.
* The Core keeps full ownership of trust-state transitions.
* Traceability is maintained via a directional `SUPERSEDES` relation.
* Project freshness and Project State projections can eventually distinguish
  current from historical trusted knowledge.
* The change is materially easier to implement because it reuses the bounded
  architecture-knowledge selection and Core-side validation built in Story 0037.

### Negative

* The trusted-knowledge entity gains trust-state semantics that must be
  maintained and migrated.
* AI and Core contracts grow: `SUPERSEDES` becomes a valid delta outcome with a
  required target.
* Additional Core-side structural rules are required.
* Legacy trusted knowledge created before this change is `ACTIVE` by default and
  may require audit before its correctness is assumed current.

### Risks

* Treating supersession as automatic contradiction resolution without human
  validation.
* Using supersession to avoid duplicate-policy enforcement.
* Overlapping `ACTIVE` statements for the same semantic claim.
* Expanding this Story into a full temporal truth engine.
* Silent rewriting of historical knowledge under the guise of supersession.

## Explicit Non-Goals

This ADR does **not** decide:

* a full temporal knowledge engine;
* automatic acceptance of contradictions;
* automatic mutation of trusted knowledge by the AI;
* a complete `KnowledgeRelation` redesign;
* a knowledge graph;
* a graph database;
* a dedicated persisted Knowledge Delta entity;
* a deterministic contradiction detector;
* a frontend redesign;
* migration of all historical trusted knowledge in one step.

## Implementation Direction

The first slice should be intentionally narrow:

* `ARCHITECTURE_REVIEW` only;
* add a trust-state marker to the trusted-knowledge entity;
* add `SUPERSEDES` to the relation vocabulary;
* extend the architecture delta contract to accept `SUPERSEDES` with a target;
* require the target to exist, be `ACTIVE`, and belong to the same project;
* promote an accepted `SUPERSEDES` by marking the target `SUPERSEDED` and
  recording a `SUPERSEDES` relation from the successor to the predecessor;
* leave `CONFIRMS`, `CONTRADICTS` as explicit later outcomes.

The slice should remain compatible with the end-to-end data flow already
established:

```text
Existing Trusted Architecture Knowledge
* New Repository Evidence
  → Architecture Analysis
  → Delta Proposal (NEW | ENRICHES | SUPERSEDES | none)
  → Existing Validation Lifecycle
  → Trusted Knowledge Evolution
```

## Compatibility With Existing Decisions

* ADR-006 — AI proposes, Core owns proposal and trust lifecycle.
* ADR-050 — incremental evolution; historical truth preserved; the new
  `SUPERSEDES` outcome extends the delta categories ADR-050 already lists.
* ADR-051 — duplicate policy remains authoritative; supersession does not
  authorize duplicate bypass.
* ADR-047 — trusted knowledge and raw occurrence layers remain distinct.

## Guiding Principle

Trusted knowledge records the project's understanding at the time it was
accepted.

A supersession records that understanding has evolved, without erasing the
understanding that preceded it.

Therefore:

**DevLog supersedes by recording a decided transition, not by rewriting the
past.**
