# ADR-066 — Persist a Replayable AI Intent Evaluation Harness

## Status

Accepted

## Date

2026-09-02

## Context

The Post-0109 investigation sequence on `architecture-overview-v2` exposed AI
behavior regressions that ordinary unit and integration tests did not represent
completely. The measured failure classes included:

- directional relationship coverage;
- implicit delta defaults;
- `NEW` versus `ENRICHES` classification;
- enrichment target selection;
- corrective-retry semantics;
- synthesis grounding;
- unsupported semantic strengthening;
- benchmark fixture validity;
- benchmark semantic correctness;
- aggregate product-gate correctness.

After the corrective sequence, the equivalent three-run benchmark established:

```text
RELATIONSHIP_EXTRACTION        = STABLE
RELATIONSHIP_NOVELTY           = STABLE
DELTA_CLASSIFICATION           = STABLE
TARGET_SELECTION               = STABLE
SYNTHESIS_GROUNDING_QUALITY    = STABLE
TRUST_BOUNDARIES               = STABLE

DELTA                          = ENRICHES 3/3
TARGET                         = exact 3/3
STRONG                         = 3/3
UNSUPPORTED                    = 0/3
TRUST_BOUNDARY_VIOLATIONS      = 0
PRODUCT_GATE                   = PASSED
```

A temporary benchmark under `/tmp/opencode/benchmark/` made these investigations
repeatable during diagnosis. It evolved to validate fixtures, expected delta and
target semantics, structured output, grounding and trust constraints,
multidimensional quality, denominators, and aggregate product gates.

The temporary benchmark also exposed a measurement failure. One invalid fixture
contained no selected Facts or Observations. Given no material relationship
evidence, the model returned no proposal:

```text
EXPECTED = ENRICHES + exact target
ACTUAL   = no proposal + no target
```

The historical evaluator initially labeled that output `STRONG` because it
measured the absence of unsupported claims but did not require the declared
semantic result. The input defect and scoring defect were independent:

```text
safe output != correct output
invalid fixture != model failure
```

The hardened temporary evaluator now rejects that false positive while still
allowing no proposal when absence is the scenario's declared expectation.

The repository currently has deterministic AI Engine pytest tests, production
Pydantic contracts, versioned Intents and prompts, and deterministic prompt
digests. It does not have a persistent executable AI behavior benchmark. Past
benchmark results primarily exist as investigation documents and temporary
artifacts, which cannot provide durable replay or CI regression protection.

## Problem

DevLog needs durable engineering evidence for a small number of important AI
Intent behaviors without making live, stochastic model execution a dependency
of ordinary development.

Persisting the temporary Post-0109 scripts directly would encode one scenario,
absolute paths, generated identifiers, ad hoc keyword rules, and investigation
reporting into repository architecture. Keeping every benchmark temporary would
instead lose reviewed fixtures, expected semantics, and known regression cases.

The architectural question is:

> What is the smallest repository-level capability that can validate reviewed
> AI Intent behavior reproducibly across structural, semantic, grounding, and
> trust dimensions while remaining outside the production behavior it measures?

## Decision

DevLog will maintain a **small replayable AI Intent evaluation harness** owned by
the AI Engine.

Its primary purpose is:

> Reproducibly validate important AI Intent scenarios against explicit
> structural, semantic, grounding, and trust expectations without making
> stochastic live-model execution part of normal deterministic CI.

The harness provides scenario-based regression evidence. It does not prove
arbitrary model correctness, provide complete behavioral coverage, make live
model behavior deterministic, or guarantee the grounding of arbitrary natural
language.

### 1. The harness is evaluation infrastructure, not production behavior

The dependency direction is one-way:

```text
evaluation -> production contracts

production -X-> evaluation
```

Evaluation code may reuse production contracts and execution boundaries,
including Pydantic schemas, Intent definitions, `KnowledgeDeltaType`, proposal
structures, prompt builders, and injected AI Engine services or providers.

Production code MUST NOT import or depend on evaluation code. Removing the
harness MUST NOT change production runtime behavior, packaging, deployment, or
trusted project state.

The harness may:

- construct controlled scenario inputs;
- validate fixtures before execution or replay;
- replay a reviewed parsed Intent result;
- optionally execute an Intent through production-compatible boundaries;
- parse and validate production-compatible outputs;
- compare expected and actual proposal, delta, and target behavior;
- evaluate deterministic grounding and trust constraints;
- attach separately reviewed qualitative grounding assessments;
- derive evaluation quality and scenario-level gates;
- produce human-readable and structured reports.

The harness MUST NOT:

- modify production prompts or inject benchmark expectations into them;
- modify, repair, or rewrite model output or generated synthesis;
- change production retry, validation, ranking, selection, or grounding logic;
- accept or reject production proposals on behalf of domain workflows;
- promote proposals or create or modify trusted project knowledge;
- persist evaluation results as trusted domain knowledge;
- alter production state to satisfy a benchmark expectation.

Scenario expectations exist only after or outside production execution.

### 2. V1 is Intent-level and replay-first

V1 evaluates controlled AI Engine Intent inputs and outputs. It does not claim
to benchmark the complete Core workflow for collection, selection, persistence,
human validation, or promotion.

V1 SHALL support:

- versioned Intent-level scenarios;
- deterministic fixture validation;
- expected proposal, delta, and target behavior;
- replay of selected reviewed parsed outputs;
- structural, semantic, grounding, and trust evaluation;
- multidimensional results and derived quality;
- scenario-owned aggregate gates;
- concise text and JSON reports.

Replay is the core V1 execution mode:

```text
versioned scenario
        +
reviewed parsed output
        |
        v
deterministic evaluator
        |
        v
evaluation result
        |
        v
scenario gate
```

Replay asks:

> Does the evaluation architecture still parse, understand, and score this
> reviewed behavior correctly?

Replay is cheap, fast, reviewable, repeatable, and CI-compatible. It does not
establish what the current live model would produce.

### 3. Live execution is a later optional mode

The same evaluator MAY later consume production-compatible output captured from
a live model execution:

```text
scenario
   |
   v
production-compatible live execution
   |
   v
parsed output
   |
   v
same evaluator
```

Live execution asks:

> Does the current model, prompt, context, schema, and retry pipeline still
> produce acceptable behavior for this scenario?

Live execution SHALL initially be manual or scheduled. It SHALL NOT run in
normal pull-request CI because it is stochastic, paid, rate-limited,
provider-dependent, latent, non-hermetic, and subject to model drift.

V1 need not implement live orchestration. Its scenario and result boundaries
must avoid preventing a later live mode. A future live runner should reuse
existing production execution boundaries rather than introduce a second
provider abstraction solely for evaluation.

### 4. Evaluation tooling and its tests have separate repository locations

The accepted V1 location is:

```text
ai-engine/
├── evaluations/
│   ├── __init__.py
│   ├── README.md
│   ├── evaluator.py
│   ├── runner.py
│   └── scenarios/
│       └── architecture-overview-v2-enriches-v1/
│           ├── scenario.json
│           └── replay.json
└── tests/
    └── test_evaluation_harness.py
```

`ai-engine/evaluations/` contains developer tooling, scenario data, replay data,
and reporting. It remains outside the production `app` package and runtime
image. `ai-engine/tests/` contains deterministic tests of evaluation semantics.
Real-model execution MUST NOT occur through ordinary pytest discovery.

This structure is the authorized minimal target, not an instruction to copy the
temporary scripts unchanged. An Engineering Story will define and implement
the concrete files.

### 5. Scenarios are declarative, explicit, and versioned

V1 scenarios SHALL be persisted as stable JSON. JSON matches the production
HTTP and Pydantic boundary, supports readable and stable diffs, deterministic
serialization and digests, schema validation, language-independent tooling,
and review without executing fixture code.

Executable Python fixtures SHOULD NOT be used when declarative data is
sufficient. YAML is not introduced because the repository has no supporting
convention or requirement that outweighs the additional syntax and dependency.

A scenario contains only the minimum information needed to identify and
evaluate one behavior:

- stable scenario identity and semantic version;
- a production-compatible controlled `PromptRequest` fixture;
- scenario-declared required selected input references;
- expected delta and target behavior;
- applicable deterministic grounding and trust constraints;
- scenario-specific aggregate thresholds;
- reproducibility defaults needed for optional live execution.

Scenario-specific semantics belong to the scenario. Evaluation mechanics
belong to the evaluator:

```text
scenario declares expected behavior
        |
        v
generic evaluator compares actual behavior
```

The generic evaluator MUST NOT know that `backend -> ai-engine` should enrich a
particular containerization Insight. It MUST NOT contain Post-0109 component
names, target answers, or architecture-specific business rules.

### 6. Scenario versions govern fixture and expectation semantics

Scenario IDs are stable. The first canonical scenario is conceptually:

```text
architecture-overview-v2-enriches-v1
```

Its version changes when the benchmark's material fixture, evidence boundary,
semantic expectation, or gate contract changes. Formatting-only changes do not
require a new scenario version. Git remains the detailed implementation and
review history; V1 does not introduce independent semantic versions for every
fixture, expectation, evaluator, and report file.

### 7. Production contracts are reused without benchmark pollution

Scenario input and replay output SHALL be validated against production-compatible
Pydantic contracts where available. The evaluation layer should reuse, rather
than duplicate, production Intent, request, proposal, synthesis, and delta
contracts.

Benchmark-only semantics remain outside production contracts. Production
currently supports:

```text
KnowledgeDeltaType = NEW | ENRICHES
```

Evaluation represents expected absence as:

```json
{"expectedDelta": null}
```

The meanings are:

```text
expectedDelta = "NEW"       -> at least one NEW proposal is expected;
                                an existing target is not applicable
expectedDelta = "ENRICHES"  -> at least one ENRICHES proposal is expected;
                                the declared exact target is required
expectedDelta = null         -> no knowledge-delta proposal is expected
```

`NONE` MUST NOT be added to production `KnowledgeDeltaType` for evaluation
convenience. `CONTRADICTS` is not a supported production or evaluation delta
and MUST NOT be invented by the harness.

No separate `ProposalExpectation` enum is introduced in V1 because proposal
presence is unambiguously derived from `expectedDelta`. An OPTIONAL proposal
mode may be considered only after a concrete scenario requires it.

### 8. Targets use exact deterministic identity

An `ENRICHES` scenario declares an exact existing target UUID. Evaluation
distinguishes:

- correct target;
- wrong target;
- missing required target;
- target not applicable.

Fuzzy title matching is rejected. Canonical fixtures SHALL use fixed,
deterministic UUIDs. Fixture-local symbolic indirection is deferred until a
real need for dynamically derived identifiers appears.

### 9. Fixture validity is a first-class result boundary

Invalid benchmark input MUST NOT be interpreted as model behavior. Scenario
validation therefore occurs before replay evaluation or live execution.

Deterministic checks include, where applicable:

- scenario identity and version are present;
- the production-compatible request and Intent resolve;
- declared required Facts, Observations, or other selected items exist;
- declared fixture references resolve;
- an expected target exists in fixture trusted knowledge;
- expected delta is supported;
- target expectation is compatible with expected delta;
- the fixture and expected output contracts are internally consistent.

Scenario-specific required evidence is declared by the scenario. Generic
fixture validation MUST NOT hardcode Docker, backend, ai-engine, or any other
scenario answer.

The minimal execution status model is:

```text
INVALID_SCENARIO   fixture/scenario validation failed; no model behavior measured
EXECUTION_FAILED   valid scenario; execution failed
EVALUATED          output was available and evaluated
```

Execution status and quality are separate. An `EVALUATED` result may be
semantically incorrect and therefore `WEAK`.

### 10. Evaluation is multidimensional

The evaluator SHALL preserve at least these dimensions:

```text
STRUCTURAL_VALIDITY
PROPOSAL_CORRECTNESS
DELTA_CORRECTNESS
TARGET_CORRECTNESS
GROUNDING_QUALITY
TRUST_SAFETY
OVERALL_QUALITY
```

Some values may be derived rather than redundantly persisted. Reports must keep
the dimensions observable so an aggregate label cannot hide the failure cause.

For example, this result is valid and representable:

```text
STRUCTURE = VALID
DELTA     = INCORRECT
TARGET    = INCORRECT
GROUNDING = SAFE
TRUST     = SAFE
QUALITY   = WEAK
```

### 11. Overall quality requires safety and semantic correctness

For a scenario with applicable semantic expectations:

```text
STRONG =
    structurally valid
    AND proposal behavior correct
    AND expected delta correct
    AND expected target correct when applicable
    AND no unsupported material claim
    AND no contradicted material claim
    AND no trust-boundary violation
    AND no disqualifying plausible-but-unproven claim presented as project fact
```

Therefore:

```text
EXPECTED = ENRICHES + exact target
ACTUAL   = no proposal + no target
```

can never be `STRONG`, even when it contains no unsupported claim. Missing
outputs count as incorrect outcomes; they do not disappear from correctness
denominators.

`ACCEPTABLE` is not a loophole for wrong delta or wrong required target. It is
reserved for semantically correct, trust-safe output with limited non-critical
grounding imprecision under a scenario's reviewed rubric. Material structural,
semantic, grounding, or trust failure is `WEAK`.

No-proposal output is not inherently failure. When `expectedDelta` is `null`, a
valid output with no proposal may be the correct behavior and may be eligible
for `STRONG` if all other applicable expectations are satisfied.

### 12. Deterministic grounding and qualitative grounding are distinct

Grounding evaluation has two categories:

```text
DETERMINISTIC_GROUNDING_CONSTRAINT
QUALITATIVE_GROUNDING_ASSESSMENT
```

Deterministic constraints include exact grounding-reference allowlists,
selected Fact and Observation membership, target membership, foreign-reference
rejection, and other rules with executable semantics.

Natural-language claim classifications such as:

```text
DIRECTLY_GROUNDED
QUALIFIED_GROUNDED
PLAUSIBLE_BUT_UNPROVEN
UNSUPPORTED
CONTRADICTED
```

may require reviewed human judgment. They MUST NOT be described as deterministic
unless a specific constraint has genuinely deterministic semantics. If a
scenario requires qualitative review and no reviewed assessment is available,
the harness must expose that absence and MUST NOT silently award `STRONG`.

A generic keyword-based claim scanner is rejected. Keyword occurrence and
nearby negation cannot reliably establish natural-language semantics and create
false positives, false negatives, benchmark overfitting, and leakage of
scenario heuristics into evaluator logic.

### 13. ADR-006 trust boundaries are preserved

AI-generated outputs remain untrusted proposal material under ADR-006. The
evaluation harness may inspect and evaluate proposals, but evaluation does not
participate in the domain proposal lifecycle.

Evaluation results are engineering evidence. They are not project knowledge,
proposal decisions, or promotion authorization. The harness cannot:

- accept or reject a domain proposal;
- promote a proposal;
- persist trusted project knowledge;
- modify existing trusted knowledge;
- bypass human validation;
- turn a reviewed replay output into trusted knowledge.

Benchmark fixtures that contain trusted knowledge are isolated test data only.

### 14. Persist curated replay evidence, not every invocation

DevLog adopts a hybrid artifact policy.

The repository persists:

- the canonical scenario fixture;
- selected reviewed parsed replay output;
- expected semantic behavior and applicable reviewed grounding assessment;
- minimum reproducibility metadata.

The repository does not automatically persist:

- every raw provider response;
- every experimental run;
- hidden reasoning or provider-specific transport noise;
- temporary diagnostics;
- large duplicated rendered prompts;
- credentials, secrets, or sensitive content.

Live raw responses may remain local or CI artifacts when needed for diagnosis.
A reviewed result is promoted into the small replay corpus deliberately, not
automatically. The repository contains curated engineering evidence rather than
an archive of model invocations.

### 15. Reproducibility uses scenario identity, production identity, and digests

A captured live result records, where applicable:

- scenario ID, version, and canonical digest;
- repository revision and dirty-worktree marker;
- Intent ID and version;
- provider and model;
- effective output limit and configured sampling settings, including an
  explicit provider-default marker when unset;
- prompt ID, version, and content digest;
- expected output schema digest;
- capture timestamp;
- request, Analysis, and AI Task identifiers;
- transport attempts and corrective retry count when observable;
- execution status.

The committed scenario retains the controlled input needed for replay. Digests
prove technical identity but do not replace immutable fixture content. Prompt
version and digest retain their distinct ADR-032 meanings.

### 16. Product gates are scenario-owned

Individual run evaluation and aggregate scenario gates remain separate. A
scenario may declare simple integer thresholds such as:

- required run count;
- minimum `STRONG` runs;
- maximum incorrect deltas;
- maximum incorrect targets;
- maximum trust violations;
- maximum execution failures.

The Post-0109 `STRONG >= 2/3` threshold is not global. A one-output deterministic
replay may require that single reviewed result to remain `STRONG`. V1 SHALL NOT
introduce a threshold expression language or global policy DSL.

### 17. Runner and evaluator responsibilities remain narrow

The runner owns:

- loading an explicitly selected scenario;
- validating it before use;
- loading replay data;
- invoking the evaluator;
- emitting concise text and JSON reports;
- later, optionally coordinating explicit live execution.

The runner does not own evaluation semantics, expected answers, model-specific
business rules, output repair, or production state mutation.

The evaluator owns:

- structural and proposal-shape correctness;
- expected-versus-actual delta and target comparison;
- trust invariants;
- deterministic grounding constraints;
- quality derivation from visible dimensions;
- scenario-gate derivation.

The evaluator does not contain scenario-specific expected answers and does not
call a model.

### 18. Normal CI remains deterministic

Normal CI SHALL be able to validate without provider credentials:

- scenario schema and fixture validity;
- replay parsing through production-compatible contracts;
- proposal, delta, and target correctness;
- trust invariants;
- deterministic grounding constraints;
- quality and gate calculations;
- historical regression cases, including false-`STRONG` prevention;
- evaluator mechanics and denominator behavior.

Deterministic replay SHALL be eligible for normal CI. Live LLM execution SHALL
NOT be part of normal pull-request CI. Replay and live evaluation answer
different questions, and neither replaces the other.

### 19. The first scenario is the minimal validated Post-0109 case

The first canonical scenario will exercise:

```text
Intent            = architecture-overview-v2
selected relation = configured backend -> ai-engine dependency/reference
trusted target    = existing containerization Insight
expected delta    = ENRICHES
expected target   = exact fixture UUID
```

The fixture contains only material context needed for the scenario. It is a
canonical regression case, not a forensic copy of the entire historical
investigation context.

Its reviewed evidence boundary preserves the distinction between:

```text
supported:
  declared startup dependency
  configured service reference or reachability
  configured protocol when explicit in a URL

not automatically established:
  successful runtime communication
  actual API invocation
  data exchange
  network reliability
  post-start operational dependency
```

Those scenario semantics remain in scenario data and reviewed assessments.
They are not hardcoded as generic keyword rules.

### 20. V1 remains deliberately small

This decision does not introduce:

- a generic AI evaluation platform;
- plugin or dynamic evaluator discovery;
- a provider-independent benchmark framework separate from production
  providers;
- a database-backed evaluation history;
- a web dashboard or benchmark management UI;
- distributed evaluation workers;
- an LLM judge;
- automatic golden-output generation;
- a statistical experiment platform;
- a full Core product-workflow benchmark orchestrator;
- Agent trajectory or tool-use evaluation;
- RAG, retrieval, embedding, RAGAS, or vector-recall evaluation;
- a model-drift subsystem;
- paid live execution in ordinary pull-request CI.

Future Agent evaluation may reuse scenario, replay, and result principles, but
V1 is Intent evaluation first. No current Agent abstraction is required. RAG
evaluation remains a separate future decision.

## Architectural Invariants

1. Evaluation is not production behavior.
2. Production never imports or depends on evaluation code.
3. Evaluation may reuse production contracts through a one-way dependency.
4. The harness is removable without affecting production runtime behavior.
5. Benchmark expectations never enter production prompts or generation input.
6. Evaluation never repairs or rewrites production-compatible output.
7. Evaluation cannot accept, reject, or promote domain proposals.
8. Evaluation cannot create or modify trusted project knowledge.
9. ADR-006 human-validation and promotion boundaries remain unchanged.
10. Invalid scenario input is not a model failure and is rejected before
    evaluation or live execution.
11. Safe output does not imply semantically correct output.
12. Expected no-proposal behavior can be correct when declared by the scenario.
13. Missing required outputs remain in correctness denominators.
14. Evaluation retains structural, semantic, grounding, trust, and overall
    quality dimensions separately.
15. Arbitrary natural-language grounding is not assumed to be deterministic.
16. Keyword-based generic grounding evaluation is rejected.
17. Replay is deterministic and permitted in normal CI.
18. Live model execution is optional/later and excluded from normal PR CI.
19. Scenario-specific semantics live in scenario data, not generic evaluator
    logic.
20. Current scope is AI Intent-level evaluation, not Agent or RAG evaluation.
21. `KnowledgeDeltaType` remains `NEW | ENRICHES`; evaluation absence is
    represented outside that production enum.
22. `CONTRADICTS` is not introduced.

## Consequences

### Positive

- important AI regressions become versioned and reproducible;
- reviewed semantic expectations become explicit engineering artifacts;
- historical failures can become durable regression cases;
- evaluation mechanics and product gates become deterministically testable;
- grounded-but-wrong and correct-but-overclaiming outputs remain distinguishable;
- fixture defects fail before being misreported as model behavior;
- selected live behavior can be compared with stable scenarios later;
- normal CI remains deterministic and credential-free;
- trust and promotion boundaries remain enforceable;
- the footprint is small and owned by the AI Engine.

### Negative and costs

- scenarios and reviewed replay outputs require maintenance;
- fixture contracts must evolve when production request/output contracts change;
- qualitative grounding review adds human effort;
- selected replay artifacts can become stale as Intent semantics evolve;
- fixed fixtures can become brittle if they include non-material transport data;
- AI Engine CI must eventually include deterministic harness tests to realize
  the intended PR protection.

### Risks

- canonical scenarios may overfit one historical incident;
- scenario expectations may become hidden prompt-training examples if the
  production/evaluation boundary is violated;
- developers may mistake replay success for current live-model validation;
- live results may be compared without checking model, prompt, fixture, or
  repository metadata;
- a growing scenario corpus may encourage premature plugins or framework
  abstractions;
- qualitative review may be mislabeled as deterministic automation.

Mitigations are the one-way dependency, expectation isolation, explicit
REPLAY/LIVE distinction, scenario versioning, reproducibility metadata, a small
curated corpus, and separately visible evaluation dimensions.

## Alternatives Considered

### Keep benchmarks temporary

Rejected. Temporary scripts maximize experimentation freedom and require no
repository maintenance, but they are easy to lose, are not versioned, cannot
protect regressions in CI, and allow investigation knowledge to disappear.

### Persist only unit tests

Rejected as the sole mechanism. Unit tests remain necessary for evaluator
mechanics, but ordinary implementation fixtures poorly represent reviewed
scenario inputs and replay artifacts and do not provide a clean later boundary
for explicit live execution.

### Build a generic AI evaluation framework

Rejected for now. Plugins, dynamic discovery, generic provider orchestration,
run databases, dashboards, and cross-workflow abstractions have no demonstrated
V1 requirement. They would increase maintenance and shift effort from DevLog AI
behavior to speculative infrastructure.

### Persist a small Intent-level replayable harness

Accepted. It provides explicit expectations, reproducible reviewed scenarios,
deterministic CI replay, optional later live evaluation, and a low architectural
footprint. Its costs are bounded scenario and review maintenance.

### Persist every raw model invocation

Rejected. It would create noisy diffs, retain provider-specific payloads, risk
sensitive data exposure, and turn the repository into an execution archive.
Selected reviewed parsed outputs provide the required replay evidence.

### Automate grounding with a keyword scanner

Rejected. Natural-language semantic support cannot be inferred reliably from
keyword presence. The Post-0109 temporary scanner demonstrated context and
negation sensitivity and would overfit generic evaluation to one scenario.

### Run live model benchmarks on every pull request

Rejected. Cost, latency, rate limits, credentials, provider availability,
stochasticity, and model drift make live execution inappropriate for normal
deterministic CI.

## Implementation Boundary

This ADR authorizes a later Engineering Story to implement the minimal V1:

- `ai-engine/evaluations/`;
- a validated JSON scenario contract;
- a deterministic evaluator;
- a replay-first runner;
- one canonical Post-0109 scenario and reviewed replay artifact;
- deterministic evaluator and replay tests;
- deterministic CI integration.

This ADR does not implement those files, migrate `/tmp/opencode/benchmark/`,
create scenarios, alter CI, or change production code. The Engineering Story
must derive its acceptance criteria from this ADR and preserve all invariants
above.

## Relations

- Preserves ADR-006: AI outputs remain untrusted; only the governed human
  workflow may promote proposals into trusted knowledge.
- Preserves ADR-010: the AI Engine remains responsible for inference and
  structured results; the Core remains responsible for business workflow and
  trusted persistence.
- Preserves ADR-014: controlled evaluation fixtures do not move retrieval,
  selection, ranking, or context ownership into the AI Engine.
- Extends ADR-028 operationally by making selected versioned Intent behaviors
  replayable as engineering scenarios without changing Intent semantics.
- Uses ADR-032 prompt version and digest semantics for reproducibility.
- Preserves ADR-060 deterministic/probabilistic/governed-effect boundaries.
- Preserves ADR-063 and ADR-064 context and grounding ownership; the harness
  evaluates their observable outputs but does not become a source of truth.
- Preserves ADR-065: synthesis remains a non-trusted, non-promotable AI output
  category distinct from knowledge proposals.
